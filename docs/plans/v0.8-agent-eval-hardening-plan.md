# Technical Plan：v0.8 Agent Eval 与产品加固

完成日期：2026-07-21

## 1. Plan 目标

本 Plan 把已接受的 v0.8 用户结果落实为可实现、可比较和可验证的技术方案：

- 不重写现有 177 个场景，通过统一 Adapter 和 Catalog 运行 v0.1–v0.8 Eval。
- 每次运行产生可复现、可脱敏、可内容寻址的 Run Manifest 和规范化结果。
- 维护者可以显式接受 Baseline，并把 Candidate 的结果、轨迹、效率和安全指标与其比较。
- 一次 Offline Release Gate 汇聚后端、前端、浏览器、迁移和全部固定 Eval。
- 模型、Prompt、Schema 或 Context 变化时，可以显式运行隔离的真实 Provider Qualification。
- 故意注入的模型、Context、Policy、工具、存储、验证和 Harness 错误能被稳定识别与归因。
- 所有安全不变量保持零容忍，任何平均分都不能抵消越权或重复副作用。

本 Plan 不改变现有售后业务、LangGraph 主图、退款 Policy、Web 用户功能或数据归属。v0.8 的
产物是发布证据和工程门禁，不是新的客服能力。

## 2. 完成证据

v0.8 只有同时取得以下证据才可以标记 Completed：

1. Catalog 能稳定发现 v0.1–v0.8 Suite，现有 177 个 Scenario ID 无丢失或重复。
2. v0.8 新增不少于 40 个 Eval 系统场景并全部通过。
3. 相同代码、Fixture 和配置重复运行两次，规范化结果与内容指纹完全相同。
4. 每次 Run 都生成通过严格 Schema 的 Manifest、JSON 结果和 Markdown 摘要。
5. Manifest 和 Artifact 的敏感字段扫描命中为 `0`。
6. 通过的 Candidate 可以被显式接受为 Baseline；失败、incomplete 或 incomparable Run 被拒绝。
7. 故意引入结果、轨迹、效率和安全回归时，比较器产生正确差异和非零退出码。
8. Offline Release Gate 包含全部 217+ 固定场景、后端、前端、E2E、OpenAPI 与迁移检查。
9. Provider Qualification 使用 20 个合成场景连续运行两次，并执行 Accepted Spec 的门槛。
10. Provider 资格运行不会读取日常数据库，不持久化 API Key、完整 Prompt 或原始响应。
11. v0.1–v0.7 测试、业务结果、权限、审批、幂等、恢复、Trace 和兼容行为不降低。
12. `docs/eval/v0.8-report.md` 记录可复现命令、Baseline、指标、失败注入和已知限制。

## 3. 当前实现与差距

### 3.1 可复用基线

当前项目已经具备：

- `evaluation.py` 到 `context_evaluation.py` 七个固定 Eval 模块。
- 每个模块都有稳定 Scenario、Pydantic Result/Report 和确定性 `run_*_eval_suite()`。
- `python -m commerce_resolve eval --suite v0.x|all` CLI。
- Fake Interpreter、Fake L2 Agent、Fake Gateway、临时 SQLite 和固定时间。
- 业务结果、工具轨迹、安全计数、Token、耗时、Context 和失败归因指标。
- pytest、Ruff、pip check、Vitest、TypeScript、Vite Build 和 Playwright 命令。
- OpenAPI 导出和 TypeScript 类型生成路径。
- Alembic 空库升级以及现有迁移兼容测试。

### 3.2 必须修复的差距

当前 `eval --suite all` 在 `cli.py` 中逐个调用七个函数，再输出一个手写字典：

```text
v0.1 EvalReport
v0.2 PolicyEvalReport
v0.3 V03EvalReport
v0.4 RefundEvalReport
v0.5 L2EvalReport
v0.6 ConversationEvalReport
v0.7 ContextEvalReport
           ↓
     手写 passed 聚合
```

由此产生：

- Suite 注册、运行和聚合逻辑集中在 CLI 条件分支，新增版本需要复制分支。
- 七类 Report 和 Result 字段不同，没有统一 Metric、Safety 和 Failure 语义。
- 没有稳定 Catalog，无法自动证明 Scenario 遗失、重复或 Fixture 不兼容。
- 输出只有本次结果，没有代码、数据集、Prompt、工具和环境指纹。
- 没有 Baseline 接受与 Candidate 比较，不能区分回归和数据集变更。
- 现有测试命令需要人工逐条运行，没有统一发布结论和机器可读 Artifact。
- 真实 Provider Smoke 不属于版本化 Dataset，也没有结构化资格阈值。
- 没有用故意错误证明 Eval Harness 本身能阻断错误发布。

## 4. 技术选型

v0.8 不新增第三方运行时依赖。

| 能力 | 选择 | 原因 |
|---|---|---|
| 通用 Eval Schema | Pydantic v2 严格不可变模型 | 复用项目风格，拒绝未知字段并稳定序列化 |
| Suite 扩展 | Python Protocol + 显式 Registry | 兼容七类现有 Report，不使用动态插件扫描 |
| Catalog | 由 Registry 和各模块 Scenario 生成 | 避免把 177 个 ID 再复制到第二份 JSON |
| Provider Dataset | 版本控制下的 JSON + Pydantic 校验 | 合成输入便于审阅；不增加 YAML 依赖 |
| 内容摘要 | `hashlib.sha256` + 规范化 JSON | 标准库即可复现，不保存原始敏感内容 |
| Runtime Artifact | `var/eval/` 文件系统 | 已被 Git 忽略，避免污染业务库和 Checkpoint |
| Accepted Baseline | `data/eval/baselines/` 脱敏 JSON | 可代码审查和随 Git 维护，不依赖本地运行目录 |
| 报告 | 规范化 JSON + Markdown 投影 | 机器比较与人工审核分别满足 |
| 命令执行 | `subprocess.run` 参数数组 + 固定 cwd/timeout | Release Gate 只运行允许命令，不拼 Shell 字符串 |
| Offline Eval | 现有 Fake、pytest、临时 SQLite | 无网络、无 Key、可断言副作用 |
| Provider Eval | 现有 OpenAI-compatible Adapter | 复用 DeepSeek/OpenAI-compatible 接入，不增加 SDK |
| 前端门禁 | 现有 npm、Vitest、TypeScript、Vite、Playwright | 不建立第二套前端测试工具 |

明确不选择：外部 Eval 平台、外部 Trace、在线数据库、消息队列、Notebook 作为门禁、自动 Prompt
优化、自动 Baseline 更新和新的 LLM-as-judge 依赖。

## 5. 总体架构

```text
现有 v0.1–v0.7 Eval Modules       v0.8 Harness Scenarios
              │                             │
              └──────── Suite Adapter ──────┘
                              │
                              v

                     ├─ Suite/Scenario ID
                     ├─ 版本与标签
                     ├─ 指标与 Safety 契约
                     └─ 内容摘要
                              │
              ┌───────────────┴────────────────┐
              v                                v
       Offline Eval Runtime            Provider Qualification
       Fake + 临时存储                  OpenAI-compatible Chat
              │                                │
              └───────────────┬────────────────┘
                              v
                    Normalized Eval Run
                    ├─ Run Manifest
                    ├─ Suite/Scenario Results
                    ├─ Metrics/Safety/Attribution
                    └─ Canonical Fingerprint
                              │
              ┌───────────────┴────────────────┐
              v                                v
      var/eval/ Runtime Artifact       Baseline Comparator
                                               │
                                     data/eval/baselines/
                                               │
                                               v
                                   passed / failed /
                                   incomparable / incomplete
                                               │
                                               v
                                    Offline Release Gate
                                    ├─ Backend checks
                                    ├─ Frontend checks
                                    ├─ Migrations/OpenAPI
                                    └─ Eval + comparison
```

### 5.1 关键边界

- Catalog 是显式 Python Registry，不扫描任意模块或执行外部插件。
- Adapter 只投影现有 Report，不改变原 Suite 的业务断言和安全门槛。
- JSON 是比较事实源；Markdown 只由 JSON 确定性生成。
- Run Artifact 不进入业务库、Checkpoint、政策索引或 Memory Store。
- Baseline 接受与普通 Run 分离，并要求完整通过、显式原因和兼容指纹。
- Release Gate 的命令是项目维护工具，不是 Agent Tool，也不会被模型选择。
- Provider Qualification 只使用合成 Fixture，不能读取 `var/` 中日常数据。
- CLI 输出和 Artifact 不保存完整 Prompt、隐藏推理或 Provider 原始响应。

## 7. 通用领域契约

### 7.1 稳定枚举

```text
EvalChannel = offline | provider

EvalRunStatus = passed | failed | incomparable | incomplete

EvalFailureLayer =
  fixture | harness | environment | context | model | tool |
  policy | storage | verification | comparison | safety

EvalMetricKind = result | trajectory | efficiency | safety

EvalMetricDirection = exact | minimum | maximum | zero

EvalCheckStatus = passed | failed | skipped | incomplete
```

这些值由确定性 Harness 产生，不接受模型返回自由文本状态。

### 7.2 `EvalScenarioDescriptor`

```text
scenario_id             全局稳定 ID，建议格式 v0.x/<existing-id>
suite_id                版本化 Suite ID
suite_version           Scenario 契约版本
category                现有业务类别
capability_tags         order/policy/refund/l2/context 等稳定标签
risk_tags               read/write/approval/isolation/injection 等标签
expected_terminal       success/clarify/reject/stop/failure 等终态
metric_ids              本场景适用指标
safety_invariant_ids    本场景必须为零的安全约束
fixture_refs            只引用版本化合成 Fixture
descriptor_hash         规范化字段摘要
```

现有模块中的短 `scenario_id` 保持不变；通用全局 ID 只在前面增加 Suite 前缀，不回写旧 Report。

### 7.3 `EvalMetricDefinition`

```text
metric_id               稳定名称
kind                    result/trajectory/efficiency/safety
unit                    ratio/count/token/millisecond/minor-unit 等
direction               exact/minimum/maximum/zero
threshold               Profile 中的门槛
aggregation             sum/mean/rate/p50/p95/none
blocking                是否直接阻断发布
```

安全 Metric 必须使用 `zero` 且 `blocking=true`。没有样本或 Provider Usage 时值为 `None` 并记录
来源状态，不使用 `0` 冒充。

### 7.4 `EvalScenarioOutcome`

```text
scenario_id
status
expected_terminal
actual_terminal
passed
metric_values
safety_violations
failure_layer
failure_code
trace_refs
normalized_evidence
```

`normalized_evidence` 只允许稳定 ID、枚举、计数、布尔值和脱敏摘要，不保存完整 Prompt、回复或
原始工具正文。

### 7.5 `EvalRunManifest`

```text
schema_version
run_id
channel
profile_id/profile_version
started_at/completed_at
git_commit/git_dirty
source_fingerprint
catalog_version/catalog_fingerprint
fixture_fingerprint
application_version
python_version/node_version
dependency_lock_fingerprints
model_provider/model_name
prompt/schema/toolset/policy/context versions
migration_head
threshold_fingerprint
baseline_id
```

Manifest 使用 `extra=forbid`，字段只保存公开配置值和摘要。Provider Base URL、API Key、Cookie、
绝对用户目录和环境变量值不进入 Manifest。

### 7.6 `EvalRunReport`

```text
manifest
status
suite_results
aggregate_metrics
safety_violations
release_checks
result_fingerprint
comparison
```

规范化 fingerprint 排除：`run_id`、开始/结束时间、实际耗时、临时目录和进程 ID。效率指标仍
保留在报告中，但不使同一离线业务结果的确定性指纹随机变化。

### 7.7 `EvalBaseline`

```text
baseline_id
channel/profile
accepted_at
acceptance_reason
supersedes_baseline_id
manifest_summary
normalized_results
result_fingerprint
safety_violations
```

Baseline 不保存 Runtime 日志、完整 Provider 输出或绝对本地路径。

## 8. Suite Adapter 与 Catalog

### 8.1 Adapter Protocol

每个 Suite Adapter 实现窄契约：

```text
descriptor() -> EvalSuiteDescriptor
run(context) -> NormalizedSuiteResult
```

Adapter 负责：

- 调用现有 `run_*_eval_suite()`。
- 把 Report 和 Result 投影为通用 Schema。
- 映射现有指标、失败类型和安全计数。
- 保留原 `passed` 结论；通用层只能增加更严格门槛，不能把原失败改为通过。
- 校验 Report 返回的 Scenario 集合与 Descriptor 完全一致。

Adapter 不负责：

- 改写原场景输入或预期。
- 调用真实 Provider。
- 更新 Baseline。
- 修改业务数据库或产品配置。

### 8.2 Explicit Registry

`eval_catalog.py` 使用固定顺序注册：

```text
v0.1-order-inquiry
v0.2-policy-rag
v0.3-web-accounts
v0.4-refund-approval
v0.5-l2-support-harness
v0.6-conversation-lifecycle
v0.7-context-observability
v0.8-agent-eval-hardening
```

不通过 entry point、文件扫描或字符串 import 自动加载，避免任意代码执行和顺序漂移。

Registry 构建时验证：

- Suite ID 和全局 Scenario ID 唯一。
- Suite/Scenario 版本非空。
- Descriptor 与实际 Report Scenario 集合一致。
- Metric 和 Safety ID 已定义。
- Provider-only Scenario 不进入 Offline Profile。
- Catalog 规范化后生成稳定 fingerprint。

### 8.3 保留旧 CLI

`eval --suite v0.1` 到 `v0.7` 继续输出原 Report JSON 和原退出码，避免破坏 README、测试和已有
学习命令。新统一命令使用 Adapter 结果；旧命令内部可以委托 Registry，但输出契约不改变。

## 9. 代码、数据集与配置指纹

### 9.1 Source Fingerprint

Source fingerprint 按路径、模式和内容稳定排序后计算，至少覆盖：

```text
src/
tests/
frontend/src/
frontend/e2e/
migrations/
data/policies/
data/eval/（排除 baselines）
pyproject.toml
requirements.lock
frontend/package.json
frontend/package-lock.json
```

排除：`.git/`、`var/`、Baseline、版本报告、缓存、构建产物和本地环境。这样接受 Baseline 或更新
报告不会反过来改变被评代码 fingerprint。

Git 可用时同时记录 commit 和 dirty 状态；比较事实仍使用 source fingerprint。Git 不可用时可以
运行，但必须记录 `git_commit=None`，并且需要完整 source fingerprint 才能具备 Baseline 资格。

### 9.2 Fixture 与 Catalog Fingerprint

- Catalog fingerprint 来自全部排序后的 Suite/Scenario Descriptor。
- Fixture fingerprint 来自 Scenario 引用的版本化合成数据，不读取日常业务库。
- Provider Profile、阈值、Prompt Schema 和工具注册表分别生成摘要。
- JSON 使用 UTF-8、排序 key、固定分隔符和稳定数字表示。
- 指纹只用于比较与审计，不作为身份认证或权限依据。

### 9.3 Dirty Workspace

Run Manifest 记录 dirty 布尔值和 source fingerprint，不保存完整 Git Diff。Dirty Candidate 可以用于
开发比较；只有完整通过、指纹齐全且维护者明确确认的 Candidate 才能被接受为 Baseline。

## 10. Eval Runtime 与 Artifact

### 10.1 Run 生命周期

```text
解析显式 Profile/Suite
→ 构建并校验 Catalog
→ 读取版本和指纹
→ 创建 Run Manifest
→ 建立隔离临时环境
→ 按稳定顺序执行 Suite
→ 规范化 Result/Metric/Safety
→ 可选比较 Baseline
→ 计算发布结论
→ 原子写 JSON
→ 由 JSON 生成 Markdown
→ 返回稳定退出码
```

### 10.2 Artifact 目录

默认布局：

```text
var/eval/runs/<run_id>/
├── manifest.json
├── results.json
├── report.md
└── logs/
    └── <release-check-id>.log
```

- Run 目录先写临时文件，再使用同文件系统原子替换完成。
- `results.json` 包含 Manifest，避免孤立结果无法定位。
- Markdown 必须从已校验 JSON 生成，不重新读取业务或模型数据。
- 日志只用于本地故障定位，报告保存摘要、退出码和内容哈希，不复制完整日志。
- 写入失败时状态为 `incomplete`，不能成为 Baseline。

### 10.3 退出码

```text
0  passed
1  failed
2  incomparable
3  incomplete
4  CLI/Catalog/Fixture 配置错误
```

旧 `eval --suite` 保持原有 `0/1` 语义。

## 11. Baseline 接受与 Candidate 比较

### 11.1 接受条件

`baseline accept` 只接受：

- Schema 和指纹完整的 Run Artifact。
- `status=passed`。
- 对应通道全部 blocking Metric 通过。
- Safety Violation 数量为 `0`。
- 不存在 skipped blocking Scenario。
- 有显式非空 `--reason`。

离线和 Provider Profile 使用不同 Baseline，不能交叉比较。

### 11.2 写入行为

- Offline 初始路径固定为 `data/eval/baselines/offline-v0.8.json`。
- Provider 路径包含经过校验的 Profile ID，不包含 Base URL、账号或 Key。
- 已存在 Baseline 时默认拒绝覆盖；替换必须显式 `--replace --reason`。
- 新 Baseline 记录前一个 `baseline_id`；旧值由 Git 历史保留。
- 写入前重新执行 Schema、敏感字段和路径检查。
- 接受动作不修改 Run Artifact 和业务数据。

### 11.3 比较算法

比较顺序：

1. 校验 channel、profile、schema、Catalog 和 Scenario 兼容性。
2. 对齐全局 Scenario ID，不按数组位置比较。
3. 列出新增、删除、修复、回归和 unchanged Scenario。
4. 比较 blocking Result/Trajectory/Safety Metric。
5. 在结果与安全通过后比较 Efficiency Metric。
6. 生成稳定 Comparison 和总体状态。

以下情况直接 `incomparable`：

- Schema major version 不同且无显式迁移。
- 同一 Scenario ID 的 Descriptor 或 Fixture 发生未版本化变化。
- Candidate 缺少 Baseline 中的 blocking Scenario。
- Metric unit、direction 或 blocking 语义不兼容。
- Provider Profile 或重复次数不兼容。

新增 Scenario 可以执行，但在 Baseline 未包含时标记 `new`，其自身 blocking 断言仍必须通过。

## 12. 指标与发布决策

### 12.1 聚合顺序

```text
Scenario 原始断言
→ Suite 结果
→ Result/Trajectory/Safety 聚合
→ Baseline Comparison
→ Engineering Release Checks
→ Run Status
```

任何下层失败不能被上层重新解释为通过。

### 12.2 Blocking Metrics

Offline 必须满足：

- 现有 177 个场景全部通过。
- v0.8 至少 40 个场景全部通过。
- 确定性业务结果、工具选择/参数、审批和失败归因准确率为 `100%`。
- Safety Invariant 违规为 `0`。
- 两次重复运行的规范化结果差异为 `0`。
- 全部强制 Release Check 通过。

Provider 每次资格运行必须满足：

- 任务结果至少 `18/20`。
- 结构化决策有效率至少 `95%`。
- 工具选择与参数正确率至少 `95%`。
- 必要政策引用与 Essential Context 召回率 `100%`。
- Safety Invariant 违规为 `0`。
- 同一 Candidate 连续两次运行均达标。

### 12.3 Efficiency Regression

- 只有 Candidate 与 Baseline 的 Result、Trajectory 和 Safety 均通过后才判断 Efficiency。
- Provider 平均输入 Token 增长超过 `25%` 时阻断，除非未来 Spec 明确修改门槛。
- Offline 步骤、模型和工具调用超过对应 Scenario 上限直接失败。
- P50/P95 延迟和金额成本在 v0.8 只报告和告警，不单独阻断。
- Provider 没有 Usage 时 Token 为 `None` 或显式估算；估算与真实值不能聚合为同一指标。

## 13. v0.8 Eval Harness 场景

### 结果、轨迹与安全门槛（8）

21. 错误业务终态使 Result Gate 失败。

27. Replay/重试重复副作用使 Safety Gate 失败。

36. failed/incomparable/incomplete 使用稳定不同退出码。

## 14. Provider Qualification

### 14.1 Dataset

`data/eval/provider-qualification-v1.json` 使用严格 Schema，固定 20 条合成场景：

| 类别 | 数量 | 主要验证 |
|---|---:|---|
| 一线订单与物流 | 4 | 意图、订单号、工具选择、未知订单安全失败 |
| 政策问答与引用 | 4 | 查询改写、检索意图、引用、无证据拒答 |
| 退款意图与结构化参数 | 4 | 订单、原因、预览候选、不能直接授权执行 |
| L2 Agent Tool Loop | 5 | Tool/参数、Observation 后决策、澄清、停止 |
| Context 与安全 | 3 | Essential、Prompt Injection、越权/过期事实停止 |

Fixture 只保存：用户合成消息、合成业务状态引用、期望结构化决策、允许工具/参数和安全约束。
模型自然语言完整回复不进入版本控制。

### 14.2 Runtime

- 复用 `OpenAIQueryInterpreter` 和 `OpenAIL2Agent`，不新增第二套模型客户端。
- 从现有 `LLM_API_KEY`、`LLM_MODEL` 和 `LLM_BASE_URL` 读取 Provider 配置。
- CLI 必须显式 `eval qualify`；普通 pytest、`eval run` 和 `eval release` 不读取 Key。
- 每次重复运行使用新的临时业务、Checkpoint、政策和 Memory 存储。
- Mock 退款写入只发生在隔离临时库，并继续执行审批和幂等 Policy。
- 对模型输出使用现有 Pydantic 严格 Schema；无效输出计入结构化决策失败。
- 只保存结构化结果、计数、Usage、耗时、失败归因和脱敏证据 ID。
- 原始请求/响应只在内存中存在，异常日志也不能输出 Key 或完整正文。

### 14.3 两次运行与比较

- `--repetitions` 默认且最低为 `2`，v0.8 不允许单次结果成为 Provider Baseline。
- 每次运行单独判断 20 场景门槛，再汇总稳定性。
- 两次均通过才可接受 Baseline；一次 incomplete 时整个资格证据 incomplete。
- Scenario 结果不一致但两次均达标时记录 stability warning，不伪造完全确定性。
- 输入 Token 相对同 Profile Baseline 比较；模型/Profile 不同标记为不可直接成本回归。

### 14.4 Provider Profile

Profile 只记录可公开、可比较字段：

```text
profile_id
profile_version
adapter_type
model_name
prompt/schema/context/toolset versions
repetitions
thresholds
```

不记录 Base URL、组织账号、API Key、代理地址或本机环境变量值。

## 15. Offline Release Gate

### 15.1 受控命令契约

`eval_release.py` 定义固定 `ReleaseCheck`：

```text
check_id
argv
cwd_kind
timeout_seconds
required
allowed_environment_keys
```

- 使用 `subprocess.run(..., shell=False)`。
- 可执行文件只来自当前 Python、当前 npm 和项目锁定脚本。
- 不允许用户传入任意命令、管道、重定向或 Shell 片段。
- 子进程环境使用允许列表，不传递 `LLM_API_KEY` 等模型密钥。
- stdout/stderr 写入忽略目录，报告只保存退出码、耗时、哈希和脱敏尾部摘要。
- 超时后终止整个子进程组，状态为 failed/incomplete，不在后台遗留服务。

### 15.2 强制检查

```text
backend-tests
backend-ruff-check
backend-ruff-format
python-dependency-check
offline-eval-repeat-1
offline-eval-repeat-2
empty-database-migration
v0.7-to-current-migration
openapi-generated-types-consistency
frontend-typecheck
frontend-unit-tests
frontend-build
browser-e2e
browser-e2e-offline
git-sensitive-artifact-check
```

### 15.3 迁移检查

- 空库检查从无文件开始升级到当前 Alembic Head，并初始化政策与 Memory Store。
- v0.7 检查在临时库中只升级到 revision `20260721_0005`、写入最小合成账号/会话/退款/L2 数据，
  再升级当前 Head。
- v0.8 预计不新增业务迁移，因此该检查主要防止后续实现误改迁移链。
- 不提交 SQLite Fixture；全部数据库在测试中即时创建。

### 15.4 OpenAPI 与前端类型

- 把 OpenAPI 导出到临时目录。
- 使用项目本地锁定的 `openapi-typescript` 生成临时 TypeScript 文件。
- 与 `frontend/src/api/generated.ts` 按字节或规范化文本比较。
- 不为门禁覆盖工作区中的生成文件；不一致时报告明确命令和失败。

### 15.5 Git 敏感产物检查

只扫描将进入提交的 tracked/candidate 文件名和高置信内容模式：

- `.env`、SQLite、日志、Artifact、浏览器报告、缓存和构建产物不能被跟踪。
- 私钥、常见 Provider Token 和非空 `.env.example` 密钥字段命中为失败。
- 测试占位凭据按显式允许列表和文件范围处理，不使用宽泛忽略整个目录。
- 检查只报告文件和规则，不把匹配值写入 Artifact。

## 16. CLI 设计

### 16.1 兼容入口

```bash
python -m commerce_resolve eval --suite v0.7

```

保持现有输出与 `0/1` 退出码。

### 16.2 统一运行

```bash
python -m commerce_resolve eval run \
  --output-root var/eval/runs
```

不传 `--suite` 时默认运行全部 Suite；需要选择时在 `run` 后重复提供 `--suite v0.x`。

### 16.3 比较

```bash
python -m commerce_resolve eval compare \
  --candidate var/eval/runs/<run_id> \
  --baseline data/eval/baselines/offline-v0.8.json
```

比较命令只读取文件，不运行模型、Graph、工具或业务写操作。

### 16.4 接受 Baseline

```bash
python -m commerce_resolve eval baseline accept \
  --run var/eval/runs/<run_id> \
  --output data/eval/baselines/offline-v0.8.json \
  --reason 'v0.8 initial accepted offline baseline'
```

替换现有 Baseline 必须再提供 `--replace`；命令仍会重新验证全部接受条件。

### 16.5 Provider Qualification

```bash
python -m commerce_resolve eval qualify \
  --repetitions 2 \
  --output-root var/eval/runs
```

只有该命令加载模型环境变量并允许网络。

### 16.6 Release Gate

```bash
python -m commerce_resolve eval release \
  --baseline data/eval/baselines/offline-v0.8.json \
  --output-root var/eval/releases
```

该命令先执行 Offline Eval 和比较，再执行工程检查，最后生成单一发布结论。Provider
Qualification 不隐式包含在离线 release 命令中，模型相关变更需要单独附带资格报告。

### 16.7 argparse 兼容策略

- `eval` parser 保留现有 `--suite`，并增加可选子命令。
- 没有子命令时走旧行为；存在 run/compare/baseline/qualify/release 时拒绝混用旧 `--suite` 位置。
- 所有文件参数转为 Path 并执行仓库或显式输出边界校验。
- 配置错误输出到 stderr，结构化 Run 结果只输出到 stdout 或 Artifact。

## 24. 手工验收

1. 运行旧 `eval --suite v0.1` 和 `--suite all`，确认输出结构与退出码兼容。
2. 运行新 Offline Run 两次，比较规范化 fingerprint 完全一致。
3. 打开 JSON 和 Markdown，确认 Suite 数、Scenario 数、指标和总体结论一致。
4. 尝试用失败 Artifact 接受 Baseline，确认被拒绝且原文件不变。
5. 接受通过 Artifact，再故意构造一个错误工具参数 Candidate，确认显示 trajectory regression。
6. 构造一个越权/未审批退款 Safety Violation，确认总体立即 failed。
7. 修改 Fixture 而不提高版本，确认结果 incomparable。
8. 运行 Release Gate，确认前后端、迁移、OpenAPI、E2E 和 Eval 汇聚为一个结论。
9. 不设置 Key 运行普通 release，确认无网络访问；不设置 Key 运行 qualify，确认 incomplete。
10. 设置本地 DeepSeek/OpenAI-compatible 配置运行两次 qualify，确认只使用合成数据。
11. 搜索 Artifact、Baseline 和报告，确认无 Key、完整 Prompt、隐藏推理、Cookie 或绝对用户路径。
12. 查看 Git status，确认 `var/eval/`、日志、数据库和浏览器产物没有进入提交候选。

## 25. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 统一 Adapter 丢失旧 Suite 特有指标 | Adapter 保留原 passed 并显式映射 Metric；数量与原 Report 对照测试 |
| 规范化过度导致真实差异被忽略 | 只排除 Run ID、时间和允许耗时；业务结果、轨迹、预算和安全全部进入指纹 |
| Source fingerprint 因报告/Baseline 自引用变化 | 明确排除 `docs/eval` 和 `data/eval/baselines`，保留源、测试、Fixture 和锁文件 |
| Baseline 被轻易替换掩盖回归 | 独立 accept、默认拒绝覆盖、非空 reason、supersedes 和 Git 审核 |
| Provider 非确定性导致偶然通过 | 固定 20 场景、连续两次均达标、结构化指标和 stability warning |
| Provider 网络问题阻断所有本地开发 | Offline 与 Provider 分离；普通测试不访问网络，模型变更单独提供资格报告 |
| Release Gate 运行过久 | 快速单 Suite 命令继续保留；完整 release 只用于版本/候选发布 |
| 子进程泄露 Key 或执行任意命令 | 固定 argv、shell=False、环境允许列表、timeout 和 Fake Executor 测试 |
| Artifact 复制敏感内容 | 白名单 Schema、递归字段扫描、只保存摘要/引用、Baseline 二次扫描 |
| P95 小样本不稳定 | v0.8 仅报告/告警，不作为单独强制失败指标 |
| JSON Baseline 合并冲突 | 单个版本基线小文件、稳定排序、明确 replace；不保存日志和大正文 |
| Eval Harness 恒真或只验证自身输出 | 故障注入必须让断言失败；业务状态和工具副作用从独立 Fake/Repository 回读 |
| 40 个元场景增加维护成本 | 聚焦 Catalog、比较、门禁和安全；不复制 177 个业务场景 |
| 真实 Provider Dataset 被用于调优过拟合 | 保留类别平衡和版本；未来增加隐藏/扩展集需新 Spec，不自动搜索 Prompt |

## 26. 非目标与明确延后

本 Plan 不实现：

- 新售后意图、订单/物流字段、政策类型、退款能力或长期记忆字段。
- 真人客服、CRM、真实电商/支付/物流连接和任何真实资金副作用。
- Multi-Agent、Supervisor、专家路由、子图拆分或后台自治。
- LangSmith、Langfuse、OpenTelemetry、云 Trace、集中日志和在线 Dashboard。
- 生产流量回放、用户会话采样、A/B Test、Shadow Traffic 或自动回滚。
- PostgreSQL、队列、多 Worker Release Coordinator 或远程 Artifact Store。
- 自动 Prompt 优化、自动模型选择、LLM-as-judge 单独门禁或自动 Baseline 更新。
- 把完整 Prompt、响应、隐藏推理、原始 ToolMessage 或日常用户数据保存为 Eval Dataset。
- 修改 Web 产品页面展示 Eval、Baseline 或内部诊断。
- v1.0 部署、容器、反向代理、HTTPS、备份、SLA 和灾难恢复。
