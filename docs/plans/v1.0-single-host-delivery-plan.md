状态：Implemented / Reference Docker Gate Incomplete  
日期：2026-07-21  
接受日期：2026-07-21  
Feature Spec：[`../specs/v1.0-single-host-delivery.md`](../specs/v1.0-single-host-delivery.md)（Accepted）

关联 ADR：[`../adr/0010-single-host-compose-and-sqlite.md`](../adr/0010-single-host-compose-and-sqlite.md)（Accepted）

## 1. Plan 目标

本 Plan 把已接受的 v1.0 用户结果落实为可实现、可验证的单机交付方案：

- 从一个明确入口构建、初始化、启动、停止、检查和升级 CommerceResolve。
- 通过稳定 Release Manifest 证明后端、前端、代码提交、数据格式和发布证据属于同一版本。
- 在业务请求进入前校验配置、路径、Schema、政策索引、静态资源和安全边界。
- 区分 Liveness、Readiness 与可选 LLM/退款/L2 Capability 状态。
- 使用有界优雅退出和启动 Reconciliation 处理进程内 Agent Run，不自动重放未知副作用。
- 对业务库、LangGraph Checkpoint 和长期 Memory 创建一致、可校验、可恢复的 Backup Set。
- 从固定 v0.8 代表性数据升级到 v1.0，并在失败时保持非 Ready 和可回退证据。
- 使用结构化脱敏日志、本机诊断和有限聚合指标支持排障。
- 把 32 条以上运维 Eval 和真实单机生命周期加入 Offline Release Gate。

本 Plan 不新增售后意图、Agent 工具或真实业务集成，不改变 Mock 交易边界，也不把现有单进程
BackgroundTasks 改造成分布式 Worker。

## 2. 完成证据

v1.0 只有同时取得以下证据才可以标记 Completed：

1. 在受支持参考环境中，从干净 Release Bundle 通过一个入口完成构建、初始化和启动。
2. Release Manifest 能对应应用版本、Git 提交、后端 Wheel、前端资源、锁文件和数据格式。
3. 配置、路径、Origin、Cookie、Schema 或资源不满足约束时，Preflight 在业务写入前失败。
4. Liveness、Readiness 和 Capability 状态分别通过自动化测试，健康检查零业务副作用。
5. SIGTERM 后不再接受新连接；在宽限期内完成的 Run 正常结束，超时 Run 稳定变为
   `interrupted`，重启不会重复 Mock 退款、消息、事件或 Memory 写入。
6. Backup Set 只包含三类权威 SQLite 和必要版本元数据，具备完整性校验与明确排除项。
7. 损坏备份、非空恢复目标和运行中实例均被安全拒绝；隔离恢复后关键计数和归属一致。
8. 固定 v0.8 数据快照可以升级到 v1.0；升级失败时服务不对外 Ready，并可使用升级前备份恢复。
9. 容器以非 root、只读根文件系统、最小 Linux Capability 和回环端口映射运行。
10. 日志、诊断、Backup、镜像、Manifest 和 Git 候选文件的敏感信息扫描命中为 `0`。
11. v0.1–v0.8 离线场景继续 `217/217`，v1.0 新增至少 `32/32`，Safety Violation 为 `0`。
12. Offline Release Gate 同时覆盖镜像构建、干净启动、健康、浏览器、重启、备份恢复、
    v0.8 升级、敏感数据和已有工程检查。
13. `docs/eval/v1.0-report.md` 记录可复现命令、Release Manifest、Eval、故障注入和已知限制。

## 3. 当前实现与差距

### 3.1 可复用基线

当前项目已经具备：

- Python 3.12、FastAPI、Uvicorn 单 worker 和 React + TypeScript 同源生产构建。
- `python -m commerce_resolve` 统一 CLI，以及显式 `db upgrade`、`policy-index build`、
  `memory setup`、`serve`、`invite` 和 `eval` 子命令。
- `var/business.sqlite`：账号、会话、Mock 业务、Run/Event、退款、L2、Trace 和审计事实。
- `var/checkpoints.sqlite`：LangGraph State 和 interrupt 恢复点。
- `var/memory.sqlite`：已确认长期偏好。
- `var/policy-index.sqlite`：从 `data/policies/` 重建的派生 FTS5 索引。
- Alembic 业务迁移、LangGraph SQLite Checkpointer/Store 和政策索引版本校验。
- 进程内 FastAPI BackgroundTasks、稳定 Run ID、幂等请求、公开 SSE 和显式重试。
- FastAPI lifespan 启动时将遗留 `accepted/running` Run 标记为 `interrupted`。
- 固定 Offline Release Gate、217 条 Eval、脱敏 Artifact 和受控 Baseline。
- `.env`、`var/`、SQLite、日志、前端构建和浏览器 Artifact 的 Git 忽略规则。

### 3.2 必须修复的差距

- 安装 Python、安装 Node、构建前端、迁移、建索引和启动需要维护者手工串联。
- 后端版本、FastAPI 版本、前端版本和 Git 提交没有统一 Release Manifest。
- `WebSettings` 只完成基础类型解析，没有部署模式、公开 URL、路径边界和跨字段安全校验。
- `/api/health` 只返回进程 `ok`，无法判断 Schema、Store、索引、静态资源和版本是否 Ready。
- Uvicorn 使用默认优雅退出设置，Compose/容器生命周期尚未定义。
- 当前启动 Reconciliation 有基础行为，但没有稳定报告、幂等证据或关闭阶段兜底。
- 三类权威 SQLite 没有一致 Backup Set；直接复制 WAL 模式文件可能得到不可恢复组合。
- 没有固定 v0.8 数据 Fixture、升级 Manifest、失败恢复和前后端版本一致性门禁。
- 日志主要依赖开发输出；没有统一 JSON 字段、请求关联、脱敏和容器轮转。
- 没有受支持单机参考环境，也没有镜像、Compose、部署脚本和故障排查手册。

## 4. 技术选型

### 4.1 总体选择

| 能力 | 选择 | 原因 |
|---|---|---|
| 参考环境 | Ubuntu 24.04 LTS + Docker Engine + Docker Compose v2 | 提供可重复 Linux 运行边界；Compose 足以管理单服务，无需集群 |
| macOS 开发 | 保留 Conda + npm 现有路径 | 不强迫日常开发进入容器，也不破坏当前环境 |
| 构建 | Node 22 Builder + Python 3.12 Slim 多阶段 Dockerfile | Vite 构建与 Python 运行分离，运行镜像不包含 Node 工具链 |
| 运行拓扑 | 一个 FastAPI 容器、一个 Uvicorn worker | SQLite、进程内 BackgroundTasks 和内存 thread lock 都要求单实例语义 |
| Web 暴露 | 宿主只绑定 `127.0.0.1`，容器内监听 `0.0.0.0` | v1.0 不引入反向代理和证书；避免把 HTTP 直接暴露到非回环网络 |
| 生命周期 | `deploy/commerce-resolve` + Compose + 应用 `ops` CLI | 宿主只需 Docker；业务校验仍由同一 Python 代码实现 |
| 持久化 | 保留三类权威 SQLite + 一类派生政策索引 | 单机负载不需要数据库迁移；保持现有事务、Checkpoint 和 Store 兼容 |
| 宿主数据 | `./var` bind mount 到 `/var/lib/commerce-resolve` | 现有 v0.8 数据可直接升级；维护者可明确备份、检查和清理 |
| 一致备份 | 停止应用后使用 `sqlite3.Connection.backup()` | 每个数据库得到 SQLite 一致快照；停机边界消除跨库时间点歧义 |
| 完整性 | SHA-256 + 文件大小 + `PRAGMA integrity_check` + 领域计数 | 标准库即可验证文件和业务恢复结果 |
| Schema | 现有 Alembic + Checkpointer/Store/索引就绪检查 | 不新增第二套迁移框架 |
| 配置模型 | 现有不可变 `WebSettings` + 严格 `DeploymentSettings` | 复用项目风格并补充跨字段 Preflight |
| 日志 | Python 标准库 JSON Formatter 输出 stdout | 无新运行时依赖；容器负责有限轮转 |
| 容器日志 | Docker `local` driver，限制大小和文件数 | 不引入 ELK/APM，同时避免日志无限增长 |
| 健康 | FastAPI 只读端点 + 本机 `ops status` | 公开响应最小化，详细诊断不开放为 Web 管理 API |
| Eval | 现有 Pydantic Catalog、Fake、pytest、Playwright 和 Release Gate | 运维能力继续确定性离线验证 |

### 4.2 明确不选择

- 不迁移到 PostgreSQL 或 MySQL：当前是单机、单 worker、Mock 业务，迁移不能改善本版本验收，
  却会同时改写 Repository、备份、迁移和测试边界。
- 不引入 Redis、Celery、消息队列或独立 Worker：v1.0 只要求有界停止和中断恢复，不要求后台
  任务跨进程自动继续。
- 不引入 Kubernetes、systemd 模板、Service Mesh 或自动扩缩容：Compose 已覆盖单机生命周期。
- 不捆绑 Caddy/Nginx 和自动证书：参考环境只暴露回环地址；非回环访问在 v1.0 明确拒绝。
- 不接入 Prometheus、OpenTelemetry、LangSmith 或日志 SaaS：先提供本地结构化证据和有限指标。
- 不做在线热备份：多 SQLite 的权威事实需要停机一致性，短暂维护窗口是主动取舍。
- 不使用 Shell 拼接执行运维子命令：应用 CLI 使用结构化参数；部署脚本只调用固定 Compose 命令。

### 4.3 官方行为依据

- Docker Compose 使用 `healthcheck` 判断容器健康，并用 `stop_grace_period` 在 SIGTERM 后提供
  有界退出窗口：<https://docs.docker.com/reference/compose-file/services/>。
- Compose 不会因为容器已运行就自动证明应用 Ready，因此部署脚本必须显式等待健康：
  <https://docs.docker.com/compose/how-tos/startup-order/>。
- Uvicorn 在 `timeout-graceful-shutdown` 内等待响应和任务完成，超时后终止请求：
  <https://www.uvicorn.org/server-behavior/>。
- Python 3.12 `sqlite3.Connection.backup()` 可以从活动连接生成数据库快照；本项目仍额外要求
  应用停止，以获得三个权威数据库之间的明确一致性边界：
  <https://docs.python.org/3.12/library/sqlite3.html>。

## 5. 总体架构

```text
受支持参考主机
┌──────────────────────────────────────────────────────────────────────┐
│ deploy/commerce-resolve                                             │
│   build | init | up | down | status | backup | restore | upgrade    │
│                              │                                       │
│                       Docker Compose v2                              │
│                              │                                       │
│   127.0.0.1:8000 ─────── app container                              │
│                           ├─ FastAPI + React dist                    │
│                           ├─ Uvicorn single worker                   │
│                           ├─ LangGraph + BackgroundTasks             │
│                           ├─ Preflight / Health / Reconciliation     │
│                           └─ JSON stdout logs                        │
│                              │                                       │
│                    bind mount ./var                                  │
│                              │                                       │
│   ┌──────────────────────────┼───────────────────────────────────┐   │
│   │ business.sqlite          │ 业务与公开会话事实               │   │
│   │ checkpoints.sqlite       │ LangGraph State                   │   │
│   │ memory.sqlite            │ 已确认长期偏好                    │   │
│   │ policy-index.sqlite      │ 派生 FTS5，可重建                  │   │
│   │ instance.json            │ 非敏感实例与数据格式元数据        │   │
│   │ operations.jsonl         │ 脱敏本机运维审计                  │   │
│   └─ backups/<backup_id>/    │ 版本化 Backup Set                 │   │
│                                                                      │
│ Docker local logging driver：有限轮转，不进入 ./var Backup Set      │
└──────────────────────────────────────────────────────────────────────┘
```

### 5.1 关键边界

- Compose 只有一个长期运行的 `app` 服务；所有运维命令使用同一镜像的一次性容器。
- 应用容器和高影响运维命令都竞争 `./var/.instance.lock`，任何时刻只允许一个写入主体。
- 应用保持单 worker；不依赖跨进程锁、队列或数据库级 Leader Election。
- 前端资源在镜像构建期生成并由 FastAPI 同源托管，不运行独立 Node 服务。
- `data/policies/` 和 Release Manifest 烘焙进只读镜像；政策索引位于可写数据目录并可重建。
- `.env` 只由 Compose 注入，不复制到镜像、Manifest、Backup 或诊断。
- Release Manifest 是镜像事实；Instance Manifest 是本地数据事实；Backup Manifest 是备份事实，
  三者不能互相替代。
- Agent 的 Policy、审批、幂等和 Verifier 保持不变；Operations 不能直接调用 Agent Tool。

## 6. Release Bundle 与镜像

### 6.1 Bundle 内容

预计新增：

```text
Dockerfile
.dockerignore
compose.yaml
.env.deploy.example
deploy/
├── commerce-resolve              # 唯一宿主生命周期入口
└── README.md                     # 参考环境和命令速查
```

Release Bundle 是一个明确 Git Tag/源码归档及其构建文件，不提交运行数据库、`.env`、备份或日志。
v1.0 不要求发布到公共镜像仓库；本地构建镜像是受支持路径，镜像名称和 Tag 必须由版本确定。

### 6.2 多阶段镜像

```text
frontend-builder
  Node 22
  npm ci
  npm run build
          │
python-builder
  Python 3.12
  requirements.runtime.lock
  build wheel
          │
runtime
  Python 3.12 slim
  非 root UID/GID 10001
  安装 runtime lock + project wheel
  copy frontend/dist + data/policies + release-manifest.json
  ENTRYPOINT ["python", "-m", "commerce_resolve"]
  CMD ["serve"]
```

- 新增 `requirements.runtime.lock`，只包含运行时与 OpenAI-compatible Adapter 所需锁定依赖；
  现有 `requirements.lock` 继续用于开发和 Release Gate。
- `npm ci` 必须使用提交的 `frontend/package-lock.json`。
- 构建参数至少包含 `APP_VERSION` 和 `GIT_COMMIT`；缺失时 Release 构建失败，不使用 `latest`
  冒充正式版本。
- 镜像写入 OCI `version`、`revision` 和 `source` Label，但应用不只依赖 Label 读取版本。
- 运行镜像不包含 npm、pytest、Ruff、Playwright、Git、源测试或 `.env`。

### 6.3 `ReleaseManifest`

镜像内只读 `/app/release-manifest.json`：

```text
schema_version          release-manifest-v1
app_version             1.0.0
git_commit              完整提交 SHA
build_timestamp         UTC；不进入确定性内容指纹
python_version          3.12.x
frontend_version        1.0.0
frontend_asset_hash     dist 内容摘要
runtime_lock_hash       requirements.runtime.lock 摘要
npm_lock_hash           package-lock.json 摘要
policy_source_hash      data/policies 规范化摘要
business_schema_head    Alembic Head
checkpoint_format       应用支持格式版本
memory_format           应用支持格式版本
data_format_version     commerce-resolve-data-v1
offline_baseline_id     Accepted v1.0 Baseline ID
```

后端 `/api/health/*`、前端 build manifest、镜像 Label 和 Release Gate 必须使用同一来源生成，
不能在四处手工维护版本。

## 7. 配置与 Preflight

### 7.1 部署配置

部署模板默认关闭 LLM，避免空 Key 的首次启动失败：

```text
APP_ENV=deployment
PUBLIC_BASE_URL=http://127.0.0.1:8000
WEB_HOST=0.0.0.0
WEB_PORT=8000
BUSINESS_DB_PATH=/var/lib/commerce-resolve/business.sqlite
CHECKPOINT_DB_PATH=/var/lib/commerce-resolve/checkpoints.sqlite
MEMORY_DB_PATH=/var/lib/commerce-resolve/memory.sqlite
POLICY_SOURCE_PATH=/app/data/policies
POLICY_INDEX_DB_PATH=/var/lib/commerce-resolve/policy-index.sqlite
FRONTEND_DIST_PATH=/app/frontend/dist
BACKUP_ROOT=/var/lib/commerce-resolve/backups
INSTANCE_LOCK_PATH=/var/lib/commerce-resolve/.instance.lock
OPERATIONS_AUDIT_PATH=/var/lib/commerce-resolve/operations.jsonl
SHUTDOWN_GRACE_SECONDS=30
LOG_LEVEL=INFO
LLM_FEATURE_ENABLED=false
```

- `APP_VERSION`、`GIT_COMMIT` 和数据格式不能由 `.env` 覆盖，只能来自 Release Manifest。
- 宿主映射固定为 `127.0.0.1:${HOST_PORT}:8000`；`HOST_PORT` 只用于 Compose 插值。
- `PUBLIC_BASE_URL` 决定 Cookie/Origin 安全校验；容器内 `WEB_HOST=0.0.0.0` 不等于允许公网暴露。
- 启用 LLM 时 `LLM_API_KEY`、`LLM_MODEL`、`LLM_BASE_URL` 必须同时存在；禁用时三者不读取。
- Preflight 错误只输出配置名和安全摘要，不输出 Secret 值、数据库绝对宿主路径或完整连接信息。

### 7.2 Preflight 模式

```text
PreflightMode = init | serve | backup | restore | upgrade | status
```

| 检查 | init | serve | backup | restore | upgrade | status |
|---|---:|---:|---:|---:|---:|---:|
| Release Manifest | 必须 | 必须 | 必须 | 必须 | 必须 | 必须 |
| 配置 Schema/跨字段 | 必须 | 必须 | 必须 | 必须 | 必须 | 必须 |
| 数据目录边界与权限 | 创建后检查 | 读写 | 只读+目标写 | 目标写 | 读写 | 只读 |
| Instance Lock | 独占 | 生命周期持有 | 独占 | 独占 | 独占 | 不持有 |
| 业务 Schema | 空或兼容 | 当前 Head | 可读 | 恢复后当前 | 支持来源 | 只读报告 |
| Checkpoint/Memory | 空或兼容 | Ready | 可读 | 恢复后 Ready | 支持来源 | 只读报告 |
| 政策索引 | 可重建 | 版本匹配 | 排除 | 恢复后重建 | 重建 | 报告 |
| 前端资源 | 必须 | 必须 | 不需要 | 不需要 | 必须 | 版本报告 |
| LLM 配置 | 条件检查 | 条件检查 | 不读取 Key | 不读取 Key | 条件检查 | 仅 configured |

### 7.3 初始化语义

- `ops init` 只允许空实例或已经完成初始化的兼容实例。
- 空实例先在受控临时目录创建并验证业务 Schema、Memory Store、Checkpoint 存储和政策索引，
  安装成功后最后原子写入 Instance Manifest；任一步失败都不能留下“已初始化”标记。
- 初始化不自动创建用户、邀请码、订单、物流、支付、会话、Case 或 Mock 退款。
- 重复 `ops init` 只验证并返回 `already_initialized`，不刷新时间或产生业务写入。
- 应用 `serve` 永远不自动迁移未知数据库，也不把路径拼写错误创建成新的空实例。

## 8. 数据布局与实例锁

### 8.1 `./var` 布局

```text
var/
├── business.sqlite               # 权威，Backup Set 包含
├── checkpoints.sqlite            # 权威，Backup Set 包含
├── memory.sqlite                 # 权威，Backup Set 包含
├── policy-index.sqlite           # 派生，恢复后重建
├── instance.json                 # 实例 ID、数据格式和恢复血缘
├── .instance.lock                # 进程锁文件，不含业务数据
├── operations.jsonl              # 脱敏运维审计，不进入业务 DB
├── backups/                      # Backup Set，默认不递归备份
├── eval/                         # 现有 Eval Artifact
└── tmp/                          # 原子写入临时目录，可清理
```

### 8.2 `InstanceManifest`

```text
schema_version          instance-manifest-v1
instance_id             初始化生成 UUID
data_format_version     commerce-resolve-data-v1
initialized_at          UTC
last_successful_release Release version + commit
source_version          新建或 v0.8
restored_from           可选 backup_id；不保存宿主路径
```

- `instance_id` 是恢复覆盖确认参数，不是用户或租户 ID。
- 新空目标恢复时保留新的 target `instance_id`，并在 `restored_from` 记录来源 Backup ID。
- Instance Manifest 使用临时文件、`fsync` 和同目录原子替换；失败时保留旧版本。

### 8.3 单实例锁

- Linux 参考环境使用 `fcntl.flock(LOCK_EX | LOCK_NB)` 持有 `.instance.lock`。
- `serve` 在完成任何可写初始化前取得锁，并持有到 Engine/Store/Checkpointer 关闭之后。
- `init`、`backup`、`restore` 和 `upgrade` 必须取得同一独占锁；运行中的 app 会使它们立即失败。
- `status` 只读检查不取得独占锁，但会报告锁是否被占用。
- 文件锁只是单机互斥，不被宣传为分布式锁；非 POSIX 平台只保留现有开发路径，不进入参考门禁。

## 9. 服务生命周期与 Reconciliation

### 9.1 启动顺序

```text
读取 Release Manifest
→ 解析 DeploymentSettings
→ 获取实例独占锁
→ serve Preflight
→ 创建 WebServices
→ Reconciliation
→ 构建 FastAPI 路由
→ Uvicorn 开始监听
→ Readiness = ready
```

- Reconciliation 在监听端口前执行。
- 它只把遗留 `accepted/running` Run 收口为 `interrupted`，不调用模型、Tool、退款或 Memory。
- 已完成、失败、已中断和等待用户审批的状态保持不变。
- Reconciliation 结果包含扫描数量、改变数量、错误码和耗时，并写入脱敏运维审计。
- 重复运行结果一致；第二次改变数量为 `0`。

### 9.2 停止顺序

参考部署固定：

```text
docker compose stop
→ SIGTERM
→ Uvicorn 停止接受所有新 HTTP 连接
→ 最多 30 秒等待在途响应和 BackgroundTasks
→ lifespan shutdown 再次中断未完成 Run
→ 关闭 Engine/Store/Checkpointer
→ 释放 Instance Lock
→ Compose 最多等待 40 秒后才允许 SIGKILL
```

读请求策略：收到 SIGTERM 后不再接受新的读或写连接；已经进入应用的读请求与写任务均可在
30 秒宽限期内完成。这样不需要在每个 Route 复制一套 `quiescing` 分支，也不会出现不同 Route
随机接受新请求。

### 9.3 强制终止

- SIGKILL 无法执行 lifespan；启动 Reconciliation 是最终兜底。
- SQLite 未提交事务由数据库回滚；Mock 退款通过既有 action ID 和唯一约束保持幂等。
- Reconciliation 不自动重试被中断 Run。用户只能通过现有显式 Retry 或 Pending Action 恢复。
- 无法证明副作用状态时保持稳定失败/中断，不生成成功消息。

## 10. 健康与 Capability

### 10.1 公开端点

```text
GET /api/health/live
  200 {status: "alive", version: "1.0.0"}

GET /api/health/ready
  200 {status: "ready", version, capabilities}
  503 {status: "not_ready", version, error_code}

GET /api/health
  保留兼容，投影为 live 结果
```

- Liveness 只读取进程内 Release Manifest，不访问磁盘、数据库、网络或模型。
- Readiness 使用只读连接检查业务 Schema、Checkpoint、Memory、政策索引和前端版本。
- Readiness 不创建 Session、不刷新配额、不调用 Provider、不执行 Graph，也不修复 Schema/索引。
- 公开错误只返回稳定 `error_code`，不返回表名、路径、异常、Provider 或配置值。

### 10.2 Capability 状态

```text
CapabilityState = enabled | disabled | degraded | unavailable
```

| Capability | 判断依据 |
|---|---|
| guest | 核心 Ready 时 enabled |
| registered_llm | Feature 开关 + 三项 Provider 配置；不主动探测远端 |
| refund | 业务 Schema、政策索引和 Checkpoint Ready |
| l2 | registered_llm + Memory + L2 Schema Ready |
| policy_rag | 政策来源与索引版本匹配 |

`enabled` 只表示配置和本地依赖可用，不声称 Provider 当前网络一定可达；实际 Provider 失败继续
通过 Run 错误和聚合指标呈现，不允许健康检查产生付费调用。

### 10.3 本机详细状态

`python -m commerce_resolve ops status --format json` 输出：

- Release/Instance/Data Format 版本。
- Instance Lock、业务 Schema、Checkpoint、Memory、政策索引、前端资源状态。
- Capability 状态和稳定失败码。
- Agent Run、模型调用、Tool、Mock 退款、失败、中断和恢复的有限聚合计数。
- 最近运维动作的类型、结果和时间，不含参数正文、用户 ID、订单号或路径。

## 11. Backup Set

### 11.1 一致性边界

- 正式备份只在 app 已停止且 `backup create` 取得 Instance Lock 后执行。
- `deploy/commerce-resolve backup` 先记录服务原状态；原本运行时执行“停止并等待 → 创建并验证
  备份 → 重新启动并等待 Ready”，原本停止时完成备份后仍保持停止。
- 如果停止、锁、快照或重启任一步失败，命令返回非零并指出阶段；不能生成虚假成功 Manifest。
- 停机是为了保证业务、Checkpoint 和 Memory 位于同一明确维护时间点，而不声称三个 SQLite
  具备跨数据库事务。

### 11.2 Backup Set 结构

```text
var/backups/<backup_id>/
├── manifest.json
├── business.sqlite
├── checkpoints.sqlite
└── memory.sqlite
```

`BackupManifest`：

```text
schema_version          backup-manifest-v1
backup_id               时间无关随机 ID
created_at              UTC
source_instance_id      来源实例
source_release          版本 + Git Commit
data_format_version     commerce-resolve-data-v1
consistency             stopped-single-host
files[]                 role/name/size/sha256/sqlite_integrity
domain_counts           用户、会话、消息、Run、退款、Case、Memory 等有限计数
excluded                policy-index/logs/eval/tmp/env/secrets/frontend-cache
```

- 使用每个源数据库的只读连接和 `Connection.backup()` 写入临时目录。
- 对目标执行 `PRAGMA integrity_check`，关闭连接后计算 SHA-256 与大小。
- Manifest 最后写入；所有检查通过后才把临时目录原子重命名为 `<backup_id>`。
- 失败时清理临时目录，不覆盖同名 Backup Set。
- Policy Source 在镜像/版本控制中，Policy Index 恢复后重建，不进入 Backup Set。
- `.env`、API Key、Cookie、日志、操作审计、Eval Artifact、浏览器产物和既有 Backup 不进入备份。

### 11.3 验证

`ops backup verify --backup <path>`：

- 严格解析 Manifest，拒绝未知字段和路径逃逸。
- 只允许三个预期 SQLite 文件，拒绝符号链接、设备文件和额外秘密文件。
- 验证文件大小、SHA-256、SQLite integrity、数据格式和支持版本。
- 只读计算领域计数并与 Manifest 对比。
- 不修改当前实例、不打开 Provider、不加载 `.env` 中的 LLM Key。

## 12. Restore

### 12.1 默认空目标

```text
停止 app
→ 获取 Instance Lock
→ verify Backup Set
→ 验证目标为空和磁盘空间
→ restore 到 var/tmp/restore-<id>
→ 校验三库 Schema、完整性、归属和关键计数
→ 原子移动到目标
→ 生成/更新 Instance Manifest
→ 重建政策索引
→ serve Preflight
→ 启动并等待 Ready
```

- 空目标恢复生成新的 `instance_id`，保留 `restored_from=backup_id`。
- 恢复文件先写临时目录；验证失败时目标保持为空。
- 不合并两个实例，不按表增量导入，也不改变 user/workspace/thread/case/action namespace。

### 12.2 覆盖现有实例

- 必须同时提供 `--replace` 与 `--confirm-instance-id <current-id>`。
- 覆盖前自动对当前实例创建一个通过校验的 rollback Backup Set；失败则拒绝覆盖。
- 当前三库先原子移动到临时 rollback 区，再安装恢复结果。
- 恢复后 Preflight 失败时把目标保持非 Ready，并输出明确 rollback 命令；不静默删除证据。
- 覆盖、结果和 rollback Backup ID 写入脱敏运维审计。

## 13. 从 v0.8 升级

### 13.1 固定 v0.8 Fixture

不提交 SQLite 二进制。新增版本化 JSON Fixture 和 Builder，在临时目录生成：

- 一名注册用户、一个 workspace、Session 和邀请码状态。
- 两个 conversation、公开消息、成功/失败/等待中的 Run 与 SSE Event。
- Mock 订单、物流、支付、退款 Action 和已完成退款。
- Pending Refund、L2 Upgrade、补充信息和 Memory Proposal 的代表状态。
- L2 Case、Context Manifest、Public Trace 和模型计量。
- LangGraph Checkpoint 与一条已确认长期偏好。

Fixture Builder 固定创建 v0.8 Alembic Head、Checkpoint/Store 格式和领域计数，然后形成
`backup-manifest-v1` 兼容输入。它只使用合成数据。

### 13.2 Upgrade 流程

```text
确认来源为 v0.8
→ 停止 app 并获取 Instance Lock
→ upgrade Preflight
→ 创建并验证 pre-upgrade Backup Set
→ 执行业务 Alembic upgrade
→ 运行 Memory/Checkpoint 兼容检查
→ 重建政策索引
→ 写入新的 Instance Manifest
→ serve Preflight
→ 启动并等待 Ready
```

- 当前版本若没有新的业务表，也必须运行兼容检查，不能把“无迁移”当作升级证据。
- 任一步失败不写入 `last_successful_release=1.0.0`，实例保持停止和非 Ready。
- v1.0 不自动 Down Migration；错误输出包含 pre-upgrade Backup ID 和明确恢复命令。
- 升级测试逐项验证账号、归属、消息、Pending、退款幂等、Case、Trace、Checkpoint 和 Memory。
- 前端与后端 Release Manifest 不一致时，Preflight 和 Release Gate 均失败。

## 14. 结构化日志、诊断与运维审计

### 14.1 应用日志

每行一个 JSON Object：

```text
timestamp
level
component
event
result
duration_ms
error_code
request_id
run_id
thread_id
case_id
action_id
release_version
```

- 字段按事件适用性出现；不把缺失值填成自由文本。
- `request_id` 接受符合长度/字符约束的客户端值，否则服务端生成 UUID，并回写响应 Header。
- 默认不记录消息正文、完整 Prompt/响应、Cookie、密码、邀请码、API Key、订单详情或绝对路径。
- 未处理异常仅在本机 stderr 包含脱敏堆栈；浏览器仍获得稳定公开错误。
- JSON Formatter 使用标准库，不修改 Public Trace、Diagnostic Trace 或 Eval Artifact 契约。

### 14.2 聚合指标

本机 `ops status` 通过只读 Repository 查询持久事实：

- 请求/Run 总数及终态分布。
- 模型调用、Tool 调用、失败归因、中断和显式重试计数。
- Mock 退款预览、批准、拒绝、完成和验证失败计数。
- L2 Case 状态和平均步骤数。
- 最近窗口只使用固定时间桶，不使用用户 ID、订单号或自由文本标签。

不在 v1.0 建立常驻 Metrics Server。运行期纯进程指标可随重启清零，业务与安全结论仍来自持久
Repository、Trace 和 Eval。

### 14.3 Operations Audit

- `init`、`preflight`、`backup`、`restore`、`upgrade` 和 `reconcile` 追加 JSONL 记录。
- 记录 operation ID、类型、来源/目标版本、Backup ID、结果、错误码、耗时和时间。
- 不记录 Secret、环境变量值、用户正文、数据库内容或完整宿主路径。
- 它与业务数据库分离，不作为业务事实，也不进入 Backup Set。
- Compose 使用 Docker `local` 日志驱动和有限大小；Operations Audit 使用固定大小轮转并保留
  最近文件，达到上限时不删除三类权威数据。

## 15. 容器与运行安全

- 容器进程使用固定非 root UID/GID `10001`。
- 根文件系统 `read_only: true`，仅 `/var/lib/commerce-resolve` bind mount 和 `/tmp` tmpfs 可写。
- `cap_drop: [ALL]`、`security_opt: [no-new-privileges:true]`。
- 不挂载 Docker Socket、SSH、宿主 Home、Git 凭据或任意项目外目录。
- 端口映射固定以 `127.0.0.1:` 开头；修改为非回环地址会被部署 Preflight 拒绝。
- `.env.deploy` 权限检查至少拒绝 group/world writable；诊断只报告权限错误，不打印内容。
- 镜像构建上下文通过 `.dockerignore` 排除 `.git`、`.env`、`var`、Backup、数据库、日志、
  node_modules、测试 Artifact 和 IDE 文件。
- Healthcheck 使用镜像内 Python 请求本机 Readiness，不额外安装 curl。
- Provider 出站网络仍由容器默认网络提供，这是 LLM 模式的已知边界；游客与 Offline Gate 继续
  通过代码和环境白名单保证零 Provider 调用。


### 16.3 Ops 退出码

```text

2  配置或参数错误

6  Restore 前置条件不满足
7  Upgrade 失败
8  安全边界拒绝
```

公开错误码比异常文本稳定；CLI 文案可以变化，自动化测试断言退出码和结构化报告。

## 19. Web 兼容与维护失败语义

- 如果实例尚未 Ready，业务 Route 返回 `503 service_not_ready`；不返回内部组件名称。
- 在正常 SIGTERM 后监听器停止，新连接由网络层拒绝；前端保留当前会话状态并允许服务恢复后刷新。
- 不新增 Web 运维后台、Backup 下载、Restore 上传或在线升级 API。
- 不把日志、Metrics、Release Manifest 全量或 Instance ID 暴露给浏览器。

## 27. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| BackgroundTask 遇 SIGKILL | Run 可能停在 running | 启动 Reconciliation + action 幂等 + 显式 Retry |
| 三个 SQLite 无跨库事务 | 在线复制可能不一致 | 正式备份要求停机和独占锁 |
| Bind mount 权限错误 | 容器无法读写或误创建空库 | Preflight、固定 UID/GID、禁止 serve 自动初始化 |
| 文件锁在非参考文件系统行为不同 | 可能出现双实例 | 只承诺 Ubuntu 本地文件系统；容器门禁验证竞争 |
| SQLite 并发能力有限 | 高并发延迟和锁竞争 | 单 worker、受控演示负载；不声称生产并发 |
| `.env` 注入 Secret 可被宿主管理员读取 | 本地密钥风险 | 文件权限检查、不烘焙/不日志化；主机管理员仍为信任边界 |
| 镜像基础层漂移 | 重建结果变化 | 锁定主版本/摘要、Manifest 记录、Release Gate 重建检查 |
| 备份本身留在同一磁盘 | 主机磁盘损坏同时丢失 | 明确为本地恢复能力；异地灾备属于非目标 |
| Restore 覆盖错误实例 | 数据丢失 | instance ID 双重确认 + rollback Backup + 审计 |
| Upgrade 中途失败 | 半迁移数据 | 独占停机、升级前备份、非 Ready、显式恢复命令 |
| 日志字段泄露正文 | 隐私泄露 | 白名单 JSON 字段、故障注入和敏感扫描 |
| 容器 Release Gate 较慢 | 日常反馈变慢 | 目标测试按任务运行；完整门禁仅候选发布强制执行 |
| 参考创意网站导致动效过度 | 干扰阅读、输入和审批 | 只采用层级、缓动和短暂进入反馈；禁用 3D、视差和持续动画，并支持 Reduced Motion |

## 28. 非目标与明确延后

- PostgreSQL/MySQL、Redis、独立 Worker、消息队列和多实例一致性。
- Kubernetes、零停机滚动升级、自动扩缩容和高可用。
- 公网 HTTPS 反向代理、域名、证书自动签发和云基础设施模板。
- 自动异地备份、对象存储、增量备份、加密密钥托管和灾难恢复站点。
- 在线 Backup、跨实例 Restore 合并和自动 Down Migration。
- 公共 Admin Web、远程 Restore API、在线升级和自动回滚。
- 外部 APM、集中日志、Prometheus、OpenTelemetry、LangSmith 或 Langfuse。
- 新售后业务、真实交易系统和任何生产 SLA/合规承诺。

## 29. 已接受决策

本 Plan 与 ADR-0010 已确认：

1. 参考环境使用 Ubuntu 24.04 LTS、Docker Engine 和 Compose v2；macOS 保留现有开发路径。
2. Release Bundle 使用多阶段镜像；运行时只有一个非 root FastAPI 容器和一个 Uvicorn worker。
3. 宿主只绑定 `127.0.0.1`；v1.0 不捆绑反向代理或公网 HTTPS。
4. 保留业务、Checkpoint、Memory 三类权威 SQLite和一类派生政策索引，不迁移 PostgreSQL。
5. `./var` 使用 bind mount，并通过 POSIX 文件锁阻止 app 与高影响 Ops 并发写入。
6. 正式 Backup 采用短暂停机 + SQLite Backup API；政策索引、日志、Eval 和 Secret 不进入 Backup。
7. Upgrade 只支持 v0.8 → v1.0，失败后保持停止，由升级前 Backup 显式恢复，不自动 Down Migration。

10. 任务按 T1–T8 顺序实施；实现不得绕过已接受的 Spec、Plan 和 ADR。

    未来出现需要可取消多步骤 Timeline 的复现需求，再以独立决策评估动画库。
