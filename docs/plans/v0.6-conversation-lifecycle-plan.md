## 1. Plan 目标

在保持 v0.1–v0.5 订单、政策 RAG、Web 身份、Mock 退款和 L2 Harness 业务行为不变的
前提下，把 Web 对话从 React 组件内存升级为可持久化、可管理、可恢复的产品对象：

- 服务端保存经过公开投影的用户消息、助手消息、引用和动作卡片。
- 页面刷新、站内路由切换、重新登录后可以恢复本人有权访问的历史。
- 注册用户可以列出、新建、选择、归档、取消归档和删除会话。
- 每条用户提交具有稳定客户端标识，并与唯一 Agent Run 关联。
- Graph 执行与浏览器 SSE 连接解耦，短暂断线不会终止同一进程中的 Run。
- SSE 只发送已经持久化、经过白名单投影的步骤进度和最终公开消息，并支持游标重放。
- 退款、L2 升级、L2 补充信息和记忆确认可以在刷新后继续原动作。
- 删除聊天历史不会级联删除订单、退款、L2 Case、审计或长期记忆。

本 Plan 不把 Checkpoint 改造成聊天数据库，也不引入 PostgreSQL、Redis、消息队列、外部
Worker、多实例广播或 Provider 原始 Token 流。

## 2. 完成证据

v0.6 完成必须同时具备以下证据：

- 至少三轮公开消息在刷新、切页和重新登录后内容、顺序、引用与动作卡片一致。
- 相同 `client_message_id` 重试只产生一条用户消息和一个原始 Run。
- 同一会话的不同并发消息被明确拒绝，不破坏 Checkpoint 顺序。
- SSE 断线后根据 `Last-Event-ID` 重放缺失事件，不重复已确认事件。
- 浏览器在最终回复完成前能够看到服务端确认的步骤进度。
- Run 失败或进程重启中断后，已接受用户消息仍可见，并具有明确失败或重试状态。
- 退款、L2 升级、L2 追问和记忆确认刷新后仍绑定原标识，重复确认不产生重复副作用。
- 注册用户的会话列表、归档、恢复和删除全部经过当前身份与工作区校验。
- 删除会话后公开消息和 Checkpoint 不再可访问，独立业务事实与长期记忆仍存在。
- 公开历史和 SSE 中不存在 Prompt、隐藏推理、原始 ToolMessage、完整 State、密钥或跨用户数据。
- v0.6 固定 32 个 Eval 场景达到 `32/32`，v0.1–v0.5 测试和 Eval 全部回归。

## 3. 当前基线与实施约束

当前 Web 已提供：

- FastAPI 同源 JSON API、React + TypeScript SPA 和服务端 Session/CSRF/Origin 防护。
- `conversations` 表中的 `thread_id`、`subject_id`、`workspace_id` 和访问模式绑定。
- `var/checkpoints.sqlite` 中按 `thread_id` 保存的 LangGraph State 与中断。
- `var/business.sqlite` 中的账号、订单、退款、L2 Case 和公开 L2 Trace。
- `var/memory.sqlite` 中用户确认的长期偏好，以及独立政策 FTS5 索引。
- `ThreadLockRegistry` 提供的单进程、单 thread 非阻塞互斥。
- `POST /api/chat/messages` 的同步 `graph.invoke()` 路径和四类 Pending Action 查询/决定接口。
- 前端 `messages` React State、Local Storage 中的单个 thread 标识和本地打字机动画。

当前缺口：

- `conversations` 只是授权绑定，没有标题、生命周期、摘要或历史分页。
- 公开用户消息与助手消息没有进入业务数据库，组件卸载后即丢失。
- `ChatResponse` 只返回本轮最后一条助手消息，不能重建完整产品历史。
- Local Storage 只保存标识，不是授权或消息事实来源。
- `graph.invoke()` 与 HTTP 请求同生命周期，无法提供真实网络进度或断线重放。
- 现有 OpenAI Adapter 使用结构化 JSON 且 `stream=False`；其原始 Token 在 Schema 校验前不可信。

实施继续遵守：

- 本地单实例、单 Uvicorn worker。
- SQLite 短事务、WAL、唯一约束和进程内 thread lock。
- Fake Model/Fake Gateway 是自动化测试默认依赖。
- 所有新增或修改函数使用中文 docstring/JSDoc。
- 不重构与本版本无关的 Graph、Policy、退款或 L2 业务规则。

## 4. 总体架构

```text
React Chat
  -> POST 消息/决定（稳定 client_request_id）
  -> 业务库事务：接受用户输入 + 创建 Agent Run + 记录 accepted 事件
  -> 202 RunAccepted
  -> 单进程 FastAPI BackgroundTask
       -> thread lock
       -> LangGraph stream(updates)
       -> PublicProgressMapper
       -> 已持久化 Run Event
       -> Graph Snapshot
       -> PublicMessageProjector
       -> 助手消息 + Run 终态 + 会话摘要

React EventSource
  -> GET Run SSE + Last-Event-ID
  -> 只读取已授权、已持久化的公开事件
  -> 断线重放 / 心跳 / 终态关闭

物理存储：
  var/business.sqlite
    conversations / public_messages / agent_runs / agent_run_events
    账号、订单、退款、L2 Case、业务审计
  var/checkpoints.sqlite
    LangGraph 内部 State、中断和恢复点
  var/policy-index.sqlite
    可重建政策索引
  var/memory.sqlite
    用户确认的长期偏好
```

公开消息、Run 与事件保存在现有业务数据库，是因为它们属于 Web 产品数据并需要与当前
身份、会话归属和列表摘要使用短事务协调；它们仍与 Checkpoint、政策索引和 Memory Store
保持物理分离。

## 5. 技术选型

| 领域 | 选择 | 原因 |
|---|---|---|
| 公开会话存储 | 现有 SQLite + SQLAlchemy 2.0 | 与身份归属同事务、本地可复现、无需新服务 |
| Schema 迁移 | 新 Alembic revision | 增量保留 v0.3–v0.5 业务数据 |
| Graph 进度 | LangGraph `stream(..., stream_mode="updates")` | 观察真实节点完成，不暴露内部完整 State |
| 执行解耦 | FastAPI/Starlette 进程内 `BackgroundTasks` | 202 后继续执行，浏览器断开不取消；不引入 Worker |
| 网络渐进输出 | SSE `text/event-stream` | 单向服务端进度、自动重连、`Last-Event-ID`，比 WebSocket 更小 |
| 断线重放 | 持久化 Run Event + 单调事件 ID | 重连只补缺失事件，SSE 连接不是事实来源 |
| 消息幂等 | 客户端 UUID + 请求摘要 + 数据库唯一约束 | 防止双击、网络重试和多标签重复调用 Graph |
| 公开载荷 | Pydantic 严格模型 + 版本化 JSON | 保留卡片结构，同时拒绝任意内部 State |
| 历史分页 | SQLite keyset cursor | 避免大偏移，保持稳定顺序 |
| 前端状态 | TanStack Query + URL thread 路由 | 服务端是事实来源，刷新和切页可恢复 |
| 自动化测试 | pytest、Vitest、Playwright、Fake Graph/Model | 离线验证事务、流、重连和 UI |

v0.6 不增加 Python 或 npm 运行时依赖。FastAPI/Starlette 已提供 `BackgroundTasks` 和
`StreamingResponse`；浏览器原生 `EventSource` 已满足同源 SSE。若实现探针证明当前
TestClient 无法可靠断言流式时间顺序，可以在测试代码中使用现有 `httpx` 依赖，不把它
增加为产品协议。

### 5.1 为什么公开历史不能直接读取 Checkpoint

Checkpoint 包含内部消息、Reducer 状态、路由字段、中断和可能的 ToolMessage。它不适合：

- 按公开时间顺序分页。
- 保存稳定产品消息标识和客户端幂等键。
- 安全删除公开历史而保留业务事实。
- 在不反序列化内部类型的情况下列出多个会话。
- 保证不会泄露 Prompt、工具正文或隐藏 State。

因此只允许服务端在 Graph 运行结束或进入中断后，把有限公开结果投影到消息表。

### 5.2 为什么选择 SSE 而不是 WebSocket

当前需求只有服务端向浏览器发送 Run 进度和完成事件；用户输入、退款审批和记忆决定仍是
独立、可幂等的 HTTP POST。SSE 已提供：

- 同源 Cookie 身份。
- 浏览器自动重连。
- `Last-Event-ID` 游标。
- 普通 HTTP 调试、代理和测试方式。

WebSocket 的双向协议、心跳、鉴权续期和重连同步在本版本没有额外用户价值。

### 5.3 为什么不直接传输 Provider Token

一线 Interpreter 和 L2 Agent 都返回结构化 JSON 决策；退款、权限、工具和政策回答还要
经过 Pydantic、Policy、业务工具和 Verifier。把 Provider 原始 Token 直接展示会：

- 在 JSON 完整校验前泄露无效或越权候选内容。
- 把模型草稿冒充已经验证的业务结论。
- 破坏当前“模型不能直接授权动作”的边界。

v0.6 采用真实网络步骤流：节点完成后，服务端持久化并发送有限的“正在理解、正在检索、
正在验证、等待决定、已完成”等进度；最终回复只在公开投影通过后发送。新完成的最终文本
可以继续使用无障碍友好的本地展示动画，但该动画不作为流式验收证据。以后若引入独立的
自然语言 Renderer Model，只有在事实与引用先冻结、文本增量可安全验证后，才评估 Token 流。

### 5.4 为什么使用进程内 BackgroundTask 而不是 Worker

消息接受和 Agent 执行必须与 SSE 连接解耦，否则浏览器刷新可能取消生成。当前仍是本地
单实例，因此使用进程内任务是最小方案：

- POST 事务完成后返回 `202`，同一进程继续运行 Graph。
- SSE 只读取数据库事件，不持有 Graph 执行上下文。
- 浏览器断开不影响后台函数。
- 服务进程退出时正在执行的任务不会被伪装成完成；重启后标记为 `interrupted`。

这不是持久任务队列，也不承诺进程崩溃后自动继续正在进行的 Provider 调用。多实例、任务
租约、分布式队列和 Worker 属于未来生产化 ADR。

## 7. 领域模型

所有模型使用 `ConfigDict(frozen=True, extra="forbid")`，枚举、字符串和集合均设置上限。

### 7.1 Conversation

```text
ConversationSummary
  thread_id
  title
  lifecycle: active | archived
  history_state: complete | partial
  message_count
  last_message_preview | null
  last_message_at | null
  run_status | null
  pending_action | null
  created_at / updated_at / archived_at
```

标题规则为确定性代码：第一条被接受的用户文本经过空白折叠后取前 32 个 Unicode 字符，
超长追加省略号；空会话标题固定为“新对话”。标题生成不调用模型、不扣配额，也不允许
浏览器提供身份或工作区字段。

`history_state=partial` 只用于 v0.6 迁移前已经存在、无法安全回填完整公开消息的会话。

### 7.2 PublicMessage

```text
PublicMessage
  message_id
  thread_id
  run_id | null
  sequence_no
  role: user | assistant
  kind: text | action | status
  content
  status: accepted | completed | failed
  payload_version
  payload | null
  created_at / updated_at
```

`payload` 是严格 `PublicMessagePayload`，只允许复用当前公开响应中的：

- `citations`
- `refund_preview` / `refund_result`
- `l2_upgrade_preview` / `l2_case_summary` / `l2_pending_action`
- `l2_trace_events`
- `memory_proposal`

不保存完整 `ChatResponse`、内部 State、ToolMessage 或任意未验证字典。JSON 只作为经过
Pydantic 验证后的版本化持久形式；读取时再次校验，失败返回明确 `public_payload_invalid`。

### 7.3 AgentRun

```text
AgentRun
  run_id
  thread_id
  client_request_id
  request_kind:
    chat_message | refund_decision | l2_upgrade_decision |
    memory_decision | retry
  request_hash
  retry_of_run_id | null
  status:
    accepted | running | waiting_action | completed |
    failed | interrupted
  pending_action | null
  checkpoint_id | null
  public_error_code | null
  created_at / started_at / updated_at / completed_at
```

同一 `(thread_id, client_request_id)` 唯一。相同标识与相同请求摘要返回已有 Run；相同标识
携带不同内容返回 `409 idempotency_conflict`。同一 thread 同时最多一个 `accepted/running`
Run，不排队；不同消息并发时返回 `409 thread_busy`。

`waiting_action` 表示本次 Graph 调用已安全停在持久化中断，SSE 可以结束；用户的下一次明确
决定或补充输入会创建新的 Run，但继续同一 `thread_id` 和 Checkpoint。

### 7.4 AgentRunEvent

```text
AgentRunEvent
  event_id                 SQLite 单调整数，也是 SSE id
  run_id
  event_key                Run 内稳定幂等键
  event_type:
    run.accepted | run.started | step.updated |
    action.required | message.completed |
    run.completed | run.failed | run.interrupted
  payload_version
  public_payload_json
  created_at
```

进度载荷只包含有限 `phase`、公开说明、消息标识、Run 状态和动作类型。节点名、State 更新、
模型原文、Prompt、工具参数和异常堆栈不进入事件。

`deleting/deleted` 是内部墓碑状态。由于 `refund_actions`、`l2_support_cases` 和

### 8.2 `agent_runs`

至少包含第 7.3 节字段，并增加：

- 唯一约束 `(thread_id, client_request_id)`。
- partial unique index：每个 thread 只有一个 `accepted/running` Run。
- `thread_id`、`status`、`created_at` 索引。
- 状态与时间字段 Check Constraint。
- `retry_of_run_id` 自引用使用 `SET NULL`，删除公开 Run 时不形成级联环。

### 8.3 `conversation_messages`

至少包含第 7.2 节字段，并增加：

- 唯一约束 `(thread_id, sequence_no)`。
- `(thread_id, sequence_no)` 与 `(run_id)` 索引。
- `run_id` 使用 `ON DELETE CASCADE`；迁移前兼容消息允许为空。
- `content`、预览和 JSON 大小由应用 Schema 与数据库 Check Constraint 双重限制。

每个 thread 的 `sequence_no` 在修改 conversation 行的同一事务中分配，不能使用
`created_at` 猜测顺序。

### 8.4 `agent_run_events`

- `event_id INTEGER PRIMARY KEY AUTOINCREMENT`，作为全局单调 SSE 游标。
- `run_id` 外键 `ON DELETE CASCADE`。
- 唯一约束 `(run_id, event_key)`。
- `(run_id, event_id)` 索引。
- 事件类型、payload version 和长度约束。

### 8.5 迁移已有会话

迁移不从 Checkpoint 反序列化或复制历史消息：

- 已有 conversation 标记 `history_state=partial`、标题“历史会话”。
- 消息数和摘要为空，原 `thread_id`、归属、退款、L2 Case 与 Checkpoint 保持不变。
- 新建 conversation 显式写入 `history_state=complete`。
- 加载旧 thread 时仍检查现有 Pending Action，并展示“早期消息未迁移”的普通说明。
- v0.6 后的新消息正常进入公开历史。

这种方案保留恢复能力，又避免把历史内部 ToolMessage 或 State 误公开。

### 9.1 接受消息事务

固定顺序：

1. 使用完整 `thread_id + subject_id + workspace_id + access_mode` 查询 active conversation。
2. 查找 `(thread_id, client_request_id)`。
3. 若存在且请求摘要一致，返回已有消息和 Run，不启动第二次 Graph。
4. 若存在但摘要不一致，返回 `409 idempotency_conflict`。
5. 若 thread 有 `accepted/running` Run，返回 `409 thread_busy`。
6. 校验当前 Pending Action 是否允许普通消息或 L2 补充信息。
7. 分配 sequence，写入 accepted 用户消息、Agent Run 和 `run.accepted` 事件。
8. 首条消息时确定标题，更新摘要、计数和活动时间。
9. 提交后才安排 BackgroundTask。

数据库唯一约束是最终并发门禁；`ThreadLockRegistry` 只减少单进程冲突，不能代替唯一约束。

### 9.2 完成投影事务

Graph 到达结束或中断后，在一个业务事务中：

1. 确认 Run 仍是 `running` 且属于当前 thread。
2. 校验 Snapshot 中 `current_run_id` 与 Run 相同。
3. 通过 `PublicMessageProjector` 构造有限助手消息和动作载荷。
4. 幂等写入一条助手消息及 `message.completed`/`action.required` 事件。
5. 保存 `checkpoint_id`、Run 终态与 pending action。
6. 更新 conversation 的摘要、消息数和最近活动时间。

如果同一事件或投影被重放，稳定 `event_key`、Run 状态和唯一约束返回原结果，不追加消息。

### 9.3 两个 SQLite 之间的一致性

业务数据库和 Checkpoint 数据库不能原子提交。采用显式可检测的一致性：

- 用户消息与 Run 先在业务库提交，再启动 Graph；因此接受后刷新一定能看见用户消息。
- Graph Checkpoint 先由 LangGraph 写入，再由 projector 写公开助手消息。
- 两者之间失败时 Run 保持 `running/interrupted/failed`，不能宣称完成。
- Snapshot 持久化可选 `current_run_id`，Run 保存已投影 `checkpoint_id`，用于检测错位。
- 历史读取始终可用；继续执行前若 Checkpoint 缺失或与 Run 不一致，返回
  `checkpoint_inconsistent`，不创建同标识新任务。
- 业务副作用继续依赖退款、Case、Trace 和 Memory 的既有稳定 ID/唯一约束，而不依赖消息事务。

## 10. Run 执行与 LangGraph Streaming

`ConversationRuntime` 接收只包含服务端可信身份、thread、run、请求类型和有限输入的不可变
执行请求。BackgroundTask 不持有 FastAPI `Request`、SQLAlchemy Session、打开的 SQLite
连接或模型客户端。

执行步骤：

```text
读取并验证 Run
  -> 获取 thread lock
  -> mark running + run.started
  -> 为当前身份装配独立 dependencies/checkpointer/store
  -> graph.stream(input_or_Command, stream_mode="updates", version="v2")
  -> 每个更新只读取节点名称，由 PublicProgressMapper 映射并去重
  -> stream 结束后 graph.get_state()
  -> project Snapshot
  -> waiting_action 或 completed
```

`PublicProgressMapper` 使用静态白名单，例如：

| 内部节点类别 | 公开 phase | 公开说明 |
|---|---|---|
| `bind_and_interpret` | `understanding` | 正在理解你的问题 |
| 订单/物流读取 | `loading_order` | 正在查询订单与物流 |
| 政策检索/验证 | `searching_policy` | 正在核对售后政策 |
| 退款 Policy/验证 | `checking_refund` | 正在核对退款条件 |
| L2 decide/tool | `l2_processing` | AI 二线客服正在核对可信信息 |
| 终端回复节点 | `finalizing` | 正在整理可验证结果 |

未知节点不自动暴露名称；只记录内部日志，公开事件可退化为通用 `processing`。相同 phase
连续出现时去重，避免 L2 Loop 产生无意义刷屏。

Graph 输入增加：

```text
current_run_id
messages[0].id = 已持久化的 public user message_id
```

`current_run_id` 是可选 State 字段，旧 CLI 和旧 Checkpoint 不受影响。`add_messages` 根据稳定
消息 ID 避免显式重试把同一用户消息重复写入内部 State。

## 11. Run 失败、重启与重试

### 11.1 已知业务失败

Interpreter 不可用、查询被拒绝、配额不足等已知错误转换为：

- 一条普通助手失败消息。
- `run.failed` 事件和有限 `public_error_code`。
- 不包含 Provider 响应、堆栈、本地路径或内部错误。

### 11.2 浏览器断线

浏览器 SSE 断开不取消 BackgroundTask。重新加载后：

1. 读取公开历史和 Run 状态。
2. 使用最新 event id 重连。
3. 服务端重放缺失事件。
4. Run 终态后关闭连接并刷新消息页。

### 11.3 服务进程重启

应用启动时调用 `interrupt_stale_runs()`：

- 只处理遗留的 `accepted/running` Run。
- 把它们标记为 `interrupted`，写入普通公开失败消息和 `run.interrupted` 事件。
- 不自动重放可能已经发生的 Provider 调用或业务动作。
- 既有 `waiting_action` 不改状态，仍由 Checkpoint 恢复。

这保证服务重启后历史一致，但不承诺恢复正在进行的网络流或模型调用。

### 11.4 显式重试

新增受限重试：

```text
POST /api/conversations/{thread_id}/runs/{run_id}/retry
body: client_request_id
```

只允许本人对 `failed/interrupted` 且没有 Pending Action 的 Run 重试。重试：

- 复用原用户消息及其稳定 message id，不追加第二条用户消息。
- 创建新 Run，并记录 `retry_of_run_id`。
- 使用新的 `client_request_id` 保证重试请求幂等。
- 重新调用 Provider 时视为新的实际尝试并正常计量；仅加载历史或重连不会扣额度。
- 退款、Case、Trace 与 Memory 继续依靠现有 action/case/event/proposal 幂等约束。

## 12. Web API

### 12.1 会话生命周期

```text
GET    /api/conversations?lifecycle=active|archived&cursor=&limit=
POST   /api/conversations
GET    /api/conversations/{thread_id}
PATCH  /api/conversations/{thread_id}
DELETE /api/conversations/{thread_id}
```

`POST` 在当前身份已有一个 active 空会话时返回该会话，避免反复进入 `/chat` 生成大量空行；
用户显式新建且当前会话已有消息时创建新 thread。

`PATCH` body 只接受：

```text
lifecycle: active | archived
```

归档会话默认从 active 列表隐藏；归档状态仍可读取历史，但发送前必须先取消归档。存在
`accepted/running` Run 或 Pending Action 时拒绝归档和删除。

### 12.2 历史分页

```text
GET /api/conversations/{thread_id}/messages?before=<opaque_cursor>&limit=50
```

- 默认返回最新 50 条，并按 `sequence_no` 升序展示。
- `next_before` 指向更早一页，客户端只把它作为不透明字符串。
- 页面加载时不读取或返回完整 Checkpoint。
- Response 同时包含 conversation 摘要、当前 Run 摘要和有限 Pending Action。

### 12.3 异步消息与 Run

```text
POST /api/conversations/{thread_id}/messages
GET  /api/conversations/{thread_id}/runs/{run_id}
GET  /api/conversations/{thread_id}/runs/{run_id}/events
POST /api/conversations/{thread_id}/runs/{run_id}/retry
```

消息 body：

```text
client_message_id: UUID
message: 1..2000 字符
```

POST 返回 `202 RunAcceptedResponse`：

```text
conversation
user_message
run
events_url
```

重复请求返回相同资源；若 Run 已完成，客户端可以直接加载历史，也可以重放完整事件。

### 12.4 Pending Action 决定

现有退款、L2 升级和记忆决定接口保留 URL 与业务校验，但增加服务端 Run 语义。请求继续只
接受现有 action/preview/proposal 标识和决定；幂等 key 由以下稳定组合生成：

```text
refund: action_id + decision
upgrade: preview_id + decision
memory: proposal_id + decision
```

接口返回 `202 RunAcceptedResponse`，后续进度与结果通过相同 SSE/历史路径获得。L2 用户补充
仍走消息 endpoint，并保留新的 `client_message_id`。

为了保持 CLI 与已有离线图测试，CLI 仍可以直接同步调用 Graph。旧
`POST /api/chat/messages` 在 v0.6 实施期间作为内部兼容入口调用同一 Runtime 并等待终态，
但 React 不再使用它；v0.7 前评估移除，不复制第二套业务逻辑。

## 13. SSE 协议

Endpoint：

```text
GET /api/conversations/{thread_id}/runs/{run_id}/events
Accept: text/event-stream
Last-Event-ID: <event_id>    # 重连时可选
```

每个持久事件：

```text
id: 123
event: step.updated
data: {"run_id":"...","type":"step.updated","payload":{...}}
```

规则：

- 初次连接从该 Run 第一条事件开始；重连只返回 `event_id > Last-Event-ID`。
- 服务端先持久化，再发送；不得先推送后补数据库。
- 终态事件发送后结束响应。
- 无新事件时每 15 秒发送 SSE comment heartbeat，heartbeat 不持久化也不参与游标。
- `Cache-Control: no-cache`，禁止代理缓冲；同源 Cookie 用于身份。
- SSE 是 GET，不使用 CSRF Token；连接建立和每次事件批次都重新确认 Session 未撤销、
  conversation 与 Run 仍属于当前身份。
- 不存在与越权使用统一 `404 conversation_not_accessible`，不能枚举其他用户 Run。
- EventSource 断线退避由浏览器负责；前端对相同 `event_id` 和 `message_id` 去重。

## 14. 前端方案

### 14.1 路由与服务端事实来源

新增：

```text
/chat                    选择最近 active 会话或空态
/chat/:threadId          显式定位当前会话
```

Local Storage 只保留最近 thread 作为非可信体验提示；页面必须先向服务端授权并加载。无权、
已删除或身份切换后立即清理提示，不展示旧账号缓存。TanStack Query 管理：

- conversation list。
- message infinite query。
- current Run。
- pending action。

路由切换造成组件卸载时，重新挂载从服务端查询，不依赖 `useState` 保留历史。

### 14.2 消息提交

前端使用 `crypto.randomUUID()` 生成 `client_message_id`：

1. 在 Query Cache 中放入 `sending` 临时项。
2. POST 成功后用服务端 `message_id`/Run 替换。
3. POST 未被接受时保留失败项，使用同一 client id 重试。
4. POST 已接受但网络响应丢失时，同一 id 重试返回已有 Run。
5. 建立 EventSource，按事件更新 Run 进度。
6. 收到终态后关闭连接并失效消息、列表和 pending 查询。

### 14.3 对话展示

- 恢复的历史消息立即显示，不重新播放打字机动画。
- 正在运行的助手占位在对话流内显示公开 phase，不使用红色系统异常横幅。
- 新完成的助手文本可以保留当前可关闭的本地动画，但真实流式验收来自 SSE 进度。
- 普通失败作为助手气泡显示；权限拒绝和审批卡保持明确但统一的视觉层级。
- 引用、退款、L2 和记忆卡片从消息 payload 恢复，不再只依赖当前页面 mutation response。
- 页面切换回来时若 Run 仍 active，按服务端游标重新连接。

### 14.4 会话管理

注册用户侧栏支持：

- 最近活动排序和分页。
- 新对话。
- active/archived 切换。
- 选择、取消归档和删除。
- 处理中/等待动作状态。

游客不显示账号级列表，只恢复当前有效 Session 有权访问的 thread；Local Storage 中旧游客
thread 在 Session 轮换后被服务端拒绝并替换。

## 15. Pending Action 恢复

公开历史加载服务在授权后读取：

1. conversation 的 denormalized pending 状态。
2. 最近 Run。
3. 必要时读取当前 Checkpoint 并使用 `_pending_action` 同等白名单规则复核。
4. 从 Snapshot 生成当前公开卡片，不返回完整 State。

覆盖：

- `refund_approval`：恢复同一 `action_id` 和预览 hash。
- `upgrade_confirmation`：恢复同一 `preview_id`。
- `user_input`：继续使用聊天输入框并创建补充信息 Run。
- `memory_confirmation`：恢复同一 `proposal_id`。

如果业务库 pending 摘要与 Checkpoint 不一致：

- 历史仍可读取。
- 禁止发送或确认。
- 展示普通 `checkpoint_inconsistent` 助手状态。
- 不自动创建新 action、Case、proposal 或 thread。

## 16. 会话归档与删除

### 16.1 归档

归档只改变 conversation 生命周期和列表可见性，不删除消息、Run、事件或 Checkpoint。
存在 active Run 或 Pending Action 时拒绝；取消归档幂等。

### 16.2 删除 Saga

由于业务库与 Checkpoint 库不能跨库事务，删除使用可重试 Saga：

```text
thread lock
  -> 再次确认无 active Run / Pending Action
  -> 业务库 active|archived -> deleting
  -> SqliteSaver.delete_thread(thread_id)
  -> 业务事务删除 public messages/runs/events
  -> conversation -> deleted 墓碑
```

- `SqliteSaver.delete_thread()` 会删除该 thread 的 checkpoints 和 writes；实施前增加针对当前
  锁定版本的契约测试。
- Checkpoint 删除失败时保留 `deleting` 并返回可重试失败；由于无法证明是否发生部分清理，
  不能把该会话重新开放为 active。
- Checkpoint 已删而业务清理失败时保留 `deleting`，产品 API 不再允许继续；再次 DELETE 只
  执行剩余清理，不重复删除独立业务事实。
- 最终墓碑保留 thread/归属和时间，以满足现有退款/L2/计量外键；产品授权查询排除墓碑。
- 长期记忆、订单、退款、L2 Case、业务审计和 Eval 不参与级联。

## 17. 身份、安全与数据最小化

所有会话、消息、Run 和 SSE 请求固定顺序：

```text
解析当前 Session
  -> Origin / CSRF（写请求）
  -> subject / workspace / access_mode
  -> conversation 生命周期与归属
  -> run/message/action 归属
  -> thread lock 或只读分页
  -> Repository / Checkpoint / Graph
```

- URL、Local Storage、message/run/event ID 都不是授权凭据。
- SSE 长连接定期重新验证 Session，退出登录后旧连接不能继续读取。
- 游客 thread 只绑定当前匿名 `subject_id`；新 Session 无法读取旧 thread。
- 公开 JSON 使用字段白名单和长度限制；存取时均通过 Pydantic。
- 不把内部节点名、State、Prompt、ToolMessage、异常或绝对路径写入公开表。
- API 错误在前端以普通对话状态展示，但真实授权拒绝仍返回正确 HTTP 状态。
- 服务端日志只记录脱敏 thread/run/event 标识和错误码，不记录完整用户消息或模型正文。

## 18. 兼容与迁移

- v0.6 migration 只增量扩展 conversations 并增加三张公开交互表。
- v0.1/v0.2 CLI 继续直接使用 Graph 和 Checkpointer，不要求创建公开消息。
- 现有 Graph 节点名、Reducer 和 v0.4/v0.5 interrupt 恢复语义保持不变。
- `AgentState.current_run_id` 为可选字段，旧 Checkpoint 不迁移。
- 现有 thread 继续有效，但标记 `history_state=partial`，不伪造历史。
- 当前 `/api/chat/messages` 作为 v0.6 兼容入口保留，统一调用新 Runtime；React 改用新 API。
- 当前 Pending Action URL 与 action/preview/proposal 请求字段保持不变；响应升级为 Run 资源时
  同步更新 OpenAPI、前端和 Web Eval。
- 旧 Local Storage thread 只作为首次选择提示，服务端拒绝后自动清理。
- downgrade 仅用于本地无保留需求环境；存在 v0.6 消息时必须先明确导出或接受删除。

## 24. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 业务库与 Checkpoint 无法原子提交 | run/checkpoint ID 对账、显式中间状态、幂等 projector、禁止静默完成 |
| BackgroundTask 在进程退出时丢失 | 启动时标记 interrupted；保留用户消息；显式安全重试 |
| SSE 重连重复消息 | 持久事件单调 ID、Last-Event-ID、message/event 双重去重 |
| 多标签同时发送破坏 State | thread lock + active Run partial unique index + 409 |
| Provider Token 暴露未验证内容 | 只流白名单步骤和验证后的最终消息 |
| L2 Loop 产生过多事件 | phase 去重、公开事件上限、内部 Trace 与产品事件分离 |
| 删除会话破坏退款/L2 外键 | conversation 墓碑；只删公开消息/Run/Event 与 Checkpoint |
| 删除跨库中途失败 | deleting Saga、幂等重试、失败恢复原状态或保留不可访问墓碑 |
| 历史 payload Schema 演进 | payload_version、读取时 Pydantic 校验、迁移策略 |
| Local Storage 泄露旧账号选择 | 仅作提示；服务端授权；Session 变化清理 Query Cache 与提示 |
| SQLite 连接和流式轮询压力 | 单 worker、有限 Run、短查询、250–500ms 自适应轮询和 heartbeat |
| 兼容 API 形成双实现 | 兼容入口只调用统一 Runtime；v0.7 前决定移除 |

## 25. ADR 判断

本 Plan 新增 Proposed ADR-0007，原因是以下选择会影响后续客户端和生产化迁移：

- 公开消息/Run/Event 与 Checkpoint 分离。
- 使用持久化事件驱动 SSE 断线重放。
- 采用进程内 BackgroundTask 作为本地单实例过渡，而非把 SSE 连接当执行生命周期。
- 不直接公开结构化 Agent 的 Provider 原始 Token。

Plan 与 ADR 被用户明确接受时，二者一起改为 Accepted。若实施需要 WebSocket、Redis、外部
Worker、多实例租约、Provider Token 流或把会话移到 PostgreSQL，必须先新增或取代 ADR。

## 26. 非目标确认

v0.6 不实现：

- PostgreSQL、Redis、消息队列、Celery/RQ、外部 Worker 或多实例广播。
- Provider 原始 Token、隐藏推理或未验证 JSON 增量展示。
- 消息全文搜索、编辑、单条删除、重新生成、分支、分享、导出或附件。
- 游客跨浏览器、跨设备历史或注册后自动合并游客会话。
- 新 L2 工具、多 Agent、真人客服、CRM 或外部业务集成。
- 改变退款资格、金额、审批、幂等或 L2 Harness 预算。
- 从旧 Checkpoint 自动反序列化并公开完整历史。
- 生产级高可用、任务租约、灾难恢复或无限消息保留。

## 27. 实施结论

T1 至 T7 已于 2026-07-21 按顺序完成，没有放宽 Feature Spec、系统约束或 ADR-0007：

- Alembic 增量迁移扩展会话并新增公开消息、Agent Run 和可重放事件表。
- 新消息和四类 Pending Action 共用幂等 Run、后台 Graph、公开投影和 SSE 管道。
- 注册用户具备服务端会话列表、新建、URL 选择、归档、恢复和安全删除能力。
- 失败、进程中断、显式重试、旧会话 partial 标记和 Checkpoint 删除均有测试覆盖。
- React 以服务端历史为事实来源，Local Storage 仅保留最近会话提示。
- v0.6 固定 Eval 达到 `32/32`，v0.1 至 v0.6 全部 Eval 通过。

完整发布证据见 [`../eval/v0.6-report.md`](../eval/v0.6-report.md)。下一阶段必须先接受 v0.7
