# Technical Plan：v0.1 订单与物流查询

状态：Completed  
日期：2026-07-15  
完成日期：2026-07-17  
对应 Spec：[`../specs/v0.1-order-inquiry.md`](../specs/v0.1-order-inquiry.md)

## 目标与完成证据

实现一个 CLI 优先、只读、可跨进程恢复的订单与物流查询工作流。

完成必须由以下证据支持：

- 有效订单查询结果与 Fake 业务数据完全一致。
- 缺少订单号的会话能跨进程恢复并继续查询。
- thread 和用户身份隔离测试通过。
- 不存在与越权订单不泄露业务字段。
- 工具故障和不支持的写操作具有明确状态。
- 15 个固定 Eval 场景全部达到 Spec 门槛。

## 设计原则

- v0.1 使用确定性图，不使用动态 Agent Loop。
- 模型只负责把当前输入解释为结构化意图和订单标识。
- 订单归属、订单状态和物流状态只来自业务适配器。
- Graph、模型解释器和业务网关通过依赖注入组合，不使用模块级全局客户端。
- 自动化测试全部使用 Fake，不访问网络或真实业务系统。
- Checkpoint 与演示订单数据使用不同存储边界。

## 组件边界

```text
CLI
  → build_graph(dependencies, checkpointer)
  → LangGraph workflow
       ├─ QueryInterpreter
       ├─ OrderGateway
       └─ LogisticsGateway
  → SQLite Checkpointer

Fake adapters ── 自动化测试与本地演示
OpenAI-compatible Chat interpreter ── DeepSeek 手工冒烟
```

### QueryInterpreter

将最新用户输入转换为结构化结果：

```text
intent: order_inquiry | unsupported_write | unknown
order_id: string | null
```

- Fake 实现返回测试预设结果。
- 真实实现保留 `OpenAIQueryInterpreter` 名称，使用 OpenAI SDK 调用 DeepSeek
  Chat Completions JSON Output，并使用 Pydantic 校验返回内容。
- 如果任务已经处于 `awaiting_order_id`，纯订单号输入继承之前的查询意图。
- 解释器不能访问订单数据库，也不能决定订单归属。

### OrderGateway

只读契约：

```text
get_order_for_user(user_id, order_id)
  → found(order)
  → unavailable
  → temporarily_failed
```

不存在和无权限访问统一返回 `unavailable`，防止资源枚举。

### LogisticsGateway

只读契约：

```text
get_shipment(order_id)
  → found(shipment)
  → not_available
  → temporarily_failed
```

只有订单归属校验成功后才能调用。

## 领域模型

使用 Pydantic 定义最小结构：

```text
OrderView
  order_id
  user_id
  status

ShipmentView
  order_id
  status
  last_event
  estimated_delivery_at | null

Interpretation
  intent
  order_id | null

ToolResult[T]
  outcome
  value | null
  error_code | null
```

不在 v0.1 模型中加入金额、商品详情、支付信息或退款字段。

## LangGraph State

内部 State 计划包含：

```text
messages              # 使用消息 reducer 保存多轮输入与公开回复
owner_user_id         # 首次调用绑定的会话用户
intent                # 当前结构化意图
order_id              # 当前订单标识
status                # 公开任务状态
order                 # 已验证的订单结果
shipment              # 已验证的物流结果
error_code            # 公开错误类型，不保存异常堆栈
audit                 # 追加式的关键步骤标识
```

约束：

- 节点只返回自己负责的 State 增量。
- `messages` 和 `audit` 使用明确 reducer；其他字段默认覆盖。
- 每次调用从 Runtime Context 获得当前 `user_id`。
- 首次调用将用户绑定到 `owner_user_id`；后续调用不匹配时立即拒绝。
- State 不保存业务客户端、SQLite 连接、API Key 或完整异常对象。

## 图结构

```text
START
  → bind_and_interpret
  → route_request
       ├─ user_mismatch
       │    → respond_unavailable → END
       ├─ unsupported_write
       │    → respond_unsupported → END
       ├─ missing_order_id
       │    → request_order_id → END
       └─ order_inquiry
            → query_order
            → route_order_result
                 ├─ unavailable
                 │    → respond_unavailable → END
                 ├─ temporarily_failed
                 │    → respond_failure → END
                 └─ found
                      → query_shipment
                      → route_shipment_result
                           ├─ temporarily_failed
                           │    → respond_failure → END
                           └─ result
                                → respond_success → END
```

关键决定：

- `request_order_id` 正常结束本轮并保存 `awaiting_order_id`，不使用 `interrupt`。
- 下一次调用通过相同 `thread_id` 读取已有 State，并继续原诉求。
- `interrupt` 保留给 v0.4 的退款审批，避免把普通补充信息误建模为高风险审批。
- 所有工具选择由显式条件边完成；v0.1 不让模型生成节点名。

## Checkpoint 与会话恢复

- 默认 SQLite 文件通过配置获得，开发默认位置为 `var/checkpoints.sqlite`。
- `thread_id` 作为 LangGraph thread 标识，不等同于用户身份。
- `owner_user_id` 与每次调用的 Runtime Context 必须一致。
- Graph 构建函数接受外部 checkpointer，测试可以替换为内存或临时 SQLite。
- 跨进程测试必须关闭第一个 Graph/SQLite 连接，再创建全新实例恢复相同 thread。
- Checkpoint 文件由 `.gitignore` 排除。

## CLI 行为

统一使用一个 `ask` 命令创建或继续会话：

```bash
python -m commerce_resolve ask \
  --thread-id demo-thread \
  --user-id user-001 \
  "查询订单 ORD-001 的物流"
```

补充订单号时复用相同标识：

```bash
python -m commerce_resolve ask \
  --thread-id demo-thread \
  --user-id user-001 \
  "ORD-001"
```

- CLI 只打印公开回答、状态和必要的下一步提示。
- 内部异常、Prompt、完整 State 和敏感业务字段不直接输出。
- Fake 模式用于无 API Key 演示；真实模型通过 `--interpreter openai` 显式
  启用。CLI 启动时从 `.env` 加载配置，但已存在的进程环境变量优先。
- v0.1 不增加 `show`、`delete`、Web API 或交互式常驻进程。

## 错误与安全处理

| 情况 | 公开状态 | 行为 |
|---|---|---|
| 缺少订单号 | `awaiting_order_id` | 请求补充，不调用业务工具 |
| 订单不存在或越权 | `order_unavailable` | 使用统一消息，不返回业务字段 |
| 网关暂时失败 | `temporarily_failed` | 返回可重试提示，不输出异常堆栈 |
| 请求退款或修改订单 | `unsupported` | 明确当前只读，工具调用为零 |
| thread 用户不匹配 | `order_unavailable` | 拒绝读取既有 State 的业务结果 |

未知编程错误在测试和开发环境中继续抛出，避免被宽泛 `except Exception` 静默伪装成正常业务结果；CLI 边界只负责将未处理错误转换为脱敏失败消息和非零退出码。

## 测试矩阵

### 工作流测试

- 单轮有效订单查询。
- 缺少订单号后第二轮补充。
- 不存在订单。
- 其他用户订单。
- 订单网关失败。
- 物流网关失败。
- 请求退款、取消和修改地址。
- thread 用户不匹配。

### 持久化测试

- 暂停在 `awaiting_order_id` 后关闭 SQLite 连接。
- 使用新的 Graph 和连接恢复相同 thread。
- 不同 thread 相互隔离。
- 同一 thread 不能被不同用户继续。

### CLI 测试

- 参数解析和退出码。
- 两次独立 CLI 调用完成缺参和补充路径。
- 输出不包含异常堆栈或未授权业务字段。

### Eval

`test_v0_1_eval.py` 使用 Spec 中至少 15 个固定场景，记录：

- 预期状态。
- 预期工具及参数。
- 禁止调用的工具。
- 预期结构化业务字段。
- 是否允许出现订单详情。

Eval 使用确定性断言，不使用 BLEU、ROUGE 或 LLM-as-judge。

### T5：接入真实模型解释器

- 保留 `openai==2.45.0` 可选依赖和 `OpenAIQueryInterpreter` 名称，底层改为
  OpenAI SDK 的 `chat.completions.create`，实际调用 DeepSeek
  `https://api.deepseek.com` OpenAI-compatible 端点。
- Chat 请求使用 `response_format={"type": "json_object"}`；Prompt 明确要求
  JSON 并给出结构示例，返回文本继续通过现有 Pydantic `Interpretation`
  校验，不能把有效 JSON 等同于有效业务 Schema。
- CLI 通过 `--interpreter fake|openai` 显式选择解释器，默认保持 `fake`；
  选择 `openai` 后不得在失败时静默回退 Fake。
- CLI 使用 `python-dotenv==1.2.2` 加载本地 `.env`；解释器只读取通用环境变量
  `LLM_API_KEY`、`LLM_MODEL` 和 `LLM_BASE_URL`，三者均不提供代码内默认值。
  仓库只提交不含密钥的 `.env.example`。
- OpenAI SDK 客户端使用 `LLM_BASE_URL` 指定 Chat 服务地址，并设置 20 秒超时和
  1 次 SDK 重试；Chat 最大输出限制为 128 tokens。
- API 超时、限流、空响应或 Pydantic 校验失败时，转换为统一的解释器暂时不可用
  错误；CLI 只输出脱敏提示和非零退出码，不修改 Graph 或持久化 State。
- 自动化测试注入 Mock Client 验证请求参数、结构化结果和失败映射；
  Fake Interpreter 仍是测试及无密钥演示的默认值。
- 真实模型只通过手工冒烟验证，真实订单与物流数据仍使用 Fake Gateway，
  冒烟不进入 CI。

## 风险与控制

| 风险 | 控制 |
|---|---|
| 模型未稳定提取订单号 | Pydantic 校验、Fake Eval、明确补充路径 |
| thread ID 被其他用户复用 | State 绑定用户并在每次调用验证 |
| 不存在和越权错误泄露信息 | 网关统一 `unavailable` 结果 |
| Checkpoint Schema 演进导致旧会话不可读 | v0.1 稳定字段最小化，变更前记录迁移 |
| SQLite 被误认为生产方案 | README 和 ADR 明确单机边界 |
| 为展示 Agent 过早引入循环 | v0.1 使用显式条件图，Agent Loop 留到 v0.5 |
