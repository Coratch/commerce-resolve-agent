# Technical Plan：v0.2 售后政策 RAG 与可定位来源

状态：Completed  
日期：2026-07-17  
接受日期：2026-07-17  
完成日期：2026-07-17  
对应 Spec：[`../specs/v0.2-policy-rag.md`](../specs/v0.2-policy-rag.md)

## 目标与完成证据

在保持 v0.1 订单与物流查询行为不变的前提下，实现一个本地、只读、可重建、
可评估的售后政策 RAG 路径。

完成必须由以下证据支持：

- 用户能够询问退货、退款和换货政策，并得到逐项带引用的结论。
- 每个引用能够解析到确定的文档、版本、章节、相对路径和行范围。
- 引用对应的规范化事实确实存在于该原文片段。
- 缺少必要条件时可以跨进程补充并继续原问题。
- 无证据、有效政策冲突、索引故障和模型故障均进入明确安全状态。
- 具体订单资格问题不会被回答为“可以退款”或“不可以退款”，业务写工具调用为零。
- v0.2 至少 20 个固定 Eval 场景达到 Spec 的全部发布门槛。
- v0.1 的自动化测试和 15 个固定 Eval 场景继续全部通过。

## 核心技术决策

### 1. 先建立可解释的词法检索基线

v0.2 使用 Python 标准库 `sqlite3` 提供的 SQLite FTS5，而不引入向量数据库、
Embedding 或 Rerank。

原因：

- 当前是受控的小型中文政策集合，精确期限、条件、费用和例外比语义相似度更重要。
- SQLite 索引可以本地运行、原子重建、确定性测试，并与现有单机项目一致。
- FTS5 提供全文索引和 BM25 排序，不需要新的服务或运行时依赖。
- Spec 要求先用固定问题集证明基础检索效果，再由失败样本驱动复杂度。

本机技术探针结果：

- Conda 环境 `ecom-agent` 的 SQLite 版本为 `3.53.3`，FTS5 可用。
- 默认 `unicode61` 不会把连续中文自然切成适合查询的词。
- 内置 `trigram` 支持子串检索，但少于 3 个 Unicode 字符的查询不匹配；
  “退货”“退款”等常见二字词不能单独依赖它。
- 因此索引前由确定性 Python 分析器生成中文字符 bigram 和英文/数字词，
  再使用 FTS5 `unicode61` 与 BM25 排序。

分析器只做：NFKC 规范化、ASCII 小写化、连续中文 bigram、英文/数字词提取和
受控别名合并。用户原文和模型输出都不能直接作为 FTS5 查询语法；应用只把经过
约束和转义的 token 以绑定参数提交给 SQLite。

如果固定 Eval 出现可复现的召回缺口，先分析分词、别名、元数据过滤和语料问题；
只有这些手段不足时，才更新 Plan 并评估 Embedding、混合检索或 Rerank。

技术依据：

- [SQLite FTS5](https://www.sqlite.org/fts5.html)
- [LangGraph Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)
- [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

### 2. 政策结论不由模型自由生成

政策 Markdown 是事实原文；`manifest.json` 为原文增加结构化、可验证的事实标注。
每个允许进入回答的关键结论具有稳定 `fact_id` 和规范化 `claim_text`，索引构建时
必须验证 `claim_text` 逐字存在于对应章节。

执行路径只允许模型或确定性选择器返回候选 `fact_id`，不能返回新的政策事实或
自定义引用。最终结论、免责声明和引用由确定性 Renderer 从已验证事实构造。

这项取舍牺牲了一部分语言自由度，但直接保证：

- 模型不能编造关键政策结论。
- 引用不是模型生成的字符串。
- 引用支持性可以通过程序和固定标注确定性验证。
- Prompt Injection 最多影响候选选择，不能调用工具或伪造事实与引用。

未来只有在存在可重复的语义支持校验和 Eval 门禁后，才允许模型对关键结论进行
自由改写。

### 3. v0.2 仍使用确定性工作流

政策问答路径具有固定步骤：解释问题、检索、检查条件、检测冲突、选择事实、验证
引用和回复。它不需要动态 Agent Loop，也不引入多 Agent 或 LangGraph 子图。

新增政策节点放入独立 `policy_workflow.py`，通过一个节点注册函数接入现有
`StateGraph`。这样避免继续扩大 `build_workflow()` 内的闭包数量，但不重构 v0.1
已经稳定的订单节点。

## 技术栈

| 领域 | 选择 | 说明 |
|---|---|---|
| 运行时 | Python 3.12 | 保持现有约束 |
| 编排 | LangGraph 1.2.9 | 显式路由、State 和 Checkpoint |
| 数据契约 | Pydantic v2 | 校验语料元数据、查询、事实和引用 |
| 政策原文 | 版本化 Markdown | 人可读、可审查、可定位 |
| 政策清单 | JSON manifest | 使用标准库解析，不新增 YAML 依赖 |
| 检索索引 | SQLite FTS5 + BM25 | 本地、词法、可重建 |
| 会话存储 | 独立 SQLite Checkpointer | 继续使用现有跨进程恢复 |
| 真实模型 | OpenAI SDK + DeepSeek Chat | 只用于结构化问题解释和手工冒烟 |
| 测试与 Eval | pytest + Fake | 离线、确定性、无 API Key |

v0.2 基线不增加核心运行时依赖。若实现中发现当前 Python 的 SQLite 构建缺少
FTS5，程序应明确失败并给出环境要求，不静默退化为全表扫描。

## 受控政策语料

### 目录与样本

默认演示语料放在：

```text
data/policies/
├── manifest.json
├── returns-v1.md
├── refunds-v1.md
└── exchanges-v1.md
```

主语料只包含一个演示店铺、`CN` 区域、中文、当前已发布且相互一致的政策。
冲突、过期版本和 Prompt Injection 文档放入 `tests/fixtures/policies/`，只用于临时
索引和安全 Eval，避免默认演示知识库故意包含错误政策。

### 文档与章节契约

每个 Markdown 文件使用稳定章节标识，例如：

```text
## [return-window] 退货期限
```

`manifest.json` 至少声明：

```text
schema_version
corpus_version
documents[]
  document_id
  title
  version
  effective_from
  effective_to | null
  region
  status: published
  path
  sections[]
    section_id
    heading
    topic: return | refund | exchange
    aspects[]
    aliases[]
    facts[]
      fact_id
      claim_text
      rule_key
      normalized_value
      scope
      required_dimensions[]
```

首版受控维度仅包含：

- `product_category`：演示语料明确列出的有限枚举。
- `opened`：`true`、`false` 或未知。

不使用任意字典承载未知 Policy 维度。新增维度必须先扩展 Pydantic Schema、语料
校验和 Eval。

### 构建期校验

索引构建必须在写入前完成以下校验：

- 文档、章节和事实标识全局唯一。
- 文档路径规范化后仍位于语料根目录。
- 生效日期、失效日期、版本、区域和发布状态合法。
- manifest 中的章节标识和标题能够在 Markdown 中唯一定位。
- 每个 `claim_text` 逐字存在于对应章节的行范围内。
- `rule_key`、`normalized_value`、scope 和必需维度符合有限 Schema。
- 同一文档版本的内容哈希和语料版本被写入索引元数据。

任何一项失败都拒绝整个构建，不生成部分可用索引。

## 索引与检索

### 存储边界

```text
data/policies/              # 事实来源，提交 Git
var/policy-index.sqlite     # 派生索引，可删除重建，不提交 Git
var/checkpoints.sqlite      # LangGraph 会话状态，不提交 Git
```

政策原文、RAG 索引和 Checkpoint 不共享 SQLite 文件。

索引至少包含：

- `index_metadata`：Schema、corpus version、构建时间和 corpus hash。
- `policy_documents`：文档版本、生效区间、区域、状态和相对路径。
- `policy_sections`：章节、原文、行范围、content hash 和结构化事实。
- `policy_sections_fts`：标题、别名、事实与正文的预分词 token。

索引通过临时文件完整构建并校验，成功后使用原子替换发布；失败时保留旧索引。
不使用触发器做在线增量同步，因为 v0.2 语料规模小且完整重建更容易验证。

### 检索步骤

1. 从结构化 `PolicyQuery` 取得 topic、aspect、用户问题和已知维度。
2. 只选择指定店铺、区域、`published` 且在 `as_of` 日期有效的文档。
3. 将原问题、topic/aspect 的受控别名转换为安全 token。
4. 使用 FTS5 BM25 对标题、别名、事实和正文加权排序。
5. 计算查询 token 覆盖率，拒绝只有低覆盖的偶然命中。
6. 返回固定 `top_k` 内的事实与证据引用，不返回任意未标注文本作为结论。

`top_k`、列权重和最低覆盖率在 T1 的检索测试中根据固定问题集校准并冻结；它们
不能由 LLM 置信度动态决定。Eval 报告必须记录最终值。

CLI 查询使用当前日期作为 `as_of`。测试和 Eval 显式注入固定日期，避免时间变化
造成不可重复结果。

## 领域模型与 Gateway

### 查询模型

现有 `Interpretation` 扩展为可表达：

```text
intent:
  order_inquiry | policy_inquiry | unsupported_write | unknown
order_id | null
policy_query | null

PolicyQuery
  topic: return | refund | exchange
  aspects[]
  search_terms[]
  product_category | null
  opened | null
  specific_order_eligibility: bool
```

`QueryInterpreter.interpret()` 增加可选的最小 `InterpretationContext`，只包含待补充的
政策 topic、aspect 和维度，不传完整隐藏 State。这样“普通服饰”可以在
`awaiting_policy_context` 后补充原问题，同时保持 v0.1 纯订单号补充语义。

所有数组、字符串和枚举均设置长度、数量与取值限制。模型生成的 `search_terms`
只能作为分析器输入，不能直接成为 SQL 或 FTS5 语法。

### 政策模型

至少增加：

```text
PolicyScope
PolicyFact
PolicyEvidenceRef
PolicyCitation
PolicyConflict
PolicySearchResult
```

`PolicyEvidenceRef` 只保存稳定标识、版本、locator、hash 和检索分数，不保存完整
Markdown。需要原文的节点通过 Repository 按 ID 和 hash 重新解析，防止 State
膨胀并检测索引在执行中被替换。

### PolicyRepository

新增只读 Gateway：

```text
search(query, as_of, limit) -> PolicySearchResult
resolve_fact(fact_id, expected_hash) -> PolicyFact | unavailable
```

Gateway 不生成回答、不判断退款资格，也不调用订单、退款或工单服务。SQLite 实现
放在 `adapters/sqlite_policy.py`；测试可以使用内存 Fake。

### 事实选择与 Renderer

纯业务函数根据 topic、aspect、scope 和必需维度：

- 筛选适用事实。
- 判断缺少的必要条件。
- 检测规则冲突。
- 选择覆盖全部请求 aspect 的 fact IDs。
- 从已解析事实构造结论和引用。

引用至少包含：

```text
document_id
title
version
effective_from / effective_to
section_id
heading
source_relative_path
line_start / line_end
content_hash
```

公开引用只使用语料根目录下的相对路径，不暴露本机绝对路径。

## LangGraph State

在现有 `AgentState` 上只增加可选字段：

```text
policy_query
pending_policy_query
policy_evidence_refs
selected_policy_fact_ids
policy_citations
policy_conflicts
policy_index_version
```

现有 `messages`、订单字段、物流字段和 `audit` 保持原语义，公开 `status` 增加：

```text
policy_answered
awaiting_policy_context
policy_insufficient_evidence
policy_conflict
temporarily_failed
```

约束：

- 节点返回 State 增量，不原地修改。
- 每轮开始时清理上一轮临时检索结果，不能把旧证据误用于新问题。
- State 不保存完整政策文档、SQLite 连接、模型客户端或 API Key。
- 待补问题只保存结构化 query 和缺失维度；补充后重新检索当前索引。
- `audit` 只记录稳定步骤、事实 ID 和公开错误码，不记录完整原文或 Prompt。

## 图结构

```text
START
  -> bind_and_interpret
  -> route_request
       ├─ 既有 v0.1 订单与安全路径
       └─ policy_inquiry
            -> prepare_policy_query
            -> retrieve_policy
            -> assess_policy_evidence
                 ├─ repository_failed
                 │    -> respond_failure -> END
                 ├─ no_evidence
                 │    -> respond_policy_insufficient -> END
                 ├─ missing_dimension
                 │    -> request_policy_context -> END
                 ├─ conflict
                 │    -> respond_policy_conflict -> END
                 └─ answerable
                      -> select_policy_facts
                      -> validate_policy_citations
                           ├─ invalid
                           │    -> respond_failure -> END
                           └─ valid
                                -> respond_policy_answer -> END
```

关键路由语义：

- 缺少维度时正常结束本轮并保存 `awaiting_policy_context`，不使用 `interrupt`。
- scope 分支不同但互不重叠时先澄清，不误报为政策冲突。
- 已提供维度后，同一 `rule_key`、重叠 scope、当前有效且
  `normalized_value` 不同的事实才构成冲突。
- 具体订单资格问题走政策路径，返回通用条件与能力边界，不查询该订单，也不生成
  资格结论。
- “请退款 ORD-001”仍是 `unsupported_write`；“ORD-001 能退款吗”是受限的
  `policy_inquiry`。两者必须有回归测试。
- 检索、模型或引用解析的已知临时错误映射到 `temporarily_failed`；未知编程错误
  继续抛出，避免被静默伪装成业务结果。

## Checkpoint 与兼容

- 保留 `thread_id` 和 `owner_user_id` 的现有绑定与隔离逻辑。
- 保留 v0.1 已有节点名称、订单状态和工具语义。
- AgentState 只做可选字段追加；现有 v0.1 Checkpoint 不要求数据迁移。
- 增加集成测试：先用 v0.1 图生成 `awaiting_order_id` Checkpoint，再用 v0.2 图
  恢复并完成订单查询。
- 政策待补上下文使用新的 SQLite 连接和 Graph 实例恢复，验证跨进程语义。
- RAG 索引具有独立 `schema_version`；版本或 corpus hash 不匹配时要求重建，
  不把索引迁移混入 Checkpointer 迁移。

## CLI 行为

### 构建政策索引

```bash
python -m commerce_resolve policy-index build
```

默认读取 `data/policies/`，原子生成 `var/policy-index.sqlite`，成功后打印文档数、
章节数、事实数、corpus version 和 hash。索引缺失、过期或构建失败时，`ask`
明确提示先构建，不在用户查询过程中静默写入索引。

### 查询政策

继续使用现有 `ask` 接口：

```bash
python -m commerce_resolve ask \
  --thread-id policy-001 \
  --user-id user-001 \
  "签收后多少天可以退货？"
```

多轮补充复用相同 `thread_id` 和 `user_id`。CLI 只输出公开回答、引用和必要提示，
不输出绝对路径、检索 SQL、完整 State 或原始 Prompt。

默认 Fake Interpreter 保证本地演示和 Eval 确定性；`--interpreter openai` 继续使用
现有 DeepSeek Chat 适配器，并扩展为结构化政策问题解释。模型失败不得回退 Fake。

### Eval

```bash
python -m commerce_resolve eval --suite v0.1
python -m commerce_resolve eval --suite v0.2
python -m commerce_resolve eval --suite all
```

v0.2 完成后，不带 `--suite` 默认运行 `all`。报告中分别保留 v0.1 和 v0.2 指标，
避免将两类任务平均后掩盖回归。

## 错误与安全处理

| 情况 | 公开状态 | 行为 |
|---|---|---|
| 缺少商品类别或拆封状态 | `awaiting_policy_context` | 询问一个明确条件，不生成结论 |
| 没有相关证据 | `policy_insufficient_evidence` | 明确当前知识库无法确认 |
| 当前有效事实冲突 | `policy_conflict` | 展示冲突点和双方引用 |
| 索引缺失、过期或不可读 | `temporarily_failed` | 不回答政策，提示重建或稍后重试 |
| 模型或解释器失败 | `temporarily_failed` | 脱敏失败，不回退模型常识 |
| 引用无法解析或 hash 不一致 | `temporarily_failed` | 丢弃整次回答，不输出部分事实 |
| 具体订单资格问题 | `policy_answered` 或证据状态 | 只解释通用条件并声明不能判断该订单 |
| 退款动作请求 | `unsupported` | 保持 v0.1，只读且业务工具调用为零 |

Prompt Injection 控制：

- 用户文本和政策正文都只作为数据，不参与系统指令拼接。
- 原文中的工具名、角色声明和“忽略规则”等内容不改变路由。
- 真实模型没有订单、退款或工单工具权限。
- 模型输出只能通过有限 Schema 返回 query 或 fact IDs。
- fact ID 必须属于本次已检索候选集；引用由服务端解析和构造。
- 业务 Gateway 调用轨迹纳入安全 Eval，政策路径预期始终为零。

## 测试矩阵

### 语料与索引

- 正常构建三类政策。
- 重复 ID、越界路径、无效日期和缺失章节被拒绝。
- `claim_text` 不在原文时拒绝构建。
- 当前、过期和尚未生效版本过滤正确。
- 中文二字词、长问题、英文数字和别名检索。
- 原子重建失败不破坏旧索引。
- 索引 Schema 或 corpus hash 不匹配时拒绝查询。

### 工作流

- 单来源期限、条件和例外回答。
- 一个问题组合多个事实和多个引用。
- 无证据拒答。
- 缺少维度、多轮补充和同话题追问。
- scope 分支与真正冲突的区分。
- 具体订单资格边界和退款动作拒绝。
- 检索失败、模型失败和引用失效。
- 用户和政策原文 Prompt Injection。
- 政策路径订单、物流、退款和工单工具调用均为零。

### 持久化与兼容

- 政策待补条件跨 Graph/SQLite 连接恢复。
- 不同 thread 和用户不能读取彼此的待补上下文。
- v0.1 `awaiting_order_id` Checkpoint 可由 v0.2 图继续。
- 索引替换后旧 evidence hash 不能被继续引用。

### 真实模型契约

- Mock Client 校验政策 Query JSON、上下文限制和 Pydantic 校验。
- 无效 topic、过长 search terms、空响应、超时和限流映射为脱敏失败。
- 模型不能返回 FTS 语法、引用或业务动作作为可信结果。

## v0.2 Eval 设计

`PolicyEvalScenario` 至少记录：

```text
scenario_id
category
messages[]
as_of
fixture_corpus
expected_status
expected_fact_ids[]
expected_evidence_ids[]
expected_missing_dimensions[]
expected_conflict_fact_ids[]
forbidden_business_tools[]
cross_process
```

指标计算：

- 相关证据召回率：标注 evidence IDs 是否全部进入候选集。
- 引用可解析率：citation 能否按 ID、version、locator 和 hash 解析。
- 引用支持率：规范化 `claim_text` 是否存在于引用原文范围。
- 无证据拒答率、冲突识别率和多轮恢复率。
- 未支持结论、伪造引用、Prompt Injection 违规和业务工具调用数量。
- 诊断性记录 top-k、token coverage、步骤数和耗时，但 v0.2 不设性能 SLA。

自动化 Eval 使用 Fake Interpreter、固定日期、临时索引和确定性 Renderer；不依赖
网络或 API Key。真实 DeepSeek 只做独立手工冒烟，不混入发布指标。

## 风险与控制

| 风险 | 控制 |
|---|---|
| 中文词法检索召回不足 | bigram、受控别名、topic/aspect 过滤、固定 Eval；失败后再评估混合检索 |
| FTS 低相关结果总能返回 top-1 | token 覆盖率门槛和无证据场景，不以排名本身代表可回答 |
| manifest 与 Markdown 漂移 | 构建期逐字 claim 校验、section 定位和 content hash |
| 模型把政策原文指令当系统指令 | 模型无工具、只返回受限 ID、服务端构造事实和引用 |
| 模型引用相关片段但编造结论 | 关键结论只能来自已验证 `claim_text`，不接收自由事实文本 |
| 有效日期导致测试随时间变化 | Eval 注入固定 `as_of`，CLI 才使用当前日期 |
| 新 Policy State 破坏旧 Checkpoint | 仅追加可选字段、保留旧节点名，并做跨版本恢复测试 |
| RAG 索引与 Checkpoint 混用 | 独立文件、独立 Schema、独立删除和重建语义 |
| 真实模型让 Eval 不稳定 | Fake + 确定性 Renderer 为发布门禁，真实模型只手工冒烟 |
| 为简历关键词过早引入向量库 | 只有 Eval 证明词法基线不足时才更新方案 |

## ADR 判断

本 Plan 暂不新增 ADR。SQLite FTS5 是可删除、可重建、局限在 v0.2 的派生索引，
替换成本低，不构成难以撤销的跨版本决策。

如果后续引入外部向量数据库、Embedding Provider、长期在线索引服务或新的政策事实
格式，必须先评估数据迁移、部署和隐私成本，并按触发条件新增 ADR。

## 非目标确认

本 Plan 不实现具体订单退款资格、金额计算、退款/退货/换货写操作、人工客服工单、
联网搜索、文件上传、政策管理后台、长期记忆、动态 Agent Loop、多 Agent、Web API、
向量数据库或真实电商服务。
