# Technical Plan：v1.3.1 商业产品可信度重构

状态：Superseded by v1.3.2 · Engineering Passed  
日期：2026-07-24  
对应 Spec：
[`../specs/v1.3.1-commercial-product-credibility.md`](../specs/v1.3.1-commercial-product-credibility.md)

## 1. Plan 目标

在不增加售后业务类型、Agent 权限和知识基础设施的前提下，把 v1.3 已经可用的客户售后中心与
Agent 运营控制台重构成信息完整、任务优先、状态可信、适合开源演示和面试讲解的产品界面。

本 Plan 解决四个实现问题：

1. 用统一设计 Token、页面框架和业务组件替换展示型 Hero、稀疏卡片和不一致术语。
2. 用既有版本化目录和幂等初始化命令提供内容完整的固定验收工作区。
3. 让订单、服务、助手和运营数据保持同一业务事实、明确下一步和正常降级语义。
4. 用确定性前端测试、离线 Eval、三视口截图和锚定量表共同证明产品可信度。

## 2. 完成证据

- 客户售后首页、订单列表、订单详情、服务列表、服务详情、完整对话、运营概览和演示数据页
  在 `1440×1000`、`1024×900`、`390×844` 三个视口可用。
- `python -m commerce_resolve demo-catalog seed` 可以为一个既有账号幂等准备全部 10 个订单场景。
- 客户界面不出现 `Fake`、`Provider`、内部节点名、原始错误码或反复出现的 `Mock` 研发术语。
- 退款演示边界在确认动作和交易说明处可发现，但不替代正常业务语言。
- 前端组件测试、构建、Playwright 核心旅程、后端全量测试、v1.3.1 固定 Eval 和既有统一 Eval
  全部通过。
- `docs/eval/v1.3.1-report.md` 记录产品量表、截图清单、命令、结果和未通过门禁。

## 3. 当前基线与缺口

可复用基线：

- React 19、TypeScript、React Router、TanStack Query 和 CSS Modules 已稳定工作。
- FastAPI 公开读模型已经提供订单、商品快照、包裹、服务、公开会话和运营只读数据。
- v1.3 目录已经包含 12 个商品、19 个 SKU、10 个订单场景和本地原创图片。
- CLI 已能为显式注册账号幂等初始化全部目录场景。
- SSE、刷新恢复、退款审批、L2 Case、Memory 和权限边界已有回归测试。

需要修复的缺口：

- 售后首页以大面积展示型欢迎区开场，待办、服务和订单不是首屏主角。
- 页面标题、卡片留白和默认数据密度不符合成熟电商任务页面。
- 客户页面仍出现 `Mock`、`Agent` 等内部视角文案。
- 运营控制台同时使用中英文模块名，概览只显示计数，缺少清晰关注项与数据来源说明。
- 已有截图测试证明页面存在和无阻塞溢出，但没有固定产品评审量表。

## 4. 实现边界与关键决策

### 4.1 延续现有前端栈，不引入组件库

继续使用 React、TypeScript、CSS Modules 和原生 CSS。现有问题是信息层级、内容和状态语言，
不是缺少组件库。图标只使用文字、CSS 形状或必要的内联装饰，不增加远程字体、热链资源或
新的运行时依赖。

### 4.2 统一设计 Token，但保持角色差异

`frontend/src/styles/global.css` 维护颜色、字号、间距、圆角、阴影和状态 Token。

- 客户中心：浅色、商品与订单优先、暖色品牌强调、低噪声状态。
- 运营控制台：高密度导航、表格和运营卡片，共享品牌色与状态语义。
- 相同业务状态使用相同中文标签和色调，不因页面不同改变含义。

### 4.3 复用公开读模型，不为视觉重构增加后端 Schema

页面只组合既有 Support、Order、Service、Conversation、Admin、Eval 与 System API。不增加
数据库迁移、服务写表、趋势指标或虚构图表；缺少权威数据时显示事实范围和正常空状态。

### 4.4 固定工作区复用版本目录和真实业务旅程

既有命令：

```bash
python -m commerce_resolve demo-catalog seed \
  --version v1.3 \
  --username <username> \
  --scenario-set commercial-service
```

会幂等初始化全部 10 个订单场景。退款、进行中服务和 L2 Case 继续通过公开产品旅程创建，不向
数据库直接插入伪造结果。README 提供固定准备顺序，Playwright 用隔离数据重复该路径。

### 4.5 产品文案由角色和业务语义决定

客户侧使用“订单、物流、售后服务、智能助手、退款确认、演示交易”等业务语言；模型或工具失败
作为普通助手消息或服务状态展示；只在全局环境披露和资金确认处说明本地演示边界。

运营侧可以使用 `Agent Run`、`Eval`、Artifact 等工程术语，但必须附中文用途。任何页面都不展示
Prompt、隐藏推理、原始工具结果、密钥或内部异常。

### 4.6 动效只表达状态变化

允许页面进入、卡片悬停、列表更新和会话渐进输出的短动效，并在
`prefers-reduced-motion` 下关闭。拒绝大型营销 Hero、3D 商品舞台、长过场、粒子和滚动劫持，
因为它们挤占订单与服务任务空间，不能提高业务可信度。

## 5. 页面信息架构

### 5.1 客户售后中心

```text
品牌与产品范围
├── 售后首页：待关注服务、任务入口、最近订单
├── 我的订单：搜索、筛选、履约与售后信号
├── 服务进度：当前步骤、下一步和最终结果
├── 智能助手：绑定业务上下文、结构化结果和审批
└── 长期偏好与账号
```

桌面使用单行主导航；移动端使用可横向浏览的任务导航。演示披露只在全局框架显示一次。

### 5.2 Agent 运营控制台

```text
运营总览
├── 业务运营：客户、订单、服务关注项
├── Agent 质量：最近 Run、Eval Candidate/Baseline
└── 系统健康：数据库、索引、版本和只读状态

工作区
├── 演示数据
└── 邀请与账号

质量与诊断
├── 运行监控
├── 质量评估
└── 系统状态
```

控制台只展示现有权威数据，不从 Web 触发 Eval、模型运行或高影响运维。

## 7. 垂直任务

### T1：接受规格并建立可执行产品基线

用户结果：维护者知道本版本为何存在、哪些页面必须改变以及如何判断完成。

实现：

- 接受 Feature Spec。
- 固化本 Technical Plan、八维产品评审量表和 24 个固定截图目标。
- 记录 v1.3 基线问题和被否决方向。

验收：

- Spec、Plan、目标地图和 README 状态一致。
- 产品量表每一维具有 `1/2/3` 分锚点，不使用“感觉更好”等主观描述。

状态：Completed

### T2：客户全局框架与售后首页

用户结果：客户首次进入即可识别账号、演示边界、待办、进行中服务和最近订单。

实现：

- 重构品牌、导航、账号区和移动布局。
- 移除大型营销 Hero，建立紧凑状态摘要和任务入口。
- 统一加载、空、错误和权限状态的正常产品语言。

验收：

- 首屏主要高度由待办、服务和订单占据。
- 客户界面内部研发术语为 `0`。
- 游客、注册客户和管理员入口保持原权限。

状态：Completed

### T3：订单、服务与上下文任务连续性

用户结果：客户可以从订单或服务理解状态、下一步并进入正确上下文助手。

实现：

- 收敛订单/服务列表和详情层级、密度和卡片结构。
- 统一商品、金额、物流、服务状态和更新时间。
- 优化上下文助手入口、空状态和资金演示披露。

验收：

- 同一事实跨首页、列表、详情、服务和会话显示一致。
- 详情首屏可以回答“是什么、到哪里、下一步是什么”。
- 浏览页面不会创建会话或执行模型。

状态：Completed

### T4：对话、审批与长期偏好的产品表达

用户结果：用户把模型降级、审批和记忆管理理解为正常服务过程，而不是系统调试状态。

实现：

- 统一对话 Header、消息、渐进状态、Composer 和结构化方案。
- 将退款卡改为业务确认语言，保留确定性审批链。
- 收敛登录、注册和长期偏好页面的产品层级与说明。

验收：

- Enter/Shift+Enter、SSE、刷新恢复和 Pending Action 保持通过。
- 失败消息不使用红色技术异常。
- 记忆、Checkpoint、业务事实和公开消息生命周期不混用。

状态：Completed

### T5：运营控制台信息架构与可信密度

用户结果：管理员可以区分业务运营、Agent 质量和系统健康，并定位关注对象。

实现：

- 重构侧栏分组、页面标题、计数、列表、表格和只读状态。
- 运营概览增加由现有权威字段支持的关注区，不构造趋势。
- 演示数据页突出目标客户、场景影响、幂等结果和数据边界。
- 统一 Run、Eval、System 的中文用途说明。

验收：

- 所有计数、列表和状态可以追溯到既有 API。
- Monitoring、Eval 和 System 的 Web 写入数为 `0`。
- 客户任务语言与运营工程术语不会混在同一页面。

状态：Completed

### T6：固定商业演示工作区与内容校验

用户结果：评审者可以通过一条明确路径看到具有真实业务密度的订单、服务和对话。

实现：

- 复用版本目录的 10 场景幂等初始化。
- README 记录账号准备、目录初始化和四条核心旅程。
- E2E Fixture 通过公开 API/产品动作建立退款、服务和会话状态。
- 校验商品图片、Alt、订单号、状态、金额和服务关联。

验收：

- 最少 8 笔订单、4 种状态、2 笔多商品订单和 1 笔多包裹/异常订单。
- 至少一条退款审批、一条服务记录和一条可恢复会话通过受控旅程产生。
- 资源破图、远程热链、测试 SKU 和占位正文数量为 `0`。

状态：Completed

### T7：响应式、可访问性与产品评审证据

用户结果：桌面、平板和移动端均能完成核心旅程，维护者能复现视觉验收。

实现：

- 三视口布局、键盘、焦点、Reduced Motion、长文本和图片失败处理。
- 8 个页面 × 3 个视口的固定截图清单与 Playwright 测试。
- 八维产品评审量表和响应式冒烟。

验收：

- 24 个截图目标可重复生成，主要动作无溢出、遮挡或不可达。
- 键盘、焦点、替代文本、颜色非唯一状态和 Reduced Motion 有证据。
- 产品量表 8 个维度全部达到 `3` 分后才允许版本完成。

状态：Completed

## 10. 风险与控制

| 风险 | 控制 |
|---|---|
| 视觉重构掩盖业务错误 | 所有金额、状态和动作继续来自公开读模型 |
| 为填充页面伪造指标 | 只显示 API 已提供的计数、列表和 Artifact |
| 默认数据污染真实账号 | CLI 只接受显式既有用户名，初始化保持幂等 |
| CSS 重构破坏移动端 | 三固定视口 + 其他页面响应式冒烟 |
| 文案隐藏安全边界 | 客户业务语言与演示资金披露分别校验 |
| 截图被误当功能测试 | 截图只做产品证据，行为由组件/E2E/后端测试断言 |
| v1.4 范围泄漏 | 不增加上传、解析、向量、Embedding 或多模态依赖 |

## 11. 迁移与回退

- 不修改数据库 Schema、Checkpoint、公开 API 或消息 Payload。
- 前端样式和文案可按文件回退，不需要业务数据迁移。

- 若新布局无法通过三视口或可访问性门禁，回退该页面，不改变既有业务链路。
