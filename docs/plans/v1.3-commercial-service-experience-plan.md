## 1. Plan 目标

本 Plan 把已接受的 v1.3 产品范围落实为四个可验证的工程结果：

1. 使用版本化、本地受控的商品与场景数据，让订单、物流和服务页面具有稳定且可重复的业务真实感。
2. 在订单行保存下单时商品快照，并以增量履约明细表达单包裹、多包裹和部分履约，不因商品模板变化改写历史订单。
3. 在现有单 Agent 主图中增加物流、政策与退款资格的组合咨询路径，由一轮结构化意图识别驱动确定性事实查询和方案装配。
4. 使用现有公开消息 `payload_json` 与 `payload_version` 持久化结构化服务方案，使刷新、切页、断线和重新登录后仍能恢复相同结果和允许动作。

本版本继续使用 React + TypeScript、FastAPI、Pydantic、SQLAlchemy、SQLite、LangGraph、SSE、
pytest、Vitest 和 Playwright。不会为了视觉升级引入整套 UI 框架、动画框架、向量数据库、第二个
Agent、Supervisor 或新的后端服务。

## 2. 完成证据

v1.3 完成必须同时具备：

- 版本化目录至少包含 12 个 SPU、18 个 SKU、3 类演示客户画像和 10 个订单/服务场景。
- 所有商品主图来自本地受控资源，具有稳定资源标识、替代文本、校验摘要和来源/生成记录。
- 固定 CLI 命令可以校验目录并为显式目标客户幂等初始化 v1.3 场景；页面访问和应用启动不会隐式覆写数据。
- 管理员可以从同一目录选择商品或场景准备 Mock 订单；普通客户和游客相关写请求均被服务端拒绝。
- Alembic `0008` 原地增加可空商品快照与履约明细，v1.2 历史订单、会话、退款、L2 Case、Checkpoint、Memory 和 Audit 保持可读。
- 新订单的商品名称、规格、数量、单价和图片引用来自订单快照；修改目录模板不会改变已创建订单。
- 售后首页、订单列表、订单详情和服务详情使用统一状态词、状态层级、商品表达和下一步动作。
- 用户可以按订单号或商品名称查找订单，并按客户可理解的状态筛选。
- 单包裹、多包裹、部分履约、无物流、图片缺失和历史快照缺失均有明确且不编造事实的展示。
- 绑定订单中的“物流到哪了，是否可以退款”等组合问题只进行一轮结构化解释，随后查询最新订单、物流和政策事实。
- 组合咨询结果公开区分目标、已验证事实、缺失/冲突、政策依据、推荐方案、允许动作、步骤、停止原因和下一步。
- `request_refund` 只表示受控候选动作；资格、金额、渠道、风险、审批、执行和验证继续复用 v0.4 确定性链路。
- 新增公开阶段由持久化 Run/Event 产生，不暴露 Prompt、隐藏推理、密钥、内部节点名称或原始工具输出。
- 公开消息 Payload v1 继续可读；Payload v2 的结构化方案在刷新、切页、SSE 重放和重新登录后恢复一致。
- 1440px、1024px、390px 三个固定视口完成售后首页、订单列表、订单详情、服务详情和上下文助手的截图与交互验收。
- 四条核心旅程通过真实 HTTP 浏览器验收：订单理解、组合咨询、Mock 退款和复杂问题跟踪。
- v1.3 固定 Eval `48/48`，统一离线 Eval 预期 `373/373`，安全违规、未经审批退款和重复副作用均为 `0`。
- 因本版本修改结构化解释 Schema 和 Prompt，必须补充受控 Provider Qualification；没有真实资格证据时版本只能保持 Candidate。
- README、目标地图、OpenAPI、生成 TypeScript、Migration Head、代码职责、资源许可、初始化说明和 Eval 报告一致。

## 3. 当前基线与缺口

现有代码已经具备：

- 一个 React/Vite 构建中的客户售后中心与 Agent 运营控制台。
- FastAPI/Pydantic OpenAPI、生成 TypeScript 类型和 TanStack Query 数据访问。
- SQLite 中的客户、订单、最小商品行、订单级物流、支付、退款、会话、Run/Event 和 L2 Case。
- `/support`、`/orders`、`/orders/:orderId`、`/services`、`/services/:serviceId` 与上下文助手。
- 订单绑定会话、公开消息恢复、可重放 SSE、Mock 退款审批和受控 L2 Agent Harness。
- FTS5 政策检索、当前版本引用、固定 Eval/Baseline 和 v1.2 安全权限矩阵。
- 全局 CSS 变量、CSS Modules、原生 `<dialog>`、键盘发送和 Reduced Motion 处理。

当前缺口：

- `order_items` 只有 SKU、标题、数量和类目，没有规格、价格、图片或目录版本快照。
- `shipments` 只有订单级摘要，无法表达一个订单多个包裹和商品级履约关系。
- Guest Fake 和管理员手工数据没有共享的版本化商品/场景事实来源。
- 售后首页偏营销 Hero，订单列表缺少图片、搜索、状态筛选和清晰的履约/售后优先级。
- 状态映射、商品单元和动作表达分散在页面函数中，难以保证跨页面一致。
- `Interpretation` 只允许单一意图，组合咨询会被迫选中订单、政策或退款中的一条路径。
- `ChatResponse` 公开正文、引用和审批卡片，但没有稳定的结构化服务方案。
- 消息数据库已经有 `payload_version`，前端却只按字段猜测 Payload，未知版本没有显式降级规则。
- v1.2 Eval 不覆盖商品资源、快照不变性、组合咨询、结构化结果和商业化响应式页面。

## 4. 实现边界与关键决策

### 4.1 延续现有设计系统，不引入 UI 框架

- 继续使用 React 19、TypeScript、React Router、TanStack Query、CSS Modules 和全局 CSS 变量。
- 在 `global.css` 中整理颜色、间距、字号、圆角、阴影、层级、状态和动效时长 Token。
- 提取有限的业务组件：商品缩略图、订单卡片、状态标识、金额摘要、履约时间线、服务步骤、动作区和结构化 Agent 方案。
- 动效只使用 CSS transition/animation，持续时间控制在 120–220ms；Reduced Motion 下关闭非必要动效。
- 不引入 Material UI、Ant Design、Tailwind、Anime.js、远程字体或远程图标 CDN。
- 视觉变化必须服务于状态识别、下一步判断或操作反馈，不以 3D、长过场和装饰动画作为验收结果。

该决策是 ADR-0011 客户订单优先方向的增量实现，不改变跨版本架构，因此不新增 ADR。

### 4.2 一个版本化演示目录，不建设运行时商品中心

新增只读目录 Manifest：

```text
data/demo/v1.3/catalog.json
frontend/public/catalog/v1.3/*.webp
frontend/public/catalog/v1.3/fallback.svg
frontend/public/catalog/v1.3/assets.json
```

`catalog.json` 是商品、SKU、画像和场景的唯一模板来源；图片文件只保存二进制资源，
`assets.json` 保存文件名、SHA-256、替代文本、来源或生成记录。目录使用严格 Pydantic Schema 加载，
路径、资源 ID、价格、场景引用和数量在任何写入前完成校验。

目录用于：

- Guest Catalog 选择固定只读场景。
- 管理员 Web 选择商品或场景创建 Mock 数据。
- CLI 重复初始化一个显式目标客户。
- 测试与截图使用同一稳定数据。

目录不提供商品 CRUD、库存、上下架、促销、购物车或订单结算。运行中的订单事实仍保存在业务库，
目录变更不会回写历史订单。

### 4.3 订单快照与履约明细

Alembic `0008` 对 `order_items` 增加可空字段：

```text
product_ref
variant_title
unit_amount_minor
currency
image_ref
catalog_version
```

对 `orders` 增加可空的 `demo_scenario_id` 和 `catalog_version`；使用工作区内部分唯一约束阻止同一
场景重复创建不同事实。历史行保持 `NULL`，读取时明确显示兼容状态，不补造价格、规格或图片。

新增履约明细：

```text
shipment_packages
  package_id
  order_pk
  status
  last_event
  estimated_delivery_at
  created_at / updated_at

shipment_package_items
  package_pk
  order_item_pk
  quantity
```

- `shipments` 继续作为 Agent、退款和旧 API 使用的订单级汇总事实。
- `shipment_packages` 是订单级汇总的明细，不是第二套独立物流系统。
- 管理员或 Seed 写入包裹时，同一事务根据包裹状态确定性更新订单级 `shipments`。
- 汇总规则固定：全部送达为 `delivered`；存在运输中或部分送达为 `in_transit`；否则为 `preparing`。
- 最新事件来自最近更新的包裹；预计送达只在可验证时返回，不由 UI 或模型推测。
- 旧订单没有包裹行时继续使用现有订单级物流，页面标记为“整单物流”。

### 4.4 组合咨询仍是同一个一线 Agent

对 `Interpretation` 做向后兼容的增量扩展：

```text
intent += service_guidance
concerns = order_status | shipment_status | policy | refund_eligibility
goal_summary
```

- 单一订单、政策、退款和 L2 意图继续走现有节点名称与路径。
- 只有同一轮包含两个及以上只读关注点时，才进入 `service_guidance`。
- 明确要求执行退款仍使用 `refund_request`，不能以组合咨询绕过退款预览和审批。
- LLM 只提取目标、关注点、订单号和政策查询；事实、资格、金额、允许动作和停止原因由确定性代码生成。
- 绑定订单经过服务端授权后可以补足省略的订单号；显式冲突在工具和模型后续调用前停止。
- 新路径添加到现有主图，不创建第二个 Agent、Supervisor 或多 Agent 子图。

组合路径固定为：

```text
bind_and_interpret
  -> prepare_service_guidance
  -> load_guidance_order
  -> load_guidance_shipment（按 concerns）
  -> retrieve_guidance_policy（按 concerns）
  -> assess_guidance_evidence
  -> assemble_service_resolution
  -> respond_service_guidance
  -> END
```

政策检索、有效期/区域过滤、冲突检测和引用校验复用 v0.2 的 Repository 与纯规则，不复制第二套
RAG。订单和物流继续通过现有 Gateway 在当前用户/工作区作用域内读取。

### 4.5 结构化服务方案由确定性投影装配

新增 `ServiceResolution` 领域模型：

```text
schema_version = 1
goal
verified_facts[]
missing_information[]
policy_evidence[]
recommendations[]
allowed_actions[]
progress
stop_reason
next_step
```

其中：

- `goal` 来自已校验的结构化解释，限制长度并按纯文本展示。
- `verified_facts` 只能来自当前 Gateway/Repository 结果，包含有限来源类型和更新时间。
- `policy_evidence` 只接受已通过现有引用校验的 `PolicyCitation`。
- `missing_information` 和 `stop_reason` 由确定性必填项及错误分类产生。
- `recommendations` 由有限规则把事实和政策结论转换为客户可理解的建议，不产生授权。
- `allowed_actions` 只允许 `view_order`、`view_policy`、`request_refund`、`upgrade_l2`、
  `provide_information`；每项包含风险、是否需确认和 UI 行为。
- `request_refund` 只提交一个新的受控退款诉求；真正退款继续经过 Policy、R2 审批、幂等执行和回读验证。
- `progress` 只公开已完成阶段、当前结果和下一步，不保存或展示隐藏推理。

现有单一意图响应也可以由相同投影器生成精简方案；旧文本正文继续保留，保证 CLI、旧客户端和无
结构化能力场景正常工作。

### 4.6 复用公开消息 Payload 版本，不新增消息表

现有 `conversation_messages` 已保存：

```text
content
payload_version
payload_json
```

v1.3 定义助手公开 Payload v2：保留 v1 的引用、退款、L2 和记忆字段，并新增可选
`service_resolution`。实现规则：

- 用户消息仍使用 Payload v1。
- 新助手消息由 `complete_run` 显式写入 Payload v2。
- 历史 Payload v1 按原行为恢复。
- 前端按版本解码；未知版本只展示 `content`，不执行任何 Payload 动作。
- `service_resolution` 在写入前经过 Pydantic 白名单投影，不保存 Graph State、Prompt、隐藏推理或原始工具输出。
- SSE 继续只发布有限阶段和消息完成事件；结构化最终结果由消息 API 回读，避免事件与消息形成两个事实来源。

该方案延续 ADR-0007 已接受的公开消息/Event 分离与版本语义，不需要新 ADR。

### 4.7 高风险动作和权限边界不变

- Support GET、目录读取和商品资源访问不创建 Conversation、不调用模型、不写业务数据。
- 管理员目录/场景 API 继续经过 `require_admin_access`、CSRF、Origin、目标客户授权和后台审计。
- 客户只读订单与物流；隐藏按钮、修改 JSON 或直接调用 URL 都不能获得写权限。
- 商品图片、标题、政策片段和用户输入全部视为不可信展示数据，React 不使用未清洗 HTML。
- Mock 退款预览增加商品摘要，但金额仍来自权威支付事实，不使用商品快照重新计算退款。
- L2 Harness、Memory、Checkpoint 和 Eval 生命周期保持独立，不因新 UI 或目录而混合。

## 6. 技术选型

| 领域 | 选择 | 原因 |
|---|---|---|
| 商品/场景目录 | 版本化 JSON + 严格 Pydantic Schema | 可审查、可重复、无需建设商品管理系统 |
| 商品图片 | Vite `public` 下本地 WebP + 本地 SVG fallback | 同源、可离线、无远程热链和外部可用性风险 |
| 资源记录 | `assets.json` + SHA-256 + 来源/生成说明 | 可检查资源一致性和使用边界 |
| 订单历史 | `order_items` 不可变快照字段 | 模板变化不改写历史订单，适合售后解释 |
| 多包裹 | 关系表 `shipment_packages` + `shipment_package_items` | 明确包裹与商品数量关系，避免 JSON 隐藏约束 |
| 数据迁移 | Alembic `0008` 可空增量迁移 | 原地兼容 v1.2 历史数据和现有恢复链 |
| 目录初始化 | Python CLI + 管理员 API 共用领域服务 | 固定命令可复现，Web 不复制业务规则 |
| 订单搜索 | SQLite 受限 `LIKE`/`EXISTS` + 稳定 Keyset Cursor | 当前单机规模足够，不引入搜索服务 |
| Agent 解释 | 现有 Fake/OpenAI-compatible Interpreter 严格 Schema | 复用访问模式和 Provider 边界，只增加组合关注点 |
| 事实查询 | 现有订单/物流 Gateway 与政策 Repository | 不复制业务事实或 RAG 实现 |
| 方案装配 | Pydantic 领域模型 + 确定性规则 | LLM 不授权动作、不编造事实或停止原因 |
| Graph | 现有 LangGraph 主图新增有限节点 | 保留 Checkpoint、恢复和路由语义，不引入第二 Agent |
| 消息持久化 | 现有 `payload_json`，助手 Payload v2 | 刷新可恢复，不增加第二套展示数据库 |
| 进度 | 现有持久化 Run/Event + SSE | 断线可重放，浏览器不伪造执行状态 |
| 前端 | React/TS/Router/Query/CSS Modules | 现有栈已满足组件化、缓存、类型和响应式需求 |
| API 类型 | FastAPI OpenAPI → `openapi-typescript` | 服务端 Schema 是公开契约唯一来源 |
| 测试 | pytest、Vitest、Playwright、临时 SQLite | 离线验证领域、迁移、UI、权限和恢复 |
| Eval | v1.3 Suite + 统一 Catalog/Baseline + Provider Qualification | 同时衡量确定性行为、Agent 结构化输出和真实模型适配 |

不选择向量数据库：本版本政策 RAG 已由 FTS5 和确定性规则满足，商品目录只用于固定演示数据；没有
Eval 证据表明向量检索能改善当前任务。

## 7. 数据与公开契约

### 7.1 目录 Manifest

目录顶层字段：

```text
schema_version
catalog_version
products[]
personas[]
scenarios[]
```

每个 Product 至少包含：

```text
product_ref
title
category
image_ref
image_alt
variants[]
  sku
  variant_title
  unit_amount_minor
  currency = CNY
```

每个 Scenario 至少包含：

```text
scenario_id
persona_id
order_id
order_status
items[]
shipment_summary | null
packages[]
payment | null
expected_service_state
```

校验要求：ID 唯一、SKU 引用存在、数量合法、包裹数量不超过订单行数量、图片引用在资源清单中、
金额使用整数分、目录版本固定、路径不能逃逸允许目录。

### 7.2 业务领域模型

`OrderItemInput` / `OrderItemRecord` 增量增加可选快照字段；旧调用方不传时保持当前行为。

新增：

```text
ShipmentPackageInput / ShipmentPackageRecord
ShipmentPackageItemInput / ShipmentPackageItemRecord
```

## 8. LangGraph 执行设计

### 8.1 路由优先级

同一轮只允许一个主路径，优先级固定：

```text
明确 L2 升级命令
  > 明确退款执行请求
  > 两个及以上只读关注点的 service_guidance
  > 单一政策查询
  > 单一订单/物流查询
  > 不支持或未知
```

优先级由校验后的 `Interpretation` 和服务端能力决定；模型不能输出节点名称。

### 8.2 组合咨询路径

1. `bind_and_interpret` 绑定身份、工作区和可信订单上下文。
2. `prepare_service_guidance` 校验 concerns、订单号、政策查询和缺失字段。
3. `load_guidance_order` 通过现有 Gateway 查询本人最新订单。
4. `load_guidance_shipment` 仅在包含物流关注点时查询汇总和包裹明细。
5. `retrieve_guidance_policy` 仅在包含政策/退款资格时执行现有 FTS5 检索。
6. `assess_guidance_evidence` 复用有效期、区域、冲突、缺失和引用规则。
7. `assemble_service_resolution` 从已验证事实和服务端允许动作构造领域模型。
8. `respond_service_guidance` 生成兼容文本正文并把方案留在 State 供公开投影。

任何必要事实不可用时均可生成部分方案，但必须列入 `missing_information` 并使用有限停止原因：

```text
completed
needs_user_input
insufficient_evidence
conflicting_evidence
order_unavailable
tool_failed
model_unavailable
```

### 8.3 Mock 退款路径

- “能否退款”属于只读资格咨询，不创建 RefundAction。
- “我要退款”继续进入 `prepare_refund_request`，补齐原因后生成 v0.4 预览。
- 预览卡片增加订单商品摘要和取消路径；金额仍来自支付事实。
- 批准前重新查询订单、物流、政策、支付和既有动作；旧方案或图片变化不能授权执行。
- 结构化方案中的 `request_refund` 按钮最多发起一个新的幂等 Chat Run，不能直接调用 Executor。

### 8.4 L2 路径

- `upgrade_l2` 只进入现有升级预览，不自动创建 Case 或调用 L2 模型。
- 已存在 L2 Case 的服务详情继续加载原 thread，不新建对话。
- ServiceResolution 可以引用 L2 的公开下一步，但不复制 Trace、Context Manifest 或隐藏指标。

### 8.5 Checkpoint 兼容

- 不重命名现有节点或移除现有 State 字段。
- 新字段全部可缺省；旧 Checkpoint 读取时按单一意图和无结构化方案处理。
- 新 `service_guidance` 节点名称视为持久化接口，进入实现后不在同一版本中随意改名。
- 任何中断前节点保持只读；目录、订单、政策查询和方案装配均无业务副作用。

## 9. API 与 CLI

### 9.1 客户 API

扩展：

```text
GET /api/support/overview
GET /api/support/orders?q=&view=&limit=&cursor=
GET /api/support/orders/{order_id}
GET /api/support/services
GET /api/support/services/{service_id}
```

- `q` 最长 80 字，只匹配当前用户工作区的订单号、商品标题和 SKU。
- `view` 使用有限客户状态：`all | processing | shipping | delivered | after_sales`。
- 搜索与筛选在 SQLite 查询内完成，不能先分页再在前端过滤。
- Cursor 继续使用更新时间与资源 ID，Query Key 绑定 `q/view`，避免不同筛选复用旧页。
- 所有新增字段为增量字段，旧 URL 和未带参数的请求保持 v1.2 语义。

### 9.2 管理员目录与场景 API

新增：

```text
GET  /api/admin/demo-catalog
POST /api/admin/customers/{user_id}/demo-scenarios
```

POST 请求包含 `scenario_id` 和 `client_request_id`：

- 服务端重新加载并校验目录，不接受客户端提供价格、图片路径、用户 ID 或退款结果。
- 同目标工作区、同场景、同指纹重复提交返回既有结果。
- 同场景但既有事实不同返回稳定冲突，不静默覆盖。
- 成功或失败均记录脱敏 Admin Audit；审计不保存图片、商品正文或客户消息。

现有手工订单维护继续可用，新增快照字段均可选；v1.3 不要求管理员手工编辑商品目录。

### 9.3 会话 API

- 现有消息提交、Run 查询、SSE、退款/L2/Memory 决定 API 路径不变。
- OpenAPI 只增量公开 `service_resolution` 和商品/履约字段。
- 服务端完成 Run 后将结构化方案写入助手消息 Payload v2；消息列表是刷新恢复的唯一公开最终结果来源。
- SSE 只增加有限阶段文案，不把完整方案重复塞入 Event。

### 9.4 CLI

新增固定命令：

```bash
python -m commerce_resolve demo-catalog validate --version v1.3
python -m commerce_resolve demo-catalog seed \
  --version v1.3 \
  --username <registered-customer> \
  --scenario-set commercial-service
```

- `validate` 零数据库写入，只检查 Schema、引用、资源、摘要和场景不变量。
- `seed` 只允许本机调用并要求目标为既有注册客户；不创建账号、不输出密码或邀请码。
- 重复执行同一版本/场景返回幂等结果；冲突时停止并列出稳定业务标识。
- 不提供清空全部业务库或覆盖任意客户数据的快捷参数。

## 15. 风险与控制

| 风险 | 控制 |
|---|---|
| 商业化目标退化为纯视觉改版 | 每个页面必须减少一次信息查找或明确一个下一步，并由四条旅程验收 |
| 目录成为第二个运行时商品库 | 目录只用于模板/Seed；订单创建后只读数据库快照 |
| 修改模板改写历史订单 | 快照字段写入订单行，Support Reader 不回查模板补值 |
| 多包裹与订单级物流冲突 | 同事务确定性汇总、数据不变量测试、Agent 使用汇总事实 |
| 图片来源或远程依赖不清 | 本地资源、SHA-256、来源/生成记录、禁止热链 |
| Seed 覆盖管理员已有数据 | 稳定场景 ID、指纹幂等、冲突停止、无全量覆盖参数 |
| 搜索导致跨客户泄露 | 所有 SQL 先绑定工作区/用户，再匹配订单和商品 |
| 组合咨询演变为开放式 Agent Loop | 固定 concerns、固定节点、单次查询预算、无任意工具选择 |
| 模型把建议当成授权 | ServiceResolution 由确定性装配，允许动作是服务端枚举 |
| “能否退款”误触发资金动作 | 资格咨询与 `refund_request` 分离，只有后者进入既有审批链 |
| Payload v2 破坏历史消息 | 版本化解码、v1 回归、未知版本正文降级 |
| SSE 与消息出现两个最终结果 | SSE 只传阶段；消息 Payload 是最终公开结果来源 |
| UI 组件抽取造成业务逻辑复制 | Presenter 只做展示映射，事实/Policy/权限继续在后端 |
| 截图测试跨平台不稳定 | 固定数据/视口/Reduced Motion；截图作证据，结构与交互断言作门禁 |
| Provider Schema 变化未经验证 | 新资格数据连续两次运行；无证据保持 Candidate |
| v1.0 Docker Gate 被误报完成 | v1.3 报告继续明确延后，不陈述参考容器已验收 |

## 16. 迁移与回退

- Alembic `0008` 只新增可空列和新表，不重写历史订单、商品行、物流或交易事实。
- 迁移前通过现有运维入口创建完整性通过的 Backup Set；失败时实例保持非 Ready。
- v1.2 历史商品行映射为 `snapshot_state=legacy`，不会从目录推断缺失字段。
- 新目录只在显式 Validate/Seed 时读取，启动失败不会因未 Seed 数据而阻塞已有用户。
- Payload v2 写入后，回退到不认识 v2 的前端仍能读取消息 `content`；正式回退使用升级前前端和业务库 Backup。
- 新 Checkpoint 字段均可缺省；若回退版本不接受新节点 Checkpoint，则使用既有会话公开历史，相关进行中 Run 标记需按运维 Reconciliation 处理，不能静默重跑。
- 不依赖破坏性 Down Migration；需要回退时恢复升级前 Backup Set 和对应 `1.2.x` 构建。
