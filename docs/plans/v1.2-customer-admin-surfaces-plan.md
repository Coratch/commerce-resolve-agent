# Technical Plan：v1.2 客户售后中心与 Agent 运营控制台

状态：Completed  
日期：2026-07-22  
接受日期：2026-07-22  
Feature Spec：[`../specs/v1.2-customer-admin-surfaces.md`](../specs/v1.2-customer-admin-surfaces.md)（Accepted）  
依赖版本：v1.1 订单优先的智能售后中心（产品范围本机验收完成）  
关联 ADR：[`../adr/0012-separate-customer-and-agent-operations-surfaces.md`](../adr/0012-separate-customer-and-agent-operations-surfaces.md)（Accepted）

## 1. Plan 目标

本 Plan 将 v1.2 已接受的双产品表面落实为同一模块化单体内的明确权限和职责边界：

- 客户售后中心只服务本人订单、服务、对话、审批、恢复和长期偏好。
- Agent 运营控制台只服务管理员的 Mock 数据准备、邀请管理、脱敏 Monitoring、只读 Eval 和有限系统状态。
- 管理员能力由服务端持久角色和受控本机 CLI 授予，不接受前端、邀请码或模型自报。
- 普通客户失去 Mock 订单、物流和支付写权限，但已有数据及全部售后能力保持可读可用。
- 管理员通过显式目标客户管理同一权威业务事实，不模拟客户 Session，不绕过退款 Policy。
- 后台业务写入保存脱敏、持久化的管理员审计；监控读取不触发任何 Agent 或业务副作用。
- Eval 页面只读取既有 Artifact；完整 Eval、Baseline 接受、Provider Qualification 和运维仍使用 CLI。
- React 应用使用客户与运营两套 Layout/路由组，继续由同一个 Vite 构建和 FastAPI 部署单元提供。

本 Plan 不拆分服务或前端仓库，不新增真实外部业务系统、客服坐席、后台 Worker、消息队列、任意
Shell、客户身份模拟或新的售后业务类型。

## 2. 完成证据

v1.2 完成必须同时具备：

- Alembic 原地迁移把现有账号设为 `customer`，原 Session、订单、退款、Conversation、Checkpoint、
  L2 Case 和 Memory 保持可读。
- 本机 CLI 能授予、撤销和查看管理员角色；Web、自助注册和邀请码不能授予管理员。
- Session 响应只公开服务端计算的运营能力；伪造请求字段或 URL 不产生任何运营访问。
- 客户导航不再出现演示数据管理；旧 `/demo-data` 与旧订单写 API 不再允许客户修改业务事实。
- 管理员可以选择客户，维护其订单、商品行、物流和退款前 Mock 支付，并查看退款结果。
- 管理员可以创建、查看和撤销邀请码；明文邀请码只在创建响应中出现一次。
- 后台每次业务写入均记录管理员、目标客户、动作、脱敏参数、结果和时间。
- Monitoring 可以筛选并查看真实 Agent Run 的脱敏生命周期、步骤、工具类别、停止原因、用量、延迟
  和失败归因；响应不含完整消息、Prompt、隐藏推理、密钥或未脱敏工具输出。
- 打开 Monitoring 页面不执行 Graph、模型、工具、Memory、审批或 Mock 退款写入。
- Eval 页面准确区分无 Artifact、不兼容、失败和通过，只读取已生成 Artifact，不启动 Eval 或 Provider。
- 系统状态只公开版本、迁移、健康、Capability 和存储状态，不公开绝对路径、密钥或完整配置。
- 客户与运营表面继续由一个 React 构建、一个 FastAPI 应用和共享领域 Repository 提供。
- 客户订单、服务、对话、退款审批、SSE、恢复、长期偏好和移动/键盘行为保持兼容。
- v1.2 固定 Eval、全量 pytest、前端测试、E2E、OpenAPI、升级和安全门禁通过；未经授权写入、跨客户
  泄露、敏感字段泄露和读取副作用均为 `0`。

## 3. 当前基线与缺口

现有代码已经具备：

- FastAPI 同源 API、React + TypeScript SPA、React Router 和 TanStack Query。
- 游客与注册 Session、CSRF、Origin、邀请码注册、Argon2 密码和私有工作区。
- SQLite 中的订单、商品行、物流、支付、退款、Conversation、消息、Agent Run/Event 和 L2 Case。
- 独立 Checkpoint、Memory、政策索引、Audit 和 Eval Artifact 生命周期。
- 客户售后首页、订单与服务详情、上下文助手、SSE、退款审批和长期偏好。
- CLI 邀请、数据库迁移、完整 Eval、Baseline、Backup/Restore、Upgrade 和健康检查。
- 版本化离线 Eval 与 v1.1 客户产品本机验收证据。

当前缺口：

- 账号没有管理员角色；任意注册用户仍可写本人 Mock 订单、物流和支付。
- 前端只有客户 Layout，账号菜单仍暴露 `/demo-data`。
- 邀请管理只有 CLI，没有受限的 Web 管理视图。
- 没有跨客户 Mock 数据管理 API，也没有后台业务写入审计表。
- Agent Run 事件虽已持久化，但没有管理员级脱敏聚合和筛选 API。
- Eval Artifact、Baseline、健康和 Capability 没有有限的只读 Web 投影。
- 没有运营路由权限矩阵、运营空/坏数据状态和双产品 E2E。

## 4. 已接受实现边界

### 4.1 单一角色模型

账号新增稳定角色：

```text
role = customer | admin
```

- 迁移默认值为 `customer`，所有现有账号均保持普通客户。
- 邀请注册只创建 `customer`。
- CLI 使用规范化用户名显式 `grant` 或 `revoke` 管理员能力。
- 管理员仍是注册账号，继续使用原 Session、CSRF、Origin、限流和 Cookie 规则。
- 管理员访问客户售后中心时只操作自己的数据；后台目标客户必须作为独立参数再次授权。
- v1.2 不引入多角色集合、细粒度 RBAC 表、权限继承或租户管理员。

### 4.2 后台写入与审计

管理员数据管理复用现有 `SqliteBusinessRepository` 与 `SqliteRefundRepository`，目标作用域通过
服务端客户查询获得。新增 `admin_action_audit` 只保存：

```text
audit_id
admin_user_id
target_user_id | null
action
resource_type
resource_id | null
result
parameter_summary_json
created_at
```

- 参数摘要只允许稳定业务标识、状态、数量和布尔值，不保存密码、邀请码明文、Cookie 或消息正文。
- 审计不是订单或退款事实来源，失败审计不能掩盖业务事务结果。
- 管理员不能直接更新 `refund_actions`、`mock_refunds`、Checkpoint、Memory、Agent Run 或 Eval Artifact。

### 4.3 Monitoring 只读投影

Monitoring 从现有 `agent_runs`、`agent_run_events`、Conversation 元数据和有限 L2 结构化指标读取：

- 列表支持 `status`、`request_kind`、开始时间和有界 `limit`。
- 详情公开事件类型、时间、步骤标签、待办类型、工具类别、停止/失败分类和有限用量/延迟。
- 事件 Payload 使用显式白名单投影，不做“删除若干敏感键”的黑名单过滤。
- 默认不返回 `conversation_messages.content`、Prompt、隐藏推理、Context 正文或未脱敏工具结果。
- 查询只使用 Repository 读方法，不构造 Graph、Model、Executor 或 Memory Writer。

### 4.4 Eval 与系统状态只读投影

Eval 读取范围固定在配置的 Eval Artifact 根目录和版本化 Baseline 目录：

- 读取 Run Manifest、结果摘要和当前 Baseline；不接受客户端路径。
- 通过 Schema 和兼容性指纹区分 `missing`、`incompatible`、`failed`、`passed`。
- 不在 Web 请求内调用 `eval run`、Provider Qualification 或 Baseline 接受。

系统状态复用现有健康、迁移和 Release Manifest 读取逻辑，响应只返回稳定枚举、版本和布尔能力；
绝对路径、连接串、环境变量和密钥永不进入公开 Schema。

### 4.5 一个构建、两个 Layout

- 客户路由继续使用 `CustomerLayout`，主导航不包含运营和演示数据维护入口。
- `/admin/*` 使用 `AdminLayout` 和独立导航；入口只在服务端 Session 能力允许时显示。
- 前端 Guard 只改善体验，FastAPI `require_admin_access` 是唯一授权依据。
- 旧 `/demo-data` 对管理员重定向至后台数据管理，对游客/客户重定向至客户售后中心。
- 不新增第二个 npm 工程、第二个静态服务、跨源 Cookie 或新的前端状态框架。

## 6. 技术选型

| 领域 | 选择 | 原因 |
|---|---|---|
| 角色 | `users.role` 枚举字段 | 当前只有客户/管理员两类，单字段比 RBAC 表更小、更可迁移 |
| 授权 | FastAPI 依赖 `require_admin_access` | 复用 Session/CSRF/Origin，所有运营路由统一服务端门禁 |
| 管理员授予 | 现有 Python CLI 子命令 | 不扩大 Web 权限面，适合单机项目维护者 |
| 业务写入 | 复用现有 SQLAlchemy Repository | 保持订单、支付锁定和退款依赖规则单一 |
| 后台审计 | 业务库关系表 | 写操作与管理员/目标客户可关联并可测试，避免仅靠易丢日志 |
| Monitoring | 现有 Run/Event/L2 只读投影 | 不新增 Trace 系统或复制运行事实 |
| Eval | 现有 JSON Artifact + Baseline 只读读取 | 保持 CLI 是执行主体，Web 无长任务和 Provider 权限 |
| 前端 | 现有 React/TS/Router/Query | 同一构建内路由分组即可满足产品分离 |
| API 类型 | FastAPI OpenAPI → 生成 TypeScript | 保持服务端 Schema 为唯一契约来源 |
| 迁移 | Alembic `0007` | 原地保留既有账号和全部业务数据 |
| 测试 | pytest、Vitest、Playwright、临时 SQLite | 离线覆盖权限、跨客户、脱敏、只读和 UI 路由 |
| Eval | v1.2 Suite + 统一 Catalog/Baseline | 保持历史能力可比较，安全违规不可被均值抵消 |

本版本原则上不新增 Python 或 npm 运行时依赖。

## 7. 后端领域与数据设计

### 7.1 角色与 Session

`UserAccount`、`SessionBundle`、`SessionIdentity` 和 `AccessPrincipal` 增加 `role`。游客没有账号角色，
公开 Session 使用能力字段表达是否可进入运营控制台：

```text
SessionCapabilities
  can_manage_orders = false       客户侧不再写 Mock 数据
  can_manage_refunds = registered
  can_use_llm = 既有策略
  can_access_admin = role == admin
```

`role` 只来源于数据库。前端和请求 Body 不提供角色字段。

### 7.2 有限客户目录

后台客户目录只公开：

```text
user_id
username
status
role
workspace_id
order_count
created_at
```

不返回密码 Hash、Session、Memory、消息正文或模型额度细节。目标客户解析必须同时验证账号存在、
工作区存在和账号状态；不存在与不可用使用统一 `admin_target_unavailable`。

### 7.3 后台业务数据

管理员 API 使用 URL 中的 `user_id` 明确目标，再由服务端解析其 `workspace_id`：

```text
GET    /api/admin/customers
GET    /api/admin/customers/{user_id}/orders
POST   /api/admin/customers/{user_id}/orders
PATCH  /api/admin/customers/{user_id}/orders/{order_id}
PUT    /api/admin/customers/{user_id}/orders/{order_id}/payment
DELETE /api/admin/customers/{user_id}/orders/{order_id}
```

响应复用现有公开订单、支付和退款读模型；写入复用既有业务约束。退款结果只读展示，后台不提供写
端点。客户原 `/api/orders` 的 GET 与退款列表保持兼容，POST/PATCH/PUT/DELETE 统一拒绝。

### 7.4 邀请与审计

```text
GET    /api/admin/invitations
POST   /api/admin/invitations
DELETE /api/admin/invitations/{invitation_id}
GET    /api/admin/audit?limit=
```

邀请列表只返回 ID、有效期、最大/已用次数、撤销状态和创建时间。明文 `code` 只存在于 POST 响应。

### 7.5 Monitoring

```text
GET /api/admin/agent-runs?status=&request_kind=&started_after=&limit=
GET /api/admin/agent-runs/{run_id}
```

Run 列表返回：`run_id`、类型、状态、Pending 类型、公开错误分类、时间、持续时长和有限关联标识。
详情返回白名单事件和可用 L2 聚合：步骤数、工具类别、停止原因、确定性失败归因、Provider 延迟和
Token/调用计数；缺失字段显式为 `null`/`unavailable`，不补造。

### 7.6 Eval、概览和系统

```text
GET /api/admin/overview
GET /api/admin/eval
GET /api/admin/eval/runs/{run_id}
GET /api/admin/system
```

- 概览只组合有界计数、最近 Run、Eval 摘要和系统状态。
- Eval Run ID 必须通过受限模式校验，再在固定根目录内解析；路径逃逸统一拒绝。
- System 只返回应用版本、迁移状态、Live/Ready、Capability 和各权威/派生存储状态。

## 9. 安全与隐私

- `/api/admin/*` 先执行 Session/CSRF/Origin，再检查数据库角色；所有后台写请求都需要 CSRF。
- 管理员目标客户来自路径参数，但完整作用域只由服务端 Repository 解析。
- 后台不能创建客户 Session、改变请求 Principal、批准客户退款或恢复客户 Agent Run。
- 订单、支付写入继续使用确定性校验；管理员角色不改变现有 Policy 或幂等键。
- Monitoring 使用响应白名单，不返回完整消息、Prompt、隐藏推理、Cookie、密钥或绝对路径。
- Eval 和系统读取只接受固定服务端根目录与版本文件，不接受任意文件路径。
- 前端未展示入口不能代替 API 授权；直接请求与角色伪造均需安全测试。
- 管理员审计参数做结构化最小摘要，邀请码明文绝不写入审计。

## 11. 垂直任务

### T1：管理员角色、迁移和本机授权

用户结果：维护者可以把现有注册账号显式授予管理员；其他注册方式只能产生客户。

实现：

- `users.role` Alembic 迁移、领域模型、Session/Principal 和公开 Capability。
- `admin grant|revoke|list` CLI。
- `require_admin_access` 及游客、客户、管理员权限矩阵测试。

验收：

- 现有账号迁移为客户，数据与 Session 可读。
- CLI 授予后新旧有效 Session 均按数据库当前角色解析；撤销后立即失去后台能力。
- 前端字段、邀请码和自助注册不能创建管理员。

状态：Completed

### T2：客户写权限迁移与管理员 Mock 数据闭环

用户结果：客户只查看本人业务事实；管理员为选定客户准备同一套 Mock 订单、商品、物流和支付。

实现：

- 客户旧写 API 统一拒绝，GET 和售后链路保持兼容。
- 后台客户目录和显式目标客户订单 API。
- 复用现有订单/支付 Repository 与冲突、锁定和删除依赖规则。
- 每次后台业务写入记录持久审计。

验收：

- 管理员修改后客户页面和 Agent 下一次查询读到相同事实。
- 客户旧 URL、直接 API 和跨客户目标均不能写入。
- 管理员不能修改退款、Checkpoint、Memory 或 Agent Run。

状态：Completed

### T3：邀请、账号与审计运营能力

用户结果：管理员可以安全创建、查看、撤销邀请码，并查看有限客户与后台动作记录。

实现：

- 邀请有限列表、一次性创建响应和幂等撤销 API。
- 客户有限账号状态和后台审计列表。
- 邀请和账号页面的加载、空、冲突和撤销状态。

验收：

- 创建后只有第一次响应包含明文；列表和审计都不包含明文或 Hash。
- 普通客户和游客读取/写入数量为 `0`。
- Web 不提供管理员授予、密码、Session 撤销或客户模拟。

状态：Completed

### T4：脱敏 Agent Monitoring

## 14. 风险与控制

| 风险 | 控制 |
|---|---|
| 隐藏菜单被误当授权 | 所有 `/api/admin/*` 使用统一服务端依赖，前端 Guard 只改善体验 |
| 管理员成为万能后门 | 显式目标客户、复用业务约束、禁止退款/Checkpoint/Memory/Eval 写入 |
| 客户失去数据后无法演示 | 管理员后台准备数据；已有客户数据原地保留且客户继续只读 |
| Monitoring 泄露用户正文 | 白名单 Schema、默认不连接消息正文、固定敏感字段扫描 |
| Monitoring 读取触发副作用 | 独立只读 Repository、调用计数和数据库快照前后对比 |
| Eval Web 请求阻塞服务 | 只读既有 Artifact，完整运行继续 CLI |
| Artifact 路径逃逸或损坏 | 固定根、受限 Run ID、Schema 验证、四态安全降级 |
| 双 Layout 复制业务逻辑 | 页面只消费共享 API/组件，订单/退款/Policy 仍在同一后端核心 |
| 管理员角色缓存导致撤销延迟 | 每次请求从 Session 关联账号读取当前数据库角色 |
| v1.0 Docker Gate 被误报完成 | 报告继续明确延后，只陈述本机产品与离线证据 |

## 15. 迁移与回退

- Alembic `0007` 只增加 `users.role`、约束/索引和后台审计表，不重写已有业务行。
- 迁移前使用现有 CLI 创建完整性通过的 Backup Set；失败时实例保持非 Ready。
- 所有现有用户初始化为 `customer`，不创建默认管理员；维护者迁移后显式执行 CLI grant。
- 现有 Session 通过关联 User 读取当前角色，不需要强制注销；Session Token 和 CSRF 不迁移。
- 客户已有订单保持所有权，只关闭 Web 维护入口；Agent/Support Reader 继续读取同一数据。
- 回退使用升级前 Backup Set，不依赖破坏性 Down Migration。
