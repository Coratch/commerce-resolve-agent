# Technical Plan：v1.1 订单优先的智能售后中心

状态：Completed  
日期：2026-07-22  
接受日期：2026-07-22  
Feature Spec：[`../specs/v1.1-post-purchase-service-center.md`](../specs/v1.1-post-purchase-service-center.md)（Accepted）  
依赖版本：v1.0 单机交付与可维护运行（Candidate，代码基线冻结）  
关联 ADR：[`../adr/0011-order-first-post-purchase-service-center.md`](../adr/0011-order-first-post-purchase-service-center.md)（Accepted）

## 1. Plan 目标

本 Plan 把已接受的 v1.1 用户结果落实为一个不重写现有 Agent 核心的增量方案：

- 默认入口从聊天工作台改为订单优先的智能售后中心。
- 为游客和注册客户提供售后首页、订单列表、订单详情、服务进度和服务详情。
- 为 Mock 订单增加可选的最小商品行事实，旧订单安全兼容。
- 从现有 Refund、Pending Action、L2 Case 和公开事件生成只读服务记录，不复制业务状态。
- 创建可选绑定订单的 Conversation；上下文助手可以理解“它到哪里了”等省略订单号的表达。
- 客户端不能通过篡改订单、会话或服务标识改变授权范围。
- 复用现有公开消息、Agent Run、SSE、退款审批、L2、RAG、Checkpoint 和恢复语义。
- 桌面端使用页内助手侧栏，移动端使用原生模态抽屉；旧聊天入口继续可用。
- 新增固定 v1.1 Eval、浏览器闭环和 v1.0 → v1.1 数据升级证据。

本 Plan 不接入真实电商、支付、物流或人工客服系统，不新增 Agent、工具权限、消息队列、
PostgreSQL、向量数据库、前端状态框架或动画库。

## 2. 完成证据

v1.1 完成必须同时具备以下证据：

- 游客和注册客户进入 `/` 后看到售后首页，而不是自动创建的空白对话。
- 售后首页可以从服务端读取最近订单、进行中服务和当前可执行动作。
- 注册客户可以为 Mock 订单维护可选商品行；旧订单没有商品行时不报错、不补造数据。
- 订单详情、物流进度、支付和退款摘要均来自服务端权威 Repository。
- 从订单详情发送“帮我看看它到哪里了”时，Graph 使用服务端绑定的订单，不要求重复订单号。
- 客户端伪造其他订单或服务上下文时，在模型和业务工具调用前被拒绝，跨用户泄露和写入为 `0`。
- Mock 退款继续通过原有预览、审批、幂等执行和回读验证，不新增旁路。
- 服务进度由现有事实投影；删除投影代码不会删除 Refund、L2 Case、Conversation 或审计事实。
- 刷新、切页、重新登录和 SSE 断线后可以继续同一服务、会话和 Pending Action。
- 客户默认页面不展示 Provider、Context Manifest、模型预算、内部 Tool 参数或 Eval 指标。
- `/chat` 与 `/chat/:threadId` 继续读取原有会话；迁移不会静默创建或丢失 Conversation。
- 桌面和移动端均可完成订单查看、上下文提问、退款批准和服务恢复。
- v1.1 固定 36 条离线场景达到 `36/36`，统一离线 Eval 预期达到 `285/285`，安全违规为 `0`。
- v0.1–v1.0 测试、OpenAPI 类型校验、前端测试、E2E 和 Release Gate 保持通过。
- 从固定 v1.0 数据快照升级后，旧账号、订单、会话、退款、L2 Case、Memory 和运维数据仍可读。

## 3. 当前基线与缺口

当前代码已经具备：

- FastAPI 同源 API、React + TypeScript SPA、TanStack Query 和 React Router。
- 游客固定 `ORD-001` Fake 订单/物流，以及注册用户 SQLite 私有订单、物流和 Mock 支付 CRUD。
- 订单、支付、退款、Conversation、Agent Run/Event 和 L2 Case 均保存在 `business.sqlite`。
- LangGraph Checkpoint、Memory Store 和政策 FTS5 索引分别独立存储。
- `/api/conversations`、公开消息、SSE、四类 Pending Action 和跨进程恢复。
- 一线工作流、确定性退款 Policy、受控 L2 Harness 和可定位政策引用。
- v1.0 对话工作台、会话上下文面板、移动布局和 Reduced Motion。
- Alembic 业务迁移、单机 Backup/Restore/Upgrade 和统一 249 条离线 Eval。

当前缺口：

- `/`、品牌和主导航仍以 `/chat` 为中心。
- 注册用户 `/orders` 是演示数据编辑器，不是客户订单浏览体验；游客没有订单列表 API。
- 订单只有订单状态和一条当前物流事件，没有可展示的商品行。
- Conversation 没有可信的订单绑定；每轮通常依赖用户或模型提取订单号。
- 退款、Pending Action 和 L2 Case 有独立事实，但没有统一的客户服务进度投影。
- `ChatPage.tsx` 同时承担全页布局、会话管理、消息、Run/SSE 和动作卡片，不能直接复用为订单页侧栏。
- 公开 L2 Trace 与处理上下文仍占据客户工作区明显位置，产品心智偏内部 Agent 控制台。

## 4. 已接受实现边界

### 4.1 最小商品行

商品行只保存：

```text
sku
title
quantity
product_category: general | apparel | hygiene | digital
```

- 不保存图片 URL、商品正文、库存、促销、税费或行级退款金额。
- 支付表继续是整单 Mock 金额事实；商品行金额不会参与 v0.4 退款计算。
- 每笔订单最多 10 个商品行，SKU 在同一订单内唯一。
- 旧订单允许 `items=[]`，页面显示“未配置商品信息”，不插入占位行。

### 4.2 服务记录是只读投影

不创建 `service_records` 事实表。统一服务记录由现有表计算：

```text
Refund Service = refund_actions + mock_refunds + conversation
L2 Service     = l2_support_cases + conversation + 有限公开事件
```

投影只提供稳定展示模型，不能执行状态迁移。所有批准、重试和补充信息继续调用现有 API，并在完成后
重新读取投影。

### 4.3 客户公开层级

客户可以看到：

- 服务类型、问题摘要、关联订单。
- 当前阶段、公开时间、待用户动作和最终结果。
- 退款金额/渠道/政策引用等原本已经公开的业务事实。
- 有限的“已提交、等待确认、处理中、已完成/需要处理”步骤。

客户默认不能看到：

- Provider/模型名、Prompt 版本、Token、预算和调用计数。
- Context Manifest、来源哈希、内部节点、Tool 参数和失败归因。
- Eval 指标、运维 Trace 和隐藏推理。

现有受控诊断和 Eval 数据继续保留，v1.1 只改变默认客户投影。

### 4.4 渐进迁移

- `/chat` 和 `/chat/:threadId` 保留为兼容页面。
- `/orders` 改为客户订单列表；原演示数据管理页移动到 `/demo-data`。
- 旧 `/orders` 书签会进入同一批订单的客户视图，数据管理入口在账号导航中明确提供。
- 打开订单或服务页面不创建 Conversation；第一次明确打开助手或发送消息时才创建。

```text

  ├─ /support                  售后首页

  ├─ /orders/:orderId          订单详情 + 上下文助手
  ├─ /services                 服务进度列表

          │
          ▼
FastAPI /api/support/*
  → Session / CSRF / AccessPrincipal
  → SupportCenterReader
      ├─ GuestSupportCatalog（固定只读 Fake）
      └─ SqliteSupportCenterReader（注册用户完整作用域）
  → ServiceProjection
      ├─ RefundAction / MockRefund
      └─ L2Case / Conversation / Public Event

Contextual Assistant
  → POST /api/conversations {related_order_id?}
  → 服务端查询并授权订单
  → conversations.related_order_id
  → POST message（请求中不再接受 order_id）

  → 既有 Tool / RAG / Refund / L2 / SSE / Checkpoint
```

## 6. 技术选型

| 领域 | 选择 | 原因 |
|---|---|---|
| 后端 | 现有 Python 3.12 + FastAPI + Pydantic | 保持同源身份、安全错误和 OpenAPI 契约 |
| 编排 | 现有 LangGraph 主图 | 只增加可信订单上下文，不复制退款或 L2 工作流 |
| 业务存储 | 现有 SQLite + SQLAlchemy 2.0 | 所有投影来源已在同一业务库，支持本地事务和测试 |
| Schema 迁移 | Alembic `0006` | 增量保留 v1.0 账号、订单、会话和业务事实 |
| 商品行 | 关系表 `order_items` | 结构固定、可约束、可随订单删除，优于不可校验 JSON |
| 服务记录 | 查询时只读投影 | 避免第二套状态和同步任务，原始事实仍是唯一来源 |
| 上下文绑定 | `conversations.related_order_id` + `RunContext` | 绑定可恢复，但每次业务查询仍重新授权和读取真实状态 |
| 客户数据读取 | 新 `/api/support/*` 只读 API | 与现有注册用户演示数据管理写 API 分离职责 |
| 前端 | 现有 React、TypeScript、React Router、TanStack Query | 不引入第二套状态或渲染框架 |
| 移动助手 | 原生 `<dialog>` + CSS Modules | 获得模态、Esc、焦点和背景 inert，不增加 UI 依赖 |
| 进度 | 现有持久 Agent Run/Event + SSE | 网络断线不是事实来源，不改为不可信 Provider Token 流 |
| 动效 | CSS transition + `prefers-reduced-motion` | 只表达抽屉和状态变化，不引入 Anime.js 等非必要依赖 |
| 测试 | pytest、Vitest、Playwright、Fake Model/Gateway | 离线验证身份、投影、恢复和真实浏览器路径 |
| Eval | 新 v1.1 Catalog Adapter + 现有 Artifact/Baseline/Gate | 保持版本间可比较和安全违规不可平均 |

本版本不需要新增 Python 或 npm 运行时依赖。

## 7. 后端领域与数据设计

### 7.1 `OrderItem`

新增领域模型：

```text
OrderItemInput
  sku                  1..40，受限字符
  title                1..120
  quantity             1..99
  product_category     general | apparel | hygiene | digital

OrderItemRecord
  上述字段
  created_at / updated_at
```

`OrderCreate.items` 默认空；`OrderUpdate.items` 使用 `None` 表示不修改、空元组表示明确清空。注册用户
只能通过既有 `/api/orders` 管理接口维护本人工作区商品行，Agent 工具继续只读且不新增写能力。

### 7.2 `SupportOrder`

客户读模型不直接复用写 API 的 `PublicOrder`：

```text
SupportOrderSummary
  order_id / status
  item_count / item_title_preview
  shipment_status / estimated_delivery_at
  payment_amount | null
  latest_service_status | null
  created_at / updated_at

SupportOrderDetail
  summary
  items[]
  shipment
  shipment_milestones[]
  payment / refunds[]
  available_actions[]
```

物流里程碑只从当前权威 `ShipmentStatus` 确定 `completed/current/upcoming`；仅当前 `last_event` 和
`updated_at` 可以显示具体时间，不补造历史时间点。`available_actions` 只是入口，不代表退款资格：

- 游客：`ask_assistant`、`view_policy`。
- 注册客户：上述动作；存在适用 Mock 支付且没有互斥结果时可显示 `request_refund`。
- 最终退款资格、金额和审批要求仍由 v0.4 Policy 产生。

### 7.3 `ServiceRecord`

```text
ServiceRecordSummary
  service_id           refund:<action_id> | l2:<case_id>
  kind                 refund | l2_support
  status               waiting_user | in_progress | completed |
                       needs_attention | cancelled
  order_id | null
  thread_id
  title
  next_action | null
  updated_at

ServiceRecordDetail
  summary
  public_steps[]
  result_summary | null
  citations[]
```

确定性状态映射：

| 来源状态 | 客户服务状态 |
|---|---|
| Refund `awaiting_approval` | `waiting_user` |
| Refund `executing` | `in_progress` |
| Refund `completed` 且结果已验证 | `completed` |
| Refund `rejected` | `cancelled` |
| Refund `stale/failed/unknown/verification_failed` | `needs_attention` |
| L2 `l2_active` | `in_progress` |
| L2 `l2_waiting_user/l2_waiting_approval` | `waiting_user` |
| L2 `l2_resolved` | `completed` |
| L2 `l2_cancelled` | `cancelled` |
| L2 `l2_unresolved/l2_budget_exhausted/l2_stopped` | `needs_attention` |

`ServiceProjection` 只读取同一 `subject_id/user_id/workspace_id` 下的数据。`service_id` 是资源定位符，
不是授权凭据；读取详情时必须重新按完整作用域查询底层事实。

### 7.4 Conversation 订单绑定

`ConversationSummary` 和 `ConversationRecord` 增加可选 `related_order_id`。绑定规则：

- `POST /api/conversations` 接受可选严格请求 `{related_order_id}`；空请求保持旧行为。
- 服务端使用当前 `AccessPrincipal` 和 Support Reader 查询订单，成功后才写入绑定。
- 游客只能绑定固定演示订单；注册客户只能绑定本人私有工作区订单。
- 有订单绑定时复用同身份、同订单的最新活动 Conversation，以便刷新恢复历史与 Pending Action；
  无订单的新会话仍只复用空 Conversation，不能重绑其他订单。
- 已创建 Conversation 不提供修改绑定 API；切换订单必须创建新的绑定会话。
- 订单删除后保留会话和绑定标识，但业务查询返回统一不可用语义。

客户端消息请求继续只有 `message` 和 `client_message_id`，不能逐轮提交或覆盖订单绑定。

### 7.5 Graph 上下文规则

`RunContext` 新增 `bound_order_id: str | None`，由 `ConversationRuntime` 在完整身份作用域内读取
Conversation 后构造：

1. Runtime 在模型前用共享订单号解析器检查用户文本中的显式订单号。
2. 显式订单号与绑定不一致时，生成普通助手消息 `order_context_mismatch`，模型、工具和写入为 `0`。
3. 文本没有订单号，但结构化意图需要订单时，`bind_and_interpret` 使用 `bound_order_id` 补齐。
4. 文本包含同一订单号时保持原值；未绑定会话继续使用原有澄清行为。
5. 每个订单、物流和退款 Gateway 调用仍使用当前 `BusinessScope` 重新查询，绑定本身不证明订单存在。
6. L2 升级没有显式订单号时使用绑定订单作为 `related_order_id`；L2 仍只能调用既有 R0 工具。

订单回填是确定性代码，不修改 OpenAI Interpreter Prompt，不新增 Provider 字段，也不允许模型决定
绑定关系。

## 8. API 设计

新增只读客户 API：

```text
GET /api/support/overview
GET /api/support/orders?limit=&cursor=
GET /api/support/orders/{order_id}
GET /api/support/services?view=active|history&limit=&cursor=
GET /api/support/services/{service_id}
```

核心响应：

```text
SupportOverviewResponse
  active_services[]    最多 5
  recent_orders[]      最多 5
  has_more_orders
  has_more_services

SupportOrdersResponse
  orders[]
  next_cursor | null

SupportServicesResponse
  services[]
  next_cursor | null
```

接口约束：

- 所有读取先解析当前 Session；不接受 `user_id` 或 `workspace_id`。
- 游客从唯一服务端 Guest Catalog 读取共享 Fake 订单，服务列表为空且所有写入口隐藏。
- 注册客户从 SQLite 完整作用域读取；不存在与无权访问统一返回 `404 order_not_accessible`。
- 列表使用稳定更新时间 + 资源 ID 的 keyset cursor，默认 20、最大 50。
- `service_id` 解析失败、底层事实不存在或不属于当前身份均返回统一不可访问语义。
- Support API 不调用模型、LangGraph 或政策检索，不消耗额度，也不产生业务写入。

现有 API 变化：

```text
POST /api/conversations
  request:  ConversationCreateRequest {related_order_id?: string}
  response: ConversationResponse {thread_id, related_order_id?}

GET /api/conversations*
  ConversationSummary 增加 related_order_id?

POST/PATCH /api/orders
  可选维护 items[]；旧请求保持有效
```

OpenAPI 是 TypeScript 类型唯一来源；修改后必须重新生成 `frontend/src/api/generated.ts`，禁止手工
补写漂移类型。

## 9. 数据迁移与兼容

新增 Alembic revision：

```text
migrations/versions/20260722_0006_v11_service_center.py
```

变更：

```text
order_items
  id                PK UUID
  order_pk          FK orders.id ON DELETE CASCADE
  sku               VARCHAR(40)
  title             VARCHAR(120)
  quantity          INTEGER CHECK 1..99
  product_category  CHECK allowlist
  created_at / updated_at
  UNIQUE(order_pk, sku)

conversations.related_order_id VARCHAR(36) NULL
INDEX(workspace_id, related_order_id)
```

- `related_order_id` 不使用数据库外键：游客订单不在业务表，且删除订单后必须保留会话历史。
- 应用层写入前校验格式和完整作用域，读取时每次重新授权。
- 旧订单商品行为 `[]`；旧 Conversation 绑定为 `NULL`，原对话行为不变。
- 不回填虚构商品、物流事件或订单关联。
- `business.sqlite` Backup 自动包含新增表和列；Checkpoint、Memory 和政策索引格式不变。
- v1.0 → v1.1 Upgrade 先生成 v1.0 Backup，再执行 `0006`、重建派生索引和验证关键计数。
- v1.1 版本目标为 `1.1.0`；是否保持现有 `data_format_version` 由实现时根据增量兼容测试确认，
  但 Release Manifest 的业务 Schema Head 必须更新。

该拆分只抽取 v1.1 必需的公开会话行为，不重写消息协议、SSE、退款卡片或 L2 卡片。

### 10.3 上下文助手行为

- 桌面宽度达到设计断点时使用订单/服务页内 `<aside>`。
- 移动端使用原生 `<dialog>` 模态抽屉，支持 Esc、关闭按钮、焦点恢复和背景 inert。
- 页面初次加载只读取业务数据，不创建 Conversation 或调用模型。
- 用户点击“咨询此订单”时，创建或复用同订单绑定的活动 Conversation；浏览页面本身不创建会话。
- 服务详情如果已有 `thread_id`，直接加载原会话，不创建第二条会话。
- 抽屉关闭不会取消后台 Run；再次打开从服务端恢复消息、事件和 Pending Action。
- 对话失败继续作为普通助手消息展示，不使用红色系统告警替代客服回复。

## 11. 安全与权限

- Support Reader 接受服务端 `RequestAccess`，不接受浏览器提交的身份和工作区。
- Support API 的游客数据来自服务端单一 Guest Catalog，不能从前端常量模拟业务事实。
- Conversation 绑定在写入前验证；无权上下文零模型、零工具、零业务写入。
- 消息接口不能携带订单绑定；已有绑定不能通过 PATCH 修改。
- 服务投影每次按完整身份作用域查询原始行，`service_id` 不构成能力令牌。
- `available_actions` 只控制入口展示，不授权退款；所有 R2 动作继续通过现有 Policy 和审批。
- 商品标题和 SKU 作为不可信文本按纯文本渲染，不执行 HTML，也不进入系统 Prompt 成为指令。
- 正常客户响应不包含内部主键、工作区、Prompt、Context Manifest、模型或 Eval 字段。
- 旧会话、旧订单和无商品行场景使用明确兼容状态，不通过删除数据“修复”迁移。

## 13. 垂直任务

### T1：订单优先读模型与商品行

用户结果：游客和注册客户可以读取真实售后首页、订单列表和订单详情；注册客户可以维护可选商品行。

实现：

- `order_items` 迁移、领域模型、Repository 和现有订单写 API。
- 单一 Guest Support Catalog，供 Graph Fake Gateway 与 Support API 共用。
- Support Overview、订单列表和订单详情 API。
- 权威物流里程碑和 `available_actions` 确定性投影。

验收：

- 旧订单返回 `items=[]`，新订单可保存最多 10 行并跨进程读取。
- 游客只看到共享演示订单；注册客户只看到本人工作区。
- Support GET 零模型调用、零业务写入。

状态：Completed

### T2：可信订单绑定与省略订单号对话

用户结果：用户从订单打开助手后可以直接问“它到哪里了”，并继续使用原有 Agent 能力。

实现：

- `RunContext.bound_order_id`、共享订单号预检、确定性回填与冲突回复。
- Conversation API、公开 Summary、Runtime、Workflow 和 Fake/注册路径测试。

验收：

- 同订单活动会话可幂等恢复；不同订单不能复用或重新绑定，无绑定新会话保持原语义。
- 省略订单号成功查询绑定订单；显式冲突在模型与工具前停止。
- 客户端篡改跨用户订单时模型、工具和写入均为 `0`。

### T3：统一服务进度投影

## 16. 风险与控制

| 风险 | 控制 |
|---|---|
| 服务记录成为第二套事实 | 只读投影，不提供写 Repository 或状态迁移方法 |
| 绑定订单被客户端当作授权 | 创建时验证、消息不接受订单字段、工具调用时重新授权 |
| 旧订单缺少商品导致 UI 编造 | 空商品行是正式兼容状态，服务端和前端测试禁止占位事实 |
| ChatPage 拆分破坏审批/SSE | 先用现有测试锁定协议，再只抽取 Hook/Panel，不改消息契约 |
| 服务列表跨表查询变慢 | 有界列表、必要索引、keyset cursor；不用缓存复制事实 |
| 移动抽屉造成焦点或输入丢失 | 原生 `<dialog>`、焦点恢复、组件状态来自 Query/服务端 |
| v1.0 Candidate 未完成却宣称 v1.1 发布 | 目标地图与 Release Gate 保留明确 Candidate 条件 |
| 版本范围扩展成商城或坐席平台 | 严格执行 Spec 非目标，不增加目录、结算、CRM 或真实 Handoff |

## 17. 回退与迁移失败

- Alembic `0006` 执行前由现有运维入口创建通过完整性检查的 v1.0 Backup Set。
- 迁移失败时实例保持非 Ready，不自动删除新表或覆盖原数据库。
- 降级不依赖 Down Migration；使用升级前 Backup Set 恢复 v1.0 实例。
- 前端路由可以回退到 v1.0 构建，但如果数据库已到 `0006`，只能由兼容声明允许启动；否则恢复 Backup。
- 服务投影没有独立事实，回退不会丢失业务状态。
- `related_order_id` 和商品行是增量字段；恢复后旧 Conversation 和订单仍按 v1.0 行为工作。
