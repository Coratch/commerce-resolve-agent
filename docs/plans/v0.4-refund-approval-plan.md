# Technical Plan：v0.4 Mock 退款预览、审批与幂等执行

状态：Completed  
日期：2026-07-17  
接受日期：2026-07-17  
完成日期：2026-07-19  
对应 Spec：[`../specs/v0.4-refund-approval.md`](../specs/v0.4-refund-approval.md)  
关联决策：[`../adr/0005-mock-transaction-boundary.md`](../adr/0005-mock-transaction-boundary.md)

## 1. Plan 目标

在保持 v0.1–v0.3 查询、RAG、Web 身份和数据隔离行为不变的前提下，为
CommerceResolve 增加一条本地 Mock 整单退款路径：

- 注册用户在私有工作区维护订单对应的最小 Mock 支付事实。
- LLM 或 Fake Interpreter 只提取退款意图、订单号和退款原因。
- 确定性 Refund Policy 读取最新订单、物流、支付、已有退款和已发布政策，计算资格与
  整单退款预览。
- LangGraph 使用 `interrupt` 暂停，等待当前登录用户明确批准或拒绝。
- 批准后使用服务端保存的动作、稳定幂等键和本地 Fake Refund Gateway 写入 Mock 退款。
- 执行后重新读取业务数据库，只有验证通过才能对外声明完成。
- 重试、节点重放、服务重启和跨 thread 竞争不会创建重复退款。

本 Plan 只解决已接受 Spec 中的 v0.4 用户结果。真实支付、部分退款、多级审批、人工客服
Handoff 和动态 Agent Loop 不进入实现。

## 2. 成功标准

实现完成后必须能够复现以下端到端路径：

```text
注册用户创建 Mock 订单并维护已结算 Mock 支付
  -> 在对话中提出整单退款并提供原因
  -> Interpreter 只提取 intent / order_id / reason
  -> Refund Policy 读取最新业务事实和当前政策
  -> 服务端生成带引用的整单退款预览
  -> LangGraph interrupt 暂停
  -> 浏览器关闭或服务重启
  -> 原用户重新打开同一 conversation 并看到原预览
  -> 用户批准
  -> 服务端重新读取并校验业务事实和政策
  -> Fake Refund Gateway 按稳定幂等键写入一笔 Mock 退款
  -> Verifier 重新读取退款与支付余额
  -> 只有验证一致时显示退款完成
```

同时满足：

- 生成预览、拒绝、游客请求和越权请求的 Mock 退款写入数均为 `0`。
- 客户端不能覆盖金额、币种、渠道、订单、身份、Policy 版本或幂等键。
- 同一动作重复批准、HTTP 重试、节点重放和跨进程恢复只对应同一退款记录。
- 同一订单在不同 thread 中并发申请时，最多只有一个有效整单退款动作。
- 预览后业务事实或政策发生实质变化时，旧预览不能执行。
- 审批恢复路径不调用 Interpreter、不消耗 LLM 配额。
- v0.1–v0.3 测试、Eval 和浏览器关键路径全部回归通过。
- v0.4 至少 24 个固定 Eval 场景达到 Spec 的全部发布门槛。

## 3. 当前基线与实施约束

v0.3 已提供：

- FastAPI 同源内部 API、React + TypeScript SPA。
- 邀请注册、服务端 Session、CSRF/Origin、防枚举错误语义和工作区隔离。
- `business.sqlite` 中的用户、conversation、订单、物流和 LLM 配额。
- 独立的 `checkpoints.sqlite` 和 `policy-index.sqlite`。
- 唯一 `build_workflow()`、服务端依赖装配和进程内 thread 锁。
- 注册用户 LLM 配额在每次新对话消息进入 Interpreter 前原子扣减。

v0.4 必须基于这些边界增量实现：

- 不复制一张“退款专用主图”；退款节点注册到现有唯一主图。
- 不把 Mock 支付或退款写进 Checkpoint。
- 不让浏览器或 LLM 直接调用数据库 Repository。
- 不把 RAG 检索结果当作退款授权。
- 不为 Mock 退款引入真实支付 SDK、网络调用、队列或后台 Worker。
- 本地交付继续只承诺单实例、单 Uvicorn worker；业务唯一约束仍必须能阻止跨 thread
  重复退款。

本机已锁定 LangGraph `1.2.9`。该版本的 `invoke()` 支持 `Command` 输入，
`get_state()` 返回 `StateSnapshot`，`interrupt(value)` 可持久暂停。Web 层在调用后统一通过
`get_state()` 读取公开 State 与中断，不依赖内部 `__interrupt__` 字段。

## 4. 总体架构

继续采用模块化单体、同步 FastAPI/SQLAlchemy 和独立 React SPA：

```text
React SPA
  -> same-origin JSON API
  -> Session / CSRF / Conversation ownership
  -> 唯一 build_workflow()
       -> Query Interpreter
            只输出 refund_request / order_id / reason
       -> Refund Query Gateway
            读取当前作用域内订单、物流、支付与已有退款
       -> Refund Policy
            纯函数计算资格、金额、渠道、风险和规则原因
       -> PolicyRepository
            解析当前退款政策事实与引用
       -> Refund Action Gateway
            幂等保存预览动作、拒绝、执行和结果查询
       -> interrupt / Command(resume=...)
       -> Verifier
            重新读取业务事实确认结果

物理存储：
  var/business.sqlite       Mock 支付、退款动作、退款和最小审计事件
  var/checkpoints.sqlite    对话、预览引用、中断和恢复点
  var/policy-index.sqlite   可重建政策索引
```

`refund_actions` 是服务端待执行动作和事务协调事实，不等于退款；`mock_refunds` 才表示
已尝试或完成的 Mock 退款。`refund_audit_events` 只记录不可变的脱敏事件，不参与资格、
金额或完成状态判断。

## 5. 技术选型

| 领域 | 选择 | 原因 |
|---|---|---|
| 编排 | 现有 LangGraph 1.2.9 单图 | 复用 State、Checkpoint、`interrupt` 和恢复语义 |
| 数据契约 | Pydantic v2 严格模型 | 限制模型、API、工具和持久化边界 |
| 业务持久化 | 现有 SQLite + 同步 SQLAlchemy 2.0 | 本地、事务明确、测试可复现，不增加服务 |
| Schema 迁移 | 新 Alembic revision | 保留 v0.3 数据，不在启动时隐式建表 |
| 金额 | 数据库整数最小货币单位；API 十进制定点字符串 | 避免二进制浮点误差和客户端改写 |
| 退款规则 | 纯 Python `RefundPolicy` | 资格和金额可单测、可审计，不依赖 Prompt |
| 政策证据 | 复用 Markdown + manifest + SQLite FTS5 | 引用可定位；不新增向量数据库 |
| 副作用 | 本地 SQLite Fake Refund Gateway | 满足 Mock 边界并可验证幂等事务 |
| 失败注入 | 测试用内存 Fake Gateway | 稳定模拟拒绝、失败、未知和验证不一致 |
| Web 协议 | 普通 JSON 请求 + 独立审批请求 | 审批跨进程，不需要维持 SSE 连接 |
| 前端 | 现有 React + TypeScript | 复用 Session、Chat 和 Orders 页面 |
| 测试/Eval | pytest、Vitest、Playwright、固定 Fake | 离线确定性，不需要 API Key 或外部系统 |

v0.4 不新增 Python 或 npm 运行时依赖。`decimal`、`hashlib`、`json` 和 `uuid` 使用 Python
标准库；金额绝不使用 `float`。

### 5.1 为什么不使用支付 Sandbox

支付 Sandbox 仍会引入网络、账号、凭据、供应商协议和不可控可用性，却不会改善
LangGraph 审批、恢复、幂等和 Eval 的学习目标。按照 ADR-0005，执行退款只修改项目内
Mock 业务状态。

### 5.2 为什么审批不用 SSE 长连接

退款审批是两个可独立恢复的 HTTP 阶段：第一次请求生成预览并暂停，第二次请求提交批准
或拒绝。页面和服务可能在两个阶段之间关闭，SSE 连接不是持久事实，也不能代替
Checkpoint。v0.4 继续使用普通 JSON；前端现有打字机效果仍是展示行为，不宣称 Token 级
网络流式传输。

### 5.3 为什么不引入通用 Action Framework

当前只有一个 R2 动作。先实现退款所需的窄模型、Policy 和 Gateway；未来 Handoff 或
Agent Loop 只有在出现重复契约后再提取通用 Action 抽象，避免提前设计。

## 6. 领域模型

### 6.1 Interpreter 输出

现有 `Intent` 增加：

```text
refund_request
```

`Interpretation` 增加可选字段：

```text
refund_reason:
  code: no_longer_needed | quality_issue | delivery_issue | other
  detail: 0..300 字符
```

约束：

- `refund_request` 可以暂时缺少 `order_id` 或 `refund_reason`，供多轮补充。
- 非退款意图不能携带 `refund_reason`。
- `other` 必须携带非空 `detail`；其他代码的 detail 可选。
- 模型没有资格、金额、币种、渠道、审批结果、风险或幂等字段。
- `InterpretationContext` 只增加最小 `pending_refund_request`，不发送支付、退款或完整
  Checkpoint 给模型。

### 6.2 Mock 支付模型

```text
MockPayment
  payment_id
  order_id
  amount_minor: int > 0
  currency: CNY
  channel: mock_card | mock_wallet
  status: pending | settled | failed | refunded
  created_at / updated_at
```

公开 API 使用形如 `"129.90"` 的十进制定点字符串。服务端校验最多两位小数后转换为
`amount_minor=12990`；数据库、Policy、Gateway、State 和 Eval 只使用整数金额。

### 6.3 退款上下文与 Policy 结果

```text
RefundContext
  order
  shipment | null
  payment | null
  active_or_completed_refunds[]

RefundEligibility
  eligible: bool
  reason_code
  refundable_amount_minor
  currency | null
  channel | null
  policy_fact_ids[]
  citations[]

RefundPreview
  action_id
  task_id
  order_id
  reason
  amount_minor / display_amount
  currency / channel
  order_status / shipment_status / payment_status
  risk: R2
  policy_fact_ids / citations
  policy_version
  facts_fingerprint
```

所有模型使用 `frozen=True`、`extra="forbid"`。公开模型不包含内部主键、工作区 ID、
数据库错误或绝对路径。

### 6.4 动作与结果状态

```text
RefundActionStatus:
  awaiting_approval | rejected | stale | executing |
  completed | failed | unknown | verification_failed

RefundStatus:
  processing | succeeded | failed | unknown

RefundExecutionOutcome:
  succeeded | business_rejected | failed_before_write |
  result_unknown | verification_mismatch
```

`task_id` 在 v0.4 等于服务端已授权 conversation `thread_id`；`action_id` 是在纯节点中
生成并先写入 Checkpoint 的随机 UUID。服务端以 `action_id` 派生稳定幂等键，浏览器和
模型均不能提供或覆盖幂等键。

## 7. 业务数据库与迁移

新增 migration：

```text
migrations/versions/20260717_0002_v04_refund_schema.py
down_revision = 20260717_0001_v03_business_schema
```

只增加新表和索引，不修改现有订单、物流、账号或 conversation 列。已有订单不会自动
生成支付记录；用户必须显式维护 Mock 支付后才能获得可执行预览。

### 7.1 `mock_payments`

```text
id                  UUID，主键
workspace_id        当前私有工作区，索引
order_pk            orders.id，唯一
amount_minor        正整数
currency            CNY
channel             mock_card | mock_wallet
status              pending | settled | failed | refunded
created_at
updated_at
```

约束：

- 一个订单最多一笔原始 Mock 支付。
- `workspace_id` 必须与订单一致，Repository 在事务内验证。
- 退款成功后支付状态变为 `refunded`。
- 已有 `completed` 或 `unknown` 退款后不能修改支付事实。
- 修改订单、物流或支付事实时，如果存在 `awaiting_approval` 动作，业务事务同时把该动作
  标记为 `stale`；政策索引变化则在恢复、查询 pending preview 或新建动作时重新校验。
- 订单存在支付、退款动作或退款记录时，订单删除返回 `409 order_has_transaction_data`，
  不使用级联删除破坏审计。

### 7.2 `refund_actions`

```text
action_id            UUID，主键
task_id              conversation thread_id
subject_id
user_id
workspace_id
order_pk
payment_id
reason_code
reason_detail
amount_minor
currency
channel
policy_version
policy_fact_ids_json 仅保存受控 fact IDs
facts_fingerprint
preview_hash
idempotency_key      服务端产生，唯一
status
created_at
decided_at | null
updated_at
```

`refund_actions` 保存服务端审批绑定和状态，不保存密码、Cookie、API Key、Prompt、隐藏推理
或完整政策原文。

SQLite partial unique index 保证同一 `order_pk` 在
`awaiting_approval | executing | unknown | completed` 状态下最多存在一个动作。`rejected`、
`stale` 或确定失败后可以创建新动作；已完成整单退款仍由完成动作和退款余额共同阻止重开。

### 7.3 `mock_refunds`

```text
refund_id            MOCK-RFD- 前缀的本地标识，主键
action_id            refund_actions.action_id，唯一
payment_id
workspace_id
order_pk
idempotency_key      唯一
amount_minor
currency
channel
status               processing | succeeded | failed | unknown
gateway_result_code
created_at
updated_at
```

同一 `payment_id` 在 `processing | succeeded | unknown` 状态下最多一条记录。重复执行同一
幂等键必须读取并返回原记录，不能插入第二行。

### 7.4 `refund_audit_events`

```text
id
action_id
event_key            同一动作内稳定且唯一
event_type           previewed | approved | rejected | stale |
                     execution_started | gateway_result | verified
actor_id
result_code
preview_hash
created_at
```

审计表只保存脱敏、有限字段，不保存用户完整原话或模型推理。退款事务需要记录的业务事件
与动作状态在同一 `business.sqlite` 事务中提交，避免出现“业务已写入但关键动作状态丢失”。
审计使用独立表和 Repository 方法，不能作为退款完成的事实来源；Eval 报告继续保存在
`docs/eval/`，Checkpoint 和 RAG 索引仍为独立数据库。

### 7.5 指纹与预览绑定

`facts_fingerprint` 使用稳定 JSON 序列化后计算 SHA-256，至少覆盖：

- 工作区、订单标识和订单状态。
- 物流状态与最近事件。
- 支付标识、金额、币种、渠道和状态。
- 现有退款的标识、金额和状态。
- 退款原因。
- 已选择的政策 fact ID、内容哈希、corpus version 和 corpus hash。

`preview_hash` 再覆盖公开预览内容、`task_id` 和 `action_id`。批准前重新生成
`facts_fingerprint`；任何影响资格、金额、渠道或政策的变化都会使旧动作进入 `stale`，
不能执行。

## 8. 确定性 Refund Policy 与 RAG 边界

### 8.1 v0.4 状态矩阵

v0.4 只模拟发货前或已取消订单的直接整单退款：

| 订单/物流 | 支付 | 其他条件 | 结果 |
|---|---|---|---|
| `processing`，无物流或 `preparing` | `settled` | 无活动/完成退款，余额等于原支付 | 可预览 |
| `cancelled`，无物流或 `preparing` | `settled` | 无活动/完成退款，余额等于原支付 | 可预览 |
| `shipped` 或物流 `in_transit` | 任意 | 需要退货/逆向物流 | v0.4 不可直接退款 |
| `delivered` 或物流 `delivered` | 任意 | 需要退货资格和入库流程 | v0.4 不可直接退款 |
| 任意 | `pending` / `failed` / 缺失 | 未形成可退支付事实 | 不可退款 |
| 任意 | `refunded` 或余额为零 | 已无可退余额 | 不可退款 |
| 任意 | `processing` / `unknown` / `succeeded` 退款已存在 | 存在冲突动作 | 不创建新动作 |
| 订单与物流状态互相矛盾 | 任意 | 业务事实冲突 | 安全失败 |

退款原因在 v0.4 用于预览、审计和后续人工语义，不改变金额。任何原因都不能绕过状态、
支付、余额、政策或审批规则。

### 8.2 政策语料更新

退款政策增加一个明确的“直接整单退款资格”章节，并在 manifest 中增加受控事实，例如：

```text
refund.eligibility.pre_fulfillment
refund.method.original
refund.process.application
```

语料 `corpus_version` 升级，重新构建可重建索引。资格节点使用固定 topic/aspect 和受控
fact ID 解析当前有效事实，不把用户检索词或 LLM 置信度作为授权输入。

`RefundPolicy` 是纯 Python 服务：它接收 `RefundContext` 和已解析、内容哈希有效的
`PolicyFact`，输出 `RefundEligibility`。若所需事实缺失、冲突、过期或无法解析，则不生成
可执行预览。

RAG 只提供：

- 当前规则的版本与可定位来源。
- 对资格、原路退款和审批流程的用户解释。

RAG 不提供：

- 最终资格布尔值。
- 金额、余额、币种或渠道。
- 审批决定或 Gateway 参数。

## 9. Gateway 契约与幂等事务

### 9.1 `RefundQueryGateway`

```text
get_refund_context(scope, order_id) -> RefundContext | unavailable
get_action(scope, task_id, action_id) -> RefundAction | unavailable
get_refund_by_action(scope, action_id) -> MockRefund | unavailable
```

每次调用都重新校验 `BusinessScope`，不因为前一个节点已经查过订单而省略归属验证。

### 9.2 `RefundCommandGateway`

```text
reserve_preview(scope, preview_draft) -> RefundActionResult
reject_action(scope, task_id, action_id, preview_hash) -> RefundActionResult
execute_refund(scope, task_id, action_id, expected_fingerprint) -> RefundExecutionResult
mark_stale(scope, task_id, action_id, expected_preview_hash) -> RefundActionResult
```

每个方法职责单一、输入结构化、同步执行并返回有限错误码。实现不能接收整段 Prompt 或
客户端提供的金额、渠道、Policy 版本和幂等键。

### 9.3 `reserve_preview` 幂等语义

- `action_id` 在前一个纯节点产生并进入 Checkpoint，Gateway 只接收稳定 ID。
- 相同 `action_id + preview_hash` 重放时返回原动作。
- 相同 `action_id` 但内容不同视为冲突，不覆盖原动作。
- 同一订单已有活动或完成动作时不创建新动作。
- 如果已有 `awaiting_approval` 动作的当前事实指纹已失效，事务先将旧动作标记为 `stale`，
  再允许新的服务端预览使用新 `action_id`；不能静默复用旧批准。
- 创建动作只记录待审批预览，不插入 `mock_refunds`，不修改支付状态。

### 9.4 `execute_refund` 原子事务

事务内必须按顺序完成：

1. 按作用域、task 和 action 锁定/读取待审批动作。
2. 检查动作状态和 `expected_fingerprint`。
3. 按幂等键查找已有 `mock_refunds`；存在则返回原结果。
4. 重新读取订单、物流、支付和冲突退款，并再次计算数据库事实指纹。
5. 指纹不同则将动作标记为 `stale`，不写退款。
6. 插入或更新同一幂等退款记录。
7. 成功时把支付状态更新为 `refunded`，动作更新为 `completed`。
8. 写入稳定 `event_key` 的最小审计事件。
9. 一次提交；任何约束冲突映射为稳定领域结果。

SQLite 的唯一约束是跨 thread 最终防线；进程内 thread 锁只减少同一 thread 的重复工作，
不能代替数据库约束。

### 9.5 未知结果和失败注入

生产本地 SQLite 实现只做确定性 Mock 写入。测试用 `FakeRefundGateway` 可配置：

```text
success
business_rejected
fail_before_write
unknown_after_write
verification_mismatch
```

遇到 `unknown_after_write` 时，Graph 首先按幂等键或 action 查询已有退款：

- 已找到并验证成功：恢复为完成。
- 找到但状态未知：保持 `refund_result_unknown`，不再插入。
- 未找到：保持未知并允许显式恢复检查，不自动创建新退款。

Gateway 业务拒绝和技术失败不得被模型改写为成功。

## 10. LangGraph State 与兼容

在现有 `AgentState` 上只增加可选字段：

```text
pending_refund_request
refund_reason
refund_action_id
refund_preview
refund_policy_fact_ids
refund_citations
refund_result
refund_verification
```

公开 `status` 增加：

```text
awaiting_refund_context
refund_ineligible
refund_awaiting_approval
refund_rejected
refund_preview_stale
refund_conflict
refund_completed
refund_failed
refund_result_unknown
refund_verification_failed
```

兼容规则：

- 不重命名已有 State 字段、Reducer 或节点。
- 新字段全部可选，旧 v0.1–v0.3 Checkpoint 可继续读取。
- State 只保存 `action_id`、小型公开预览和验证摘要，不保存支付/退款表副本或完整政策原文。
- 新对话轮次清理上一轮临时查询结果，但不能清理尚未决定的退款中断。
- thread 处于退款中断时，普通 Chat 消息返回 `409 refund_approval_required`，不能把新消息
  当作 `Command(resume=...)`。
- 恢复节点使用当前可信 `RunContext` 再次验证用户和工作区。

## 11. 图结构与节点职责

退款节点放入新的 `refund_workflow.py`，采用与 `PolicyNodes` 相同的节点类和注册函数，
避免继续扩大 `build_workflow()` 的内嵌闭包数量，但仍编译为同一张图，不使用子图。

```text
START
  -> bind_and_interpret
  -> route_request
       ├─ 既有订单 / 政策 / unsupported 路径
       └─ refund_request
            -> prepare_refund_request
                 ├─ 缺 order_id 或 reason
                 │    -> request_refund_context -> END
                 └─ 信息完整
                      -> load_refund_context
                      -> load_refund_policy
                      -> assess_refund
                           ├─ missing / conflict / ineligible
                           │    -> respond_refund_ineligible -> END
                           └─ eligible
                                -> build_refund_preview       # 纯节点，生成 action_id
                                -> reserve_refund_action      # 幂等保存待审批动作
                                -> await_refund_approval
                                     └─ interrupt(preview)

Command(resume=decision)
  -> await_refund_approval 从节点开头恢复
       ├─ reject
       │    -> reject_refund_action
       │    -> respond_refund_rejected -> END
       └─ approve
            -> revalidate_refund
                 ├─ stale / ineligible
                 │    -> mark_refund_stale
                 │    -> respond_refund_stale -> END
                 └─ valid
                      -> execute_refund
                      -> verify_refund
                           ├─ verified -> respond_refund_completed -> END
                           ├─ unknown  -> respond_refund_unknown -> END
                           └─ mismatch -> respond_refund_failure -> END
```

关键节点语义：

- `build_refund_preview` 是纯节点。它先生成稳定 `action_id` 并让 LangGraph 完成该步
  Checkpoint，后续外部写入重放时仍使用同一 ID。
- `reserve_refund_action` 是幂等业务写；崩溃发生在写入后、节点 Checkpoint 前时，重放只
  返回原动作。
- `await_refund_approval` 在 `interrupt` 前不执行任何非幂等副作用。恢复时节点从开头
  重跑，`Command` 只决定去拒绝或重新验证。
- `revalidate_refund` 不信任旧 State，重新读取业务库和政策索引。
- `verify_refund` 使用新的 Repository 读取结果，不能复用 Gateway 的成功返回值自证。

`await_refund_approval` 返回类型显式限制为：

```text
Command[Literal["reject_refund_action", "revalidate_refund"]]
```

该节点不再额外配置普通边或条件边，避免 `Command(goto=...)` 与静态边同时触发。

## 12. 审批、恢复与 LLM 配额

### 12.1 第一次请求

`POST /api/chat/messages` 继续执行：

1. Session、CSRF、Origin、速率限制。
2. conversation 归属验证。
3. 获取当前 thread 锁。
4. 查询当前 thread 是否存在待审批退款动作；存在则在 LLM 配额和 Checkpoint 前返回
   `409 refund_approval_required`。
5. 注册用户模型权限与 LLM 配额扣减。
6. Graph 首次 `invoke()`。
7. `get_state()` 读取暂停后的公开预览和中断。

生成预览后接口正常返回 `200` 和 `refund_awaiting_approval`，不把业务暂停当作异常。

### 12.2 恢复请求

审批使用独立接口，先验证 conversation 和 action 归属，再打开 Checkpoint：

```text
POST /api/conversations/{thread_id}/refund-approval
body: { action_id, decision: approve | reject }
```

服务端构造：

```text
Command(resume={action_id, decision, actor_id})
```

客户端不能提交订单、金额、币种、渠道、reason、Policy 版本或幂等键。

恢复路径不调用 `_registered_dependencies()`，不检查或消耗新的 LLM 配额。它使用注册用户
业务 Gateway、PolicyRepository 和一个“被调用即失败”的 Interpreter sentinel 重新编译
同一张图；正常恢复应从中断节点继续，测试断言 Interpreter 调用为 `0`。

### 12.3 页面关闭后的恢复

新增：

```text
GET /api/conversations/{thread_id}/pending-refund
```

接口先授权 conversation，再比对业务动作与 `StateSnapshot.interrupts` 中的 `action_id` 和
`preview_hash`。只返回当前用户可见的待审批预览；不存在、已结束或越权统一使用安全
语义，不泄露其他用户内容。

### 12.4 重复决定

- 相同 action 重复批准：返回同一笔已验证退款，HTTP `200`。
- 相同 action 重复拒绝：返回相同拒绝终态，HTTP `200`。
- 拒绝后再批准或批准后再拒绝：`409 refund_action_closed`。
- stale action：`409 refund_preview_stale`。
- action 与 thread/用户/工作区不匹配：统一 `404 refund_action_not_accessible`。

## 13. Web API 与公开响应

### 13.1 支付事实管理

注册用户 Orders 页面增加确定性接口：

```text
PUT /api/orders/{order_id}/payment
GET /api/orders/{order_id}/refunds
```

支付请求只允许：

```text
amount: "129.90"
currency: CNY
channel: mock_card | mock_wallet
status: pending | settled | failed
```

没有“直接设为 refunded”的管理接口。退款状态只能由 Refund Gateway 改变。游客、跨工作区
和存在完成/未知退款后的修改请求均无副作用。

`PublicOrder` 增加可选 `payment` 和只读 `refunds` 摘要；现有没有支付的订单仍能按 v0.3
Schema 正常返回。

### 13.2 Chat 公开模型

`ChatResponse` 增加可选：

```text
refund_preview
refund_result
```

不引入任意字典或通用 action payload。退款预览包含 UI 所需字段和引用，不包含内部主键、
幂等键或工作区信息。

`SessionCapabilities` 增加服务端计算的 `can_manage_refunds`；游客为 `false`，注册用户为
`true`。该字段只控制前端展示，实际授权仍由每个 API 请求重新判断。

### 13.3 稳定错误与状态

| 情况 | HTTP / public status | 副作用 |
|---|---|---|
| 缺订单号或原因 | `200 awaiting_refund_context` | 0 |
| 缺支付事实 | `200 refund_ineligible` | 0 |
| 状态/政策不满足 | `200 refund_ineligible` | 0 |
| 等待审批 | `200 refund_awaiting_approval` | 仅待审批 action |
| 用户拒绝 | `200 refund_rejected` | 无退款记录 |
| 旧预览失效 | `409 refund_preview_stale` | 无退款记录 |
| 已有活动/完成退款 | `409 refund_conflict` 或返回既有结果 | 无重复记录 |
| 执行并验证成功 | `200 refund_completed` | 一笔 Mock 退款 |
| Gateway 业务拒绝 | `200 refund_failed` | 无成功退款 |
| 结果未知 | `202 refund_result_unknown` | 不盲目重试 |
| 验证不一致 | `503 refund_verification_failed` | 不声明成功 |
| conversation/action 越权 | `404 *_not_accessible` | 0 |
| thread 正在等待审批却发送新消息 | `409 refund_approval_required` | 0，LLM 调用 0 |

业务不符合资格使用 `200`，因为请求已正确处理；身份、资源冲突和技术失败才使用相应
HTTP 错误。错误响应继续通过现有 `ErrorResponse` 和通用非泄露文案返回。

## 14. 前端交互

### 14.1 Orders 页面

- 注册用户为订单维护一笔 Mock 支付。
- 金额输入按两位小数显示，提交字符串，不使用 JavaScript 浮点计算退款额。
- 显示支付状态、渠道以及只读退款记录。
- 已退款或结果未知时禁用支付编辑，并以服务端能力/错误为准。

### 14.2 Chat 页面

- 普通聊天行为和现有客户端打字机效果保持不变。
- `refund_awaiting_approval` 使用结构化 `RefundApprovalCard` 展示订单、原因、金额、币种、
  渠道、关键状态、R2 风险和政策引用。
- “批准”和“拒绝”分别发送独立 mutation；按钮提交后立即禁用，防止重复点击，但服务端
  幂等仍是最终保证。
- 待审批时禁用普通消息输入，避免把新消息误当恢复决定。
- 页面加载时按当前 thread 调用 pending-refund API，支持关闭页面后恢复预览。
- pending-refund 读取当前事实后若发现预览已失效，返回 stale 状态而不是继续展示可批准
  按钮；业务事实维护事务也会主动使对应动作失效。
- 不做退款成功的乐观更新；必须展示服务端验证后的结果。
- 业务拒绝、过期、未知和验证失败使用普通对话/状态卡，不把可预期业务结果渲染成前端
  崩溃式红色错误。

OpenAPI 是前后端契约事实来源。后端 Schema 完成后重新导出 OpenAPI 并生成
`frontend/src/api/generated.ts`，不手写重复接口类型。

## 15. 安全与审计

### 15.1 授权顺序

所有退款读写请求必须按固定顺序：

```text
解析有效 Session
  -> require_mutation_access / CSRF / Origin
  -> conversation 归属
  -> action 的 subject / user / workspace / task 绑定
  -> thread 锁
  -> Checkpoint
  -> Gateway
```

未通过前一步时不读取后一步的敏感数据。游客请求在业务 Gateway 前被拒绝，真实 LLM 和
退款写方法调用均为 `0`。

### 15.2 Prompt Injection 与参数篡改

- 用户退款原因和政策正文均作为数据，不改变系统指令。
- Interpreter Schema 不包含资格、金额、渠道、审批或幂等字段。
- Refund Policy 只读取领域模型和已验证事实。
- 审批请求 `extra="forbid"`；额外金额、工作区、模型模式等字段直接拒绝。
- 公开预览中的 action ID 只是引用，不构成授权。

### 15.3 审计事件

至少记录：

- previewed：task/action、脱敏订单、风险、Policy 版本和 preview hash。
- approved/rejected：可信 actor、决定和时间。
- stale：旧/新 facts fingerprint 的摘要，不记录完整业务正文。
- gateway_result：稳定 result code 和耗时。
- verified：验证状态、refund ID 和金额摘要。

日志不记录 Cookie、CSRF Token、API Key、密码、完整 Prompt 或模型隐藏推理。

## 17. 测试策略

### 17.1 纯规则与 Schema

- 金额字符串与 minor units 双向转换，不接受负数、三位小数、指数、NaN 或超限金额。
- 退款原因枚举、`other` detail 和 Interpreter 字段互斥。
- 状态矩阵全部分支、支付缺失、余额为零和业务事实冲突。
- Policy fact 缺失、冲突、过期和 hash 失效。
- canonical JSON 与 fingerprint 对字段顺序稳定、对实质变化敏感。

### 17.2 Repository 与迁移

- 从 v0.3 head 升级后旧账号、订单、物流和 conversation 保留。
- 一订单一支付、金额约束和作用域隔离。
- 支付/动作/退款存在时订单删除被阻止。
- `reserve_preview` 重放返回原动作，内容冲突被拒绝。
- 同幂等键重复执行只产生一笔退款。
- 不同 thread 对同一订单竞争时唯一约束生效。
- 支付状态、动作状态、退款和关键审计事件在同一事务中一致。

### 17.3 Graph

- 缺订单号、缺原因和多轮补充。
- 不符合资格时无 action/refund 写入。
- 预览后 `StateSnapshot.next` 指向等待审批节点并含一个 interrupt。
- 拒绝后 Gateway 执行调用为零。
- 批准前重新校验，旧预览进入 stale。
- 成功、业务拒绝、执行前失败、unknown 和 verification mismatch。
- 节点重放、跨 Graph/SQLite 连接恢复和旧 Checkpoint 兼容。
- 审批 `Command(resume=...)` 不调用 Interpreter。

### 17.4 Web 安全与集成

- 游客退款请求、支付管理和审批均无业务写入、无 LLM 调用。
- 用户 A 不能读取或批准用户 B 的 action/thread/order。
- 伪造金额、渠道、工作区、用户、Policy 版本和幂等键被严格 Schema 拒绝。
- Session 过期、CSRF 错误、Origin 错误、thread busy 和 action closed。
- 发送新消息到待审批 thread 返回 `refund_approval_required`，不扣 LLM 配额。
- 重复批准和 HTTP 重试返回相同退款。
- 服务重启后 pending GET 和审批恢复成功。

### 17.5 前端与浏览器

- 支付表单金额、渠道、状态及 API 错误。
- Preview Card 展示全部不可编辑字段和政策引用。
- 按钮重复点击只发起一次前端 mutation；服务端测试仍覆盖真正幂等。
- 待审批时禁用消息输入，拒绝/批准后恢复。
- 刷新页面后恢复待审批预览。
- 成功只在服务端 verified 结果后展示。
- 游客界面不展示支付或退款管理入口。

## 18. v0.4 Eval

`RefundEvalScenario` 至少记录：

```text
scenario_id
category
principal / workspace / thread
messages[]
order / shipment / payment / existing_refunds fixture
policy_fixture / as_of
decision | none
gateway_mode
expected_intent / status / reason_code
expected_preview
expected_gateway_calls
expected_refund_count
expected_audit_events
cross_process / repeated / concurrent
```

至少 24 个固定场景按 Spec 分组：

- 4 个正常预览、批准和验证。
- 5 个未支付、状态不允许、政策不满足、余额为零和已有退款。
- 4 个拒绝、关闭页面、跨进程恢复和过期预览。
- 4 个重复批准、HTTP 重试、节点重放和跨 thread 并发。
- 4 个游客、跨用户、参数篡改和失效 Session。
- 3 个 Gateway 失败、结果未知、验证不一致或 Prompt Injection。

指标：

- 固定场景通过率。
- 资格、金额、渠道和工具参数正确率。
- 未批准退款数、重复退款数和越权退款数。
- stale preview 阻断率和恢复幂等率。
- Gateway 调用数、验证成功率和安全错误语义。
- 政策 fact/citation 可解析率。
- Interpreter 调用与 LLM 配额变化。
- 诊断性步骤数和耗时；v0.4 不设性能 SLA。

Eval 使用 Fake Interpreter、固定日期、临时业务/Checkpoint/政策数据库和可配置 Fake
Refund Gateway。真实 DeepSeek 只验证退款结构化意图，不执行任何不同的业务路径，也不计入
发布门槛。

## 22. 兼容与迁移

- v0.4 migration 只增加表和索引；已有 v0.3 业务数据无需重建。
- 旧订单没有支付时仍可查询，只是在退款路径中返回缺少 Mock 支付事实。
- AgentState 只增加可选字段；旧 Checkpoint 不迁移。
- 现有节点名称、订单/政策状态和 `messages` / `audit` Reducer 不变。
- 政策索引升级 corpus version，属于可重建派生数据；运行 migration 后必须重新执行
  `policy-index build`。
- OpenAPI 增加可选响应字段和新路径；现有 v0.3 请求字段不变。
- 支付或退款事实存在后，删除订单从原来的成功变为明确 `409`；这是保护交易与审计事实的
  有意收紧，必须更新 Web 测试和说明。

回滚应用代码前必须先确认数据库中没有 v0.4 动作/退款数据；Alembic downgrade 只用于
本地开发，不能在有审计需求时静默删除交易表。

## 23. 风险与缓解

| 风险 | 缓解 |
|---|---|
| `interrupt` 恢复时节点从开头重跑 | 中断前无非幂等副作用；action/退款方法均以稳定 ID 幂等 |
| 批准时重复调用 LLM | 独立恢复依赖和 Interpreter sentinel；测试配额不变 |
| 客户端篡改退款参数 | 审批 body 只接受 action_id/decision，执行参数全部从服务端 action 读取 |
| 预览与执行间业务事实变化 | fingerprint + 执行事务内重新读取与唯一约束 |
| SQLite 并发竞争 | WAL/busy timeout、短事务、partial unique index、冲突映射 |
| Gateway 写入后响应丢失 | 幂等键查询既有结果，unknown 状态不盲目重试 |
| Gateway 自报成功但数据不一致 | 独立 Verifier 新 session 回读，失败不声明完成 |
| RAG 结果被当作授权 | RefundPolicy 纯函数做最终资格；RAG 仅提供当前受控事实与引用 |
| 金额舍入或浮点误差 | API 定点字符串、内部整数 minor units、禁止 float |
| 老订单删除破坏交易记录 | 事务数据存在时显式阻止删除 |
| 单文件继续膨胀 | RefundNodes、规则和 SQLite 事务按明确职责拆分，不引入微服务 |
| 前端重复点击 | 按钮禁用只是体验；数据库唯一约束和幂等键提供最终保证 |

## 24. ADR 判断

本 Plan 不新增 ADR：

- Mock/Fake 外部边界已经由 ADR-0005 接受。
- SQLite、LangGraph、服务端访问模式和同源 Web 已由 ADR-0001 至 ADR-0004 决定。
- 本 Plan 中的表、节点、API 和页面是 v0.4 范围内可演进实现细节。

如果实施中需要接入真实支付/Sandbox、引入队列或 Worker、改变为多角色审批、把审计迁到
独立服务，必须先新增 ADR，而不是在任务中静默扩大范围。

## 25. 非目标确认

v0.4 不实现：

- 真实支付、电商、物流或客服系统。
- 部分退款、组合支付、多币种、优惠券、税费或运费分摊。
- 退货入库、逆向物流或自动取消订单。
- 自动审批、角色矩阵或多级审批。
- 人工客服 Handoff。
- 动态 Agent Loop、多 Agent 或后台自治任务。
- Token 级 SSE、WebSocket 或消息队列。
- 生产多实例、高并发、对账、通知和灾难恢复。

## 26. 实施结果

T1–T6 已按顺序完成。最终实现保持以下边界：

1. Mock 支付、待审批动作、退款和审计使用业务数据库；Checkpoint 只保存 Graph 状态。
2. 金额使用整数分，资格状态矩阵、余额、原路渠道和风险均由确定性代码生成。
3. 预览通过 `interrupt` 暂停；拒绝零退款，批准前重读业务与政策并校验指纹。
4. 执行事务使用稳定 action 标识、唯一约束和幂等回查；只有独立验证通过才声明完成。
5. Web 绑定 Session、工作区、thread 和 action，前端只能提交批准或拒绝决定。
6. 固定退款 Eval `24/24`，v0.1–v0.3 全部回归，浏览器与真实模型冒烟通过。

完整复现结果见 [`../eval/v0.4-report.md`](../eval/v0.4-report.md)。下一版本不得从本 Plan
继续追加 Handoff 或 Agent Loop；应先创建并接受独立 v0.5 Feature Spec。
