## 结论

v1.3 T1–T8 已实现并通过当前 macOS 本机产品验收。客户售后中心现在使用版本化商品与场景、
订单商品快照、多包裹履约、统一状态与金额表达；上下文助手可以在一轮结构化解释后组合查询
订单、物流和政策，并持久化公开的 `ServiceResolution`。

确定性产品门禁全部通过，固定 Release Gate 为 `19/20`。唯一未完成项是当前机器没有 Docker，
`docker-compose-config` 按设计返回 `incomplete: docker_unavailable`。

真实 Provider Qualification 已执行，但当前 DeepSeek 模型与 Prompt 组合只通过 `10/24`
双轮任务，状态为 `incomplete`。因此本报告不把本机产品验收描述为版本 Completed，也不接受
真实 Provider Prompt 资格。

## 产品结果

- 受控目录包含 12 个 SPU、19 个 SKU、3 类客户画像和 10 个订单/服务场景。
- 12 张本地商品主图、fallback 和资源 Manifest 具有稳定 ID、替代文本、SHA-256 与生成记录。
- CLI 与管理员页面可以为显式目标客户幂等初始化场景；页面读取和应用启动不会自动写数据。
- 新订单保存商品名称、规格、数量、单价、图片引用和目录版本快照；目录变化不改写历史订单。
- 订单详情可以表达单包裹、多包裹、部分履约、未发货和历史无快照状态。
- 售后首页、订单列表、订单详情、服务列表和服务详情复用统一商品、状态、金额和履约组件。
- 订单列表支持服务端订单号/商品搜索、状态筛选、稳定游标和 URL 状态。
- `service_guidance` 组合咨询至多各查询一次订单、物流和政策，随后由确定性代码装配公开方案。
- `request_refund` 仍只是候选动作，资格、金额、审批、执行和验证继续复用 v0.4 退款链。
- Payload v1 保持可读；Payload v2 可以恢复结构化方案；未知版本只降级显示纯文本。
- 管理员、客户和游客权限继续由服务端判定，测试显式选择目标客户，不依赖列表顺序。

## 安全与兼容边界

- 游客使用同一版本目录的只读演示投影，真实 Provider 调用为 `0`。
- 客户和游客不能调用管理员目录或 Seed API，跨客户写入和数据泄露为 `0`。
- 商品快照金额不参与退款执行金额计算；退款仍以 Mock 支付事实为准。
- 组合咨询不会创建退款动作，未经审批退款和重复退款均为 `0`。
- Payload v1、旧订单、旧服务、旧 Checkpoint 和 Pending Action 继续可读。
- 客户 DOM 不公开 Prompt、内部节点、原始工具输出、Key、Token 或隐藏推理。
- 所有商品资源均为仓库内本地文件，不使用远程热链。

## 已知限制

- 真实 Provider Qualification 未达门槛，受邀用户的 LLM 组合咨询质量尚不能标记为合格。
- 当前验收机没有 Docker，参考镜像、Compose 生命周期和容器故障注入仍未取得证据。
- `npm audit` 报告 3 个 High，均沿开发期 `openapi-typescript → @redocly/openapi-core → js-yaml`
  依赖链产生；当前只解析本地生成的 JSON OpenAPI，不接收不可信 YAML。上游给出的修复是
  `openapi-typescript` 主版本降级，未在本次收口中强制执行，需作为独立依赖升级任务验证。
- 商品目录是演示模板，不是商品中心；不提供库存、促销、购物车、结算或运行时商品 CRUD。
- 多模态政策、文件上传、OCR、向量数据库和混合检索仅存在于 v1.4 Proposed Spec，未实现。
- 所有订单、物流、支付和退款仍为本地 Mock 数据，不连接真实外部系统。
