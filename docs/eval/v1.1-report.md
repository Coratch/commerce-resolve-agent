# v1.1 订单优先售后中心验收报告

状态：Candidate

版本：`1.1.0`

## 结论

v1.1 T1–T8 已实现并通过当前 macOS 本机验收。订单优先入口、可信订单绑定、只读服务投影、
上下文助手、移动交互、升级兼容和离线 Eval 均取得可复现证据。

固定 Release Gate 已执行并得到 `19/20`；当前机器未安装 Docker，`docker-compose-config` 按设计
返回 `incomplete: docker_unavailable`。参考 Ubuntu 24.04 + Docker Compose 的镜像构建、容器
生命周期和故障注入仍未执行，因此版本保持 Candidate，不标记 Completed，也不宣称可生产部署。

## 产品结果

- `/` 稳定跳转 `/support`，页面读取最近订单、进行中服务和常用动作，不自动创建 Conversation。
- `/orders` 与 `/orders/:orderId` 展示服务端权威订单、可选商品行、物流里程碑和可用动作。
- `/services` 与 `/services/:serviceId` 展示 Refund/L2 既有事实的只读客户投影，并复用原会话。
- 桌面使用页内助手，移动使用原生 `<dialog>`；只有用户明确打开助手时才创建或复用订单绑定会话。
- 发过消息或存在 Pending Action 的同订单活动会话在刷新后继续复用，不退回新的空白对话。
- 绑定订单后的“它到哪里了”由服务端可信上下文补全；显式冲突在模型和业务工具前终止。
- `/chat` 与 `/chat/:threadId` 保持兼容，既有消息、审批、SSE 和恢复协议未改变。

## 安全与数据边界

- Support GET 只读，不运行 Graph、模型或业务写入。
- 游客只读取共享演示目录，注册客户查询使用完整 subject/user/workspace 作用域。
- 消息请求不接受订单绑定字段；Conversation 创建时验证订单，绑定创建后不可重绑。
- 订单冲突在 Interpreter 和业务 Gateway 前停止。
- 服务记录不具有写 Repository，删除投影代码不会删除 Refund、L2 Case、Conversation 或审计事实。
- 客户 UI 不执行消息 HTML，也不公开 Context Manifest、内部节点、工具参数、Token 或 Eval 指标。
- Mock 退款仍只走原确定性 Policy、interrupt 审批、幂等执行和回读验证链路。

## 升级证据

代表性测试先创建当前 Schema 数据，再降级为 v1.0 的 `20260721_0005`，随后升级到
`20260722_0006`。升级后既有订单和 Conversation 计数保持不变；旧订单返回 `items=[]`，旧会话
返回 `related_order_id=null`，不补造商品或绑定事实。

`data_format_version` 保持 `commerce-resolve-data-v1`，因为本次只增加可空字段和新表，没有改变
既有数据库文件角色或恢复语义。

## 已知限制

- 所有订单、物流、支付、退款和 L2 Case 均为本地 Mock/Fake，不连接真实外部系统。
- 商品行只有 SKU、名称、数量和政策类别，不参与退款金额计算。
- 服务时间线是现有业务事实的有限公开投影，不是完整工单或客服坐席系统。
- Provider Token 级流式、部分退款、逆向物流、真实人工客服、多实例和高可用均不在 v1.1 范围。
- 参考 Docker Gate 已在本机按预期报告不可用，仍待在支持环境完成；在此之前不能把 Candidate
  提升为 Completed。
