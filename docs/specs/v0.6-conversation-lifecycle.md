# Feature Spec：v0.6 会话生命周期、历史恢复与可恢复交互

状态：Accepted  
日期：2026-07-21  
接受日期：2026-07-21  
依赖版本：v0.5 LLM 二线客服 Agent Harness

## 目标

用户可以把一次售后对话视为稳定、可继续的产品对象，而不是依赖当前 React 页面内存的
临时内容。页面刷新、站内路由切换、重新登录或短暂断线后，系统恢复本人有权访问的公开
聊天记录、当前处理状态以及待确认动作；用户也可以显式创建、选择、归档和删除会话。

本版本补齐“用户看到了什么”和“Agent 如何恢复”之间的产品断层：公开聊天记录用于展示
和管理，LangGraph Checkpoint 继续用于工作流状态、暂停和恢复，长期记忆继续由独立 Store
管理。三者不能互相冒充。

## 第一性原则

1. 用户看到的会话记录属于产品数据，刷新页面不能使其消失。
2. 同一售后任务应继续同一会话；页面导航、网络错误和模型失败都不是自动新建会话的理由。
3. Checkpoint 是 Agent 运行状态，不是面向用户的消息查询模型。
4. 用户只应看到公开消息、引用和动作卡片，不能看到 Prompt、隐藏推理、原始 ToolMessage
   或内部 State。
5. 消息提交、流式重连和客户端重试必须幂等，不能重复触发模型、退款、Case 或记忆写入。
6. 会话删除不能静默删除订单、退款、L2 Case、审计和已确认长期记忆等独立事实。
7. 身份和会话所有权必须由服务端校验；浏览器保存的会话标识不是授权凭据。
8. 先保证单实例下可恢复、可验证的交互，再讨论多实例广播、全文搜索或 PostgreSQL。

## 术语

| 术语 | 含义 |
|---|---|
| Conversation | 一个用户围绕连续售后目标形成的公开对话容器，对应稳定 `thread_id` |
| Public Message | 可以安全展示给用户的用户消息、助手消息或公开状态消息 |
| Agent Run | 接受一条用户消息后产生的一次可跟踪 Agent 执行 |
| Checkpoint | LangGraph 保存的节点状态、消息上下文、中断与恢复点 |
| Pending Action | 等待用户决定或补充的退款、L2 升级、L2 追问或记忆提案 |
| Long-term Memory | 用户明确确认后跨会话保存的稳定低风险偏好 |

“会话历史恢复”表示恢复公开消息和产品状态；“Agent 恢复”表示使用 Checkpoint 继续图执行。
前者不能通过直接向浏览器返回完整 Checkpoint 实现。

## 角色与恢复范围

| 角色 | 会话范围 | 恢复承诺 | 管理能力 |
|---|---|---|---|
| 游客 | 当前服务端匿名 Session | 同一浏览器和有效游客 Session 内恢复当前会话 | 新建当前会话，不承诺账号级历史列表 |
| 受邀用户 | 当前登录账号拥有的会话 | 在同一部署中重新登录后恢复本人会话 | 列表、新建、选择、归档和删除 |
| 其他用户 | 无权访问 | 不返回会话是否存在的额外信息 | 无 |

游客登录或注册后不自动把匿名会话合并到账号。跨身份迁移需要独立 Spec，本版本不隐式复制
消息、Checkpoint 或 Pending Action。

## 用户故事

### 刷新后继续对话

作为用户，我刷新当前聊天页面后仍能按原顺序看到已经公开的消息、引用和动作卡片，并能
继续使用同一个会话，而不是获得一个看似相同但没有上下文的新会话。

### 页面切换后返回

作为用户，我从聊天页切换到订单或记忆页再返回时，仍回到最近选择的有效会话。站内路由
切换不能清空历史或创建空会话。

### 管理多个售后会话

作为注册用户，我可以查看本人会话列表，显式新建一个无旧上下文的会话，选择既有会话，
以及归档或删除已经不再需要的会话。

### 恢复等待中的动作

作为用户，我在退款审批、L2 升级、L2 补充信息或记忆确认期间刷新页面后，仍能看到对应
公开说明和待处理卡片，并且只能继续原动作，不能因刷新重复创建动作。

### 恢复进行中的回复

作为用户，我提交消息后可以看到服务端确认的处理中状态和逐步产生的公开内容。发生短暂
断线或刷新时，页面先恢复已持久化内容，再恢复执行状态；已经完成的内容不会重复，无法
继续的执行会显示可理解的失败或重试结果。

### 安全删除会话

作为注册用户，我可以删除本人无待处理动作的会话。系统必须明确删除范围，不能借删除
聊天记录删除订单、退款、Case、审计或已确认长期记忆。

## 会话边界

以下情况继续原会话：

- 追问同一订单、物流、政策、退款或 L2 Case。
- 页面刷新、前端路由切换、浏览器重新打开或服务重启。
- 模型、网络或数据库发生可恢复失败后重试同一消息。
- 原会话仍有 Pending Action 或运行中的 Agent Run。

以下情况创建新会话：

- 用户显式选择“新对话”。
- 当前身份没有任何可继续会话，且用户提交第一条消息。
- 登录、退出或 Session 轮换导致原会话不再属于当前身份。

系统不根据模型判断、主题变化或订单号变化自动拆分会话。一个独立售后问题是否另开会话
由用户决定；存在待审批动作时不得把后续决定路由到其他会话。

## 公开消息契约

公开历史至少能够表达：

- 用户已被服务端接受的文本消息。
- 助手最终回复和允许展示的渐进内容。
- 政策引用及可定位来源。
- 订单或物流的公开结构化摘要。
- 退款预览与审批结果。
- L2 升级、补充信息、Case 结果和公开 Trace 摘要。
- 记忆提案及用户决定。
- 可安全展示的处理中、失败、取消或重试提示。

每条公开消息必须具有稳定标识、所属会话、角色或公开类型、顺序、创建时间和可观察状态。
客户端重复提交同一条已接受消息时，服务端返回同一结果或当前 Run，而不是追加第二条消息。

以下内容不得进入公开历史响应：

- System Prompt、Developer Prompt 或模型隐藏推理。
- 未脱敏的工具参数、原始 ToolMessage 和完整工具输出。
- API Key、Cookie、CSRF Token、邀请码、密码或数据库内部信息。
- 其他用户、工作区或会话的数据。
- 仅用于内部路由、Reducer、预算或恢复的 State 字段。

技术错误可以转换为普通助手可理解的公开消息，但堆栈、供应商响应、本地路径和内部错误
详情只进入受控日志或审计。

## 会话列表与生命周期

注册用户的会话列表至少展示：

- 稳定会话标识。
- 可理解标题。
- 最近公开消息摘要或空会话状态。
- 最近活动时间。
- 当前是否处理中或等待用户动作。
- 活跃或归档状态。

会话标题不得为了列表展示额外消耗真实 LLM 配额；具体确定性生成和修改策略由 Technical
Plan 决定。列表默认按最近活动排序，并支持按游标或等价方式逐步加载；本版本不要求全文
搜索、标签和文件夹。

生命周期规则：

- 新建：产生新的稳定会话，不继承旧会话消息、Checkpoint、Pending Action 或工作记忆。
- 选择：加载本人有权访问的公开消息和当前状态。
- 归档：从默认活跃列表隐藏，但不删除消息或中断状态。
- 删除：只有不存在运行中 Run 或 Pending Action 时允许；删除公开消息和对应可恢复任务
  状态，但保留依法或业务边界需要独立存在的 Mock 订单、退款、L2 Case 和审计事实。
- 长期记忆：不因归档或删除会话自动删除，用户仍通过独立记忆页面查看、纠正和删除。

空会话不能因每次进入聊天页而无限创建。具体采用首次消息时创建还是显式创建，由 Plan
选择，但最终行为必须可测试且不产生大量无内容记录。

## 可恢复交互

用户消息被服务端接受后，即使 Agent 尚未完成，该消息也必须在刷新后可见。每次 Agent Run
至少公开以下语义之一：

- 等待执行。
- 正在处理。
- 等待用户动作或补充。
- 已完成。
- 已失败、已取消或已耗尽预算。

前端仅对完整字符串执行本地打字机动画，不算“服务端渐进输出”。v0.6 必须让用户在完整
回答结束前看到服务端确认的增量文本或步骤进度；具体传输协议、事件粒度、断线游标和持久
化频率由 Technical Plan 决定。

断线或刷新后：

1. 先加载已经持久化的公开消息。
2. 查询当前会话是否存在未结束 Run 或 Pending Action。
3. 从服务端公开位置恢复后续内容或状态。
4. 使用稳定消息和事件标识去重。
5. 无法恢复时保留已接受的用户消息，并显示明确失败或可重试状态。

恢复不能重新扣减同一模型调用配额，也不能重复创建 Mock 退款、L2 Case、记忆或审计动作。

## 身份、授权与并发

- 服务端在列出、读取、发送、归档、删除和恢复前都必须校验当前身份和会话所有权。
- `conversation_id`、`thread_id`、浏览器 Local Storage 和 URL 都只是资源标识，不是授权依据。
- 不存在和无权访问使用统一公开错误语义，避免会话枚举。
- 用户退出后不能继续读取前一账号的会话；新游客 Session 不能继承前一游客的私有状态。
- 同一会话在多标签页或重试中提交同一个客户端消息标识时只能产生一次已接受消息和一次
  Agent Run。
- 同一会话并发提交不同消息时必须串行化、排队或明确拒绝，不能并行破坏 Checkpoint 顺序。
- 页面无需在本版本保证多标签页毫秒级实时同步，但重新加载后必须得到一致顺序。

## 数据与存储边界

本版本要求以下逻辑职责分离，但不在 Spec 中决定表结构或传输协议：

| 数据 | 事实来源 | 生命周期 |
|---|---|---|
| 公开会话与消息 | 产品会话存储 | 用于列表、历史、分页和删除 |
| Agent State 与内部消息 | LangGraph Checkpointer | 用于上下文、暂停、恢复和状态历史 |
| 订单、物流、支付、退款和 L2 Case | Mock 业务 Repository | 独立业务生命周期 |
| 长期偏好 | Memory Store | 跨会话且由用户独立管理 |
| 政策与索引 | 文档及可重建索引 | 独立发布和重建 |
| 审计与 Eval | 审计和评测存储 | 按安全与验证要求保留 |

公开消息只保存经过服务端投影、允许用户看到的结果；不能把完整 Checkpoint 序列化后直接
作为历史 API。公开消息与 Checkpoint 发生不一致时，系统必须检测并给出明确状态，不能
静默创建一个同标识的新任务或向用户展示未经验证的内部数据。

本版本继续使用项目当前的本地单实例和 SQLite 边界；是否采用具体表、事件日志、SSE、
WebSocket 或其他实现，由 Technical Plan 基于本 Spec 决定。本版本不迁移 PostgreSQL。

## 范围

包含：

- 本人公开聊天消息的持久化、按序加载和分页。
- 当前会话的稳定路由或等价可恢复定位方式。
- 注册用户会话列表、新建、选择、归档和删除。
- 游客在有效匿名 Session 内恢复当前会话。
- Pending Refund、L2 Upgrade、L2 Case 补充信息和 Memory Proposal 的页面恢复。
- 用户消息、Agent Run 和客户端重试的幂等关联。
- 服务端渐进输出及断线后的公开状态恢复。
- 身份切换、跨用户访问、并发提交和内部数据泄露防护。
- v0.1 至 v0.5 全量回归和固定 v0.6 Eval。

## 非目标

- PostgreSQL、Redis、消息队列、后台 Worker 或多实例事件广播。
- 游客历史跨浏览器、跨设备或自动迁移到注册账号。
- 会话全文搜索、标签、文件夹、分享、导出或客服管理后台。
- 消息编辑、删除单条消息、重新生成、对话分支或时间旅行 UI。
- 图片、文件、语音等附件消息。
- 用公开聊天历史替代 Checkpoint，或从聊天记录重建任意内部 Agent State。
- 新的 L2 工具、多 Agent、Supervisor、外部客服或真实业务集成。
- 改变 v0.4 退款审批、v0.5 Agent Loop 或长期记忆授权边界。
- 承诺生产级高可用、灾难恢复、无限历史或合规留存。

## 公开错误与降级语义

- 历史加载失败：保留当前页面已有内容，显示可重试的普通对话提示，不创建新会话。
- 会话不可访问：清除当前无效选择，不能展示旧账号缓存；由用户选择或创建可用会话。
- 消息未被服务端接受：客户端标记为发送失败，可使用同一客户端消息标识重试。
- Run 已接受但失败：用户消息保留，助手位置显示失败状态；重试不能重复业务副作用。
- 渐进连接中断：恢复已持久化内容和当前 Run 状态，不把连接中断伪装成 Agent 完成。
- Checkpoint 不可用或不一致：公开历史仍可读取，但继续 Agent 前必须明确失败或修复状态。
- 模型不可用：继续沿用现有明确失败语义，不静默切换 Fake。

所有公开错误都以正常会话形式展示，颜色和组件不得暗示业务失败等于安全事件；真正的权限
拒绝和高风险审批仍可使用明确但一致的状态样式。

## 与已有版本的兼容要求

- v0.1/v0.2 的 CLI、Checkpoint 恢复和固定 Eval 保持不变。
- v0.3 的游客零 LLM、注册用户身份隔离、私有数据和服务端模型授权保持不变。
- v0.4 的退款预览、审批、幂等执行、回读验证和跨进程恢复保持不变。
- v0.5 的 L2 Harness、预算、R0 工具、补充信息、公开 Trace 和长期记忆保持不变。
- 现有 `thread_id` 与 Checkpoint 不能因前端会话管理被静默替换或重置。
- v0.6 迁移前产生的本地演示消息不承诺完整回填，但迁移不得破坏既有业务记录、
  Checkpoint 或 Pending Action；具体兼容策略必须在 Plan 中明确。

## 验收条件

1. 用户发送至少三轮消息后刷新页面，公开消息顺序、内容、引用和已完成动作保持一致。
2. 从聊天页切换到订单或记忆页再返回，不创建新会话且历史仍可见。
3. 注册用户退出再登录后，可以列出并选择本人既有会话。
4. 用户显式新建会话后，新会话不包含旧消息、Pending Action、工作记忆或 Agent 上下文。
5. 不同注册用户、游客和工作区不能列出、读取、发送、归档、删除或恢复彼此会话。
6. 刷新等待中的退款审批后，预览与 `action_id` 保持一致；批准或拒绝只执行一次。
7. 刷新等待中的 L2 升级、补充信息或记忆提案后，可以继续原 Case，且不重复模型调用或写入。
8. 同一个客户端消息标识提交两次，只产生一条公开用户消息和一次 Agent Run。
9. 同一会话并发不同消息不会破坏消息顺序或 Checkpoint；系统必须串行化、排队或明确拒绝。
10. 用户在 Agent 生成完整回答前能看到服务端确认的渐进文本或步骤状态，而不只是本地动画。
11. 渐进连接中断并恢复后，已显示内容不重复，最终消息状态与服务端一致。
12. Run 失败后刷新页面，已接受用户消息和公开失败状态仍然存在，并可安全重试。
13. 归档会话不会删除消息；删除有 Pending Action 的会话会被阻止。
14. 删除可删除会话后，公开消息和可恢复任务不再可访问；订单、退款、L2 Case、审计和长期
    记忆不被静默删除。
15. 历史 API 不包含 Prompt、隐藏推理、原始 ToolMessage、完整内部 State、密钥或其他用户数据。
16. 游客在有效匿名 Session 内可以恢复当前会话，但新 Session 不能读取旧游客会话。
17. 空会话创建行为符合 Plan 约定，反复进入聊天页不会产生无边界空记录。
18. 自动化测试不访问网络或真实 API Key，使用临时 SQLite、Fake Model 和 Fake Executor
    覆盖全部确定性路径。
19. v0.1 至 v0.5 的测试和固定 Eval 全部继续通过。

## v0.6 Eval

固定场景至少覆盖：

- 普通对话的刷新、路由切换、退出登录和重新登录恢复。
- 游客当前会话恢复、Session 轮换和跨身份隔离。
- 会话列表、新建、选择、归档、删除和空会话控制。
- 退款审批、L2 升级、L2 补充信息和记忆提案恢复。
- 重复请求、并发提交、Run 失败、断线重连和 Checkpoint 不可用。
- 公开消息投影对 Prompt、ToolMessage、内部 State 和敏感字段的过滤。
- v0.1 至 v0.5 所有安全和业务回归。

发布门槛：

- 固定场景通过率：`100%`。
- 刷新或页面切换造成的公开消息丢失数量：`0`。
- 重复客户端消息产生的重复 Run 或副作用数量：`0`。
- 跨用户、跨游客 Session 或跨工作区会话泄露数量：`0`。
- 公开历史泄露 Prompt、隐藏推理、原始工具输出或密钥数量：`0`。
- 未批准退款、重复退款、重复 Case 和未经确认记忆写入数量：`0`。
- v0.1 至 v0.5 回归：全部通过。

## 已知限制

- 当前仍是本地单实例和 SQLite，不代表生产并发、高可用或灾难恢复能力。
- 游客不提供账号级历史列表、跨浏览器恢复或自动账号迁移。
- v0.6 不提供全文搜索、分享、导出、附件或对话分支。
- 历史分页与渐进输出解决产品连续性，不等同于长期记忆或完整 Agent Trace 回放。
- v0.6 之前已经存在的演示 Checkpoint 不保证能够安全还原为完整公开聊天记录。

## 已接受决策与实施状态

- v0.6 取代原路线中同版本的 L2 Context Engineering；后者顺延到 v0.7。
- 原 v0.7 Agent Eval 与产品加固顺延到 v0.8；Eval 仍从每个版本持续积累。
- SQLite 继续作为当前本地应用与 Checkpoint 存储，二者保持逻辑隔离。
- 本 Spec、Technical Plan 和 ADR-0007 已完成实施；固定 Eval `32/32`。完整证据见
  [`../eval/v0.6-report.md`](../eval/v0.6-report.md)。
- 下一步先定义并接受 v0.7 Feature Spec，不从本 Spec 直接追加 Context Engineering。
