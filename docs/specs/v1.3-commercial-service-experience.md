# Feature Spec：v1.3 商业化售后中心与智能服务体验

状态：Accepted  
日期：2026-07-22  
接受日期：2026-07-22  
依赖版本：v1.2 客户售后中心与 Agent 运营控制台（本机产品验收完成）  

## 目标

把 CommerceResolve 客户售后中心从“功能完整的作品集界面”提升为具有成熟电商产品信息层级、
订单真实感、状态反馈和任务闭环的智能售后中心。用户从订单或进行中服务进入，能够查看商品、
物流、支付和售后事实，由绑定当前业务上下文的 Agent 解释问题、核对政策、提出受控方案，并在
同一任务空间内完成既有 Mock 退款审批、结果跟踪或 AI 二线客服升级。

v1.3 的质量参考淘宝、Shopify、京东等成熟电商产品，但不复制其品牌、视觉资产或全部功能，
也不以页面数量和动画数量作为成功标准。这里的“达到商业化产品水平”特指：

- 用户不阅读项目说明也能找到订单、理解状态并完成售后任务。
- 页面使用真实感、内部一致的商品与订单数据，而不是只有订单号和文本占位符。
- 视觉层级、组件状态、响应式布局、可访问性和错误反馈形成统一产品系统。
- Agent 的事实、依据、建议、动作和最终结果可以被用户区分和验证。
- 所有高风险动作继续受确定性 Policy、人工审批、幂等执行和结果回读约束。

## 参考边界

本 Spec 借鉴成熟产品的共同结构，不进行像素级复刻：

- Shopify Customer Accounts 将订单列表用于查找和管理订单，将订单状态页用于跟踪与管理单笔订单。
- Shopify 订单状态页围绕物流/售后时间线、订单动作、商品摘要和订单详情组织；移动端优先状态与动作。
- 淘宝与京东均从具体订单或商品进入退款、退换或售后申请，而不是先进入无业务上下文的聊天框。
- 商品、状态、资格和费用来自权威业务数据；客服或 Agent 负责解释与引导，不能生成这些事实。

外部参考只用于产品研究。代码、文案、图片、图标、Logo、色值和布局实现必须保持
CommerceResolve 自有表达，并遵守资源许可证。

## 第一性原则

1. **用户先识别订单和状态，再选择动作。** 页面首要任务是降低“我买了什么、进行到哪、现在能做什么”的认知成本。
2. **商品是订单的基本视觉单位。** 售后围绕具体商品发生，订单号不能继续成为页面唯一主角。
3. **动作必须靠近上下文。** 查物流、咨询、退款预览和查看服务应出现在对应订单、商品或服务附近。
4. **Agent 是任务协作者，不是独立聊天站。** 它读取已授权上下文并推进任务，不要求用户重复输入已有事实。
5. **结构化结果优先于长文本。** 事实、证据、建议、审批和结果必须使用适合扫读与操作的产品组件表达。
6. **真实感不等于真实系统。** 演示数据可以丰富，但仍然全部来自本地 Mock/Fake 业务事实。
7. **视觉质量不能削弱安全。** 动效、快捷动作和推荐方案不能跳过授权、Policy、审批或结果验证。
8. **商业化水平必须可以验收。** 关键页面、屏幕宽度、业务状态和端到端任务都要有固定证据。

## 角色与既有边界

### 游客

- 使用版本化、只读的共享演示订单和确定性 Fake Agent 路径。
- 可以体验商品、物流、政策和服务页面的完整视觉结构。
- 不能修改演示数据、触发真实 LLM、创建 Mock 退款或进入运营控制台。

### 注册客户

- 查看本人订单、商品、物流、支付摘要、服务记录、公开会话和待办动作。
- 使用服务端授权的 LLM、审批本人 Mock 退款、恢复会话和管理本人长期偏好。
- 不能创建或修改订单、商品、物流和支付业务事实。

### 管理员

- 继续在独立运营控制台为明确目标客户准备 Mock 数据和查看脱敏运营状态。
- 可以从预置商品与场景中准备演示订单，但不能绕过退款、审批、数据归属和审计规则。
- v1.3 不扩大 Agent Monitoring、Eval 或高影响运维权限。

## 核心用户旅程

### 旅程 A：查找并理解订单

1. 用户从售后首页看到需要关注、进行中服务和最近订单。
2. 用户通过状态筛选、订单号或商品名称定位订单。
3. 订单卡和订单详情展示商品、价格、状态、物流和可用动作。
4. 用户无需打开对话即可理解当前权威状态。

### 旅程 B：处理物流与退款组合诉求

1. 用户从运输中或异常订单打开上下文助手。
2. 用户提出“包裹还没到，现在能退款吗”等组合问题。
3. Agent 使用绑定订单查询最新订单、物流和政策，不要求重复输入已有订单号。
4. Agent 分离已验证事实、政策依据、缺失信息和可选方案。
5. 退款候选继续进入既有确定性预览与审批链；不满足条件时解释原因和下一步。

### 旅程 C：完成 Mock 退款

1. 用户从订单、服务或 Agent 推荐动作进入退款预览。
2. 页面展示商品、订单、原因、金额、渠道、风险和政策依据。
3. 用户明确批准或拒绝。
4. 系统幂等执行并回读业务事实。
5. 服务详情和订单详情同步展示最终状态与时间线。

### 旅程 D：跟踪复杂售后问题

1. 一线流程不能安全解决时，用户明确确认升级 AI 二线客服。
2. 页面展示 AI 身份、当前目标、已用工具和有限预算。
3. L2 Case 暂停、补充、恢复和最终结果继续使用已有公开会话与服务时间线。
4. 用户离开页面、刷新或重新登录后仍能回到相同任务。

## 客户售后中心信息架构

### 全局框架

- 清晰区分售后首页、订单、服务、消息/助手和账号入口。
- 桌面端使用稳定内容宽度与明确主次栏；移动端保持主要动作在单手可达区域。
- 页面标题、面包屑或返回关系能够说明用户当前处理的订单或服务。
- 全局 Agent 入口不能遮挡主要内容，也不能在未授权时自动创建会话或调用模型。

### 售后首页

- “需要关注”优先展示物流异常、待审批、待补充信息和处理失败等本人状态。
- “进行中的服务”展示当前步骤、更新时间、下一步和关联商品。
- “最近订单”展示商品缩略图、核心状态、金额与最相关动作。
- 常用动作至少包含查物流、查询政策、查看服务和打开智能助手。
- 无订单、无服务和全部完成都有正常产品空状态，不使用开发说明或内部术语。

### 订单列表

- 支持按订单号和商品名称查找。
- 支持全部、待发货、运输中、已完成和退款/售后等面向客户的状态视图。
- 每个订单单元至少展示下单时间、订单号、商品图片、名称/规格/数量、金额、履约状态、
  售后状态和上下文动作。
- 多商品订单不能只展示第一件商品而隐去其余数量；折叠时必须明确剩余商品数。
- 状态标签在订单列表、详情、服务和 Agent 结果中使用统一名称、颜色与优先级。

### 订单详情

- 首屏优先展示当前状态、预计或实际送达信息、下一步动作和物流/售后时间线。
- 商品清单展示下单时的标题、图片、规格、单价、数量和小计快照。
- 金额摘要区分商品金额、优惠、运费、支付、已退和预计退款，不混淆订单金额与可退金额。
- 物流区域支持无物流、单包裹和多包裹的安全展示；异常节点具有可理解说明。
- 服务区域展示既有 Refund/L2 投影和可用入口，不创建第二套售后事实。
- 订单助手明确绑定当前订单；冲突订单号继续在模型调用前停止。

### 服务列表与详情

- 服务列表按进行中优先，并展示服务类型、关联商品、当前步骤、更新时间和下一步。
- 服务详情使用时间线展示申请、审批、执行、验证、失败或升级结果。
- 退款服务展示政策依据、金额、渠道与结果；L2 服务展示 AI 身份和公开步骤。
- 页面不得展示完整 Prompt、隐藏推理、内部节点名称、Provider 配置或开发诊断。

### 上下文 Agent

- 桌面端可以使用页内面板，移动端可以使用独立页面或原生对话层，但必须共享同一公开会话。
- 打开助手前展示当前绑定的订单或服务；用户可以明确切换上下文。
- 输入区始终可达，支持 Enter 发送和组合键换行，并保留键盘焦点语义。
- 所有回复、失败、澄清和降级使用对话或任务组件表达，不使用红色系统异常冒充客服回复。

## 产品视觉与交互质量

- 建立 CommerceResolve 自有的颜色、字体、间距、圆角、阴影、层级、图标、状态和动效规则。
- 不使用竞品 Logo、品牌色组合、受保护图标、商品图或逐像素布局。
- 使用一致的商品图片比例、卡片密度、状态标签和主次按钮；不使用 Emoji 充当核心产品图标。
- 加载使用与最终结构对应的 Skeleton；空状态、失败、无权限、过期和数据损坏具有独立语义。
- 高风险动作使用清晰确认层，展示对象、金额、后果和取消路径。
- 动效只用于状态变化、层级转换和渐进反馈，不能延迟主要操作；尊重 `prefers-reduced-motion`。
- 颜色不是传递状态的唯一手段；交互控件具有键盘焦点、可读名称和足够点击区域。
- 桌面 `1440px`、平板 `1024px` 和移动 `390px` 为固定验收视口，同时不能依赖精确宽度才能工作。

## 预置商品、订单与图片资源

v1.3 提供可重复初始化、无真实个人信息的版本化演示数据集。建议下限为：

| 数据 | 最小范围 |
|---|---:|
| 商品 SPU | 12 |
| 商品 SKU/规格 | 18 |
| 本地主图 | 每个 SPU 至少 1 张 |
| 演示客户画像 | 3 |
| 订单场景模板 | 10 |
| 多商品订单 | 至少 2 个场景 |
| 多包裹或部分履约 | 至少 1 个场景 |
| 进行中退款/L2 服务 | 各至少 1 个场景 |

演示场景至少覆盖待发货、运输中、派送中、已签收、配送异常、已取消、退款待审批、退款处理中
和已退款。状态来自当前 Mock Repository 可验证事实；不存在的业务能力不能仅靠文案伪造。

商品资源要求：

- 图片由项目自建、生成或使用允许再分发的明确许可资源，不抓取或热链电商平台图片。
- 图片与演示数据一起版本化，使用稳定资源标识，不在 State、Checkpoint 或消息中保存二进制正文。
- 至少提供缩略图、加载占位和失败回退；图片包含适合商品名称的替代文本。
- 订单商品保存下单时标题、规格、单价和图片引用快照；后续商品模板变化不能静默改写历史订单。
- 管理员准备订单时优先从预置商品和场景中选择，同时继续遵守目标客户、业务冲突和审计边界。

## Agent 能力增强

v1.3 在既有一线工作流、RAG、退款链和 L2 Harness 上增加面向产品的结构化售后方案能力，
不新增第二套 Agent。

### 输入与上下文

- 优先使用服务端绑定的当前订单或服务上下文。
- 组合诉求可以同时包含物流、政策、退款资格和下一步咨询。
- 用户输入中的订单号与绑定上下文冲突时继续在模型前停止。
- Agent 需要最新事实时调用既有受控工具，不能从历史消息推断当前订单状态。

### 结构化结果

Agent 面向 UI 的公开结果至少能够表达：

- 当前目标。
- 已验证订单、商品、物流或服务事实。
- 缺失或冲突的信息。
- 带版本和定位信息的政策依据。
- 推荐方案及原因。
- 当前用户真正允许执行的动作。
- 当前步骤、停止原因和下一步。

具体 Schema、State 字段和节点由 Technical Plan 定义，但自然语言正文不能成为动作授权或页面
状态的唯一来源。

### 路由与动作

- Agent 可以在订单、物流、政策、退款预览和 L2 升级候选之间选择下一步。
- 确定性 Router/Policy 根据结构化结果、授权和业务状态决定实际路径。
- 推荐动作只能来自服务端允许列表；页面不得执行模型生成的任意 URL、命令或工具名称。
- 退款资格、金额、渠道和审批要求继续由既有确定性 Policy 产生。
- 工具失败、模型不可用、结构化输出无效和信息不足保持可区分的停止或澄清语义。

### 进度与恢复

- 用户可以看到“核对订单”“查询物流”“检索政策”“生成方案”等有限公开阶段，不展示隐藏推理。
- 公开阶段必须来自持久化 Run/Event 投影，不能由浏览器定时伪造。
- 刷新、断线和重新登录后继续使用既有公开消息、SSE 重放、Pending Action 和 Checkpoint 恢复语义。
- 重试不能产生重复消息、Run、退款、L2 Case 或记忆写入。

## 事实、安全与权限

- 商品、订单、物流、支付、退款和服务状态继续以 Mock 业务 Repository 为事实来源。
- 政策结论必须带当前发布版本和可定位引用；检索片段不能授权退款。
- UI 展示的可执行动作由服务端权限和 Policy 返回，隐藏按钮不能代替服务端拒绝。
- 游客、客户、管理员和跨客户数据继续保持 v1.2 权限矩阵。
- LLM 不直接写订单、物流、支付或退款状态，不决定风险等级，也不产生管理员权限。
- 页面资源、演示数据和 Agent 内容不得包含真实 API Key、Cookie、支付凭据或个人信息。

## 错误与降级语义

| 场景 | 用户可观察结果 |
|---|---|
| 商品图片缺失或损坏 | 展示稳定占位图和商品名称，订单与售后动作仍可用 |
| 历史订单缺少商品快照 | 展示兼容信息，不伪造图片、规格或价格 |
| 无物流或多包裹数据不完整 | 展示可验证的有限状态，不补造地图或预计时间 |
| Agent 信息不足 | 在当前会话提出最小澄清问题，不丢失绑定上下文 |
| 模型不可用 | 以普通客服对话状态说明暂时不可处理，不显示堆栈、Provider 或红色系统异常 |
| 政策无证据或冲突 | 明确无法给出确定结论，展示冲突来源或建议升级 |
| 动作已过期或业务事实变化 | 阻止旧动作，刷新事实并生成新的方案或预览 |
| 页面刷新或 SSE 断线 | 从服务端恢复公开历史、当前 Run 和待办，不重复执行 |

## 兼容与迁移

- v1.2 的客户/管理员角色、URL、Session、订单、会话、退款、L2 Case、Checkpoint、Memory、
  Audit 和 Eval Artifact 保持可读。
- 历史订单允许没有新商品图片或扩展快照字段，使用明确兼容状态，不能因读取旧数据而非 Ready。
- 新预置演示数据使用稳定版本和显式初始化，不在应用启动或页面访问时静默覆盖现有业务数据。
- 客户既有会话、Pending Action 和服务投影继续使用原 ID 与恢复语义。
- 如果 State、工具契约、业务 Schema 或前端公开协议发生变化，Technical Plan 必须提供迁移和回归方案。

## 版本范围

v1.3 包含：

- 客户售后首页、订单列表、订单详情、服务列表/详情和上下文助手的统一商业化体验。
- 版本化预置商品、图片、客户画像和订单/服务场景。
- 管理员使用预置商品和场景准备 Mock 订单的产品能力。
- 支持商品名称查找、客户状态筛选、多商品和兼容旧订单的页面表达。
- 物流、政策与退款组合诉求的结构化 Agent 方案。
- Agent 公开阶段、结构化事实/依据/动作和既有恢复链的 UI 集成。
- 桌面、平板、移动、键盘、焦点、Reduced Motion 和图片失败状态验收。
- 数据一致性、Agent 任务、权限、安全和视觉回归的固定测试与 Eval。

## 非目标

v1.3 不包含：

- 复制淘宝、Shopify、京东的代码、视觉资产、品牌、商品数据或全部业务功能。
- 真实商品中心、库存、购物车、结算、支付、物流、CRM 或电商平台接入。
- 新售后业务类型：退货、换货、取消、维修、逆向物流、部分退款或店铺积分。
- 客服坐席、管理员冒充客户、真实人工接管、SLA、工单分配或消息通知平台。
- 第二个 Agent、Supervisor、多 Agent 协作或开放式自主规划。
- 运营控制台故障处置、Web 运行 Eval、Web Backup/Restore/Upgrade 或高影响运维。
- 拆分后端服务、独立前端仓库、消息队列、多实例、高可用或多租户 SaaS。
- 为视觉效果引入无任务价值的 3D、长时间过场、游戏化动画或远程图片依赖。
- 补齐已延期的 Docker 参考环境 Gate；该 Gate 仍单独记录且不能冒充通过。

## 验收条件

1. 游客、客户和管理员看到与角色一致的产品表面，客户侧不存在演示数据写入口或运营内部入口。
2. 售后首页明确区分需要关注、进行中服务和最近订单，并从权威数据生成计数与状态。
3. 用户可以按订单号和商品名称定位订单，并按客户可理解的状态查看订单集合。
4. 订单单元展示商品图片、名称/规格/数量、金额、时间、履约和售后状态；多商品数量不会被隐去。
5. 订单详情首屏能够回答当前状态、送达进度、下一步和可执行动作。
6. 商品清单和金额摘要使用下单时快照；商品模板变化不会改写历史订单。
7. 无物流、单包裹、多包裹或异常数据使用明确状态，页面不编造地图、承运商或预计时间。
8. 服务列表与详情展示 Refund/L2 权威投影、当前步骤、下一步和关联商品，不创建第二套服务事实。
9. 订单、服务和 Agent 中同一状态使用一致名称、视觉标识和优先级。
10. 至少 12 个商品、18 个 SKU 和 10 个订单场景能够通过固定命令重复初始化。
11. 所有商品主图来自本地受控资源；远程热链、竞品图片和无许可证资源数量为 `0`。
12. 图片加载、缺失、损坏和替代文本具有可重复验收结果，不阻塞订单与售后操作。
13. 管理员可以为显式目标客户从预置商品/场景准备订单，普通客户相关写请求全部被服务端拒绝。
14. 用户从绑定订单提出物流与退款组合诉求时，Agent 查询最新订单、物流和政策并返回结构化方案。
15. 已验证事实、政策依据、缺失信息、推荐方案、允许动作和下一步在公开结果中可区分。
16. 用户不需要重复提供页面已经绑定且服务端验证通过的订单号。
17. Agent 推荐的动作全部来自服务端允许列表，任意工具名、URL 或未注册动作执行数量为 `0`。
18. 退款资格、金额、渠道和审批继续由确定性 Policy 产生；未经批准 Mock 退款数量为 `0`。
19. Agent 公开阶段来自持久化白名单事件，不包含 Prompt、隐藏推理、密钥或内部节点细节。
20. 模型不可用、结构化输出无效、政策无证据和工具失败具有正常产品语义，不展示技术异常。
21. 页面刷新、路由切换、SSE 断线和重新登录后，公开会话、当前 Run 和待办可以恢复。
22. 重试或恢复造成的重复消息、Run、退款、L2 Case 和记忆写入数量均为 `0`。
23. 售后首页、订单列表、订单详情、服务详情和上下文助手在 `1440px`、`1024px`、`390px`
    固定视口完成截图与真实交互验收，无阻塞操作的溢出、遮挡或不可达控件。
24. 所有核心动作支持键盘操作和清晰焦点；状态不只依赖颜色；Reduced Motion 下无必要动画。
25. 高风险确认准确展示订单、商品、金额、后果和取消路径，视觉简化不能绕过审批。
26. 四条核心旅程均通过真实 HTTP 浏览器验收：订单理解、组合咨询、Mock 退款、复杂问题跟踪。
27. 固定 v1.3 Eval 覆盖商品/订单一致性、组合意图、工具选择、引用、动作权限、恢复和安全失败。
28. 既有 v0.1–v1.2 自动化测试、Offline Eval 和安全门禁保持通过，安全违规为 `0`。
29. 历史 v1.2 数据升级后保持可读；缺少新商品资源的旧订单使用兼容状态而不是迁移失败。
30. README、目标地图、代码职责、初始化说明、资源许可和已知限制与最终实现一致。
