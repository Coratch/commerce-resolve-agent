# Feature Spec：v1.0 单机交付与可维护运行

状态：Accepted

日期：2026-07-21

接受日期：2026-07-21

验收补充日期：2026-07-22（商业化 UI 布局与克制动效）

依赖版本：v0.8 Agent Eval 与产品加固

## 目标

项目维护者能够在一台受支持的主机上，以一个明确入口安装、配置、启动、停止和升级
CommerceResolve，并能判断服务是否真正可用、数据是否安全持久化、未完成任务在重启后处于
什么状态，以及发生故障时如何恢复。

演示用户在服务重启、应用重新部署或前端重新加载后，仍能访问本人有权查看的账号、会话、
Mock 业务数据、待审批动作、L2 Case 和已确认长期偏好。维护者能够创建经过校验的备份，在
隔离环境中恢复并证明数据一致。

v1.0 成功不是“把开发命令包进容器”，而是形成一份可重复交付、可观察、可恢复、可升级且有
发布证据的单机产品。它继续是学习和作品集项目，不宣称达到多实例、高可用或真实交易系统的
生产等级。

候选版本还必须提供一版以对话为核心的商业化工作台布局：桌面端充分利用可用空间，移动端保持
可操作，正常状态不暴露 LLM、Fake、Provider 或模型费用等内部术语，必要动效只用于表达层级与
状态变化，不能妨碍阅读、审批或输入。

## 第一性原则

1. **可部署必须可重复。** 新环境不能依赖开发者记忆、IDE 状态或未记录的本机文件。
2. **进程存活不等于服务可用。** Readiness 必须验证必要配置、Schema、存储和静态资源。
3. **进程生命周期不能定义数据生命周期。** 重启后持久化事实必须保留，运行中任务必须进入
   确定且可解释的状态。
4. **备份只有成功恢复后才有意义。** 创建文件不是完成证据，必须验证清单、完整性和恢复结果。
5. **派生数据与事实数据不同。** 可重建政策索引不应冒充唯一事实来源，也不应扩大备份边界。
6. **配置错误必须在产生副作用前失败。** 缺少密钥、路径不可写、Schema 不兼容或权限错误不能
   等到用户请求后才随机暴露。
7. **运维能力同样遵守最小权限。** 备份、恢复、升级和诊断不能泄露密钥、Cookie、Prompt、
   用户正文或跨工作区数据。
8. **失败必须可归因。** 维护者需要稳定错误码、关联标识和修复方向，而不是只能阅读堆栈。
9. **发布是证据集合。** 版本号、代码、数据兼容、构建、迁移、浏览器路径和 Eval 必须对应同一
   候选版本。
10. **先交付可靠单机，再讨论分布式。** 没有单机故障和恢复证据前，不引入多实例、队列或集群。

## 当前基线与问题

v0.8 已具备：

- FastAPI 同源服务、React 生产构建和 CLI 管理入口。
- 业务数据库、LangGraph Checkpoint、政策索引和长期记忆四类独立 SQLite 数据。
- Alembic 业务迁移、政策索引重建和 Memory Store 初始化。
- 服务端公开消息、Agent Run/Event、Pending Action、Checkpoint 和 L2 Trace 恢复语义。
- 统一 217 条离线 Eval、真实 Provider 资格评测和 17 项 Offline Release Gate。
- `.env`、运行数据库、日志、浏览器与 Eval Artifact 的 Git 隔离。

当前交付缺口：

- 安装、迁移、索引、前端构建和启动仍由维护者手工串联。
- 没有一个明确的受支持运行包、启动顺序和版本清单。
- 没有区分 Liveness、Readiness 和可选 LLM 能力状态的稳定契约。
- 进程收到终止信号时，停止接收请求、处理运行中任务和退出超时的语义未形成交付门禁。
- 启动后对遗留 `running` Agent Run 的协调主要依赖现有请求路径，没有独立启动核对证据。
- 四类存储没有统一、可校验的备份与恢复流程。
- 没有以 v0.8 数据快照验证升级、失败恢复和版本兼容。
- 日志与诊断分散在开发输出和既有业务 Trace 中，没有统一的运维字段、脱敏和保留边界。
- 当前 README 能指导开发运行，但尚不是从零部署、升级、备份和排障手册。

## 角色

### 项目维护者

- 准备配置并执行安装、启动、停止、状态检查、备份、恢复和升级。
- 查看公开版本、健康摘要、脱敏日志和聚合运行指标。
- 在执行恢复或升级等高影响动作前看到范围、目标和风险，并明确确认。
- 不需要读取数据库内部表或修改源码才能完成标准运维路径。

### 演示操作员

- 创建邀请码并验证游客、注册用户和 LLM 能力是否符合配置。
- 可以判断系统是核心可用、LLM 能力停用、依赖故障还是正在维护。
- 不能通过 Web 操作绕过既有身份、Policy、退款审批或数据隔离。

### 演示用户

- 使用现有聊天、订单、政策、Mock 退款、L2 Case 和长期记忆能力。
- 服务暂时不可用或维护时收到稳定、非技术化的失败语义。
- 服务恢复后看到已持久化历史和真实任务状态，不会得到伪造的“处理中”或重复副作用。

## 术语

| 术语 | 含义 |
|---|---|
| Release Bundle | 与一个版本和代码提交对应的可交付应用、静态资源、配置模板和运维入口 |
| Deployment Instance | 一台受支持主机上的一个 CommerceResolve 单机实例 |
| Preflight | 启动或升级前对配置、路径、权限、版本和依赖的只读校验 |
| Liveness | 应用进程能够继续处理内部事件，不代表业务依赖已经可用 |
| Readiness | 实例具备接受新业务请求所需的配置、存储、Schema、索引和静态资源 |
| Capability Status | `guest`、`registered_llm`、`refund`、`l2` 等能力的启用或降级状态 |
| Quiesce | 停止接受新写任务，并把现有任务推进到可安全停止或明确中断的阶段 |
| Backup Set | 权威数据快照、版本清单、校验摘要和恢复说明组成的原子备份单元 |
| Restore | 在停止服务和明确目标范围下，用一个通过校验的 Backup Set 重建实例数据 |
| Reconciliation | 启动后把遗留运行状态与持久化事实核对为可恢复、已中断或失败状态 |
| Deployment Manifest | 记录应用版本、提交、Schema、配置能力和数据格式版本的非敏感清单 |

## 支持边界

- v1.0 支持一个维护者管理的单机实例和一个明确的参考部署环境。
- macOS 本地开发路径继续保留；参考部署主机和所需运行时由 Technical Plan 确定并锁定版本。
- 本地回环地址可以使用 HTTP；任何非回环访问必须经过受支持的 HTTPS 终止边界，并启用安全
  Cookie。证书和 DNS 的具体实现由部署环境负责。
- 一个实例只运行一个对外 Web 服务入口；前端与 API 保持同源。
- 是否采用容器、进程管理器、SQLite 或其他持久化实现由 Technical Plan 和必要 ADR 决定，
  但必须满足本 Spec 的单机、兼容、恢复和数据隔离结果。
- LLM 是显式可选能力。`LLM_FEATURE_ENABLED=false` 时游客和无需模型的核心能力仍可 Ready；
  启用 LLM 却缺少完整 Provider 配置时 Preflight 必须失败，不能静默降级。
- 所有订单、物流、支付、退款和 L2 Case 继续是项目内 Mock/Fake 数据。

## 用户故事

### 从干净主机启动

维护者获取一个明确版本的 Release Bundle，复制配置模板、填写必要值并执行一个受支持入口。系统
在启动业务进程前完成 Preflight、必要数据初始化或迁移、派生索引准备和前端资源检查。成功后
维护者可以通过健康检查与浏览器路径确认实际可用版本。

### 配置错误安全失败

维护者遗漏必需配置、设置不可写目录、使用无效 Origin、启用 LLM 却缺少 Provider 配置，或把
数据路径指向不兼容内容时，系统在绑定公开服务或执行业务写入前失败，指出稳定配置项和修复方向，
但不回显密钥值。

### 判断服务与能力状态

监控或维护者可以分别检查 Liveness 和 Readiness。用户可见健康摘要不暴露内部路径、Schema、
账号或 Provider；本机运维入口可以显示脱敏的组件状态、应用版本和失败码。LLM Provider 临时
不可用时，核心服务状态与 LLM 能力状态分别呈现。

### 安全停止与重启

维护者停止服务后，实例先拒绝新的写任务，给运行中任务一个有界完成窗口，再把无法完成的 Run
标记为 `interrupted`。重启时系统执行 Reconciliation，不自动批准动作、不重复调用模型或工具、
不重复创建 Mock 退款。原有待审批动作继续保持待审批，用户可以按既有契约恢复或显式重试。

### 创建并验证备份

维护者发起备份前看到将包含的权威存储、排除项和一致性策略。成功结果包含版本化 Manifest、
文件清单、大小和校验摘要。API Key、Cookie、日志、缓存、政策派生索引、前端构建缓存和 Eval
Artifact 不进入 Backup Set。

### 从备份恢复

维护者在停止服务的隔离目标中校验并恢复 Backup Set。默认只允许恢复到空目标；覆盖已有实例
属于高影响动作，必须明确确认并先保留现有数据。恢复后系统重新构建派生索引、验证 Schema、
数据归属和关键计数，再允许 Readiness 通过。

### 从 v0.8 升级

维护者使用一份经过校验的 v0.8 数据快照执行升级。系统先完成 Preflight 和备份，再执行兼容
变更；任一步失败时实例不得以半升级状态对外 Ready。已存在账号、会话、Mock 业务数据、
Checkpoint、Pending Action、L2 Case、Trace 和长期偏好保持可访问。

### 查看运行证据与排障

维护者可以按 `request_id`、`run_id`、`thread_id`、`case_id` 或 `action_id` 关联脱敏日志和
既有 Trace，查看稳定错误码、耗时和状态变化。默认日志不保存消息正文、完整 Prompt、模型回复、
Cookie、密码、邀请码、API Key 或数据库绝对路径。

### 发布一个可识别版本

维护者能够确认当前运行实例的应用版本、代码提交、数据格式和 Release Gate 结论。部署内容与
版本清单不一致、前端和后端版本不一致或必要发布证据缺失时，候选版本不能宣称发布完成。

## 功能要求

### 交付与 Preflight

- Release Bundle 必须具有稳定版本、不可混淆的启动入口和从零安装说明。
- 启动前检查必要配置是否存在、格式是否有效、路径是否在允许范围且可读写。
- 启动前检查业务 Schema、Checkpoint、Memory、政策来源/索引和前端资源是否兼容。
- 初始化、启动和升级必须分开记录；应用启动不能静默创建未知空业务库掩盖路径错误。
- 重复执行初始化或启动必须幂等，不能重复创建演示数据、账号、邀请码或业务动作。
- Deployment Manifest 只保存非敏感版本事实，不复制 `.env` 或密钥。

### 服务生命周期与任务协调

- 启动、停止和重启必须具有稳定退出码和可判断终态。
- Quiesce 后不接受新的消息、审批、重试、记忆写入或订单维护请求。
- 读请求是否在 Quiesce 期间允许由 Plan 明确，不能出现不同 Route 随机行为。
- 运行中任务具有有界停止时间；超时后持久化为 `interrupted` 或稳定失败，不无限阻塞退出。
- 启动 Reconciliation 只读取并核对持久化状态，不自动产生模型、工具、退款或记忆副作用。
- 重启后公开消息、SSE 事件、Pending Action 和 Run 状态保持既有去重和恢复契约。

### 健康与能力状态

- Liveness 和 Readiness 使用不同契约和状态码。
- Readiness 至少验证必要 Schema、存储连接、政策可用性、前端资源和配置版本。
- LLM、退款、L2 等能力状态必须与核心 Readiness 分开，明确 `enabled`、`disabled`、
  `degraded` 或 `unavailable`。
- 公开健康响应只返回版本、总体状态和有限能力摘要；详细组件错误只通过本机运维入口提供。
- 健康检查是只读的，不调用真实模型、不创建 Session、不修改数据库或刷新用户配额。

### 备份与恢复

- Backup Set 包含业务事实、LangGraph Checkpoint、已确认长期记忆和恢复所需版本元数据。
- 政策原文继续由版本控制管理；派生政策索引在恢复后重建，不作为唯一备份事实。
- 备份必须使用明确的一致性策略；运行中写入不能产生跨存储时间点含糊的“成功”备份。
- Manifest 记录应用版本、数据格式、文件清单、校验摘要、创建时间和排除项，不记录密钥。
- 恢复前验证版本兼容、文件完整性、目标范围和可用空间；失败时不修改目标实例。
- 恢复默认拒绝合并两个实例或覆盖非空目标；高影响覆盖需要明确确认和可回退快照。
- 恢复完成后必须重新验证身份归属、关键业务计数、Checkpoint 可读性、Memory namespace 和
  派生索引，不以文件复制成功作为完成证据。

### 升级与兼容

- 支持从已接受 v0.8 数据版本升级到 v1.0。
- 升级前必须生成或确认一个通过完整性检查的 Backup Set。
- 升级过程具有独占边界，不能在迁移期间继续接受业务写入。
- Schema 或持久化格式变化必须具有版本、兼容检查和失败处理；不能通过删除旧数据解决迁移。
- 降级不要求自动 Down Migration；不兼容时使用升级前 Backup Set 恢复到原版本。
- 版本不兼容、迁移失败或前后端版本不一致时 Readiness 必须失败。

### 日志、诊断与指标

- 应用日志使用稳定结构，至少包含时间、级别、组件、事件、结果、耗时和适用的关联标识。
- 错误使用稳定 `error_code` 和安全摘要；堆栈只进入本机受控诊断，不返回浏览器。
- 默认不记录用户消息正文、完整模型请求/响应、隐藏推理、Cookie、密码、邀请码或 API Key。
- 至少提供请求、Agent Run、模型调用、工具调用、Mock 退款、失败、中断和恢复的聚合计数。
- 指标不以用户 ID、订单号或自由文本作为无界标签。
- 日志和指标具有明确本地保留、轮转或清理方式；不会无限占满数据卷。
- 现有 Public Trace、Diagnostic Trace 和 Eval Artifact 继续保持各自边界，不合并为一个日志库。

### 配置与安全

- 配置模板只包含空密钥和安全示例；Release Bundle、镜像或前端资源不得内置真实密钥。
- 服务端启动日志、健康响应、错误页面和诊断报告不得回显 Secret 值或完整连接信息。
- 非回环部署必须启用安全 Cookie、受限 Origin 和 HTTPS 边界；不满足时 Preflight 失败。
- 运维入口默认只允许本机维护者访问，不新增公开 Web 管理 API。
- 备份、恢复和升级操作必须记录脱敏审计；恢复覆盖属于 R2 运维动作。
- 运行目录、备份、日志和临时文件默认不进入 Git，也不能由 Web 静态目录访问。
- Provider 出站网络与其他依赖访问必须明确；游客和离线 Release Gate 继续保持零 Provider 调用。

### 文档与演示

- 提供从干净环境开始的安装、配置、启动、停止、状态检查和卸载说明。
- 提供首次初始化、创建邀请码、游客体验、注册用户、Mock 退款和 L2 Case 演示脚本。
- 提供备份、恢复、v0.8 升级和常见故障排查手册。
- 文档区分本地开发、参考部署和测试命令，不能混用不同安全假设。
- 明确所有交易数据为 Mock、LLM 二线并非真人，以及单机交付的能力限制。

## 错误与降级语义

| 场景 | 必须结果 |
|---|---|
| 必需配置缺失或格式错误 | Preflight 失败；不绑定非回环端口，不产生业务写入 |
| 显式停用 LLM | 核心可 Ready；注册用户 LLM 能力显示 disabled，不降级为 Fake |
| 启用 LLM 但配置不完整 | Preflight 失败，不以 degraded 掩盖配置错误 |
| Provider 运行期不可用 | 核心服务保持可判断；相关 Run 明确失败或中断，不切换 Fake |
| 必要数据库不可访问或 Schema 不兼容 | Readiness 失败；写请求不进入 Graph |
| 政策派生索引缺失 | 尝试受控重建或保持相关能力 unavailable，不用模型编造政策 |
| 前端和后端版本不一致 | Readiness 或发布门禁失败，不宣称部署成功 |
| 收到终止信号 | 进入 Quiesce；有界等待并持久化未完成 Run 状态 |
| 启动发现遗留 running Run | 确定性 Reconciliation 为 interrupted/可重试，不自动执行副作用 |
| 备份期间仍存在未协调写入 | 备份失败或等待一致性边界，不能生成成功 Manifest |
| Backup Set 校验失败 | 恢复前失败，目标数据保持不变 |
| 恢复目标非空 | 默认拒绝；明确覆盖时先保存目标快照并审计 |
| 升级失败 | 不对外 Ready；保留错误证据并允许从升级前备份恢复 |
| 日志或数据卷接近容量限制 | 明确告警；不能静默删除权威业务或 Checkpoint 数据 |

## 数据与兼容要求

- v0.8 的账号、邀请、Session、workspace、conversation、公开消息、Run/Event、Mock 订单、物流、
  支付、退款、L2 Case、Trace、Checkpoint 和长期偏好必须保持可读取。
- 恢复后 `user_id`、workspace、thread、case、action 和 Memory namespace 归属不能改变。
- Pending Refund、L2 Upgrade、L2 补充信息和 Memory Proposal 保持原状态，不自动批准或取消。
- 已完成 Mock 退款不得因升级、备份、恢复或 Reconciliation 重复创建。
- Checkpoint、业务库、Memory 和政策索引继续具有独立生命周期和删除语义。
- Backup Set 不作为新的业务事实来源；恢复后仍以对应 Repository、Policy 和 Checkpointer 为准。
- v0.8 Accepted Baseline 继续用于确定性业务回归；v1.0 新增运维场景不能替换已有 217 条场景。

## 范围

包含：

- 一个受支持参考环境的单机 Release Bundle 和明确生命周期入口。
- 配置模板、Preflight、Deployment Manifest 和版本识别。
- Liveness、Readiness、Capability Status 和本机脱敏诊断。
- Quiesce、优雅停止、启动 Reconciliation 和明确任务恢复语义。
- 权威数据 Backup Set、完整性校验、隔离恢复和派生索引重建。
- 从 v0.8 数据快照升级、失败恢复和兼容验证。
- 结构化本地日志、有限聚合指标、轮转/清理和关联标识。
- 部署、演示、备份、恢复、升级和排障文档。
- 将交付、重启、备份、恢复和升级路径纳入 Offline Release Gate。
- 对话工作台、全局导航、游客提示和响应式布局的一次商业化收敛。
- 尊重 `prefers-reduced-motion` 的轻量进入、消息和交互反馈动效。

## 非目标

- 真实电商、物流、支付、退款、CRM 或人工客服集成。
- 新售后意图、部分退款、逆向物流、多级审批或新的 L2 工具。
- 多实例 Web、分布式 Worker、消息队列、Leader Election、分布式锁或高可用数据库。
- Kubernetes、自动扩缩容、Service Mesh、跨区域部署或零停机滚动升级。
- 生产 SLA、灾难恢复站点、实时异地复制、自动故障转移或合规认证。
- 公开注册、公开运维 API、租户管理员后台、计费或真实商业化账号体系。
- 外部 APM、集中日志 SaaS、在线 Trace 平台、生产流量采样或用户行为分析。
- 自动恢复并继续执行中断前未知状态的模型、工具或 Mock 退款副作用。
- 把 API Key、完整 Prompt、用户正文、数据库或 Backup Set 上传到远端服务。
- 自动接受 Eval Baseline、自动发布、自动回滚或修改远端基础设施。

## 验收条件

1. Release Bundle 与应用版本、代码提交、前后端资源和数据格式具有可验证对应关系。
2. 在文档声明的干净参考环境中，只需安装明确的前置运行时并执行一个入口即可完成初始化和启动。
3. 重复初始化和启动不产生重复账号、邀请码、演示数据、消息、Run、Case、Memory 或 Mock 退款。
4. 缺少必要配置、路径不可写、Origin 不安全或数据版本不兼容时，Preflight 在业务写入前失败。
5. 配置、日志、健康、诊断、Bundle 和部署产物中不存在真实 API Key、Cookie、密码或邀请码。
6. Liveness 和 Readiness 使用独立契约；数据库不可用、Schema 错误或前后端版本不一致时
   Readiness 失败。
7. 显式禁用 LLM 时核心服务可以 Ready；启用但配置不完整时 Preflight 失败。
8. 健康检查不调用模型、不创建 Session、不修改数据库、不消耗用户额度。
9. 非回环部署缺少 HTTPS、安全 Cookie 或允许 Origin 时不能通过 Preflight。
10. 停止服务后不再接受新写任务，运行中任务只在有界窗口内完成。
11. 未在停止窗口完成的 Run 被持久化为 `interrupted` 或稳定失败，不遗留虚假的 `running`。
12. 启动 Reconciliation 不调用模型、工具、退款或 Memory 写入，重复执行结果一致。
13. 重启后本人公开历史、Pending Action、L2 Case、Trace 和长期偏好保持可访问且归属不变。
14. 重启、Reconciliation、显式重试和 SSE Replay 不产生重复公开消息、Run、事件或 Mock 退款。
15. Backup Set 具有版本化 Manifest、文件清单、大小、校验摘要和明确排除项。
16. Backup Set 不包含 API Key、Cookie、日志、缓存、派生政策索引、Eval Artifact 或浏览器产物。
17. 并发写入无法满足一致性策略时备份失败，不生成成功 Manifest。
18. 损坏、缺文件、版本不兼容或校验失败的 Backup Set 在修改目标数据前被拒绝。
19. 恢复默认只允许空目标；覆盖现有实例必须明确确认、保留原数据快照并生成审计记录。
20. 恢复后账号、会话、Mock 业务记录、Checkpoint、Pending Action、L2 Trace 和 Memory 关键计数
    与备份 Manifest 一致。
21. 恢复后派生政策索引从版本化政策来源重建，政策问答引用仍可定位。
22. 一份包含 v0.8 代表性数据的固定快照可以原地升级到 v1.0，且既有数据和行为保持兼容。
23. 升级前存在通过校验的 Backup Set；升级失败时实例不对外 Ready，并可从该备份恢复。
24. 日志具有稳定事件名、错误码、耗时和适用关联标识，且默认不含用户正文、完整 Prompt、
    原始模型回复或绝对敏感路径。
25. 本机维护者可以判断应用版本、组件状态、能力状态、最近失败和数据版本，无需直接查询表。
26. 日志、临时文件和本地指标具有可验证的保留或清理边界，不会静默删除权威数据。
27. 现有 v0.1–v0.8 的 217 条离线场景全部继续通过，Safety Violation 保持为 `0`。
28. v1.0 新增交付、配置、生命周期、健康、备份、恢复、升级和安全场景并全部通过。
29. Offline Release Gate 覆盖 Bundle 构建、干净启动、健康、浏览器冒烟、重启、备份恢复、
    v0.8 升级、敏感数据和已有工程门禁。
30. 真实 Provider Qualification 只有在模型、Prompt、Schema 或 Context 契约变化时重新运行；
    部署测试不会隐式读取 `.env` 或访问网络。
31. README 和运维文档能够从零复现安装、演示、停止、备份、恢复、升级和排障路径。
32. 所有订单、物流、支付、退款和 L2 Case 仍为本地 Mock/Fake 数据，恢复测试不接触真实系统。
33. 在 `1280×720` 桌面视口，游客对话区不落入会话侧栏列，主对话区占据可用工作区主体，
    消息和输入框无需横向滚动即可使用。
34. 注册用户桌面布局明确区分会话导航、主对话和处理上下文；首屏不再由营销 Hero 主导，
    输入区在正常工作台视口内可见，长消息只滚动消息区域。
35. 正常注册状态不展示“LLM 模式”等内部实现标签；游客只看到“访客体验、使用演示数据”等
    能力边界，智能能力不可用时使用面向任务的降级文案。
36. 在 `390×844` 移动视口不存在页面级横向溢出，导航、消息、审批卡和输入区均可操作。
37. 布局和消息动效不阻塞输入、导航或审批；系统启用“减少动态效果”时必须关闭非必要动画，
    且不为了展示效果引入 WebGL、3D 场景或持续背景动画。

- 浏览器验收同时覆盖游客/注册桌面布局、移动布局、用户可见状态文案和 Reduced Motion。

## 已知限制

- 单机交付不提供高可用；主机、磁盘或本地数据卷损坏会导致服务中断。
- Backup Set 只提供维护者触发的本地恢复能力，不等同于异地灾难恢复。
- 优雅停止只能处理应用可观察到的任务；进程被强制终止时依赖启动 Reconciliation。
- SQLite 或最终 Plan 选择的单机存储不代表生产高并发能力。
- 本地日志和指标用于排障与作品集演示，不是生产级集中监控。
- 参考部署环境之外的平台不承诺兼容。
- Eval 和部署通过不构成真实支付、隐私、财务或合规认证。

## 已接受决策

本 Spec 已确认：

1. v1.0 定位为单机可交付、可观察、可备份恢复的作品集版本，不扩大售后业务能力。
2. 交付目标是一个受支持参考环境和一个明确生命周期入口，具体容器/进程技术在 Plan 决定。
3. v1.0 不要求多实例、消息队列、Kubernetes、生产 SLA 或真实外部系统。
4. 核心 Readiness 与可选 LLM 能力状态分离；启用 LLM 却配置不完整属于启动错误。
5. 停止和启动必须执行 Quiesce/Reconciliation，不能自动重放未知副作用。
6. 备份覆盖业务、Checkpoint 和 Memory 权威数据；政策索引作为派生数据恢复后重建。
7. 只保证从 v0.8 升级；不要求自动 Down Migration，以升级前备份作为安全回退。
8. v1.0 新增不少于 32 条运维 Eval，并继续强制现有 217 条场景和安全零容忍。
9. v1.0 Candidate 验收增加一次 UI 工作台收敛；参考创意网站的层级和动效节奏，但不照搬
   沉浸式 3D、长滚动或会降低客服任务效率的交互。

本 Spec 已被接受。下一步基于这些边界制定 Technical Plan，并在 Plan 中比较数据库、容器、
进程管理和日志方案；Plan 审核通过前不修改产品代码、部署文件和运行配置。
