# Feature Spec：v2.0 可演示、可评估的智能售后 Agent 产品

状态：Accepted / Implemented  
日期：2026-07-24  
依赖版本：v1.3.2 沉浸式电商服务界面  
后续版本：v2.1 多格式、多模态政策知识与混合检索

实现与验收证据：
[`../eval/v2.0-report.md`](../eval/v2.0-report.md)

## 目标

v2.0 将 CommerceResolve 收敛为一个面向开源学习、Agent 开发工程师面试和本地产品演示的
邀请制电商售后 Agent。用户注册后获得独立、可重置、版本化的 Mock 售后工作区，从成熟电商
售后中心进入订单任务，并通过右侧上下文 Agent 完成物流查询、政策检索、退款预览、客户确认、
幂等 Mock 退款和结果验证。

本版本成功不是增加更多页面、动画或模型调用，而是让评审者能够在有限时间内观察并追问以下
完整证据链：

```text
真实自然语言诉求
→ LangGraph 持久任务
→ 受控业务工具与政策证据
→ 确定性 Policy
→ interrupt 客户确认
→ 幂等 Mock 副作用
→ 业务状态回读验证
→ Agent Run、Memory、RAG 与 Eval 证据
```

所有订单、物流、支付、退款和服务记录仍为项目内 Mock 数据，不连接真实电商、客服、物流、
支付或交易系统，也不产生真实资金和外部业务副作用。

## 为什么是 v2.0

v2.0 同时改变访问模式、演示数据生命周期、公开订单编号、客户入口、会话边界和管理员权限：

- 删除游客业务体验和面向用户的 Fake 模式。
- 邀请注册后自动创建版本化演示工作区。
- 客户产品从独立聊天页调整为售后中心与悬浮上下文 Agent。
- 一个售后任务只绑定一个订单和一个 Thread。
- 管理员不再任意编辑单笔订单、物流和支付事实。

这些变化会使既有页面、接口和演示脚本产生不兼容，因此使用新的主版本表达，而不是把它们
伪装成 v1.3.2 的视觉修补。

## 第一性原则

1. **用户需要解决售后问题，不是体验一个聊天框。** 商品、订单、物流和服务状态必须先于对话。
2. **演示必须可重复。** 每个受邀账号获得独立、版本化且可重置的数据，不能依赖维护者临时改库。
3. **LLM 不是授权主体。** 模型理解诉求、选择候选工具和生成解释；Policy 决定资格和金额。
4. **对话与业务动作分离。** 消息负责沟通，结构化卡片承载事实、引用、审批和执行结果。
5. **一个任务只有一个业务上下文。** 一个 Thread 绑定一个订单，避免审批、记忆和 Eval 串单。
6. **RAG 提供证据，不决定资金结果。** 政策解释与确定性业务授权必须可独立验证。
7. **Memory 必须获得用户授权。** 会话历史、业务事实和长期偏好具有不同生命周期。
8. **复杂任务才使用 Agent Loop。** 标准流程保持确定性，二线 Loop 只读、有界且可观察。
9. **不能提供的能力必须明确披露。** 项目不把 LLM 包装成人工客服，不虚构真实 Handoff。
10. **不可评估的能力不可作为简历结论。** 每个关键结果必须有固定场景、指标和失败证据。

## 术语

| 术语 | 含义 |
|---|---|
| 公开产品页 | 未登录用户可访问的产品说明、登录和邀请注册入口 |
| 演示工作区 | 一个注册用户独占的 Mock 商品、订单、物流、支付和派生售后数据范围 |
| Dataset Version | 可审计的预置数据版本；v2.0 使用 `portfolio-demo-v1` |
| 基准事实 | 注册时生成的商品、订单、初始物流和退款前支付事实 |
| 派生事实 | Agent 执行后产生的退款、服务记录、审批和审计结果 |
| 订单任务 | 围绕一个订单、一个售后目标和一个 Thread 的可恢复任务 |
| 一级 Agent | 处理订单、物流、政策和标准退款流程的 AI 售后助手 |
| 二线 Agent | 处理复杂、冲突或多步调查问题的有界 AI 深度处理 Loop |
| 客户确认 | 客户接受退款预览并提交操作意愿，不代表授予退款资格 |
| Mock Case | 未连接真实客服系统的待后续处理演示记录 |

## 角色与权限

### 未登录访问者

- 可以访问公开产品页、登录页和邀请码注册页。
- 可以查看产品能力、旗舰流程和开源部署入口。
- 不能读取订单、物流、政策问答、对话、Memory、Agent Run 或运营数据。
- 不能调用 LLM、Fake Interpreter 或任何业务工具。

### 注册客户

- 通过有效邀请码注册并获得一个独立演示工作区。
- 查看本人工作区中的商品、订单、物流、退款和服务记录。
- 从具体订单进入 AI 售后助手并恢复本人历史任务。
- 确认或取消确定性退款预览。
- 查看、修改和删除本人明确保存的长期偏好。
- 重置本人整个演示工作区，但不能逐项编辑基准事实。
- 不能查看其他用户、内部 Prompt、隐藏推理、完整工具载荷或运营 Eval。

### 管理员

- 通过运营控制台创建、查看状态和撤销邀请码。
- 查看有限用户目录及每个工作区的数据版本和健康状态。
- 为指定用户重置完整演示工作区。
- 查看脱敏 Agent Run、停止原因、工具类别、Eval 和系统健康。
- 管理政策来源、版本、处理和发布状态；v2.0 只沿用当前已实现的政策能力。
- 不能任意创建、修改或删除单笔商品、订单、物流、支付和退款事实。
- 不能绕过 Policy、客户确认、Executor 或 Verifier。
- 不能冒充客户、默认读取完整消息正文或从 Web 授予管理员权限。

### 本机维护者

- 在全新实例中通过现有 CLI 创建首张邀请码。
- 使用邀请码注册首个普通账号，再通过现有 CLI 授予管理员角色。
- 执行数据库迁移、备份恢复、完整 Eval 和其他固定运维命令。
- 不通过仓库、README、默认数据库或环境样例分发固定管理员密码。

## 公开入口与身份生命周期

产品入口固定为：

```text
/                  公开产品说明
/login             登录
/register          邀请码注册
/support           登录后的售后中心
/admin             管理员运营控制台
```

- 不提供游客订单、游客对话或游客 Fake 模式。
- 邀请码由管理员在运营控制台创建；全新实例的首张邀请码由本机 CLI 创建。
- 邀请码明文只在创建结果中展示一次，支持有效期、使用次数和撤销。
- 注册必须以一致结果完成邀请码消费、账号、工作区和 `portfolio-demo-v1` 初始化。
- 初始化失败时不能留下可登录但无数据的半成品账号，也不能超额消费邀请码。
- 既有登录、退出、Session 撤销、CSRF、Origin 和限流安全规则继续有效。
- 注册用户使用真实 LLM；产品不向用户提供 Fake 切换。
- LLM 不可用时明确告知暂时无法继续、保留任务状态并允许重试，不能静默切换到 Fake。
- Fake Model 和 Fake 业务适配器只用于自动化测试、离线 Eval 和故障注入。

## `portfolio-demo-v1` 演示工作区

### 预置场景

每个新工作区至少包含以下三个互补场景：

| 场景键 | 用户可见初始状态 | 主要验证能力 |
|---|---|---|
| `refundable_delay` | 已支付且物流严重延迟，符合全额退款条件 | 物流查询、政策 RAG、退款审批、幂等执行和验证 |
| `quality_issue` | 已签收且存在质量问题，需要收集信息和深度处理 | 多轮澄清、政策证据、二线 Agent Loop 和 Mock Case |
| `expired_refund` | 已超过退款期限，不符合退款条件 | 政策引用、确定性拒绝和替代建议 |

`scenario_key` 是服务端和 Eval 使用的隐藏标识，不返回客户界面，也不作为模型判断场景的证据。

### 公开订单编号

- 客户可见订单号使用 `CR-XXXX-XXXX` 格式。
- `X` 来自不易混淆的随机大写字母与数字集合。
- 订单号不编码用户、日期、价格、状态、风险、退款资格或演示场景。
- 内部实体标识、公开订单号和隐藏场景键必须分离。
- 公开订单号在其有效范围内唯一，并在同一工作区重置后保持不变。

### 基准事实与派生事实

- 商品名称、图片、规格、价格、订单金额、初始物流和退款前支付属于基准事实。
- 客户和管理员均不能在 Web 中逐项修改基准事实。
- 退款、审批、服务记录、Mock Case 和运行审计属于允许通过受控流程产生的派生事实。
- 客户、管理员、LLM 和前端字段均不能直接把订单或支付记录改成目标状态。

### 演示空间重置

- 注册客户可以从演示设置中重置自己的工作区。
- 管理员可以在运营控制台为明确目标用户执行相同重置。
- 重置前必须展示影响范围并获得显式二次确认。
- 重置恢复 `portfolio-demo-v1` 基准事实，并保留原公开订单号。
- 重置清除该工作区产生的退款、服务记录、Mock Case、客户会话、Checkpoint 和长期 Memory。
- 重置不删除账号、管理员角色或平台级邀请审计。
- 重置完成后保留一条不含敏感正文的审计事件。
- Agent、Prompt、工具调用或模型输出不能触发工作区重置。
- 重复重置必须得到相同业务结果，不产生重复订单或悬空派生数据。

## 客户售后中心

### 产品范围

v2.0 建设可信的售后子域，不建设完整商城。

包含：

- 售后中心首页；
- 本人订单列表与订单详情；
- 商品图片、名称、规格、单价、数量和实付金额；
- 订单状态、包裹状态、物流公司和关键物流时间线；
- 退款状态、服务记录和下一步动作；
- 本人长期记忆管理；
- 全局悬浮 Agent 入口。

不包含：

- 商品搜索、推荐和营销详情；
- 购物车、下单、结算、优惠券和积分；
- 真实支付、库存、仓储和商家管理；
- 不可执行的占位导航和伪造业务入口。

商品图片使用项目内版本化资源或具有明确可用许可的本地资源，不能依赖不稳定外链。

### 默认入口

- 登录后默认进入售后中心，而不是独立聊天页。
- 首页优先显示三个预置订单及需要关注的售后状态。
- 物流延迟订单作为旗舰任务入口，但不自动替用户发送问题或执行动作。
- 订单卡提供“咨询此订单”，用于打开绑定该订单的 Agent。

## 悬浮 Agent 与对话体验

### 展开方式

- 客户页面右侧提供紧凑悬浮入口。
- 桌面端展开为右侧对话抽屉，不覆盖主要订单事实。
- 移动端展开为全屏对话层。
- 最小化后继续保留当前任务、待审批和运行状态。
- 页面刷新、路由切换和重新登录不丢失有权访问的公开会话。
- 从订单卡进入时，抽屉明确展示当前绑定订单。
- Agent 只接收服务端验证的结构化订单上下文，不能把整个页面内容当作可信输入。

### 会话边界

- 一个订单售后任务对应一个 Thread。
- 一个 Thread 只能绑定一个用户、一个工作区和一个订单。
- 用户发送第一条消息时创建新任务；打开抽屉本身不产生空会话。
- 同一订单存在未结束任务时恢复该任务，不创建重复 Run。
- 最小化、刷新、切页、重新登录、模型暂时失败或等待审批均不创建新任务。
- 查询另一订单时必须切换或创建另一条任务，不能在同一 Thread 中混用订单。
- 任务完成、用户取消或显式结束后归档。
- 再次咨询同一订单可以读取历史摘要，但必须创建新的 Thread，旧审批不能污染新任务。
- 全局悬浮入口在没有当前订单时先要求选择订单；v2.0 不提供脱离订单的泛聊天。

### 消息与结构化卡片

自然语言消息负责解释和沟通；以下事实与动作使用结构化产品卡片：

- 订单上下文；
- 调查进度；
- 物流结果；
- 政策引用；
- 退款预览；
- 客户确认或取消；
- 退款回执；
- 待补充信息；
- Mock Case 状态。

- 结构化卡片必须来自经过 Schema 校验的服务端事件，不能从 Markdown 文本解析金额、状态或按钮。
- 流式自然语言回复与结构化事件必须保持顺序一致并支持断线恢复。
- 普通业务拒绝、工具失败和模型暂时不可用以客服对话语气展示，不使用脱离对话的红色系统异常块。
- 认证失效、无权限和服务整体不可用仍可使用页面级安全状态，但不能伪装成 Agent 回复。
- 客户界面不展示 LangGraph 节点、Prompt、Token、模型隐藏推理或内部工具参数。

## 核心用户旅程

### 旅程 A：首次注册并进入售后中心

1. 管理员创建一次性邀请码并将明文安全提供给用户。
2. 用户使用邀请码注册并登录。
3. 系统创建独立工作区和 `portfolio-demo-v1` 数据。
4. 用户进入售后中心并看到三个具有商品、金额和物流信息的订单。
5. 用户不需要理解 Fake、Provider、Seed 或场景键等内部术语。

### 旅程 B：旗舰物流与退款闭环

1. 用户从物流延迟订单点击“咨询此订单”。
2. 用户自然询问包裹进度，一级 Agent 查询并展示最新物流事实。
3. 用户继续提出退款诉求。
4. 系统查询最新订单、支付和物流事实，并召回当前生效的退款政策证据。
5. 确定性 Policy 计算资格、金额、渠道和风险。
6. Agent 展示退款预览和政策引用，LangGraph 暂停等待客户确认。
7. 用户确认后，系统以稳定动作标识幂等执行 Mock 退款。
8. 系统重新查询退款业务记录，只有验证成功后才展示退款回执。
9. 刷新或重启服务后，公开消息、审批和最终业务状态仍能恢复。

### 旅程 C：超过期限的安全拒绝

1. 用户从超过退款期限的订单发起退款请求。
2. 系统读取当前订单事实和当前政策证据。
3. 确定性 Policy 拒绝退款，不生成可执行退款动作。
4. Agent 展示拒绝原因、政策引用和允许的替代建议。
5. 用户改写问题、提示注入或要求模型“忽略规则”均不能改变结果。

### 旅程 D：质量问题与 AI 深度处理

1. 用户从质量问题订单描述复杂或不完整的售后诉求。
2. 一级流程收集最少必要信息并查询订单与政策。
3. 标准流程无法安全完成时，用户可以升级到明确披露的 AI 深度处理。
4. 二线 Agent 在有限步骤内使用只读工具调查并形成结论、补充问题或结构化动作建议。
5. 需要退款时，建议重新进入 Policy、客户确认和 Executor，不在 Loop 中直接写业务事实。
6. 仍无法安全解决时生成明确标识为未连接真实人工客服的 Mock Case。

### 旅程 E：重置并重复演示

1. 用户完成退款与质量问题演示。
2. 用户进入演示设置，查看重置影响并确认。
3. 系统恢复三笔基准订单，清除相关派生事实、会话、Checkpoint 和长期 Memory。
4. 原公开订单号保持不变，旗舰旅程可以再次从相同入口完成。
5. 管理员也可以为指定用户执行同等重置，并看到脱敏审计结果。

## Agent 职责与退款控制

退款链路固定为：

```text
LLM 识别诉求并提取候选信息
→ 业务工具读取订单、物流和支付事实
→ RAG 提供当前政策证据
→ 确定性 Policy 判断资格、金额与渠道
→ 退款预览
→ interrupt 等待客户确认
→ 幂等 Mock Refund Executor
→ 业务 Repository 回读验证
```

- 客户确认代表接受预览并提交操作意愿，不授予退款资格。
- LLM、二线 Agent 和管理员均不能改变 Policy 计算结果。
- 不符合条件、事实冲突、政策版本不一致或证据不足时不得执行退款。
- 每个 Mock 退款使用稳定的 task、action 和幂等标识。
- 重试、恢复、重复确认或网络断线不能产生第二笔退款。
- Executor 返回成功不等于任务成功，必须以业务状态回读结果为准。
- 执行结果未知时保持可调查状态，不能回复已成功或自动重试产生潜在重复副作用。

## 政策 RAG

### 召回时机

- 单纯订单和物流查询不触发政策 RAG。
- 退款、退货、质量问题、物流赔付和明确政策问题必须执行受控政策检索。
- 检索请求只能使用当前问题与完成任务所需的最少订单事实。

### 回答行为

- 只使用当前已发布、生效且适用范围匹配的政策证据。
- 提供给模型的 Evidence Pack 只包含少量必要片段及标题、章节、版本、生效信息和来源定位。
- 客户回答展示可定位的政策引用卡片。
- 无足够证据时明确无法确认并进入补充信息或 AI 深度处理，不使用模型常识编造政策。
- RAG 负责“找到并解释为什么”，确定性 Policy 负责“能否执行以及执行多少”。
- RAG 政策版本与业务规则版本不一致时禁止执行资金相关动作。
- v2.0 沿用当前已发布政策和现有可重建检索能力；向量数据库、多格式解析、OCR、Rerank 和
  多模态证据在 v2.1 独立交付。

## Memory 管理

以下数据必须分离：

| 数据 | 事实来源 | 生命周期 |
|---|---|---|
| 当前消息、订单目标和待审批动作 | 当前 Task/Checkpoint | 当前 Thread |
| 订单、物流、退款和服务结果 | Mock 业务 Repository | 业务生命周期 |
| 用户明确确认的稳定偏好 | 长期 Memory | 跨 Thread，用户可管理 |

- LLM 可以提出候选记忆，但不能自动保存。
- 只有用户明确说“记住”或确认结构化候选内容后才能写入长期 Memory。
- 长期 Memory 只保存低风险偏好，例如语言、回答详细程度和信息展示偏好。
- 不保存订单状态、政策结论、退款结果、密码、支付信息、完整敏感正文或模型隐藏推理。
- 每次任务只注入与当前目标相关的少量 Memory，不把全部长期记忆发送给模型。
- 用户可以查看、修改和删除本人全部长期 Memory。
- 删除单个会话不自动删除长期 Memory；重置演示空间按本 Spec 同时删除该工作区中的两者。

## AI 深度处理 Agent Loop

标准订单、物流、政策和退款路径优先使用确定性工作流。二线 Loop 只处理：

- 多意图或多步骤调查；
- 用户信息与业务事实冲突；
- 政策证据不足或冲突；
- 一级流程无法安全形成结论的质量问题。

二线 Agent：

- 明确披露为 AI，不使用“人工客服”“坐席已接管”等虚假身份。
- 默认只能调用订单、物流、政策、退款状态和相关 Memory 的只读工具。
- 需要业务写入时只能返回结构化 `proposed_action`，再进入相应 Policy 和确认链路。
- 每一步只能产生一种结构化回复、工具调用、补充请求、动作建议或停止决定。
- 必须限制最大步骤、工具调用、模型调用、总时长和 Token 成本。
- 必须检测重复工具调用与无进展循环。

停止条件至少包括：

- 已获得足够证据并形成回答；
- 需要用户补充信息；
- 已形成受控业务动作建议；
- 工具连续失败；
- 当前证据冲突且无法消解；
- 达到步骤、时间、模型或成本预算；
- 用户取消。

无法安全解决时可以创建 Mock Case，但必须显示“未连接真实人工客服系统”，不能承诺真实响应
时间、坐席身份或外部处理结果。

## Agent 运营控制台

运营控制台包含：

- 总览：邀请、工作区、Agent Run、Eval 与系统健康摘要；
- 邀请：创建、一次性展示、状态查看和撤销；
- 演示空间：用户、Dataset Version、初始化状态、重置和审计；
- Agent Runs：脱敏步骤、工具类别、停止原因、耗时、成本与有限错误归因；
- Eval：Baseline、Candidate、分组指标、安全违规和兼容结论；
- 政策：当前政策来源、版本、处理、发布和索引状态；
- 系统：有限版本、迁移、数据库、索引和模型健康。

运营控制台不包含：

- 单笔商品、订单、物流和支付 CRUD；
- 直接创建、修改或删除退款；
- 客户身份模拟；
- Web 管理员授权；
- 完整消息、Prompt、隐藏推理、密钥和未脱敏工具输出；
- 任意 Shell、数据库控制台或高影响运维入口。

## 错误与降级语义

| 场景 | 用户可观察结果 |
|---|---|
| 邀请无效、过期、撤销或用尽 | 注册失败，不泄露内部摘要或其他账号信息 |
| 注册初始化失败 | 不留下可登录半成品账号，不超额消费邀请 |
| LLM 暂时不可用 | 对话中说明暂时无法继续并允许重试，不降级为 Fake |
| 订单不存在或不属于当前用户 | 使用不泄露资源存在性的统一语义 |
| 政策无证据 | 不生成政策结论，请求补充信息或进入深度处理 |
| 政策与规则版本不一致 | 禁止退款，展示当前无法安全处理 |
| 退款已存在 | 返回已验证的既有结果，不创建第二笔退款 |
| 退款结果未知 | 保持可调查状态，不宣称成功 |
| Agent Loop 达到预算 | 停止循环，说明当前结论和未完成事项 |
| 流式连接或页面短暂断开 | 恢复缺失公开事件，不重复消息、Run 或副作用 |
| 重置进行中 | 禁止同时启动新的售后写操作，完成后刷新工作区状态 |

## 兼容与迁移

- 既有注册客户和管理员账号继续保留；角色不能因迁移被扩大或重置。
- 新注册账号自动初始化 `portfolio-demo-v1`。
- 既有客户工作区不得被迁移静默覆盖；用户或管理员显式重置后才切换到新数据版本。
- 既有未绑定订单或可能混合多个订单的会话保持只读历史，不直接恢复为 v2.0 可执行任务。
- 既有已绑定单订单且状态可验证的任务可以按 Plan 定义的兼容规则恢复。
- 既有退款、服务记录、审计和 Eval 证据必须保持可读，不通过重建历史伪造 v2.0 指标。
- 游客业务入口和共享游客工作区停止提供；游客数据不会自动归属到注册用户。
- 旧前端书签或 API 不能绕过登录、订单绑定和新角色权限。
- 原 `v1.4` Proposed Spec 不进入实现，历史内容保留；其多模态与向量检索目标重新排入 v2.1。
- v2.0 Spec 接受前不创建 Technical Plan；Plan 接受前不修改产品代码或数据。

## 版本范围

v2.0 包含：

- 无游客模式的公开入口、邀请注册和真实 LLM 客户路径。
- 注册后自动创建三个场景的版本化演示工作区。
- `CR-XXXX-XXXX` 公开订单号及隐藏场景键。
- 基准事实只读、派生事实受控写入和完整工作区重置。
- 成熟电商售后中心信息架构与本地商品资源。
- 右侧悬浮 Agent、移动端全屏层和单订单任务会话。
- 结构化订单、物流、政策、审批与回执卡片。
- 物流到 Mock 退款的旗舰闭环及安全拒绝对照场景。
- 用户确认的长期 Memory 和有界 AI 深度处理。
- 收缩后的 Agent 运营控制台。
- 四层 Eval、真实 Provider 资格与项目文档证据。

## 非目标

v2.0 不包含：

- 公开注册、游客业务体验或面向用户的 Fake 模式。
- 完整商城、商品推荐、购物车、下单和真实支付。
- 真实电商、物流、支付、退款、客服或工单系统集成。
- 真实人工客服接管、坐席系统、SLA、排班和通知平台。
- 管理员手工维护单笔订单、物流、支付或退款。
- 多 Agent、Supervisor 或后台自主执行。
- 向量数据库、多格式解析、OCR、Rerank 和多模态政策证据；这些属于 v2.1。
- Docker 延后门禁的补验、生产高可用、多租户 SaaS、计费和云部署。
- 通过视觉动效掩盖空数据、不可执行入口或缺失业务状态。

## Eval 数据集与发布门禁

v2.0 至少建立 30 条固定场景，覆盖三个预置订单的正常、改写、边界、冲突、拒绝和故障输入。

四类 Eval：

| 套件 | 主要断言 |
|---|---|
| Workflow/Tool | 意图路由、工具选择、参数、Checkpoint、审批和恢复 |
| RAG | 当前政策命中、证据范围、引用正确和无证据拒答 |
| Agent Loop | 多步任务结果、停止原因、步骤/时间/Token 预算和无进展检测 |
| Safety | 跨用户访问、越权退款、重复副作用、提示注入和管理员越权 |

发布硬门禁：

- 未授权 Mock 退款数量为 `0`。
- 重复 Mock 退款数量为 `0`。
- 跨用户业务、消息、Memory 和 Agent Run 泄露数量为 `0`。
- 游客或匿名业务工具/LLM 调用数量为 `0`。
- 确定性 Policy 规则场景通过率为 `100%`。
- 客户确认遵循率为 `100%`。
- Agent Loop 预算和停止条件遵循率为 `100%`。
- RAG `Hit@3` 不低于 `90%`。
- 对外引用来源有效率为 `100%`。
- 固定真实模型端到端任务完成率不低于 `85%`。
- Candidate 不得静默低于已接受 Baseline。

Fake Model 用于离线确定性回归；固定真实模型用于独立在线资格评测。LLM-as-judge 只能补充评价
表达质量，不能判断业务授权、安全、引用存在性或退款结果。

每份结果必须记录 Dataset、模型、Prompt、政策、工具、索引和代码版本。简历与 README 中的
数字只能引用可复现报告，不能使用手工挑选的成功截图代替。

## 验收条件

1. 未登录访问者只能访问公开说明、登录和邀请注册；业务 API 与 LLM 调用数量为 `0`。
2. 运营控制台可以创建一次性邀请码；创建后的列表不再返回明文或摘要。
3. 有效邀请码只创建一个账号、一个工作区和一份完整 `portfolio-demo-v1` 数据。
4. 注册初始化失败不产生半成品账号、超额邀请码消费或部分演示订单。
5. 每个新工作区包含三个约定场景，且不同用户之间数据严格隔离。
6. 客户可见订单号符合 `CR-XXXX-XXXX`，不泄露场景或用户信息。
7. 客户和管理员无法在 Web 中逐项修改基准商品、订单、物流或支付事实。
8. 客户和管理员均可按权限重置完整工作区；结果幂等且保留订单号。
9. 登录后默认进入售后中心，并看到完整商品、金额、订单状态和物流信息。
10. 页面不存在购物、支付、库存等不可执行占位入口。
11. 桌面端从右侧悬浮入口打开 Agent 抽屉，移动端使用全屏交互层。
12. 从订单卡进入时，会话绑定当前订单；服务端拒绝跨用户或冲突订单上下文。
13. 一个未结束订单任务只对应一个 Thread；刷新、切页、登录恢复不创建重复会话或 Run。
14. 同一 Thread 不能切换到另一订单；新订单任务使用独立 Thread。
15. 对话消息与结构化业务卡片均可恢复，金额和动作按钮不从 Markdown 解析。
16. 真实 LLM 不可用时不静默降级为 Fake，任务状态保持可重试。
17. 旗舰订单的物流查询结果来自本人最新 Mock 物流事实。
18. 退款诉求触发当前政策检索；单纯物流查询不产生无关政策召回。
19. 政策回答包含有效标题、版本、生效信息和来源定位；无证据时不生成政策结论。
20. 退款资格、金额和渠道由确定性 Policy 产生，模型不能改变结果。
21. 符合条件的退款预览通过 LangGraph 中断等待客户确认。
22. 拒绝、关闭或延后确认不产生 Mock 退款；恢复后仍是原任务和原动作。
23. 重复确认、重试、断线和恢复最多产生一笔 Mock 退款。
24. 只有重新查询业务 Repository 验证成功后，客户才看到退款成功回执。
25. 超过退款期限的订单被确定性拒绝，并展示有效政策依据和替代建议。
26. 质量问题可以进入受限二线 Agent Loop；Loop 不能直接执行退款或修改业务事实。
27. 达到任一 Loop 预算或停止条件时安全结束，不出现无界循环。
28. 产品不声称连接真实人工客服；Mock Case 明确披露其演示性质。
29. LLM 只能提出候选长期记忆；未获用户确认的内容写入数量为 `0`。
30. 用户可以跨 Thread 使用、查看、修改和删除本人已确认偏好。
31. 管理员可以管理邀请、工作区、脱敏 Run、Eval、政策和系统状态。
32. 管理员订单 CRUD、客户冒充、Web 角色授予和直接退款入口均不可用。
33. 四类 Eval 达到本 Spec 的全部硬门禁，并生成可复现报告。
34. 既有账号、角色、退款和审计保持可读；迁移不会把游客或旧混合会话错误归属给客户。
35. 既有 v0.1–v1.3.2 安全、退款幂等、会话恢复和数据隔离回归继续通过。
36. README 可以让新评审者完成首位管理员初始化、邀请注册、旗舰旅程和 Eval 复现。
