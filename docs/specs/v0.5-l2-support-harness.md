# Feature Spec：v0.5 LLM 二线客服 Agent Harness

状态：Accepted  
日期：2026-07-19  
接受日期：2026-07-19  
依赖版本：v0.4 Mock 退款预览、审批与幂等执行  
关联决策：[`../adr/0006-llm-l2-support-harness.md`](../adr/0006-llm-l2-support-harness.md)

## 目标

当现有确定性售后流程无法安全解决问题，或者受邀用户明确要求进一步协助时，系统可以
将当前问题升级到一个明确标注为 AI 的 LLM 二线客服。该客服通过受控 Harness 加载当前
账号的最小上下文，在有限步骤内选择只读工具、检索政策、请求补充信息并形成有证据的
处理结果。

Harness 同时建立两类记忆：当前 Case 的工作记忆由 LangGraph Checkpointer 管理；只有
用户明确确认的稳定偏好才进入独立长期记忆 Store，并支持查看、纠正和删除。订单、物流、
支付、退款和政策仍由原业务数据库与 RAG 来源提供，不能被记忆替代。

系统不接入真实客服平台，也不声称真人参与。LLM 二线客服不能批准退款、修改权限或绕过
既有 Policy；涉及 R1/R2 写操作时只能提出候选动作，并进入对应的确认或审批流程。

本版本建立以下最小闭环：

```text
一线流程无法安全完成或用户要求升级
→ 展示“AI 二线客服”升级预览
→ 用户确认进入 L2 Support Case
→ Harness 装配可信上下文与允许工具
→ 有界 Agent Loop：决策 → Policy → 工具 → 观察
→ 回答、请求用户补充、提出受控动作或安全停止
→ 保存 Case 结果、Checkpoint、公开 Trace 与 Eval 证据
```

## 第一性原则

1. 用户需要的是问题被解决，不是把“转人工”文案替换成另一个聊天机器人。
2. LLM 二线客服必须明确披露为 AI，不能让用户误以为真人接单。
3. Agent Loop 只用于需要多步观察和工具选择的问题；简单请求继续走已有确定性路径。
4. 模型提出下一步，Harness 决定它是否符合 Schema、权限、工具和预算约束。
5. 业务数据库和已发布政策是事实来源；工作记忆和长期记忆不能覆盖实时事实。
6. 长期记忆必须有明确用途、用户同意和独立删除语义，不能从所有对话静默学习。
7. 写操作沿用现有风险分级；L2 Agent 不能替用户确认或批准自己的候选动作。
8. 每个循环都必须可停止、可恢复、可审计和可评估，不能依赖隐藏推理解释成功。

## 产品语义

- 页面统一使用“AI 二线客服”或“L2 Support Agent”，不使用“真人客服已接入”等表述。
- “升级”表示切换到一个工具能力更完整、上下文更丰富的受控 LLM Agent，不表示请求已
  被外部客服组织接收。
- L2 Support Case 是项目内可恢复任务，不是 CRM 工单，不触发消息、电话或外部通知。
- L2 Agent 与当前一线工作流职责不同，但本版本只新增一个 Agent，不构建 Agent 群、
  Supervisor 或自主协作网络。

## 角色与权限

| 角色 | 数据范围 | L2 Harness 能力 |
|---|---|---|
| 游客 | 共享只读演示数据 | 不能启动真实 LLM L2 Case，也不能读写长期记忆 |
| 受邀用户 | 所属私有工作区、conversation 与本人记忆 | 可以确认进入 L2、继续 Case、审批动作和管理本人记忆 |
| L2 Support Agent | 当前请求注入的最小可信上下文 | 只能通过 Harness 选择候选工具或动作，没有独立授权身份 |
| 可信操作员 | 邀请和服务端配置 | 不查看用户 Case，不代替用户批准业务动作 |

模型看到的 `user_id`、工作区、模型权限、工具集和预算都来自服务端可信上下文。浏览器、
用户文本、记忆内容或模型输出不能扩展这些权限。

## 用户故事

### 升级到 AI 二线客服

作为受邀用户，当一线流程无法解决问题或我明确要求进一步协助时，我可以先查看升级说明，
确认对方是 AI、会使用哪些数据和工具，再决定是否启动 L2 Support Case。

### 多步骤处理

作为受邀用户，我可以让 L2 Agent 组合本人订单、物流、退款状态和售后政策证据分析复杂
问题。Agent 应展示结论和证据，而不是展示隐藏思维过程。

### 补充信息与恢复

作为受邀用户，当 L2 Agent 缺少必要信息时，我可以补充回答。页面关闭或服务重启后，
Case 可以从同一恢复点继续，不重复已经完成的工具副作用或模型步骤。

### 审批高风险动作

作为受邀用户，当 L2 Agent 建议 Mock 退款时，我仍然看到由确定性 Policy 生成的原退款
预览，并由我明确批准或拒绝。L2 Agent 不能替我点击批准。

### 管理长期记忆

作为受邀用户，我可以查看 L2 Agent 建议保存的稳定偏好，确认后再写入长期记忆，并可以
以后查看、纠正或删除。删除记忆不删除业务订单或历史 Case。

### 查看 Case 结果

作为受邀用户，我可以查看本人 L2 Case 的公开状态、使用过的工具类别、证据、最终结果
和停止原因，但看不到模型隐藏推理或其他用户的数据。

## 进入 L2 Harness 的条件

系统可以提供 L2 升级预览：

- 受邀用户明确要求“进一步处理”“高级客服”或等价的 AI 升级诉求。
- 当前请求属于电商售后领域，但需要组合多个现有只读工具才能形成结论。
- 政策证据不足或冲突，需要结合用户补充信息与业务事实继续分析。
- 退款结果未知、验证不一致或业务拒绝，需要读取多类证据后说明后续路径。
- 当前一线能力返回明确的未支持状态，但问题仍属于本项目售后范围。

以下情况不能启动 L2 Case：

- 游客、未登录、Session 失效或 conversation 不属于当前身份。
- 问题信息不足到无法确定售后目标，应先要求用户说明问题。
- 请求明显与电商售后无关，或要求真实交易、越权访问、绕过审批等禁止动作。
- 一线流程已经能可靠完成请求，仅因为模型偏好更长推理而建议升级。
- 用户拒绝升级、预览已失效，或当前用户的 LLM 权限和配额不允许启动。

是否展示升级入口由确定性路由和 Policy 判断。LLM 可以识别升级诉求，但不能自行创建
Case、授予工具或扩大预算。

## 升级预览与确认

启动前至少向用户展示：

- 明确的“AI 二线客服，并非真人”说明。
- 当前问题和可选关联 Mock 订单。
- 将提供给 L2 Agent 的上下文类别，不展示内部凭据或隐藏配置。
- 允许使用的工具类别和任何可能出现的后续审批。
- 最大步骤或等价的有界执行说明。
- 是否会读取现有长期记忆；默认不会写入新长期记忆。
- 稳定的 Case 预览标识或等价服务端绑定。

用户只能确认或取消升级，不能覆盖身份、工作区、工具、预算、风险、模型权限或服务端
上下文。取消不会创建 L2 Case，也不会产生新的业务工具调用。

## Harness 行为契约

Harness 必须提供以下行为边界，具体代码结构由 Technical Plan 决定：

### 上下文装配

- 只装配当前用户、工作区、conversation 和可选订单所需的最小上下文。
- 业务正文按需通过工具重新读取，不把完整业务数据库复制进 Prompt 或 State。
- 当前有效政策、工具结果和用户确认记忆都保留来源及时间信息。
- Prompt、工具说明、用户数据和检索内容使用明确边界，防止数据伪装为系统指令。

### 结构化决策

每次循环只能产生一种受 Schema 约束的公开决策类型：

- 调用一个允许的工具。
- 请求用户补充必要信息。
- 提出需要用户确认或审批的候选动作。
- 提出一条长期记忆变更建议。
- 基于已验证证据回答并结束。
- 说明无法完成、预算耗尽或安全拒绝并停止。

模型不能输出任意节点名称、任意 Python 函数、SQL、Shell 或网络请求作为可执行动作。

### Tool Registry 与 Policy

- 每个 Case 获得服务端固定的工具白名单，工具契约必须类型化、单一职责并可替换为 Fake。
- v0.5 自动工具限定为 R0：查询本人订单、物流、退款状态、已发布政策和已确认长期记忆。
- R1 记忆写入必须进入独立确认；R2 Mock 退款必须复用 v0.4 审批和执行链。
- Harness 在调用前重新验证身份、工作区、参数、风险和循环预算。
- 工具返回值先进行结构和归属校验，再作为下一步 Observation；模型自报结果不算工具结果。

### 循环预算与停止

- 每个 Case 必须限制最大循环步骤、模型调用、工具调用、总时长和估算成本。
- 重复同一无进展动作、持续无效参数或工具连续失败必须触发提前停止。
- 用户取消、身份失效、工具越权、Prompt Injection、预算耗尽和恢复冲突都有明确终态。
- 循环结束后保存公开结果和停止原因，不保存或展示模型隐藏推理。

### 恢复与幂等

- Case、Step 和候选动作使用稳定标识；服务重启后复用同一 Checkpoint。
- 已成功完成的工具调用不能因节点重放而被无条件重复执行。
- 等待用户输入或动作审批时暂停；恢复前重新验证 Session、Case 归属和当前业务事实。
- 模型调用结果可以按稳定 Step 重放或重新获取，但不能伪造已经完成的业务副作用。

### 公开 Trace

用户和 Eval 可以观察 Case 状态、步骤编号、工具类别、脱敏参数摘要、结果状态、耗时和停止
原因。公开 Trace 不包含完整 Prompt、隐藏 Chain-of-thought、密钥或敏感工具正文。

## 记忆管理

### 工作记忆

- 当前 Case 的用户输入、结构化决策、已验证 Observation、待处理动作、预算和停止原因进入
  LangGraph State，并由 Checkpointer 支持暂停恢复。
- State 不保存数据库连接、模型客户端、密钥、完整业务库或可重新读取的大型正文。
- Case 完成后工作记忆不会自动转为长期记忆。

### 长期记忆

v0.5 只允许保存对后续客服交互稳定且低风险的信息，例如用户明确表达的语言、回复详细
程度或联系偏好。订单状态、物流、支付、退款资格、政策结论和模型推断不能保存为长期
事实。

- L2 Agent 只能提出结构化记忆建议，不能直接写入 Store。
- 写入前必须展示内容、用途和作用域，由用户明确确认或拒绝。
- 每条记忆保存来源、创建时间、最后确认时间和稳定标识。
- 用户可以列出、纠正和删除本人记忆；不同用户和工作区不能相互读取。
- 记忆在每次使用前经过 Schema 和作用域校验，不能扩展工具、权限或风险等级。
- 删除会话、删除业务数据和删除长期记忆具有独立语义。
- 具体 Store 实现、保留期限和更新冲突策略由 Technical Plan 决定。

## Case 状态

v0.5 最小公开状态包括：

```text
l2_awaiting_confirmation
  ├─ 用户取消 → l2_cancelled
  └─ 用户确认 → l2_active
                     ├─ 缺信息 → l2_waiting_user → l2_active
                     ├─ 候选写动作 → l2_waiting_approval → l2_active
                     ├─ 有证据完成 → l2_resolved
                     ├─ 无法完成 → l2_unresolved
                     ├─ 预算耗尽 → l2_budget_exhausted
                     └─ 安全拒绝/取消 → l2_stopped
```

- L2 Support Case 的公开元数据和最终状态属于业务事实，保存在业务 Repository。
- 循环恢复点和工作记忆保存在 Checkpointer。
- 用户长期记忆保存在独立 Store。
- RAG 索引继续是可重建派生数据。
- 三类数据不能相互替代。

## L2 Agent 与业务动作边界

- L2 Agent 可以解释并组合本人订单、物流、退款状态和政策证据。
- L2 Agent 可以提出退款申请候选，但资格、金额、渠道、风险和审批要求仍由 v0.4 的确定性
  Refund Policy 计算。
- L2 Agent 不能批准退款、修改 Mock 支付、直接创建退款、修改订单归属或写审计成功状态。
- L2 Agent 不能把长期记忆当作订单、退款或政策事实。
- 任何未来新增写工具都必须先进入独立 Spec 或 Plan 风险审查，不能仅添加 Prompt 描述。

## 公开用户结果

Web 至少能明确区分：

- 一线流程已经完成，无需升级。
- 可以升级到 AI 二线客服，正在等待确认。
- 用户取消升级，未创建 L2 Case。
- L2 Agent 正在执行、等待用户补充或等待动作审批。
- L2 Agent 基于工具与政策证据完成回答。
- L2 Agent 无法完成、预算耗尽、模型不可用或安全停止。
- 长期记忆建议正在等待确认、已保存、已拒绝、已纠正或已删除。
- Case、conversation 或记忆无权访问，使用不泄露资源存在性的统一错误语义。

系统不能使用“真人已接入”“客服已接单”等误导文案，也不能在没有业务或工具证据时声称
问题已经解决。

## 范围

包含：

- 受邀用户通过 Web 确认进入一个明确标注为 AI 的 L2 Support Case。
- 基于现有订单、物流、政策和退款只读能力的类型化 Tool Registry。
- 单个 L2 Agent 的有界决策、工具调用、Observation、补充信息和停止循环。
- R1/R2 候选动作分别进入记忆确认和现有退款审批链，不由 L2 Agent 自行执行。
- Case 工作记忆、Checkpoint、跨页面和跨进程恢复。
- 用户确认的低风险长期记忆，以及查看、纠正和删除。
- L2 Case 公开状态、最小业务元数据、公开 Trace 和审计。
- 模型失败、工具失败、无进展、预算耗尽和 Prompt Injection 的安全停止。
- Fake Model、Fake Tool、Fake Store 和固定 Agent Loop/Memory Eval。
- v0.1–v0.4 自动化测试、固定 Eval 和浏览器路径的完整回归。

## 非目标

- 真实人工客服、CRM、呼叫中心、消息、邮件、通知或真人接管。
- 多 Agent、Supervisor、专家群、Agent 间自主通信或后台自治任务。
- 任意 Shell、SQL、浏览器控制、开放网络请求或运行时注册未知工具。
- 自动批准退款、自动修改支付或绕过已有 R2 审批。
- 从所有对话静默提取长期记忆、跨用户共享记忆或自动学习模型权重。
- 把订单、物流、退款和政策快照长期记住并作为未来事实。
- 新向量数据库、Embedding、Rerank 或对 v0.2 RAG 的无证据升级。
- 模型隐藏推理存储、展示或作为 Eval 的必要输入。
- 生产并发、分布式 Worker、消息队列、SLA、计费或真实外部副作用。

## 安全、隐私与审计

- Case 创建、运行、恢复、工具调用、动作审批和记忆管理均限制在当前可信账号及工作区。
- 所有状态变更继续执行 Session、CSRF、Origin、输入上限和 thread/Case 互斥校验。
- 游客、跨用户、跨工作区、失效 Session 和未确认升级的 L2 模型调用及记忆写入均为零。
- 工具和记忆返回内容均是不可信数据，不能覆盖系统规则或注入下一步工具调用。
- 审计至少记录 Case/Step/Action 标识、模型与 Prompt 版本、工具、脱敏参数、预算、风险、
  用户决定、耗时、结果、停止原因和验证状态。
- 审计不记录 API Key、Cookie、完整 Prompt、隐藏推理或无关敏感业务正文。
- 使用云模型前继续遵守现有服务端授权和配额；长期记忆不会自动发送完整历史。

## 与已有版本的兼容要求

- v0.1 的 15 个订单/物流 Eval 场景继续全部通过。
- v0.2 的 20 个政策 RAG Eval 场景继续全部通过，引用语义不降低。
- v0.3 的 20 个 Web/权限 Eval 和浏览器路径继续全部通过。
- v0.4 的 24 个退款 Eval、审批、幂等和安全门禁继续全部通过。
- 游客继续使用确定性 Fake 一线模式，真实 LLM 调用和业务写入均为零。
- 简单订单、物流、政策和退款请求不会为了展示 Agent Loop 被强制升级到 L2。
- L2 Agent 提出的退款必须复用原有预览、审批、幂等和回读验证，不能复制一套写路径。
- 新增 Case 与 Memory 持久化使用增量迁移或独立 Store，不能要求删除已有本地数据。

## 验收条件

1. 受邀用户看到“AI 二线客服、并非真人”的升级预览，确认前不创建 Case 或调用 L2 模型。
2. 游客、越权用户、失效 Session 和非售后请求不能启动 L2 Case。
3. 简单可解决请求继续使用一线确定性路径，不产生不必要的 Agent Loop。
4. L2 Agent 每一步只产生一种合法结构化决策，非法或未知决策不能执行工具。
5. Tool Registry 只开放当前 Case 允许的工具；模型不能调用未注册工具或扩大参数范围。
6. 多步骤场景能够读取至少两类可信证据，并基于工具结果生成可追溯回答。
7. 缺少信息时 Case 暂停等待用户，跨页面或服务重启后从同一状态恢复。
8. 每个 Case 的步骤、模型、工具、时长和成本预算都有上限，耗尽后进入明确终态。
9. 重复无进展动作和连续工具失败会提前停止，不形成无限循环。
10. L2 Agent 提出退款时必须进入 v0.4 预览和用户审批，模型不能自行批准或修改参数。
11. 已完成工具调用、候选动作和记忆写入在重试、节点重放和恢复时不会重复产生副作用。
12. L2 Agent 只能提出长期记忆建议；未经用户确认的 Store 写入数量为 `0`。
13. 用户可以查看、纠正和删除本人长期记忆，操作不会改变订单、退款或历史 Case 事实。
14. 长期记忆不能覆盖最新业务工具结果、政策版本、权限或风险等级。
15. 不同用户和工作区的 Case、Checkpoint、工具结果和长期记忆泄露数量为 `0`。
16. 用户文本、政策、工具结果和记忆中的 Prompt Injection 不能改变工具白名单、审批或预算。
17. Case 完成、失败和停止均提供公开 Trace 和证据，但不暴露完整 Prompt 或隐藏推理。
18. 模型不可用、输出无效或配额不足时明确停止，不静默冒充真人或切换未授权模型。
19. 自动化测试不访问真实客服、电商、支付或物流系统，也不需要真实 LLM。
20. v0.1–v0.4 自动化测试、固定 Eval、浏览器路径和安全边界全部继续通过。

## v0.5 Eval

固定数据集至少覆盖 30 个场景：

- 6 个明确升级、政策冲突、退款未知、组合查询和复杂售后任务结果场景。
- 5 个多工具选择、参数、Observation、补充信息和正常停止的 Loop 场景。
- 5 个记忆建议、确认、拒绝、纠正、删除和业务事实优先场景。
- 5 个工具白名单、R2 审批、循环预算、无进展检测和恢复幂等场景。
- 5 个游客、跨用户、参数篡改、工具结果注入和记忆注入安全场景。
- 4 个模型失败、工具失败、预算耗尽和服务重启恢复场景。

发布门槛：

- 固定场景通过率：`100%`。
- 合法任务结果、工具选择和工具参数正确率：`100%`。
- 未授权工具调用、退款批准和长期记忆写入数量：`0`。
- 循环超过配置预算或无停止状态的场景数量：`0`。
- 恢复、重试或节点重放造成的重复副作用数量：`0`。
- 跨用户 Case、业务工具结果和记忆泄露数量：`0`。
- 已确认记忆写入、纠正和删除正确率：`100%`。
- 业务事实被长期记忆或模型内容覆盖的数量：`0`。
- 必要政策引用可解析率：`100%`。
- v0.1–v0.4 回归：全部通过。

Eval 断言结构化决策、工具轨迹、Observation、Case State、预算、用户输入、动作审批、
记忆副作用、公开结果和停止原因。自然语言措辞不要求逐字一致；LLM-as-judge 不能单独
决定发布。

## 已知限制

- L2 Support Agent 仍是 LLM，不具备真人判断、法律责任或真实客服组织能力。
- 所有订单、物流、支付、退款和 Case 均为本地 Mock 数据。
- 本版本只提供单个 L2 Agent，不实现专家 Agent 分工或跨 Agent 协作。
- 长期记忆只保存用户明确确认的低风险偏好，不实现自动画像或语义记忆网络。
- 当前 Tool Registry 只复用已有售后能力，不开放任意第三方工具。
- SQLite 和单实例 Web 不代表生产级并发、任务队列、计费或灾难恢复能力。

## 已接受决策

以下产品边界已随本 Spec 一并接受：

1. 产品统一称为“AI 二线客服”，不再使用“人工客服”。
2. 用户必须确认后才启动 L2 Case，用于披露 AI、上下文和成本。
3. v0.5 只实现一个 L2 Agent，不提前引入 Agent 群。
4. R0 工具可以在循环内自动调用，但仍执行服务端 Policy。
5. 退款等 R2 动作继续由用户审批，L2 Agent 不能代批。
6. 长期记忆只保存用户确认的低风险偏好。
7. 不保存模型隐藏推理，只保存结构化公开 Trace。
