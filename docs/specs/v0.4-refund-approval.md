# Feature Spec：v0.4 Mock 退款预览、审批与幂等执行

状态：Accepted  
日期：2026-07-17  
接受日期：2026-07-17  
依赖版本：v0.3 Web、邀请注册与私有业务数据  
关联决策：[`../adr/0005-mock-transaction-boundary.md`](../adr/0005-mock-transaction-boundary.md)

## 目标

受邀用户可以通过 Web 对话为所属私有工作区中的 Mock 订单申请整单退款。系统必须先
读取最新订单、物流、Mock 支付与已发布政策，由确定性 Policy 判断资格并计算退款预览；
只有当前登录用户明确批准后，系统才能幂等写入一笔 Mock 退款，并通过重新读取项目内
业务数据库验证最终结果。

本版本建立“自然语言退款诉求 → 业务事实与政策 → 确定性退款预览 → LangGraph
`interrupt` 审批 → 幂等 Fake Gateway → 执行后验证”的最小高风险 Agent 闭环。

所有交易数据和副作用均位于本地 Mock 环境，不接入真实支付渠道、电商平台、物流服务
或交易系统，也不产生真实资金变化。

## 第一性原则

1. 用户需要的是一笔经过验证的退款结果，不是模型承诺“已经退款”。
2. LLM 可以识别诉求和提取参数，但不能决定资格、金额、渠道或授权执行。
3. 退款预览只是候选动作；没有明确批准时，业务副作用必须为零。
4. 批准针对的是一份确定内容和版本的预览，业务事实变化后不能继续执行旧批准。
5. 重试、恢复、重复批准和并发请求都不能产生第二笔退款。
6. Gateway 返回成功不等于任务完成，必须重新读取业务状态进行验证。
7. 订单、支付、退款和审计是业务事实，不能以 Checkpoint 代替业务数据库。
8. Mock 环境不降低安全语义；审批、权限、幂等和失败处理仍按高风险动作设计。

## 角色与权限

| 角色 | 数据范围 | 退款能力 |
|---|---|---|
| 游客 | 共享只读演示工作区 | 可以询问通用政策；不能生成或执行退款预览 |
| 受邀用户 | 所属私有演示工作区 | 可以申请、查看、批准或拒绝本工作区的 Mock 整单退款 |
| 可信操作员 | 邀请管理入口 | 本版本不承担退款审批职责 |

当前登录的受邀用户是 v0.4 的演示审批人。发起退款请求不等于批准；系统必须在展示完整
预览后获取独立、明确的批准决定。

该审批模型只用于展示 Human-in-the-loop，不代表真实商家的客服、运营或财务授权体系。
多角色和多级审批不属于本版本。

## 用户故事

### 准备 Mock 交易事实

作为受邀用户，我可以通过确定性 Web 管理能力为所属工作区的演示订单准备退款所需的
最小 Mock 支付事实，并查看已有 Mock 退款状态。数据维护不通过 LLM 完成。

### 申请整单退款

作为受邀用户，我可以在对话中提供订单号和退款原因。系统读取最新业务事实和政策后，
如果订单符合条件，应展示一份不可由客户端修改的整单退款预览。

### 补充必要信息

作为受邀用户，如果订单号、退款原因或判断资格所需的 Mock 业务事实不足，系统应明确
要求补充或维护数据，不得猜测金额、支付状态或政策条件。

### 批准或拒绝

作为受邀用户，我可以在预览页面或对话审批入口明确批准或拒绝。拒绝不得创建退款；
批准只能作用于当前账号、工作区、thread 和待审批动作绑定的那份预览。

### 跨进程恢复审批

作为受邀用户，我可以关闭页面或重启服务，之后继续同一个待审批任务。恢复后展示的
预览和审批人边界必须与暂停前一致，不能自动批准。

### 查看验证后的结果

作为受邀用户，批准后应看到从 Mock 业务数据库重新读取的退款标识、金额、状态和验证
结果；如果结果未知或验证不一致，系统必须明确说明，不能声称退款成功。

## 范围

包含：

- 注册用户通过 Web 对话发起所属工作区 Mock 订单的整单退款请求。
- 退款意图、订单号和退款原因的结构化提取及多轮补充。
- 退款所需最小 Mock 支付事实的确定性维护和本地数据库持久化。
- 基于最新订单、物流、支付、已有退款和当前政策的确定性资格判断。
- 整单退款金额、原支付渠道、币种、原因、政策依据和风险摘要的预览。
- 使用 LangGraph `interrupt` 暂停并等待明确批准或拒绝。
- 待审批任务跨页面关闭和服务重启恢复。
- Fake Refund Gateway 的幂等写入、失败注入和执行后状态回读验证。
- 同订单已有待处理或已完成退款时的重复请求处理。
- 业务事实或政策在预览后变化时的过期预览检测。
- 当前账号、工作区、thread 与待审批动作的服务端绑定。
- Mock 退款结果的只读查看和最小审计记录。
- v0.1–v0.3 功能、权限、安全测试和固定 Eval 的完整回归。
- 固定的 v0.4 退款 Policy、审批、幂等、恢复和安全 Eval。

本版本只支持一个 Mock 订单对应一笔原始 Mock 支付，以及针对当前可退款余额的整单退款。
具体数据 Schema、Policy 表达、节点名称、API 路径和页面组件由 Technical Plan 决定。

## 非目标

- 真实支付渠道、真实电商平台、真实物流或任何外部交易系统接入。
- 部分商品退款、按件退款、多次部分退款或换货差价。
- 优惠券、积分、赠品、运费、税费、折旧和赔偿的复杂分摊。
- 多币种换算、组合支付、分期、预授权、拒付或资金清算。
- 退货入库、逆向物流和自动取消订单。
- 无需人工确认的自动退款。
- 客服、运营、财务等角色矩阵和多级审批。
- 人工客服 Handoff；该能力属于 v0.5。
- 自主组合多个售后工具的动态 Agent Loop；本 Spec 接受时规划为 v0.6，后由
  [`ADR-0006`](../adr/0006-llm-l2-support-harness.md) 前移到 v0.5 L2 Harness。
- 生产并发、真实支付合规、对账、灾难恢复和外部通知。
- 通过 LLM、Prompt 或客户端参数直接维护支付、退款或审批事实。

## Mock 交易事实

- Mock 订单、物流、支付和退款记录属于项目内业务事实，持久化到独立本地业务数据库。
- LangGraph Checkpoint 只保存对话、预览引用、待审批动作和恢复点，不保存业务表的替代副本。
- 每笔可退款订单必须具有可验证的 Mock 支付状态、已支付金额、币种和原支付渠道。
- 整单退款金额由当前可退款余额确定，不能由 LLM、浏览器或审批人手工改写。
- 当前可退款余额不得超过原已支付金额，并扣除已经完成或仍在处理的 Mock 退款。
- 币种和退款渠道继承原 Mock 支付事实；本版本不允许用户切换渠道或换算币种。
- 缺失或冲突的 Mock 支付事实必须阻止预览或执行，并给出可操作的补充说明。
- 数据库中的 Mock 标识不能使用真实支付渠道格式冒充外部交易编号。

## 退款资格与政策

- 退款资格必须由确定性 Refund Policy 根据最新业务事实计算。
- Refund Policy 至少考虑订单归属、订单状态、支付状态、物流/签收状态、当前可退款余额、
  已有退款和适用政策版本。
- v0.2 RAG 证据用于解释期限、条件和例外，不能直接授权退款或覆盖确定性 Policy。
- 预览中的每项政策性结论必须保留可定位引用；无法获得必要证据时不得生成可执行预览。
- 不符合资格时应展示确定性原因和相关政策引用，且退款 Gateway 调用数量为零。
- 资格规则的具体状态矩阵和测试样本由 Technical Plan 定义，但不得放入 Prompt 作为唯一实现。
- 用户退款原因和政策原文中的 Prompt Injection 只能作为数据，不能改变资格、金额或审批要求。

## 退款预览

可审批预览至少向用户展示：

- Mock 订单标识。
- 退款原因。
- 原支付金额、当前可退款金额、币种和原支付渠道。
- 关键订单、支付和物流状态。
- 资格结论和确定性原因。
- 支持政策结论的来源。
- 动作风险及“批准后将写入本地 Mock 退款”的明确说明。
- 预览标识或等价的服务端绑定信息。

预览内容由服务端产生。客户端只能提交批准或拒绝决定，不能回传并覆盖订单、金额、渠道、
资格、Policy 版本或工作区。

生成预览本身不得创建退款记录、改变订单/支付状态或调用具有副作用的 Gateway。允许保存
Checkpoint 和最小审计事件，但这些记录不构成业务退款。

## 审批行为

- 每个可执行退款必须进入暂停状态并等待明确决定。
- 批准和拒绝必须验证登录状态、CSRF、当前账号、工作区、thread、待审批动作和预览版本。
- 用户关闭页面、Session 过期或服务重启不会改变待审批任务，也不会自动批准。
- 拒绝后任务进入明确终态，不创建 Mock 退款；后续新申请必须产生新的动作标识。
- 批准前必须重新读取订单、物流、支付、已有退款和适用政策。
- 业务事实或政策发生影响资格、金额或渠道的变化时，旧预览和旧批准立即失效；系统应展示
  冲突并要求重新生成预览。
- 不存在、已结束、属于其他用户或其他工作区的待审批动作使用安全错误语义，不能泄露内容。
- 客户端伪造金额、订单、身份、模型模式或幂等键不能改变服务端执行参数。

## 幂等执行与验证

- 每次退款动作必须具有稳定的 `task_id`、`action_id` 和幂等语义；具体字段由 Plan 定义。
- 同一动作的重复批准、HTTP 重试、节点重放和跨进程恢复只能对应同一笔 Mock 退款。
- 同一订单不得同时存在多笔相互冲突的整单退款；跨 thread 请求也必须由业务约束识别。
- Fake Refund Gateway 必须能够模拟成功、业务拒绝、执行前失败、超时后结果未知和验证不一致。
- 对“结果未知”的动作，系统必须先按幂等标识查询现有业务结果，再决定是否重试，不能直接
  再次创建退款。
- Gateway 返回成功后必须重新读取 Mock 退款和可退款余额，验证订单、金额、币种、状态和
  幂等关联符合预期。
- 只有验证通过时才能向用户声明退款完成；验证失败或结果未知必须进入独立可恢复状态。
- 任意失败都不能通过修改 Checkpoint 伪造业务成功。

## 对话与 LLM 边界

- LLM 只输出受 Schema 约束的退款意图、订单标识、退款原因和必要补充信息。
- LLM 不能输出或覆盖退款资格、金额、币种、渠道、风险等级、审批结果和 Gateway 参数。
- 注册用户的 LLM 权限继续由服务端 Session、配置和配额决定；客户端不能选择模型模式。
- 模型不可用、输出无效或配额不足时明确失败，不回退到 Fake 并伪装为相同能力。
- 自动化测试和 Eval 使用 Fake Interpreter，不依赖网络或真实 API Key。
- 游客退款请求不得触发真实 LLM 或任何退款写工具。

## 公开用户结果

Web 至少能明确区分：

- 缺少订单号、退款原因或必要 Mock 业务事实，需要补充。
- 订单不可访问或不属于当前工作区。
- 不符合退款资格，并展示确定性原因和政策引用。
- 退款预览已生成，正在等待批准。
- 用户已拒绝，且没有退款副作用。
- 预览因业务事实或政策变化而失效，需要重新生成。
- 已存在待处理或已完成的 Mock 退款，未创建重复记录。
- Mock 退款执行并验证成功。
- Gateway 业务拒绝、暂时失败、结果未知或验证不一致。
- 会话、审批或模型权限失效。

具体公开状态字段、HTTP 状态码和页面路由由 Technical Plan 定义。

## 安全与审计

- 退款申请、审批、执行和查看都必须限制在当前可信账号及工作区。
- 游客和跨工作区请求的 Mock 退款写入数量必须为零。
- 所有状态变更请求继续执行 v0.3 的 Session、CSRF、Origin 和输入上限校验。
- 审计至少记录 task/action 标识、工作区、脱敏订单标识、风险、Policy 版本、预览摘要、
  审批决定、Gateway 结果、验证状态和时间；不记录密码、Cookie、API Key 或模型隐藏推理。
- Mock 退款、审计、Checkpoint 和政策索引保持独立职责，不能用其中一个伪造另一个。
- 对外错误不暴露本地路径、数据库结构、堆栈、Prompt、模型密钥或其他工作区数据。

## 与已有版本的兼容要求

- v0.1 的 15 个固定 Eval 场景继续全部通过。
- v0.2 的 20 个固定 RAG Eval 场景继续全部通过，政策引用语义不降低。
- v0.3 的 20 个固定 Web/权限 Eval 和浏览器路径继续全部通过。
- 游客仍然零 LLM 调用、零业务写入；注册用户和工作区隔离不能回归。
- 现有订单、物流、认证数据、Checkpoint 和政策索引继续分离。
- 新增持久化字段或 State 发生不兼容变化时，Technical Plan 必须提供迁移或明确重建策略。
- 订单与物流查询、通用政策问答仍保持只读，不因增加退款路径产生意外副作用。

## 验收条件

1. 注册用户提供有效订单和原因后，系统读取最新 Mock 订单、物流、支付、退款及政策事实。
2. LLM 只提取结构化诉求；资格、金额、币种、渠道和审批要求全部由确定性代码产生。
3. 可执行预览展示订单、原因、可退款金额、币种、渠道、关键状态、风险和政策来源。
4. 生成预览和进入暂停状态不会创建 Mock 退款或改变订单、支付状态。
5. 用户拒绝后退款 Gateway 调用为 `0`，Mock 退款记录新增数量为 `0`。
6. 用户批准后只使用服务端保存且重新校验的预览参数执行，客户端篡改参数无效。
7. 批准前业务事实或政策发生实质变化时，旧预览不能执行，并要求重新生成。
8. 退款执行后重新读取业务数据库；只有订单、金额、币种、状态和幂等关联全部匹配时才
   返回完成。
9. 同一动作重复批准、请求重试、节点重放和跨进程恢复只产生一笔 Mock 退款。
10. 同一订单从不同 thread 并发申请整单退款，不会产生相互冲突的重复退款。
11. Gateway 超时且结果未知时先查询既有结果，不会无条件再次创建退款。
12. 不符合资格、缺少业务事实、已有退款和可退款余额为零时不会调用退款写工具。
13. 游客、跨用户、跨工作区和已失效 Session 的退款写入数量均为 `0`。
14. 服务重启后可以恢复待审批预览，恢复不会自动批准或重复执行。
15. 退款原因和政策内容中的 Prompt Injection 不能改变资格、金额、审批或工具参数。
16. Mock 支付与退款事实持久化在本地业务数据库，不进入 Checkpoint 或 RAG 索引。
17. 自动化测试不访问真实支付、电商、物流或交易系统，也不需要真实 LLM。
18. v0.1–v0.3 自动化测试、固定 Eval 和既有安全边界全部继续通过。

## v0.4 Eval

固定数据集至少覆盖 24 个场景：

- 4 个符合资格的预览、批准和验证场景。
- 5 个未支付、状态不允许、政策不满足、余额为零或已有退款的不符合资格场景。
- 4 个拒绝、关闭页面、跨进程恢复和过期预览场景。
- 4 个重复批准、HTTP 重试、节点重放和跨 thread 并发幂等场景。
- 4 个游客、跨用户、参数篡改和失效 Session 安全场景。
- 3 个 Gateway 失败、结果未知、验证不一致或 Prompt Injection 场景。

发布门槛：

- 固定场景通过率：`100%`。
- 未经批准的 Mock 退款新增数量：`0`。
- 重试、恢复或并发导致的重复 Mock 退款数量：`0`。
- 客户端或模型篡改资格、金额、渠道和权限成功数量：`0`。
- 跨用户或跨工作区退款及审批成功数量：`0`。
- 执行成功但未通过业务状态验证仍对外声明完成的数量：`0`。
- 政策引用可解析率和资格规则确定性断言：`100%`。
- 游客 LLM 调用和业务写工具调用数量：`0`。
- v0.1–v0.3 回归：全部通过。

自然语言措辞不要求逐字一致。Eval 断言结构化意图、Policy 结果、预览、审批轨迹、Gateway
调用、数据库副作用、验证结果和公开状态；LLM-as-judge 不能单独决定发布。

## 已知限制

- 所有订单、支付和退款均为本地 Mock 数据，不代表真实资金、支付合规或电商平台能力。
- 当前受邀用户同时充当申请人和演示审批人，不提供生产级职责分离。
- 只支持整单和单笔原始 Mock 支付，不覆盖复杂金额分摊及逆向物流。
- 本地 SQLite 与单实例范围不代表生产并发、对账或灾难恢复能力。
- 演示 Refund Policy 和政策语料不代表任何真实平台的正式规则。
- 无法自动处理时只能安全失败；人工客服 Handoff 在 v0.5 才实现。
