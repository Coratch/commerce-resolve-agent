# Feature Spec：v1.1 订单优先的智能售后中心

状态：Accepted  
日期：2026-07-22  
接受日期：2026-07-22  
依赖版本：v1.0 单机交付与可维护运行（当前为 Candidate）  
关联决策：ADR-0011

## 目标

客户打开 CommerceResolve 后，可以先看到自己正在处理的售后服务、最近订单和常用动作，再围绕某个
订单或服务目标查询物流、理解政策、申请 Mock 退款或继续复杂售后处理。智能助手在明确的订单和服务
上下文中提供帮助，而不是要求用户从一个空白聊天框开始并重复系统已经知道的事实。

v1.1 成功不是“重新设计聊天页”，而是把现有订单、物流、政策 RAG、退款审批、L2 Case 和公开会话
组织成一个可理解、可恢复、可继续操作的售后产品。所有交易和外部系统继续是本地 Mock/Fake，既有
身份、Policy、审批、幂等、Checkpoint、审计和 Eval 边界不得放宽。

## 第一性原则

1. **用户要的是售后结果，不是一次聊天。** 页面先回答发生了什么、能做什么、处理到哪里。
2. **业务对象先于自由文本。** 订单、物流和服务记录提供稳定上下文，对话负责澄清和辅助操作。
3. **事实必须来自服务端。** 商品、订单、物流、资格、金额和状态不能由 UI 或模型补造。
4. **高影响动作必须结构化。** Mock 退款继续经过预览、批准、执行和验证，不在自然语言中隐式完成。
5. **对话仍是可恢复产品数据。** 页面结构变化不能退回浏览器内存历史或丢失现有会话。
6. **客户结果与内部诊断分离。** 默认展示业务证据，Agent Trace 和 Eval 只在适当入口渐进披露。
7. **同一能力必须跨设备尺寸可用。** 桌面和移动端可以采用不同布局，但不能改变权限与任务语义。

## 角色

### 游客

- 使用共享的只读演示订单和确定性 Fake 模式体验售后中心。
- 可以查看演示订单、物流和政策，但不能创建或执行 Mock 退款等业务写操作。
- 不触发真实 LLM，也不能通过客户端上下文访问注册用户数据。

### 受邀注册客户

- 查看和维护本人私有演示订单、物流与必要 Mock 支付事实。
- 从订单或服务记录发起上下文对话、Mock 退款审批和 AI 二线客服流程。
- 刷新、切页和重新登录后继续本人有权访问的会话、待办动作和服务进度。

### 项目维护者

- 使用既有本机运维、诊断和 Eval 入口验证系统状态。
- v1.1 不新增公开客服坐席后台，也不允许维护者通过客户页面绕过身份或 Policy。

## 核心产品对象

| 对象 | 用户看到的结果 | 权威来源 |
|---|---|---|
| 订单摘要 | 订单号、当前状态、金额和可用售后入口 | Mock 业务 Repository |
| 物流进度 | 当前节点、承运信息和已存在的时间线事实 | Mock 物流 Repository |
| 售后服务记录 | 服务类型、当前阶段、待用户动作和最终结果 | 既有 Refund、Pending Action、L2 Case 与公开事件的服务端投影 |
| 上下文助手 | 围绕当前订单或服务目标的公开对话 | 服务端授权上下文、公开消息与 LangGraph Task |
| 政策依据 | 与结论直接相关的政策名称、版本和可定位片段 | 已发布政策来源与 RAG 索引 |

现有数据若没有商品行、图片、精细物流节点或其他展示字段，页面必须使用明确的“暂无数据”或兼容
布局。v1.1 只增加本 Spec 已接受的最小商品行，其他字段不扩展；任何阶段都不能用前端常量冒充
用户订单事实。

## 用户故事

### 从售后首页开始

用户进入产品后，首先看到需要关注的售后服务、最近订单和常用动作。没有订单、没有进行中服务、
加载中和失败均有明确状态；页面不会用一个空白大聊天框代替这些状态。

### 查看订单与物流

用户选择一笔有权访问的订单，查看服务端返回的订单事实、物流状态、已存在的物流时间线和当前可用
动作。无权访问与不存在订单继续使用不泄露资源存在性的统一语义。

### 在订单上下文中对话

用户在订单详情或服务记录中打开智能助手后，可以直接问“什么时候到”“能否退款”等问题，不需要
重复订单号。服务端绑定并验证当前订单；篡改客户端上下文不能读取其他用户或其他工作区的订单。

### 完成 Mock 退款流程

符合条件的注册用户从订单动作或对话进入退款流程，先看到由确定性 Policy 生成的预览、金额、渠道、
风险和依据。只有明确批准后才能幂等执行，完成后页面回读并展示真实 Mock 退款结果和服务进度。

### 继续复杂售后服务

无法由一线流程安全解决的问题可以按既有规则升级到明确披露为 AI 的二线客服。用户在服务记录中
看到当前状态、缺少的信息、公开步骤和可执行下一步；刷新或重登录不会丢失进行中的 Case。

### 查看政策依据

政策结论旁直接显示有限、可理解的来源入口。用户需要时可以展开政策名称、版本和相关片段，不需要
进入内部 Trace 页面判断答案从哪里来。

### 恢复历史服务

用户能够从服务进度或历史入口返回原订单、公开会话和待处理动作。旧会话和既有 URL 在迁移后仍可
访问或安全重定向，不产生重复消息、Agent Run、Case 或 Mock 退款。

## 版本范围

v1.1 包含：

- 客户侧售后首页、订单详情、服务进度和上下文助手的信息架构。
- 游客演示与注册客户的加载、空状态、错误、权限和移动端体验。
- 基于既有权威业务数据的订单、物流和服务状态投影。
- 将订单或服务上下文绑定到对话请求，并由服务端重新授权和校验。
- 复用既有政策 RAG、Mock 退款审批、L2 Case、公开消息、SSE 和恢复能力。
- 政策来源与公开处理证据的渐进披露。
- 旧对话入口和既有公开历史的兼容迁移。
- 对新增用户路径、上下文安全和旧能力回归的固定测试与 Eval。

## 非目标

v1.1 不包含：

- 真实电商、支付、物流、仓储、CRM 或人工客服系统接入。
- 完整商城、商品目录、购物车、结算或营销能力。
- 客服坐席工作台、队列分配、SLA、工单协作或真实 Handoff。
- 兑换、部分退款、优惠分摊、退货标签、逆向物流、订单取消或自动补偿。
- 新增 Agent 身份、更多 Agent、任意 Tool、自动批准或扩大资金操作权限。
- 用前端静态数据、模型生成或图片占位内容冒充真实订单事实。
- Provider Token 级网络流式传输、附件、图片上传或多媒体客服。
- 多实例、高可用、云端运营平台或真实生产 SLA。

## 兼容与迁移约束

- v1.0 已持久化的账号、公开消息、Conversation、Agent Run/Event、Checkpoint、Pending Action、
  Refund、L2 Case、Memory 和审计数据必须保持可读。
- 旧对话 URL 可以保留或重定向，但不能静默创建新会话、丢失 thread 绑定或改变用户归属。
- 客户端提供的 `order_id`、`conversation_id`、`case_id` 和服务记录标识不能成为授权依据。
- 如果新增服务记录投影，其重建、版本和缺失降级必须明确；不能把派生投影变成退款或 Case 的唯一事实来源。
- 如果扩展 Mock 订单数据模型，旧订单必须具有安全默认值和可验证迁移；不能要求删除现有数据。
- v1.1 不改变 v1.0 单机部署、SQLite 分库和 Mock 交易边界。

## 错误与降级语义

| 场景 | 用户可观察结果 |
|---|---|
| 没有订单或服务记录 | 展示可理解空状态和可用下一步，不伪造示例为本人数据 |
| 订单不存在或无权访问 | 使用统一语义，不泄露订单是否存在 |
| 上下文被篡改 | 拒绝请求，不读取目标订单，不调用模型或产生业务写入 |
| 订单扩展字段缺失 | 展示已有权威字段和明确缺失状态，不由 UI/LLM 补造 |
| 政策无证据或冲突 | 明确无法给出确定结论，并提供澄清或安全升级路径 |
| Provider 不可用 | 以普通对话消息表达当前无法处理；已持久化业务事实和服务记录仍可查看 |
| 退款资格或数据已变化 | 预览过期并要求重新生成，不执行旧动作 |
| 进行中 Run 被服务重启中断 | 展示既有 `interrupted` 语义和安全重试入口，不假装仍在处理 |
| 服务记录投影不可用 | 降级显示权威订单、退款或 Case 状态，不覆盖事实来源 |

## 验收条件

1. 默认客户入口展示进行中服务、最近订单和常用售后动作，而不是只展示空白聊天首页。
2. 游客、无订单注册用户、有订单注册用户和有进行中服务用户具有可区分且可理解的首页状态。
3. 用户可以从订单进入详情，并看到来自服务端权威 Repository 的订单与物流事实。
4. 页面缺少商品或物流扩展字段时明确降级，自动化测试证明前端没有补造业务事实。
5. 用户从订单上下文发问时无需重复订单号，服务端实际查询绑定且已授权的订单。
6. 篡改订单、会话、Case 或服务记录上下文不能跨用户读取数据，模型调用和业务写入数量为 `0`。
7. 不存在和无权限订单继续使用不泄露资源存在性的统一响应。
8. Mock 退款从订单动作或上下文对话进入后，继续满足确定性预览、明确批准、幂等执行和回读验证。
9. 刷新、切页和重新登录后，服务进度、公开会话和 Pending Action 均能从服务端恢复。
10. 政策结论附近可以展开来源名称、版本和可定位片段；内部 Prompt 和隐藏推理不会公开。
11. 默认客户界面不展示 LLM/Fake/Provider、Context Manifest、内部节点、Token 或 Eval 指标。
12. 需要排障时仍能通过既有受控入口取得公开 Trace 或脱敏诊断，信息架构调整不删除审计证据。
13. 游客路径继续保持只读、零真实 LLM 调用和零 Mock 资金写入。
14. 桌面与移动端均能完成订单查看、上下文提问、审批和服务恢复，不出现遮挡、横向溢出或不可达操作。
15. 键盘操作、焦点可见性、语义标签和 Reduced Motion 满足现有 v1.0 可访问性边界。
16. 加载、空状态、业务失败和模型失败均通过正常产品内容或对话表达，不使用红色系统异常冒充客服回复。
17. 已完成的 v0.1–v1.0 自动化测试、Offline Eval 和安全门禁保持通过。
18. 新增固定场景至少覆盖正常、空状态、权限篡改、事实缺失、审批恢复、Provider 失败和移动布局。
19. README、目标地图、代码职责文档、运行说明和已知限制与最终实现一致。

## 已接受产品决策

1. v1.1 为 Mock 订单增加可选的最小商品行数据：SKU、商品名称、数量和政策商品类别。旧订单可以
   没有商品行，页面明确显示兼容状态；本版本不引入商品图片、目录、库存或部分退款。
2. 售后服务记录是 Refund、Pending Action、L2 Case 和公开事件的只读服务端投影，不新增可以与
   原始事实独立变化的第二套服务状态。
3. 客户只看到问题摘要、当前阶段、必要依据、待办动作和最终结果。Context Manifest、模型调用、
   工具参数、预算、失败归因和 Eval 指标只保留在现有受控诊断入口。
4. 旧对话入口在 v1.1 保持可访问；桌面端上下文助手使用订单或服务页内侧栏，移动端使用可关闭的
   抽屉。打开页面不能自动创建空会话，只有用户明确开始对话或发送消息后才创建并绑定。

具体路由、API、Schema、迁移和组件复用方式由 Technical Plan 决定。
