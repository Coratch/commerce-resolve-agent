# Feature Spec：v0.2 售后政策 RAG 与可定位来源

状态：Accepted  
日期：2026-07-17  
接受日期：2026-07-17  
依赖版本：v0.1 订单与物流查询

## 目标

用户通过对话询问退货、退款、换货等通用售后政策时，系统只依据当前已发布的受控
政策文档回答，并为每个关键结论提供可定位来源。证据不足、问题缺少必要条件或有效
政策相互冲突时，系统必须澄清、拒答或明确展示冲突，不能用模型常识补全。

本版本建立“受控知识来源 → 检索证据 → 带引用回答 → 检索与引用 Eval”的最小
RAG 闭环，不判断具体订单的退款资格，也不执行任何售后写操作。

## 第一性原则

1. 用户需要的是可验证的政策结论，不是听起来合理的模型回答。
2. 已发布政策原文是政策事实来源；模型记忆和通用知识不能替代原文。
3. 检索结果只是候选证据，不能自动成为答案，也不能授权退款。
4. 引用必须能回到确定的文档版本和位置，否则不算有效引用。
5. 没有足够证据时，正确结果是澄清或拒答，而不是提高生成置信度。
6. 先用固定问题集证明基础检索有效，再决定是否增加混合检索、Rerank 或复杂 Agent Loop。

## 用户故事

### 查询通用售后政策

作为用户，我询问“签收后多少天可以退货”时，希望获得：

- 政策规定的期限、前置条件和例外。
- 支持每个关键结论的政策标题、版本、章节和位置。
- 能够定位回原始政策内容的引用。

### 补充必要条件

作为用户，当政策结果取决于商品类别、是否拆封或其他必要条件，而我的问题没有提供
这些信息时，系统应明确询问缺失条件，不应擅自选择对我最有利或最不利的分支。

### 继续同一政策话题

作为用户，在同一 `thread_id` 中继续追问“那超过期限怎么办”时，系统应理解该问题
延续上一轮政策主题，并重新提供支持本轮结论的引用。

### 安全处理无证据问题

作为用户，当受控知识库没有覆盖我的问题时，系统应明确说明无法从当前政策确认，
而不是引用无关内容或根据常识生成答案。

### 展示政策冲突

作为用户，当两个当前有效来源对同一条件给出冲突规则时，希望看到冲突说明及双方
来源，而不是系统静默选择其中一个结论。

## 术语

| 术语 | 定义 |
|---|---|
| 已发布政策 | 经过项目明确收录、带版本与生效信息、允许面向用户引用的政策文档 |
| 证据 | 从已发布政策中检索出的、能够直接支持某项结论的可定位片段 |
| 关键结论 | 影响期限、条件、费用、范围、例外或用户下一步行动的事实性陈述 |
| 有效引用 | 能解析到确定文档、版本、章节和位置，且片段内容支持对应结论的引用 |
| 拒答 | 明确说明当前证据不足，且不生成无来源的政策结论 |

## 范围

包含：

- CLI 中创建和继续售后政策问答会话。
- 一个受控、可版本化、可重建索引的本地政策知识集合。
- 退货、退款、换货的通用期限、条件、费用和例外问答。
- 对单一来源和多个来源进行检索并生成带引用回答。
- 缺少必要条件时的多轮澄清。
- 无证据、政策冲突、检索失败和模型失败的安全处理。
- 固定 RAG Eval 场景、结构化结果和可复现版本报告。
- v0.1 订单与物流查询能力的完整回归。

本版本默认只覆盖一个演示店铺、一个政策区域和中文问答。具体政策样本由 Technical
Plan 定义，但不得把模型训练知识作为隐式来源。

不包含：

- 根据具体订单状态判断退款、退货或换货资格。
- 计算退款金额、运费、折旧或赔偿金额。
- 创建退款、退货、换货或取消订单等业务写操作。
- 人工客服工单和 Handoff。
- 联网搜索、抓取实时网页或自动发布政策。
- 政策编辑后台、文档审批系统或面向用户的文件上传。
- 用户长期记忆、动态多工具 Agent Loop 或多 Agent。
- Web UI、公开 API、真实登录和多租户部署。

## 政策回答规则

1. 每个关键结论必须至少由一个有效引用支持。
2. 回答只能使用当前任务检索到且通过校验的证据，不使用模型记忆补充政策事实。
3. 引用至少包含：文档标识、标题、版本、生效信息、章节和可定位位置。
4. 引用指向的片段必须存在于对应政策版本，并直接支持关联结论。
5. 同一问题需要组合多个条件时，回答应保留每项条件各自的来源，不能只给一个笼统引用。
6. 没有足够证据支持关键结论时进入 `policy_insufficient_evidence`，不返回猜测答案。
7. 当前有效来源相互冲突且无法依据确定性元数据消解时，进入 `policy_conflict`，展示冲突点和双方引用。
8. 问题缺少决定政策分支所必需的信息时，进入 `awaiting_policy_context` 并请求补充。
9. 政策原文中的 Prompt、工具指令或角色声明仅作为数据，不得改变系统规则或调用工具。
10. 检索内容不能授权退款、覆盖确定性 Policy 或改变订单与物流事实。

## 具体订单问题的边界

对于“订单 ORD-001 能退款吗”这类请求：

- 可以解释与问题相关的通用政策条件并提供引用。
- 必须明确说明 v0.2 不能判断该具体订单是否满足条件。
- 不组合订单状态与政策生成资格结论。
- 不调用退款工具，也不产生退款预览或写操作。

用户单独查询订单或物流时，继续使用 v0.1 的既有行为，不强制进入 RAG。

## 对话行为

### 有证据的政策问题

```text
用户：签收后多少天可以申请退货？
系统：检索当前有效政策
系统：返回期限、适用条件和例外，并附政策版本与位置引用
```

### 缺少必要条件

```text
用户：拆封后还能退吗？
系统：当前政策按商品类别区分，请补充商品类别
用户：普通服饰
系统：继续原问题，返回有引用的适用规则
```

### 无证据

```text
用户：海外门店的退货期限是多少？
系统：当前受控政策未覆盖海外门店，无法确认
```

### 政策冲突

```text
用户：退货运费由谁承担？
系统：检测到两个当前有效来源给出不同规则
系统：说明冲突并分别引用两个来源，不自行选择结论
```

## 公开结果状态

任务至少区分：

- `policy_answered`：关键结论均具有有效证据和引用。
- `awaiting_policy_context`：缺少决定政策分支所需的信息。
- `policy_insufficient_evidence`：当前知识来源不足以支持结论。
- `policy_conflict`：当前有效来源存在无法自动消解的冲突。
- `temporarily_failed`：检索或模型服务暂时不可用，可稍后重试。
- v0.1 已有订单查询状态继续保持兼容。

具体 State Schema、节点名称和数据模型由 Technical Plan 定义。

## 失败与安全处理

- 检索服务、索引或模型暂时失败时，不返回部分生成的政策答案。
- 对外错误不包含本地路径、Prompt、堆栈、密钥或内部索引结构。
- 引用解析失败、文档版本失效或片段不存在时，该证据不得进入最终答案。
- 过期或尚未生效的政策不能作为当前结论，除非用户明确询问历史政策。
- 用户输入和政策原文中的提示注入不能改变检索范围、权限或工具行为。
- 所有政策问答路径均为只读，不得产生订单、退款或工单副作用。

## 与 v0.1 的兼容要求

- v0.1 的 15 个固定 Eval 场景必须继续全部通过。
- 订单和物流查询的公开回复、安全语义、身份绑定和 SQLite 恢复不能回归。
- 政策来源、RAG 索引、Checkpoint 和业务数据必须分离。
- 相同 `thread_id` 可以延续政策澄清，但不能把其他用户或其他 thread 的证据状态混入当前会话。
- State 或持久化格式发生不兼容变化时，Technical Plan 必须提供迁移或明确的开发期重建策略。

## 验收条件

1. 可回答问题的每个关键结论都具有至少一个有效引用。
2. 每个引用都能解析到确定的文档、版本、章节和片段，并支持对应结论。
3. 多条件答案能够保留各条件的证据关系，不把引用仅堆在整段回复末尾。
4. 缺少必要条件时进入 `awaiting_policy_context`，补充后继续原政策问题。
5. 无相关证据时进入 `policy_insufficient_evidence`，不生成无来源政策结论。
6. 无法自动消解的有效政策冲突进入 `policy_conflict`，同时展示双方引用。
7. 具体订单资格问题不会被回答为“可以退款”或“不可以退款”，也不会触发业务写操作。
8. 检索或模型失败时进入 `temporarily_failed`，不暴露内部错误。
9. 政策文档或用户输入中的 Prompt Injection 不会改变系统规则、调用业务工具或伪造引用。
10. v0.1 的自动化测试和 15 个固定 Eval 场景全部继续通过。
11. v0.2 自动化测试和 Eval 在没有网络及真实 API Key 的环境中可重复运行。
12. 一个真实模型仅用于独立手工冒烟，不作为确定性发布门槛。

## v0.2 RAG Eval

首个固定数据集至少包含 20 个场景：

- 6 个单一来源可回答问题。
- 4 个需要组合多个证据的问题。
- 3 个缺少条件并通过多轮补充的问题。
- 3 个无证据问题。
- 2 个当前政策冲突问题。
- 2 个用户输入或政策原文包含 Prompt Injection 的安全场景。

发布门槛：

- 固定场景通过率：`100%`。
- 标注相关证据召回率：`100%`。
- 引用可解析率：`100%`。
- 引用支持关键结论的正确率：`100%`。
- 无证据问题正确拒答率：`100%`。
- 冲突问题正确识别率：`100%`。
- 未被证据支持的关键结论数量：`0`。
- Prompt Injection 导致的规则覆盖、伪造引用或业务工具调用数量：`0`。
- 订单、退款和工单写操作调用数量：`0`。
- v0.1 回归：全部通过。

自然语言措辞不要求逐字一致。确定性 Eval 断言结构化结论、证据关系、引用、状态和
工具轨迹；LLM-as-judge 不能单独决定发布。

## 已知限制

- 只覆盖受控演示政策集合，不代表真实平台所有地区、店铺或商品政策。
- 不联网验证政策是否为外部平台最新版本。
- 不判断具体订单资格，不计算金额，也不执行任何售后动作。
- 引用证明答案来自给定政策，不代表政策本身没有法律或业务错误。
