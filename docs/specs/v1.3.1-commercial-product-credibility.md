# Feature Spec：v1.3.1 商业产品可信度重构

状态：Accepted  
日期：2026-07-23  
接受日期：2026-07-24  
依赖版本：v1.3 商业化售后中心与智能服务体验（Candidate）  
后续版本：v1.4 多模态政策知识与复杂问答（Proposed）  

## 目标

把 CommerceResolve 从“功能完整、页面齐全的高保真演示”提升为具有成熟电商售后产品信息架构、
视觉可信度、内容完整性和任务连续性的开源产品体验。用户第一次打开页面时，应当能够相信自己
正在使用一个围绕订单、物流和售后服务设计的真实产品，而不是一组展示 Agent 能力的页面。

v1.3.1 不重新实现 v1.3 已完成的业务能力，也不通过增加页面、动画或技术名词制造“商业化”。
本版本专门解决以下问题：

- 已有自动化验收能够证明页面存在、功能可用和三视口不阻塞，但不能证明视觉层级和内容组织
  已达到成熟产品标准。
- 默认运行实例数据过少时，大面积空状态、占位商品和稀疏运营数据会让完整能力不可发现。
- 客户页面仍存在过大的展示性标题、通用品牌表达和弱业务上下文，订单、服务和下一步动作没有
  始终成为视觉主角。
- 客户售后中心、智能助手和 Agent 运营控制台虽然职责已分离，但设计语言、术语和状态表达尚未
  形成统一产品系统。
- 视觉回归只能发现“页面变了”，不能判断“页面是否可信、清晰、像成熟产品”。

版本完成后，项目既要提供可重复的自动化证据，也要提供固定页面、固定数据、固定视口和锚定
评分标准组成的人工产品验收证据。

## 成功定义

“商业产品可信度”在本项目中具有以下可观察含义：

1. 用户在不阅读 README 的情况下，可以从订单或进行中服务完成查询、咨询、审批和结果跟踪。
2. 首屏优先显示用户当前需要关注的事实和动作，不使用营销大标题挤占主要任务空间。
3. 商品、订单、物流、退款、服务和会话数据彼此一致，且足以呈现真实业务密度。
4. 客户页面只使用客户可理解的语言；Agent、Policy 和演示边界透明但不暴露内部实现术语。
5. 客户中心和运营控制台各自适配角色任务，同时共享稳定品牌、组件和状态语言。
6. 加载、空、失败、无权限、过期、恢复和完成状态都像正常产品状态，而不是调试提示。
7. 桌面、平板和移动端都保持任务、上下文和主要动作可发现。
8. 项目能够通过文档和证据解释关键设计取舍，适合作为开源学习和面试作品。

商业可信不等于伪装成真实交易系统。页面必须明确披露本地演示和 Mock 资金边界，但披露方式应当
稳定、克制、可理解，不能把研发状态或技术异常当作客户内容。

## 第一性原则

1. **产品界面的单位是用户任务，不是技术模块。** 页面围绕“查看订单、跟踪物流、处理退款、
   继续服务”组织，而不是围绕 Graph、RAG、Run 或 Provider 组织。
2. **可信度来自一致事实。** 真实感商品图或动效不能弥补订单、金额、物流和服务状态之间的矛盾。
3. **默认演示路径必须展示能力。** 正常空状态需要保留测试，但项目首次验收不能要求评审者手工
   构造大量数据后才能看到完整产品。
4. **Agent 必须嵌入业务上下文。** 对话帮助用户理解和推进当前订单或服务，不成为与电商产品割裂
   的通用聊天页面。
5. **结构和内容先于装饰。** 先确定信息优先级、页面密度、状态和动作，再决定颜色、动效与视觉资产。
6. **设计系统服务一致性。** Token 和组件的价值是让相同事实、状态和动作在不同页面保持同一语义。
7. **视觉不能改变安全边界。** 快捷入口、推荐动作、乐观反馈和动画都不能跳过服务端权限、Policy、
   `interrupt`、幂等执行和结果回读。
8. **自动化与人工评审互补。** 测试负责正确性和回归，锚定产品评审负责信息层级和视觉可信度；
   两者不能互相冒充。
9. **前沿技术必须可解释。** UI 只展示 Agent 的公开结果和证据；面试材料必须解释 LangGraph、
   RAG、Memory 和 Agent Loop 为什么存在、如何失败以及如何评估。

## 角色

### 游客

- 进入稳定的只读演示售后中心，不需要先理解邀请码、Fake Model 或项目内部模式。
- 使用预置演示画像体验订单、物流、政策和服务结果。
- 能看到演示环境披露，但不会在每个模块重复看到 `Fake`、`Mock` 或技术警告。
- 不能修改演示事实、调用真实 LLM、批准 Mock 退款或访问运营控制台。

### 注册客户

- 看到本人订单、进行中服务、待办动作和历史会话。
- 从订单或服务进入上下文助手，不重复提供已经授权和绑定的事实。
- 对 Mock 退款进行明确审批，并从订单、服务和会话三个入口看到一致结果。
- 查看、纠正和删除本人允许管理的长期偏好。

### 管理员

- 在独立运营控制台准备目标客户的版本化演示数据。
- 查看脱敏 Agent Run、Eval 结果、邀请和有限系统状态。
- 通过任务队列、筛选、状态和详情理解当前运营情况，而不是只看到静态计数卡片。
- 不能冒充客户、查看隐藏推理、直接执行 Eval 或绕过退款审批。

### 开源项目评审者

- 可以从 README 快速启动一个内容完整的验收实例。
- 可以通过固定截图、核心旅程和产品评审量表理解本版本改善了什么。
- 可以定位 LangGraph、RAG、Memory、Agent Loop、安全和 Eval 的代码与设计说明。
- 不需要依赖作者口头解释才能理解项目边界、技术取舍和已知限制。

## 产品体验主线

### 主线 A：首次进入售后中心

1. 用户识别产品品牌、当前账号和演示边界。
2. 首屏展示需要关注的物流、退款审批、待补充信息或进行中服务。
3. 最近订单使用可信商品、金额、状态和动作表达。
4. 用户可以直接进入订单、服务或助手，不先经过营销式引导页。

### 主线 B：从订单完成售后任务

1. 用户通过商品、状态或订单号定位目标订单。
2. 订单详情首屏说明当前状态、物流进度、服务状态和最相关下一步。
3. 用户查看时间线、金额、商品和政策依据。
4. 用户打开已绑定该订单的助手，获得结构化事实、建议和允许动作。
5. 如需退款，既有预览、审批、执行和回读链保持不变。
6. 完成后订单、服务和对话同步展示最终结果。

### 主线 C：恢复进行中的服务

1. 用户从首页待办或服务列表找到待审批、待补充或处理中服务。
2. 页面明确展示已完成步骤、当前阶段、下一步和最后更新时间。
3. 刷新、切页和重新登录后回到相同任务。
4. 失败或过期操作使用正常产品语言解释，并提供安全恢复路径。

### 主线 D：运营人员准备和观察演示

1. 管理员从概览识别需要处理或关注的对象。
2. 管理员为明确目标客户选择一个可解释的业务场景并幂等初始化。
3. 管理员通过客户、Run、Eval 和系统详情验证演示状态。
4. 控制台区分业务运营、Agent 质量和系统健康，不把不同层次指标混在同一组卡片中。

## 客户售后中心

### 全局框架

- 品牌区、主导航、账号区和页面任务区具有稳定位置和清晰层级。
- 管理员可以进入运营控制台，但该入口不应与客户最常用的订单和服务入口争夺主视觉。
- 页面宽度、留白和字体层级适应业务数据密度，不使用超大标题制造空旷感。
- 客户主要导航使用一致中文命名；研发、发布和 Provider 术语不进入客户主导航。
- 页面标题、面包屑、绑定对象和返回关系能够说明用户当前在处理什么。

### 售后首页

- 首屏第一优先级是“需要你处理”与“正在处理”，而不是品牌宣传。
- 需要关注区区分物流异常、待退款审批、待补充信息、失败和已过期动作。
- 进行中服务展示商品、服务类型、当前阶段、最近更新和下一步。
- 最近订单至少展示商品主图、名称、订单状态、金额、下单时间和最相关动作。
- 常用入口作为辅助导航，不替代动态业务状态。
- 所有完成、无订单或无服务时展示有帮助的空状态，但固定商业验收实例不得只呈现空状态。

### 订单列表与详情

- 列表卡片在一个扫读单元内建立商品、订单、履约、金额、售后状态和动作的关系。
- 筛选、搜索、分页或有限列表行为具有明确状态，不在数据加载时隐藏页面结构。
- 商品名称、规格、数量、图片和金额使用内部一致的商业文案，不出现“验收商品”“测试 SKU”
  等开发占位命名。
- 详情首屏优先呈现订单状态、物流/服务时间线和主要动作，次要元数据渐进披露。
- 多商品、多包裹、异常物流、已退款和历史兼容订单具有专门表达，不挤进通用文本框。
- 退款金额、已退金额、支付金额和订单总额具有清晰标签，不能只靠颜色区分。

### 服务列表与详情

- 进行中服务优先，已完成和已关闭服务可以筛选或折叠。
- 服务详情将申请、审批、执行、验证、失败、补充信息和升级表达为业务时间线。
- Pending Action 始终靠近其服务上下文，并展示对象、后果、有效性和取消路径。
- Refund 与 L2 Case 继续来自权威投影，不创建仅供 UI 使用的伪状态。

### 智能助手

- 助手入口在订单或服务上下文附近可发现，但不遮挡页面主要内容。
- 独立对话页在桌面端形成稳定的会话导航、消息区和上下文区，不因内容稀少产生大面积失衡。
- 对话顶部始终展示当前绑定订单或服务，并允许用户通过明确动作切换。
- 回复中的事实、政策依据、建议、审批和最终结果使用不同产品组件表达。
- 普通回复、澄清、模型不可用和工具失败都作为会话中的服务消息展示，不使用红色系统告警替代。
- 内部 Run、Context Manifest 和 Trace 只通过受控渐进披露提供，不成为客户主内容。
- 输入框、发送、快捷问题、审批和恢复状态在键盘及移动端均可达。

### 登录、注册与长期偏好

- 登录与注册页面延续客户产品品牌和信任语言，不表现为独立的后台表单 Demo。
- 邀请注册明确解释用途、隐私和演示边界，不展示内部授权实现。
- 长期偏好说明哪些内容会被记住、为何使用、如何纠正和删除。
- 密码、邀请码、Session 和长期记忆继续遵守既有服务端安全边界。

## Agent 运营控制台

### 全局框架

- 运营控制台具有独立但同源的视觉身份，明确区别于客户售后中心。
- 导航按“概览、演示数据、账号邀请、Agent 运行、质量评估、系统状态”组织。
- 英文标准术语可以保留，但必须提供稳定中文含义，避免中英文随机混排。
- 只读能力和可写能力在视觉和文案上明确区分。

### 运营概览

- 概览优先展示需要关注的 Run、Case、邀请和系统状态，不只展示累计数字。
- 数据按业务运营、Agent 质量和系统健康分组。
- 趋势或比例只有在存在权威时间序列时才展示，不使用虚构图表填充空间。
- 空状态说明数据为什么为空、如何通过受控演示路径产生数据，以及哪些操作不可在 Web 执行。
- Release Candidate、Provider 资格和 Docker Gate 等维护信息进入系统或质量区域，不占据客户视角。

### 演示数据与账号

- 管理员先选择目标客户，再选择场景；当前目标始终可见。
- 场景卡说明会产生哪些订单、物流、支付和服务事实，以及是否可重复执行。
- 写入前后展示影响摘要和结果，不暴露数据库字段或内部 Fixture 名称。
- 邀请码明文仍只展示一次；列表不出现 Hash、密码或可复用敏感数据。

### Agent Monitoring、Eval 与系统状态

- Run 列表提供状态、时间、用户可公开目标、步骤、停止原因和失败归因的有限筛选。
- Run 详情区分公开轨迹、脱敏诊断和不可展示的信息。
- Eval 页面突出当前 Baseline、Candidate、回归、安全违规和 Provider 资格，而不是原始 JSON。
- 系统页面展示版本、Capability、迁移、存储和健康，并明确哪些检查尚未完成。
- Monitoring、Eval 和 System 全部保持只读，不从浏览器启动模型、Eval、备份、恢复或升级。

## 品牌、内容与视觉系统

### 品牌表达

- CommerceResolve 使用自有 Logo、图标、配色、字体层级和语气，不复刻任何电商平台。
- 品牌表达应传达可靠、清晰和受控，而不是游戏化、实验室或通用 AI 聊天工具。
- Logo、商品图片和插图必须具有明确来源及再分发许可。

### 内容语言

- 客户内容以中文售后语言为主，避免 `Candidate`、`Provider`、`Agent Run`、`Payload`、`Mock`
  等内部术语直接出现。
- “演示环境”作为持续但克制的全局说明；具体高风险动作继续明确说明不会产生真实资金影响。
- 状态、按钮和错误使用面向动作的语言，例如“补充信息”“查看退款进度”“重新核对”，不使用
  “未知错误”“执行失败”等无下一步的系统语言。
- 运营台可以使用 Agent、Eval、Run 等标准词，但首次出现时提供中文含义或上下文。

### 视觉与组件

- 颜色、字体、间距、圆角、边框、阴影、图标、状态和动效遵循统一 Token。
- 同一业务状态在首页、订单、服务、对话和运营投影中保持一致名称和视觉语义。
- 主要、次要、文字和危险动作具有明确层级；不能用多个同强度按钮竞争。
- 商品图保持统一比例和裁剪策略，并具有加载、失败和替代文本。
- Skeleton 与最终结构一致，避免大面积闪烁和明显布局跳变。
- Empty、Loading、Error、Forbidden、Expired、Partial、Interrupted 和 Completed 状态具有
  可重复的组件和文案规则。
- 动效只用于导航切换、内容进入、状态变化和反馈；不延迟操作，不制造无意义视差或 3D 展示。
- `prefers-reduced-motion` 下关闭非必要动画。

## 默认演示内容

商业验收使用显式、可重复初始化的演示工作区，不在应用启动或普通页面访问时静默 Seed。

该工作区至少包含：

| 数据 | 最小要求 |
|---|---:|
| 有可信商品图片和名称的订单 | 8 |
| 不同履约状态 | 4 |
| 多商品订单 | 2 |
| 多包裹或异常物流订单 | 1 |
| 进行中退款服务 | 1 |
| 待用户审批动作 | 1 |
| 进行中或待补充 L2 Case | 1 |
| 已完成售后服务 | 1 |
| 有公开消息的会话 | 2 |
| 可供 Monitoring 展示的脱敏 Run | 2 |
| 可读取的当前 Eval Artifact | 1 |

要求：

- 数据必须来自现有版本化 Catalog、业务 Repository、公开消息和 Eval Artifact。
- 不为截图直接写死前端数据，不把演示数据保存在组件或 `localStorage`。
- 演示用户名、商品名、图片、价格和时间线内部一致，不包含真实个人信息。
- 商业验收同时覆盖内容完整实例和空实例，不能通过隐藏空状态提升截图观感。
- README 提供一条明确路径初始化、登录和恢复该演示工作区。

## 响应式、可访问性与动效

- 固定验收视口为 `1440px`、`1024px` 和 `390px`。
- 客户首页、订单列表、订单详情、服务详情、对话、登录、运营概览和 Run 详情共 8 个核心页面，
  在三个视口形成 24 份固定截图基线。
- 其他客户与运营页面在三个视口完成无阻塞操作的响应式冒烟。
- 移动端按任务优先级重排，不只是缩小桌面卡片；主要动作不依赖横向滚动。
- 所有核心动作支持键盘，焦点顺序与视觉顺序一致，焦点可见。
- 颜色不是状态唯一载体；图标具有文本或可访问名称；正文与关键控件保持足够对比度。
- 页面缩放、长中文、长订单号和错误文案不能造成关键控件遮挡。

## 产品评审门禁

自动化截图只用于发现变化，不能单独判定商业可信度。本版本增加一份固定产品评审量表：

| 维度 | 3 分“商业可信”锚点 |
|---|---|
| 信息架构 | 首屏任务、状态和下一步明确；不依赖说明文档 |
| 内容真实感 | 商品、订单、金额、时间线和文案内部一致，无开发占位内容 |
| 视觉系统 | 层级、密度、组件和状态跨页面一致，无明显拼装感 |
| 任务连续性 | 订单、服务、对话、审批和结果之间上下文连续 |
| Agent 信任 | 事实、依据、建议、动作和失败可区分，不暴露隐藏实现 |
| 运营可用性 | 管理员能够发现目标、异常和质量状态，页面不是静态指标陈列 |
| 响应式与可访问性 | 三视口主要任务可完成，键盘、焦点和 Reduced Motion 有证据 |
| 开源可解释性 | README、设计取舍、架构和验收证据足以支持复现与面试讲解 |

每个维度使用 `0–3` 分锚定：

- `0`：缺失、错误或阻塞。
- `1`：功能可见但具有明显 Toy/Demo 表达。
- `2`：结构完整、可用，但仍缺少商业一致性或内容可信度。
- `3`：达到本项目限定范围内的商业可信标准。

版本接受要求：

- 8 个维度全部达到 `3` 分。
- 项目所有者审核固定截图和四条核心旅程并明确接受。
- 评分证据、仍存在的差距和不纳入范围的能力写入版本 Eval 报告。
- 评分不能替代安全、功能、Provider 和离线 Eval 门禁。

## 开源学习与面试证据

本版本需要保留能够经得起追问的公开材料：

- 解释为什么产品以订单和服务为一级对象，而不是以聊天为首页。
- 解释客户界面、运营控制台和领域核心为什么分离但不拆成微服务。
- 解释前端展示状态如何映射业务数据库、公开消息、Checkpoint、Memory 和 Eval Artifact。
- 解释 Agent 公开事实、依据、建议和动作如何避免自然语言直接授权。
- 解释视觉回归、功能测试、Agent Eval 和人工产品评审分别证明什么、不能证明什么。
- 记录至少一个被否决的设计方向及取舍，例如“大型营销 Hero”“全局悬浮聊天”“虚构运营图表”
  或“用动画掩盖空数据”。
- README 提供架构入口、商业演示路径、固定截图和已知限制。

代码和文档不得声称接入真实电商或支付系统，也不得把未通过的 Provider 或 Docker 门禁描述为完成。

## 错误与降级语义

| 场景 | 用户可观察结果 |
|---|---|
| 默认演示数据未初始化 | 展示可理解空状态；维护说明给出显式初始化路径，不在浏览器自动写入 |
| 商品图片缺失或损坏 | 使用稳定占位与商品文本，订单和服务动作继续可用 |
| 模型不可用 | 在当前对话中以客服消息说明暂时无法处理，既有订单和服务仍可查看 |
| Agent 结构化结果未知版本 | 使用安全正文降级，不渲染未经允许动作 |
| 政策证据缺失或冲突 | 明确限制、展示可用来源或建议升级，不伪造确定结论 |
| 服务动作过期 | 禁止旧动作并提示重新核对当前事实 |
| Eval Artifact 缺失 | 运营台显示“尚无当前评测”，不展示虚构趋势或沿用不兼容结果 |
| 页面刷新或 SSE 断线 | 恢复持久化消息、Run 和待办，不重复请求和副作用 |
| 无权限 | 使用稳定产品语言拒绝，不泄露目标对象是否存在 |

## 兼容与安全

- v1.3 的 URL、OpenAPI、账号、Session、订单、物流、退款、服务、Conversation、Run/Event、
  Checkpoint、Memory、Audit 和 Eval Artifact 默认保持兼容。
- 不为视觉重构新建第二套订单、服务、消息或 Agent 状态。
- 不把业务事实、认证状态或待办动作迁移到 `localStorage`。
- 客户、管理员、游客和跨工作区权限继续由服务端确定。
- Mock 退款继续经过确定性 Policy、`interrupt`、幂等执行和结果回读。
- 未经审批退款、重复退款、跨用户读取、游客 LLM 调用和浏览器高影响运维数量均为 `0`。
- 如果 Technical Plan 证明公开 API 或业务 Schema 必须改变，必须单独说明迁移、兼容和回归范围。
- 商品和视觉资产必须具备可再分发许可，不能抓取或热链竞品资源。

## 版本范围

v1.3.1 包含：

- 客户售后中心全局框架、售后首页、订单、服务、对话、登录注册和长期偏好的统一产品收口。
- Agent 运营控制台全局框架、概览、演示数据、邀请、Monitoring、Eval 和系统页面的统一收口。
- 默认商业验收工作区和完整/空状态双路径。
- 品牌、内容、设计 Token、组件状态、商品资源和动效规则。
- 24 份核心截图基线、响应式与可访问性验收。
- 锚定产品评审量表、版本 Eval 报告和开源学习说明。
- 所有既有业务、安全、恢复、Agent 和 Eval 回归。

## 非目标

v1.3.1 不包含：

- 新订单、退货、换货、维修、部分退款、逆向物流、优惠分摊或真实售后业务类型。
- 真实电商、物流、支付、CRM、客服坐席或消息通知系统。
- 新 LangGraph 节点、第二个 Agent、多 Agent、开放式规划或扩大工具权限。
- v1.4 的文件上传、OCR、向量数据库、Embedding、Rerank 或多模态政策问答。
- 客户模拟登录、管理员冒充客户、生产 RBAC 或 Web 高影响运维。
- 微服务拆分、消息队列、多实例、高可用或 SaaS 多租户。
- 复制淘宝、Shopify、京东等产品的品牌、资源、代码或逐像素布局。
- 为作品展示引入无任务价值的 3D、长过场、粒子动画或远程视觉依赖。
- 把 Docker 延后门禁或真实 Provider 未通过项标记为完成。

## 验收条件

1. 客户售后中心首屏优先展示待办、进行中服务和最近订单，不由营销 Hero 占据主要任务空间。
2. 固定商业验收工作区满足本 Spec 的最小数据要求，且通过显式、可重复方式初始化。
3. 正常页面不存在“验收商品”“测试 SKU”、Lorem Ipsum、破图、热链或无许可资源。
4. 客户主导航、状态、按钮和错误文案使用一致中文业务语言，内部研发术语数量为 `0`。
5. 演示环境边界始终可发现，但不会在每个客户组件重复显示 `Fake/Mock/Provider`。
6. 首页、订单、服务和对话中同一商品、金额、履约、退款和服务状态完全一致。
7. 用户可以在不阅读 README 的情况下完成订单定位、物流理解、Mock 退款和服务恢复四条旅程。
8. 订单列表和详情能够在一个扫读路径中回答商品、状态、金额、进度和下一步。
9. 服务详情能够区分已完成、当前、待用户动作、失败和最终结果。
10. 助手始终显示已验证绑定上下文；切换上下文、冲突订单和无上下文状态具有明确表达。
11. Agent 回复中的事实、依据、建议、允许动作、审批和最终结果可在视觉与语义上区分。
12. 模型不可用、工具失败和政策无证据均作为正常服务消息或任务状态展示，不使用红色技术异常。
13. 运营概览区分业务运营、Agent 质量和系统健康，并展示可解释的关注项。
14. 运营台不存在无权威数据支撑的趋势、比例或图表。
15. 管理员场景写入始终绑定明确目标客户，并展示影响摘要和脱敏结果。
16. Monitoring、Eval 和 System 保持只读，不从 Web 触发模型、Eval 或高影响运维。
17. 8 个核心页面在三个固定视口生成 24 份稳定截图，主要动作无溢出、遮挡或不可达。
18. 其他客户与运营页面在三个固定视口完成响应式冒烟。
19. 键盘、焦点、颜色非唯一状态、替代文本和 Reduced Motion 均有自动或明确手工证据。
20. Loading、Empty、Error、Forbidden、Expired、Partial、Interrupted 和 Completed 状态均有
    受控示例或测试。
21. 页面刷新、路由切换、重新登录和 SSE 重放不会丢失或重复消息、Run 和 Pending Action。
22. 未经审批退款、重复退款、跨用户读取、游客 LLM 调用和浏览器高影响运维数量均为 `0`。
23. 既有 v0.1–v1.3 自动化测试、Offline Eval 和安全门禁保持通过。
24. 真实 Provider 和 Docker Gate 继续独立报告，不因 UI 重构被跳过或冒充通过。
25. 产品评审量表 8 个维度全部达到 `3` 分，并由项目所有者明确接受。
26. README 提供商业演示初始化、登录、核心旅程、架构入口、固定截图和已知限制。
27. 版本文档解释 UI 状态与业务事实、公开消息、Checkpoint、Memory 和 Eval Artifact 的边界。
28. 至少记录一个被否决的视觉或产品方向及其取舍。
29. 所有新增或修改的 React 组件、Hook 和工具函数符合项目中文 JSDoc 约束。
30. 资源许可、代码职责、运行说明、评审结果和已知限制与最终实现一致。
