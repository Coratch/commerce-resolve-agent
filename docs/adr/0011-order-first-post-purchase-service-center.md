# ADR-0011：客户产品采用订单优先的智能售后中心

状态：Accepted  
日期：2026-07-22  
接受日期：2026-07-22  
关联版本：v1.1

## 背景

CommerceResolve 已具备订单与物流查询、政策 RAG、Mock 退款审批、AI 二线客服、公开会话恢复、
上下文观测和 Agent Eval。v1.0 候选版将这些能力集中到一个以对话为中心的工作台中，但默认页面
仍以输入框、消息流和技术上下文组织产品，用户需要先想好怎样提问，再从对话中寻找订单事实、
服务状态和下一步动作。

电商售后用户真正关心的是“我的订单发生了什么、现在能做什么、服务进行到哪里”，对话只是完成
这些任务的一种交互方式。继续给聊天页增加卡片和动效只能改善外观，不能改变产品仍以聊天记录而
非售后业务对象组织信息的问题。

因此需要决定客户侧产品的主要信息架构，以及订单、服务记录、对话和内部 Agent 诊断之间的关系。

## 决策

### 使用订单优先的信息架构

- 客户侧产品调整为“CommerceResolve 智能售后中心”。
- 订单、物流和售后服务记录是一级业务对象；自由对话不再是唯一入口或默认页面的唯一主角。
- 售后首页优先展示进行中的服务、最近订单和常用售后动作。
- 用户从订单或服务记录进入具体任务，查看权威事实、可执行动作和处理进度。

### 将 Agent 作为上下文能力

- 智能助手绑定当前用户、订单、服务目标和公开会话上下文，用户不必重复输入已有订单号和状态。
- 上下文只提高交互效率，不能授予订单访问权、改变 Policy 或绕过审批。
- 服务端继续验证订单归属、数据版本、动作资格和风险；客户端传入的订单或服务标识均视为不可信。
- 没有明确订单时，助手可以澄清或引导选择订单，但不能编造商品、物流或退款事实。

### 用服务进度表达高影响任务

- Mock 退款等高影响动作继续使用“预览 → 明确批准 → 幂等执行 → 回读验证”的既有链路。
- 客户侧将该链路投影为可理解的服务进度和结果，不以内部节点、Tool Call 或 Trace 代替业务状态。
- 公开会话、Pending Action、退款事实和 L2 Case 继续保持既有生命周期，不因 UI 改造合并存储。

### 分离客户体验与内部诊断

- 客户默认界面展示订单事实、处理状态、可执行动作、政策来源和必要的公开解释。
- LLM/Fake/Provider、Prompt、Context Manifest、内部节点、Token 和 Eval 指标不作为客户界面的主要内容。
- 对用户有帮助的来源和处理证据采用渐进披露；隐藏内部诊断不能删除既有审计和回放能力。
- 后续运营或维护控制台使用独立产品表面并复用服务端权限链路；v1.1 不实现完整客服坐席系统。

### 保持渐进迁移

- v1.0 已持久化的公开会话和可恢复动作不能因信息架构变化而丢失。
- 既有对话入口可以在迁移期作为兼容入口；具体路由、重定向和移动端呈现由 v1.1 Technical Plan 决定。
- 本决策不扩大 Agent 工具、资金权限、外部系统或真实交易边界。

## 备选方案

### 保持聊天优先，只增加更多业务卡片

改动较小，也能继续复用当前页面；但订单、进度和动作仍埋在消息流中，用户刷新或处理多个订单时
需要反复从对话重建业务状态，不能解决产品心智问题。

### 只提供站点右下角客服 Widget

适合把客服嵌入现有商城，但本项目没有商品、购物车和结算主站。独立 Widget 会缺少承载订单列表、
退款进度和服务历史的主产品表面。

### 先建设客服运营控制台

可以展示 Case、Trace 和 Eval，技术辨识度高；但当前没有真实客服团队或 CRM，优先建设运营面会
再次让内部 Agent 结构而非客户结果成为产品中心。

### 直接复制成熟客服或退货平台布局

可以快速获得视觉参考，但这些产品依赖真实订单、仓储、物流和坐席系统。照搬功能会制造项目当前
无法兑现的数据和流程，破坏 Mock 边界。

## 后果

正向结果：

- 用户可以从订单和服务目标开始，而不是先学习如何向 Agent 提问。
- 订单事实、会话能力、退款审批和政策引用形成一个可持续扩展的售后闭环。
- Agent 仍能展示 LangGraph、RAG、记忆、审批和 Eval 能力，但不再用技术概念主导客户界面。
- 客户侧与未来运营侧职责分离，减少一个页面同时服务消费者、开发者和客服人员的冲突。

代价：

- v1.1 不只是视觉换肤，需要定义售后首页、订单详情、服务进度和上下文助手的产品契约。
- 现有 Mock 订单可能缺少商品行、图片或更细物流事件；缺失数据必须明确降级，不能由前端编造。
- 服务记录可能需要从现有退款、Pending Action 和 L2 Case 建立只读投影，具体持久化方案需要 Plan 评估。
- 需要为旧对话入口、已有 URL 和公开历史设计兼容迁移。

## 长期约束

- 客户默认入口以订单、服务状态和待办动作组织，不以空白聊天框作为唯一首页。
- Agent 对上下文的使用不能改变服务端身份、数据归属、Policy 和审批边界。
- 客户可见业务状态必须来自权威 Repository 或经验证的服务记录投影。
- 正常客户界面不把内部 Agent 诊断当作业务结果；诊断隐藏不等于审计删除。
- 未来若改回聊天优先、将运营控制台与客户界面合并，或引入真实外部售后系统，必须由新 Spec 和 ADR 驱动。
