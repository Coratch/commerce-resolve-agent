# ADR-0005：交易与外部业务系统仅使用 Mock 实现

状态：Accepted  
日期：2026-07-17

## 背景

CommerceResolve 的目标是学习和实践 LangGraph、Agent Loop、RAG、权限审批、幂等执行、
恢复和 Eval。接入真实电商、物流、支付或交易系统会引入商户资质、资金安全、凭据管理、
合规和外部可用性问题，但不会直接改善这些 Agent 工程学习目标。

退款等高风险场景仍需要接近真实系统的审批、幂等和验证语义，否则无法有效验证 Agent
在副作用场景中的安全边界。

## 决定

- 所有订单、物流、支付、退款和客服工单数据均为本地生成或用户自定义的 Mock 数据。
- 所有业务 Gateway 只提供 Fake 或本地持久化实现，不连接真实电商平台、物流服务、支付
  渠道或交易系统。
- Web 场景以本地业务数据库持久化 Mock 业务事实；单元测试和 Eval 可以替换为内存 Fake
  或临时数据库。Mock 描述数据来源和外部边界，不等同于非持久化。
- 项目不保存真实支付凭据、商户密钥、支付 Token，也不产生真实资金或外部业务副作用。
- 可以调用真实 LLM 验证结构化意图理解，但模型处理的交易上下文仍然是 Mock 数据。
- Mock 退款仍按照 R2 动作处理，必须经过确定性 Policy、明确审批、稳定幂等键、执行后
  回读验证和审计。
- Gateway 契约保持可替换、可测试，但“未来可能替换”不构成接入真实系统的路线承诺。
- 如果未来要接入任何真实外部业务或资金系统，必须先调整目标地图和系统约束，并新增
  ADR、威胁模型、权限方案和独立 Feature Spec。

## 理由

- 项目复杂度集中在 Agent 编排、安全和评估，而不是第三方商务接入。
- 本地数据使自动化测试、跨进程恢复、重复执行和失败注入可以稳定复现。
- Fake Gateway 可以模拟成功、拒绝、超时、未知结果和重复请求，覆盖真实副作用场景中最
  重要的 Agent 行为。
- 明确边界可以避免把演示结果描述为生产支付或真实电商集成能力。

## 备选方案

- 接入支付渠道 Sandbox：比真实资金安全，但仍增加账号、网络、凭据和供应商协议依赖，
  对当前 Agent 学习目标没有必要。
- 接入真实订单与物流的只读 API：可以提高展示真实性，但会降低 Eval 可重复性，并引入
  数据授权和隐私问题。
- 仅 Mock 自动化测试、手工冒烟连接真实系统：会形成两套行为边界，且真实副作用无法作为
  安全的开发验证路径。

## 结果与代价

- 项目可以完整演示退款审批和幂等执行，但不能声称具备真实支付、物流或电商平台集成。
- v0.4 及后续版本的“执行退款”“创建工单”均指修改项目内 Mock 业务状态。
- Mock 交易记录可以跨进程保留，但业务数据库、LangGraph Checkpoint、政策索引和审计数据
  必须继续保持独立生命周期。
- Eval 可以确定性断言副作用、重复执行和审计结果。
- 业务规则用于模拟接近真实售后的约束，不代表任何真实平台的正式政策。
